# Package layout

Create implementation directories with working consumers as their tasks begin. Follow [the coding standards](../CODING_STANDARDS.md) for module/file placement and typed strategies and visitors.

## Package names

Package names are flat under the `@saga-a2ui` scope: `@saga-a2ui/core`, `@saga-a2ui/mcp`, `@saga-a2ui/components`, `@saga-a2ui/lit`, `@saga-a2ui/react`, the stacks `@saga-a2ui/react-mcp-stack` and `@saga-a2ui/lit-mcp-stack`, and `@saga-a2ui/lynx` (retired, see below). Tooling packages take a name only when implemented; `@saga-a2ui/publish` remains a proposal. There are no aggregate `protocol`, `transport`, `genui` or `tools` packages, and no `a2a` package before a working consumer needs one.

Flat names follow from how npm names work. A scoped name has the form `@scope/name` (see npm's [scope documentation](https://docs.npmjs.com/about-scopes/) and [name validation rules](https://github.com/npm/validate-npm-package-name)), so a nested name such as `@saga-a2ui/genui/lit` is not a publishable package name. A `genui` group package would instead be one package with one version and one set of dependency and peer declarations. That would tie the maturity of the Lit, React and Lynx renderers together and make it harder to keep an application's own catalog free of what it did not choose.

Grouping belongs in the documentation and bundling belongs in CLI templates, so neither needs a package. Where one concern has several entry points within a package, a subpath groups them. The `@saga-a2ui/mcp` package does this with `/server`, `/view` and `/policy`. Moving packages into nested directories is optional and is not done now. The four published packages use these flat names.

## Packages by group

Core, components, MCP and React are available on public npm at `0.1.0-rc.1`. See the [installation recipe](../docs/public-install.md). Lit remains private and unversioned. Local candidate builds remain available for all five; source manifest versions can advance ahead of the published release.

### Core

`core/` (published at `0.1.0-rc.1`) holds renderer-independent interfaces, value objects and processing. It owns the A2UI wire-version protocols, including A2UI decoding, and keeps parsing and message cases under `src/protocols/a2ui/<version>/`, not in generic utilities or renderer adapters. The shared behavior of the [action binding](../blueprints/modules/action_binding.blueprint.md) module lives in its own subtree, `src/actions/`, exported as `@saga-a2ui/core/actions`. It implements the delivered contract: local and server actions, prerequisites, bounded hooks, activation-scoped resources, `subject` freshness and optional limits with error categories (ACT1 to ACT6 and the action-default amendment; the [development reference](../docs/development-reference.md) per-slice sections record each delivery and its limits, and "The action contract across the current codebase (ACT7)" gives the current reading). The action subtree imports no renderer, DOM implementation, MCP runtime or third-party module; the package as a whole also holds the A2UI protocol modules, which use upstream `@a2ui/web_core` and Zod. `@saga-a2ui/core/host-links` is the renderer- and delivery-neutral contract for asking a host to open a validated link (`HostLinks`, `LinkOpenOutcome`, `NO_HOST_LINKS`, `describeLinkOutcome`): the card renderers consume it and MCP delivery supplies an implementation, with no dependency between them. It imports nothing. Actual-host acceptance and the Lynx adapter are not part of it.

### Delivery

`mcp/` is for MCP/MCP Apps delivery, host capabilities and lifecycle. It provides separate `/server`, `/view` and `/policy` entry points. It consumes core where needed (the host link contract, as a type); it does not own visual protocol parsing, and it never depends on components or a renderer. `/view` owns every ordering rule of a view: `runToolResultView` installs handlers before `connect`, holds early results until the view is ready, applies the host context before the first result, ends the view once on dispose, host teardown or `pagehide` and reports a throwing application callback without rolling its changes back; `hostLinksFromApp`, `startOwnSizing`, `readingProfile` and `readStructuredResult` (the one place that decides what MCP's `isError` and `structuredContent` mean for a card result's default reading) sit beside it.

### GenUI renderers

GenUI here means SAGA's graphical A2UI rendering, in which an application's handlers and catalogs supply the interface. It does not require a model to generate it. `lit/`, `react/` and `lynx/` are the renderer adapters and hold their optional component implementations. `lit/` is the only full renderer package; its opt-in action control and setup (`ActionButton`, `createLitActions`) are the optional `@saga-a2ui/lit/actions` export, and the Lit FaithfulCard element, its catalog entry and the content-view seam are the optional `@saga-a2ui/lit/faithful-card` export; the main `@saga-a2ui/lit` entry imports neither. `@saga-a2ui/components` is an optional peer of `@saga-a2ui/lit`, so installing Lit does not install it. The shipped Lit sources declare reactive state with `static properties` and `declare`, not decorators, because an application compiles them with its own settings. `react/` is not the full renderer: it holds the shared action seam's qualification (ACT2), the card slices and the composition capabilities of the view composition design. Its optional `@saga-a2ui/react/actions` export (`ActionButton`, `ActionButtonEntry`, `InstanceHostProvider`, `useActionSetup`), its optional `@saga-a2ui/react/faithful-card` export (`FaithfulCard`, `faithfulCardEntry`, `FaithfulCardProvider`, the card factory and presenting surface, with the explicit `@saga-a2ui/react/faithful-card.css`) and its `@saga-a2ui/react/a2ui` typed bound surfaces (`openSurface`, `Surface`) deliver those named composition capabilities for React as the Lit package does for Lit. They do not by themselves establish full React parity, which E15 owns, or acceptance in a named host, which the host runs record. `@saga-a2ui/components` is an optional peer of `@saga-a2ui/react` as it is of Lit, and the supported React and React DOM are pinned to the one version its tests ran on. Both controls share the renderer-neutral contract at `@saga-a2ui/core/actions/action-button-schema`. No `lynx/` package exists: `apps/lynx-fixture` is a retained qualification fixture and a separate project outside the npm workspace, not that package (see [Lynx action attachment qualification (ACT3)](../docs/development-reference.md#lynx-action-attachment-qualification-act3)). The owner retired the Lynx delivery chain on 2026-10-19: no `lynx/` package is planned, and the fixture is historical qualification evidence, not a Lynx recipe, adapter or requirement.

### Stacks

A stack package connects one renderer to one delivery, so an application installs one stack plus its framework peers and writes only its own decisions. `react-mcp-stack/` (public, in the release set with core, components, MCP and React) and `lit-mcp-stack/` (private and unversioned like Lit) connect a renderer to the MCP Apps bridge. Each has a main entry, `startA2uiView`, that imports nothing from components or Markdown, so an own-catalog application's emitted bundle excludes both, and a `/faithful-card` entry (`startFaithfulCardApp` with its optional `classifyResult`, the `FaithfulCardApp` definition from components, the card's host link, `readingProfile` and, for React, the card stylesheet). Two further entries serve the application's server composition without a new package: `/content-policy` (`createContentPolicy`, `embedContentPolicy`) and the Node-only `/server` (budgets, operation registration, operation views and request lifetimes re-exported from `@saga-a2ui/mcp/server`); no browser entry imports `/server`. A stack declares components and the MCP Apps bridge as regular dependencies, so its installed tree includes them; that is the correct install result and not a footprint of the bundle. The two stacks hold the same lifecycle code, copied, not shared. An application installs one stack plus its framework peers (`react` and `react-dom` for React, singletons; `lit` for the Lit stack) and imports from the stack only: the stack's main entry re-exports the own-catalog authoring surface (`defineSurface`, `z`, the renderer's action helpers) and the `/faithful-card` entry re-exports the card application definition. Consumer code (templates, examples, the `apps/lit-host` view modules, starter output, adopters) holds application meaning only; `scripts/consumer-boundary.test.ts` enforces that over an explicit include list, and each package's `exports.test.ts` enforces its own dependency direction. See [the stacks reference](../docs/development-reference.md#the-mcp-stacks-and-the-card-application-e1-e2).

### Components

`components/` (published at `0.1.0-rc.1`) holds renderer-neutral contracts and shared component behavior, one optional export per component. Today it has only `@saga-a2ui/components/faithful-card`: the versioned FaithfulCard content contract and reader, Markdown interpretation under a trusted dialect and bound, the content policy and image consent scopes, and the A2UI catalog contract. It is the passive preparation slice of CARD1 (see [The passive FaithfulCard and an installed second consumer](../docs/development-reference.md#the-passive-faithfulcard-and-an-installed-second-consumer-card-prep)) together with the evidence that it composes with an authored control and runs from installed packages ("The FaithfulCard beside an authored control (CARD1)"); the card still accepts no action itself, and it is not the complete component. It imports no MCP, renderer, DOM or server API, and depends on `markdown-it`, `zod`, upstream `@a2ui/web_core` and `@saga-a2ui/core` (for the Zod 3 alias) only. Each component owns its own contract; the next component does not inherit FaithfulCard's Markdown or policy requirements.

### Tooling

No tooling package is implemented. The draft [host publication design](../blueprints/features/host_publication.blueprint.md) proposes `@saga-a2ui/publish` as optional developer tooling behind the planned SAGA CLI. It would validate and prepare application packages for host directories, with host-specific formats kept outside runtime packages. The package and commands remain unapproved and unimplemented. Core, MCP and renderers must not depend on publication tooling, and an application's runtime does not need it.

## Dependencies and versions

Dependency direction points toward renderer-independent contracts. Core must not depend on MCP, a renderer, or a DOM runtime. MCP and renderer adapters can consume core without depending on one another's implementations; a stack package connects them, and the application installs one stack. The components package must not depend on MCP or renderers, and core must not require the optional components package. Renderer support for optional components belongs in an optional export.

Renderers keep independent maturity and independent dependency and peer declarations. A renderer used with an application's own catalog must not pull in the optional components, including `FaithfulCard`, a Markdown parser, or any renderer the application did not select.

The workspace root is not published. Core, MCP, components, React and the React stack use coordinated release versions (one major.minor across every package); Lit and the Lit stack remain unpublished workspace packages. Keep server-only modules out of browser entry points. CI also packs the seven implemented packages as a private candidate whose prerelease identity exists only in the packed copy, with every package pinned to its siblings' exact candidate version; see [candidate contents, update and rollback](../docs/candidate-update-and-rollback.md).

The new-project CLI templates and the existing-backend recipes are not packages; the first maintained template is [`templates/lit-node`](../templates/README.md). They are described in [application setup](https://github.com/MachineWisdomAI/saga-a2ui/blob/b10a8882fa5b15ad9a7243f592e5c3dc086d5340/blueprints/features/application_setup.blueprint.md).
