# saga-a2ui - AI Agent Instructions

## Project

This repository is a MachineWisdom TypeScript SDK, initially private and intended for a later public release.

## Shared Operating Rules

- Read the repo-local `AGENTS.md` first. Tool-specific files are additive and must not contradict it.
- Follow explicit operator instructions. Treat AI reviewer findings as evidence: verify and classify them before acting. Do not expand scope because a reviewer suggested it.
- Inspect the exact repo, branch, worktrees, and dirty state before editing. Preserve unrelated changes.
- Make tracked edits only on a dedicated worktree or feature branch. Keep the default checkout clean. Never commit or push directly to the default branch; land tracked changes through a pull request.
- Never force-push or amend a pushed commit. Stage explicit paths only; do not use `git add -A` or `git add .`.
- Versioned PRs: follow `docs/version-policy.md` before review and after syncing main. Docs, tests, CI, and development checks alone need no bump. Use Conventional Commits; enroll owned versions through bootstrap. Publication stays separate.
- Resolve exact targets before destructive work. Do not discard changes, delete material data, merge, deploy, publish, post externally, or alter access without authority for that action.
- Never expose secrets. Keep provider credentials and user data within their authorized boundary.
- Treat `~/git/vendor/` checkouts as read-only. Develop in an owned repository or worktree.
- Route ambiguous new builds through `skills-sage` before coding. Use one shaping route; keep GStack/Pocock advice within the accepted outcome. Use `mw-implementation-stages` for multi-stage delivery or a stalled frontier, and `mw-review` for tracked review and non-converging repairs; use repo-local validation and workflow instructions.
- Keep durable non-trivial specs, plans, decisions, status, and handoffs in FAVA Trails. Promote finalized truth and sync it.
- Do not build “shared-something” helper identities. Use shared-all or shared-none; give shared artifacts one owner and one documented repair path.

## Local tooling

Set up formatting hooks in every development checkout or worktree, including Hermes Helmet worker checkouts. Install missing pinned root tools with `npm ci --workspaces=false --ignore-scripts`, run `npm run hooks:install`, and verify with `npm run hooks:check` before committing. Hooks are shared by linked worktrees, but root dependencies must be installed in each committing worktree. Preserve the existing pre-commit and pre-push safety guards. The hook formats whole staged source/configuration files; keep the formatting baseline current so later changes avoid unrelated formatting hunks.

Install pinned root tools when needed with `npm ci --workspaces=false --ignore-scripts`. Optional correctness feedback: `npm run lint -- PATH...` (see the development guide for pinned actionlint setup). Findings and analyzer failures are advisory; assess concrete defects through ordinary review. See [formatting and hooks](docs/development-reference.md#formatting-and-hooks) for the installation procedure and troubleshooting.

## Repo Notes

- This is the SDK source repository. It is private initially; making it public requires a separate explicit instruction.
- Keep internal plans, customer records and sensitive research out of this repository and its history.
- SDK issues are for community bug reports and feature requests. All internal delivery tickets, including implementation work, belong in Backstage; code checkouts and PRs remain here. Public PRs and Blueprint evidence must stand alone without private records. See [contribution review](CONTRIBUTING.md#review).
- Apache-2.0 applies to SDK code; preserve third-party notices.
- The plan is approved. Refine one task at a time and keep implementation within the selected ticket. Do not repeat the entire planning process.
- The private Lit application renders A2UI fixtures and the public answer view. `packages/mcp` (`@saga-a2ui/mcp`), `packages/core` (`@saga-a2ui/core`), `packages/lit` (`@saga-a2ui/lit`) and `packages/react` (`@saga-a2ui/react`: the optional action-attachment qualification of ACT2, the optional FaithfulCard slices and the named composition capabilities of the view composition design, which do not by themselves establish full React parity or named-host acceptance) and `packages/components` (`@saga-a2ui/components`, only the passive FaithfulCard preparation slice of CARD1) are the extracted SDK packages. Core, components, MCP and React are published on public npm at `0.1.0-rc.1`; their source manifest versions may be newer. Lit remains private and unversioned. See `docs/public-install.md` for the registry installation recipe. Use `release:pack` for the four-package release set and candidate tooling for private qualification copies. `packages/lit-mcp-stack` (`@saga-a2ui/lit-mcp-stack`, private like Lit) and `packages/react-mcp-stack` (`@saga-a2ui/react-mcp-stack`, in the public release set) are the two stack packages: a stack connects one renderer to MCP delivery, so an application installs one stack plus framework peers and imports from it only. No other SDK package exists yet. `examples/answer-consumer` (Lit), `examples/pack1-consumer` (the notes application: two separately installed Lit consumers, PACK1, and one React consumer, REACT1, sharing one contract, server and set of actions) and `examples/react-card-consumer` (React) are synthetic applications built outside the workspace from the packed packages; they are development checks, not installation recipes. For build and browser-test commands, read [Local development](docs/development-reference.md#local-development).
- Consumer code holds application meaning only. `scripts/consumer-boundary.test.ts` scans an explicit include list (the five `templates/*/src`, `examples/*/src`, the `apps/lit-host/src` view modules, starter output and documentation code fences) for the SDK's own glue: A2UI wire literals, imports of `@modelcontextprotocol/ext-apps`, `@saga-a2ui/mcp/view` and `@a2ui/*`, and the `createMessageSession`, `a2uiV0_9Decoder` and `IngestResult` symbols. The exclude list is explicit and reasoned (host-side modules, qualification fixtures, tests, dated observations, fences marked `before` or `historical`). A supported lower-level use, such as a catalog authored against upstream's component API, takes one reviewed per-line `// saga-boundary: <rule> <reason>`, never a file-wide disable. Each package's `exports.test.ts` separately asserts its dependency direction. Do not add glue to a consumer: if the SDK lacks the export, add the export.
- `apps/lit-host` builds the protected player twice from one controller (REACT2): the Lit view (`playback.html`) and a React view (`playback-react.html`, `src/react/play-control.tsx`; no description card). `e2e/playback-view.spec.ts` runs against both through the `lit` and `react` Playwright projects (`e2e/player-renderer.ts`). The React page uses the application's own React runtime and the `core` and `mcp` packages only; it does not use `@saga-a2ui/react`.
- `templates/` holds maintained starter templates (STARTER1: `templates/lit-node`, the `lit-mcp` stack on the `node` server target; STARTER-EXPRESS #62: `templates/lit-express`, the same stack on the `express` target; STARTER-FASTIFY #64: `templates/lit-fastify`, the same stack on the `fastify` target; STARTER-HONO #63: `templates/lit-hono`, the same stack on the official `@modelcontextprotocol/hono` adapter, qualified by `scripts/starter-hono.test.ts`). SAGA also owns `templates/lit-hapi`: its maintained `server/bridge.ts` carries Hapi-authenticated request context into the Node MCP transport; `scripts/starter-hapi.test.ts` and `scripts/starter-hapi-identity.test.ts` qualify it without an external repository dependency. A template is not a package and not an example: it is the one source the starter output, the existing-backend snippets and the qualification (`scripts/qualified-starters.ts`, `scripts/starter-qualification.ts`, `scripts/starter.test.ts`, `scripts/starter-express.test.ts`, `scripts/starter-fastify.test.ts`, `scripts/starter-hono.test.ts`, `apps/lit-host/e2e/starter.spec.ts`) all read. Test identities and policy stay in the specifications, never in a template; see `templates/README.md`.
- `scripts/saga.ts` is the one CLI parser: `saga init --a2ui-stack <renderer>-mcp --server <target> DIR` (CLI1) and `saga demo` with the same options (CLI2). `init` composes `exportTemplate` and offers only the pairs in its `SUPPORTED_PAIRS` list (today `lit-mcp` on `node`, `express`, `fastify`, `hono` and `hapi`, each naming its own maintained template; #179); a further pair adds one row there after its own qualification passes. `demo` offers `SUPPORTED_DEMO_PAIRS`, the pairs whose template is `DEMO_TEMPLATE` (`scripts/qualified-starters.ts`), builds the DEMO1 download outside the destination with `stageDemo` (`scripts/build-demo.ts`) and writes it through `createDirectoryInterruptibly`, the destination handling `init` uses too (`scripts/starter-template.ts`). Each creates one new directory and installs and runs nothing of its output; `publish` (CLI3, CLI4) is optional tooling loaded only for that command (`scripts/publish/`, read [its README](scripts/publish/README.md)): one release input and one findings record prepare either target, `chatgpt` (the plugin package) or `claude` (the connector dossier, with a plugin bundle only when the release input supplies its scope). `publish handoff` (CLI5, `scripts/publish/handoff.ts`) keeps the resumable record of the manual submission that follows: numbered, hash-chained event files for preparation, submission, review and a verified listing, with an uncertain attempt inspected before any retry. It deploys, uploads and submits nothing, and local Desktop or Code packaging is never reported as web distribution.
- `docs/getting-started.md` is the setup guide (GUIDE1) and `docs/attach-to-existing-backend.md` its generated existing-backend recipes. Never edit the generated file by hand: `scripts/guide-recipes.ts` (`npm run guide:recipes`) renders it from the qualified templates in `scripts/qualified-starters.ts`, and `scripts/guide.test.ts` checks that it is current and that every command, snippet, package name and link in both documents is real. A newly qualified server joins the recipes by regenerating; a pair joins `saga init` only through `SUPPORTED_PAIRS`.
- `docs/actions.md` is the action guide (GUIDE2). Its quoted source is checked against the files it names by `scripts/guide-actions-document.test.ts`; `scripts/guide-actions.test.ts` runs every case it traces against the notes application installed from packed tarballs. The guide's confirmation and audit prerequisites are qualification source in `scripts/guide-actions/guarded-archive.ts`, not part of the notes example or an SDK export. A qualified Hapi template must add its identity-handoff trace to the guide (the document test fails until it does).
- `demo/lit-node` is the standalone synthetic demonstration (DEMO1) of the one qualified pair. `scripts/build-demo.ts` builds it from packed candidate tarballs outside the repository into the download `apps/lit-host/dist/demo`. All synthetic identity, media and business data stay in `demo/lit-node/fixtures`; the clean starter and the SDK packages never import it. Its authentication is local-only and stays visibly so.
- `demo/tour` is the static source-linked tour (TOUR1): the notes example's real Lit and React views and action runtime, mounted by the local host fixture over a simulated server that answers from `demo/lit-node/fixtures/notes.ts` data. `scripts/build-tour.ts` (`npm run build:tour`) builds it from packed candidate tarballs outside the repository into `apps/lit-host/dist/tour`. It has no backend, credential or service, and a simulated answer is not server or host evidence. `scripts/tour.test.ts` requires the simulated server to answer as the real `createNotesServer` does and checks every quoted source line and guide heading it links; `apps/lit-host/e2e/tour.spec.ts` drives the page. Renderer previews are offered only while they work; Lynx is not offered.
