No actual-host audio, OAuth/DCR, public registry install or production deployment is asserted.

**CLI1: `saga init` ([SDK #26](https://github.com/MachineWisdomAI/saga-a2ui/issues/26)).** `scripts/saga.ts` parses the explicit pair and destination and calls `exportTemplate`, reusing template content; only Lit/MCP on Node was offered. Existing targets, symlink targets and parents, and unsupported pairs are rejected without modifying an application; no implicit install or remote hook runs. Output creation is exclusive with device and inode ownership checks, so real SIGINT and SIGTERM are serviced before success and only still-owned output is removed, and a replacement directory keeps another application's contents. Output excludes demo credentials, verifiers and qualification fixtures. The supported-pair table stays separate from the qualification inventory; later framework qualification does not add CLI rows by itself, and React support is neither preclaimed nor a blocker. Review found and repaired two safety defects (an OS interrupt reporting success; cleanup deleting a replacement destination). Hard process termination can leave partial output and adjacent filesystem races are documented limits. No registry installation, publication, deployment, demo command or host-publication tooling is claimed. SDK #26 stays open until its record is reviewed and merged.

**Framework starters: Express #62, Fastify #64, Hono #63.** The approved design is unchanged. Each framework implements the same Lit/MCP contract through its official adapter, with application-owned identity verification and authorization, exports public SDK imports, ships no test identity or verifier, and supplies template-derived authentication, operation and action snippets. Pins: Express adapter 2.0.2 with Express 5.3.0; Fastify adapter 2.0.1 with Fastify 5.12.7; Hono adapter 2.0.2 with Hono 4.13.13 and Node server adapter 1.19.17; Node transport 2.1.1 where used; MCP server 2.3.1 throughout. These are tested recipes, not a promise for other versions or frameworks.

Each template is exported and built outside the workspace from packed core, lit and mcp candidates. Public and protected endpoints, allowed, denied and missing credentials, concurrent immutable identities and own-process refusal were qualified against real local MCP clients. Host, Origin, body receipt and delivery bounds belong to the framework adapter, not a second SDK runtime; the request deadline starts before authentication and does not reset for body or handler stages. A 90 ms verifier inside a 180 ms request produced body-timeout HTTP 408 at 188 ms (Fastify) and 191 ms (Hono) without authorization; these validate deadline composition, not production latency. Express owns the common qualification harness; Fastify and Hono integrate through `QUALIFIED_STARTERS`, `starter-qualification.ts`, the generic builder and browser spec, keeping pair-specific assertions local. All three built Lit views matched SHA-256 `1a9898b1c8a9227246aab6e40a9c6448281437f2309611371842d6fbc8341748`; server artifacts and dependencies stay distinct. Local browser and transport observations are not assistant-host, OAuth, remote audio or production acceptance. Criteria 1 to 4 of each issue are covered here; criterion 5 (CLI registration) is covered by SDK #179 below.

Separate real CLI processes produced Express, Fastify and Hono projects pinned to the candidate with no dependency installation and refused a Hono demo before creating output. Linking declared third-party dependencies from the locked review tree is not a registry-install claim. This closes the registration gap, not publication, deployment or renderer parity. SDK #179 and the three framework issues stay open until this record lands and live criteria are reconciled.
