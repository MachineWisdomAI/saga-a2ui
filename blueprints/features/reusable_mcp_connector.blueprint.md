## Problem and current behavior

`@saga-a2ui/mcp` connects application-owned operations to MCP hosts. It validates inputs and explicit result projections, bounds request work, and manages view delivery and teardown. Applications keep HTTP hosting, authentication, domain authorization, backend calls, capability issuance and rendering.

A server action sends a request through the host; a local action runs in the view. Play combines a protected server request with client work that starts a player. Pause and Resume act locally on that player. Public operations use the same validation and failure rules without a fabricated identity. [Status](#status) records the delivered scopes and their evidence limits.

## Behavior

For an authenticated subscription read, the application listener verifies the request and supplies an immutable identity. The connector validates the declared input, invokes the application handler and validates the explicitly constructed output before serialization. The application decides which subscriptions belong to the caller. The host receives the result and the linked immutable HTML resource, and the view passes delivered data to the application's renderer.

For a protected server action, the view invokes a named typed operation with the selected item's ID. The application checks identity and authorization on every invocation and owns any capability it issues. The connector carries separately validated model and view projections through a supported MCP Apps mapping. An unsupported recipient path fails before protected acquisition, and no private field moves into model-visible output as a fallback.

A public operation declares that access mode explicitly, supplies input and output contracts and uses the same validation and failure rules. Public access does not make questions, credentials or diagnostics fit for logs. Neither mode accepts caller-supplied account fields as authority.

## Responsibilities and interfaces

`@saga-a2ui/mcp` has distinct `/server`, `/view` and `/policy` subpaths. A2UI wire-version protocols stay in `@saga-a2ui/core`. Server exports attach to an application-owned MCP server and accept declared operations, runtime schemas and callbacks. View exports own bridge initialization, result delivery and teardown. Policy exports express MCP delivery decisions and required capabilities without importing a renderer or the application's subscription policy. The package README documents the current public exports. See the [package layout](../../packages/README.md).

| Owner | Inputs and outputs | Required boundary |
| --- | --- | --- |
| Application listener | Transport and credentials; verified request identity | HTTP setup and authentication stay outside the connector; no mutable shared current-user state. |
| Application operation | Validated arguments and identity; domain result | Backend calls, entitlement and effects stay here. A public operation gets no fabricated principal. |
| MCP server integration | Declared operation, schemas, explicit projections; validated wire result | Protected registration without identity or projection configuration fails. Upstream registration is not a saga a2ui action registry. |
| MCP view integration | Host notifications and connection lifetime; typed delivery callbacks | Install handlers before connecting, deliver once, retire callbacks and release listeners on disposal. No A2UI interpretation. |
| Application renderer | Delivered result and application catalog; visible state | Rendering, content presentation and player ownership stay in the application until adapter migration. |
| Action runtime | Invocation execution, outcomes and cleanup, per the [action binding](../modules/action_binding.blueprint.md) module | Not part of the connector. The application owns definitions, the application or adapter owns bindings, and the resource owner keeps acquired resources. The connector carries the request a server action's handler sends; it owns no prerequisites, hooks, busy policy or binding. |

Three policies meet here with different owners. *Delivery policy* is the connector's: which recipient gets which projection and which host capabilities a protected operation needs. *Domain authorization* is the application's: who sees which records and whether this caller may act on this item. *Content policy* decides what supplied text may do when rendered; the [content safety design](content_safety_levels.blueprint.md) defines Standard and Strict; applications supply trusted configuration to the SDK content-policy implementation.

The connector owns the transport and request contract: operation declaration, input and result validation, projection delivery, the request deadline, cancellation and late-output retirement, and the JSON and SSE lifecycle. A client-side prerequisite never substitutes for the server checks it delivers. When an action aborts its wait, that shows only that the client stopped waiting; whether the host forwarded cancellation and whether the server stopped are separate facts that [CORE3](https://github.com/MachineWisdomAI/saga-a2ui/issues/16) and host observation must establish.

**Recipient mapping.** Real-host evidence must establish the recipient mapping before any slice adopts it. CORE1 adopts none: its projections are the model-visible `content` and the validated `structuredContent`. The merged protected-action prototype (Play) declares app-only visibility, reads a recipient public key from request metadata, returns safe model text in `content` and puts the playback payload under its own result `_meta` key. That is the implemented candidate mapping, not a portable contract; the [authorized playback third open decision](authorized_playback.blueprint.md#open-decisions) still applies.

A bounded baseline run of that path (built by [PLAY1](authorized_playback.blueprint.md#implementation-sequence), which added the app-only action with separate results and one client-held player, and PLAY2, which added expiry, revocation and misuse rejection) was made in ChatGPT web and Claude web on the merged source with MCP Apps 1.7.5. Authentication succeeded and the opening operation ran in both. ChatGPT then showed a blank opening frame and Claude returned text without an interactive card; one reload retry each; neither showed the action control, so no authorization or resource call occurred. The runs are inconclusive: they establish no recipient mapping and no cause for the missing view.

**Dependency recipe.** The original comparison used saga a2ui's MCP Apps 1.7.5, monolithic MCP SDK 1.32.1 and Zod 3.25.76 against Ansari's MCP Apps 2.0.3, split MCP server and client 2.3.1, Node integration 2.1.1 and Zod 4.2-compatible schemas. A peer-complete disposable install of the unchanged source gave 32 TypeScript diagnostics, so migration needed transport, context and schema changes, not a version bump. The landed CORE1 recipe pins MCP Apps **2.0.3**, split client, core and server **2.3.1**, Node integration **2.1.1** and Zod **4.6.7** at the MCP seam; A2UI 0.13 stays on its upstream Zod 3 schema boundary. The 1.7.5 run is historical baseline only. Do not downgrade Ansari or add a dual-version abstraction.

On the qualified target, the mapping must be measured again in both web hosts before any slice adopts it. Each run must show whether the model is excluded from the protected action, whether the view can invoke it with the required metadata, whether the intended view result arrives, and whether recognizable private test values stay out of model-visible responses and resources. It also exercises rejection when the mapping is unavailable and records source, resource hash, package recipe and limits. Another client, a local AppBridge fixture or source inspection cannot replace either web-host run. Missing access or an inconclusive result leaves the decision unresolved; unrelated preparation continues, but CORE1 must not rely on an assumed mapping.

## Failure and recovery

The connector exposes safe outcomes without making callers reconstruct callback order or transport state. It enforces finite input, result, item, string and retained-state bounds at the owning interfaces before copying or serializing. One finite request deadline covers identity, authorization, handler and projection work without restarting per stage. It is independent of the client-side work deadline and hook budget of the action binding module; neither bounds a whole invocation and neither implies the other. Cancellation stops waiting and retires late output; the application remains responsible for cleaning up uninterruptible work. The [Ansari adoption design](ansari_adoption.blueprint.md) requires the integration to preserve progress and delayed JSON and SSE completion within that one bounded request. Handlers use `OperationRequest.signal`, `within` and `reportProgress`; the [request lifetime contract](request_view_lifetimes.blueprint.md#what-exists-today) describes their ownership and limits.

| Trigger | Observable result and recovery |
| --- | --- |
| Protected registration lacks identity, projection or capability requirements | Registration fails before serving; the error names the missing requirement without printing credentials. |
| Identity missing, invalid, expired or service-only | The established authentication status and challenge stay intact; no protected handler or acquisition runs. |
| Malformed protocol call or unknown operation | The supported JSON-RPC failure is returned; no handler runs. |
| Known operation with invalid input, denial or expected backend failure | A safe tool failure per the selected upstream contract. Backend 401, 429 or 503 does not become the endpoint status. |
| Callback throws, stalls or yields malformed or oversized projected data | The request ends within its bound with no success payload or private diagnostics. The view clears invalid current state and offers only permitted recovery. |
| Cancellation, disconnect, late output or disposal | No duplicate operation, late response, headers after stream start or restoration of retired data. Cleanup responsibilities stay explicit. |
| Host cannot preserve required recipients | Protected behavior fails before acquisition; no capability appears in model text, structured output, resource HTML, A2UI payloads, errors or ordinary logs. |

Failure mapping is verified at the wire: HTTP status and challenge, JSON-RPC result or error, and `isError` are separate observations. The prototype's safe tool failures do not settle every generic contract fault. Successful-output schemas stay strict and error handling must not weaken them.

## Verification outcomes

| Condition | Observable result |
| --- | --- |
| Allowed, denied, empty and failed subscription reads via public package exports | The real listener and built view keep prior authorization, request correlation and displayed results, including declared filters. |
| Two principals concurrent, or an input adds a forged account | Each handler gets only its request's verified identity; supplied fields cannot select another account. |
| A public answer-style operation declared | Runs without user authentication, with explicit validation, projections and safe failures. |
| Allowed and denied protected server actions | Every valid invocation reauthorizes; denial causes no acquisition; the permitted view gets only its projection. |
| Identity, authorization, handler and projection callbacks each stall or fail | Configured bounds hold at every stage; late emissions are retired; diagnostic canaries do not escape. |
| JSON and supported SSE delivery with notifications, cancellation, disconnect and resume | No duplicate operations or invalid second responses; disposed views ignore late delivery. |
| Instruction-like field or private canary in backend data | Changes no action arguments and appears only to its allowed recipient, including logs and resource metadata. |
| Server and view exports imported independently | Server use imports no renderer; browser artifacts contain no Node or server module or credential. |

CORE3 keeps its full callback, contract, disclosure and transport verification; extraction does not shrink it to the first consumer's cases. The complete protected workflow still needs its content-policy and session-lifetime implementation and actual host runs, run as soon as the integrated candidate exists. Pending maintainer signoff may stay open while compatible downstream coding proceeds. Missing host evidence or a contradicted interface is a technical issue, not a signed-off success.

## Implementation sequence

[Status](#status) owns the standing of each slice. The design set this order. CORE1 ([#14](https://github.com/MachineWisdomAI/saga-a2ui/issues/14)) extracts the browse connector and the server, view and policy separation and tests an explicitly public answer operation beside protected browsing. It adopts no recipient mapping that has not been measured: browse and the public answer use `content` and `structuredContent`, and the Play-only `_meta` mapping stays in the application. CORE2 ([#15](https://github.com/MachineWisdomAI/saga-a2ui/issues/15)) moves the protected server action through the same declared contract and waits for STATE2. CORE3 ([#16](https://github.com/MachineWisdomAI/saga-a2ui/issues/16)) establishes the complete bounded failure and lifecycle contract through installed public exports.

[STATE1](https://github.com/MachineWisdomAI/saga-a2ui/issues/12) and [STATE2](https://github.com/MachineWisdomAI/saga-a2ui/issues/13) cover view retirement, selection races and bounded request completion ([request and view lifetimes](request_view_lifetimes.blueprint.md)); [POL1](https://github.com/MachineWisdomAI/saga-a2ui/issues/5) and [POL2](https://github.com/MachineWisdomAI/saga-a2ui/issues/7) cover Standard and Strict content. The [Lit adapter](https://github.com/MachineWisdomAI/saga-a2ui/blob/b10a8882fa5b15ad9a7243f592e5c3dc086d5340/blueprints/features/reusable_lit_adapter.blueprint.md) progresses beside CORE2 and CORE3 through VIEW1 and VIEW2, and the Lynx Web investigation informed VIEW1 without blocking extraction. Full SDK qualification joins CORE3, VIEW2 and the optional components, then [PACK1](https://github.com/MachineWisdomAI/saga-a2ui/issues/21) and [PACK2](https://github.com/MachineWisdomAI/saga-a2ui/issues/22) release readiness. [Ansari adoption](ansari_adoption.blueprint.md) adds a later requirement: exact package versions publicly installable from npm before the destination merge.

The slices were unreleased when planned, so owned consumers and tests migrate together with no compatibility shims or aliases, following the [coding standards](../../CODING_STANDARDS.md). The settled dependency recipe and the open host-mapping question are under Open decisions.

### Approved sequencing amendment (2026-10-17)

The operator approved starting the Ansari preparation slices without waiting for the proposed lifetime and action-binding designs ([#69](https://github.com/MachineWisdomAI/saga-a2ui/pull/69), [#73](https://github.com/MachineWisdomAI/saga-a2ui/pull/73)), keeping final release gates intact. It is a bounded sequencing and breakdown change, not approval of either design or implementation, and replaces the earlier clauses that made CORE1 and VIEW1 wait for STATE2.

- CORE1 and VIEW1 are preparation slices. Each preserves current authentication, immutable request identity, per-view isolation, result correlation, cancellation, cleanup and safe failures, and neither implements nor claims the guarantees of the proposed lifetime or action-binding interfaces.
- STATE1 and STATE2 remain design- and breakdown-held. CORE2 and VIEW2 keep STATE2 as a prerequisite. CORE3 keeps its entire failure, deadline, callback, projection and transport matrix.
- Full CORE3, VIEW2, PACK1 and PACK2, exact public source and npm installation, required actual-host evidence and the destination maintainer's authority remain final gates. Preparation candidates are unreleased and may change; owned consumers migrate together.
- CORE1 acceptance includes a synthetic public-answer operation through the installed candidate exports, the real MCP listener and the built view: answer bound to its exact question, one handler invocation, progress and delayed JSON and SSE completion, safe failures, early, repeated and late results, and cleanup. It fabricates no authentication and keeps the existing bounded and cancellation behavior instead of the whole-request deadline CORE3 qualifies.

Under the amendment, Blueprint and breakdown approval remained required before dispatch. Host runs stay scheduled work; only final maintainer acceptance may wait while ready implementation advances. Publication is a separate authorized action after the complete package and release checks. Since this amendment, the action binding module and the lifetime amendment have each been approved on their own, which changes nothing it authorized and establishes no implementation. At the amendment, where the module's first slice lands relative to CORE2 was a breakdown decision not yet made; CORE2 has since landed with Play on mapping A (see [Status](#status)).

## Open decisions

**Settled.**

- **Peer and engine recipe.** The 2.0.3 direction was selected and landed with CORE1: MCP Apps 2.0.3, split client, core and server 2.3.1, Node integration 2.1.1 and Zod 4.6.7 at the MCP seam (see Dependency recipe above). The recipe applies to the scopes in [Status](#status); no other version or pair inherits it.
- **Limits, failure codes and callback interfaces.** CORE3 (#140) established the callback, deadline, cancellation and progress contract, and the server-budget amendment (STATE2) set the defaults. The current interfaces are `OperationRequest.signal`, `within`, `reportProgress` and the request lifetime, described in [request and view lifetimes](request_view_lifetimes.blueprint.md#what-exists-today).

**Still open.**

- **Which host mapping can the projection interface promise?** Play's mapping (an app-only tool, the recipient key in request metadata, the playback payload under its own result `_meta` key) is implemented, and CORE2 records host acceptance in ChatGPT web and Claude web for that scope ([Status](#status)). The 1.7.5 runs were inconclusive and establish no mapping. A mapping the interface can promise beyond Play's recorded scope is not established. A failed path needs an SDK or application repair or an explicit supported-host limitation, not a claim of success.
