## Problem and current behavior

`@saga-a2ui/core` validates and processes supported A2UI input; `@saga-a2ui/lit` renders its surfaces using the application's catalog and owns mount, update and disposal. Applications keep their components and domain behavior. The Lit MCP stack combines the renderer and delivery for an application; lower-level core and Lit exports remain available.

The adapter supports own-catalog and optional FaithfulCard views. It preserves read, content and protected-action behavior while keeping server authorization separate from view lifetimes. [Status](#status) records which scopes are implemented and qualified.

## Behavior

The application supplies its catalog and layout. The adapter creates the default SDK session, with optional session injection for advanced integrations. A result arrives through the public MCP view interface and the application passes the presentation input to the adapter. Core validates the A2UI envelope and message cases, the upstream processor applies component support, references and partial updates, and Lit binds the surface to the application's components.

When a title or answer changes, data-model updates change the visible text without replacing the application's architecture. Invalid current input clears the affected presentation and shows a safe fallback, so an older success never looks current; a valid replacement recovers. On disconnect the adapter retires delivery, unsubscribes and disposes the owned session. Reconnection creates a fresh instance rather than restoring retired private state.

## Responsibilities and interfaces

| Owner | Required behavior |
| --- | --- |
| `@saga-a2ui/core` | Validate supported A2UI input and apply typed message cases; import no MCP, renderer or DOM runtime. |
| `@saga-a2ui/lit` | Connect validated surface state to Lit, expose clear mount, update and dispose ownership, release subscriptions exactly once. |
| `@saga-a2ui/mcp` | Deliver host results and lifecycle events through its public view contract; no protocol interpretation or renderer selection. |
| Consumer application | Supply catalog, content rules, host theme and resource hooks, local and server action definitions, prerequisites, handlers and composition; keep domain authorization and protected-resource decisions. |

Core keeps A2UI knowledge in a named protocol and version module. Its decoder treats input as `unknown`, uses upstream schemas, preserves supported fields and returns typed cases or an explicit failure. Its visitor handles every supported case, so renderer code never inspects raw wire tags. Mutable session state stays separate from immutable validated values. The session must distinguish schema validity, component support, reference integrity and state-dependent update validity. A successful decode authorizes no server action. Valid partial updates, supported action data, state and attribution are preserved; unsupported essential behavior fails explicitly. The session can apply earlier messages before a later processor rejection, so the public adapter must define and test how a rejection clears or replaces the display rather than claim an atomic rollback it does not implement.

Lit owns mounting, binding integration, events, accessibility and disposal. It accepts the application's catalog and explicit integrations rather than discovering them through a registry, and the application chooses renderer, host and trusted content policy independently. Upstream custom-element and catalog registration stays at the Lit integration seam; importing saga a2ui configures nothing globally. Within one `CustomElementRegistry`, catalog registration may reuse an existing definition only when tag and constructor both match. A tag already bound to a different constructor fails explicitly and keeps the first definition; distinct implementations need distinct tags.

The own-catalog import must not require `@saga-a2ui/components`, FaithfulCard or a Markdown parser. A consumer such as Ansari may use its own Markdown parser and branded component without making those requirements of core or Lit.

In the [action binding](../modules/action_binding.blueprint.md) module's terms, the adapter owns the instance lifecycle and nothing about server authorization. It creates and retires instances; stamps each admitted event with its installation epoch so a stale event is ignored; answers whether an instance is still the live one; detaches only the installation its own binding made; and calls `dispose()` on its bindings when the surface is deleted, the host disconnects or setup fails. Undecided invocations are then canceled as disposed and a decided outcome stays decided. The shared action runtime, not the adapter, decides outcomes and owns the work-deadline and per-step hook timers. Listener deadlines, controller read bounds and any application-owned spanning bound keep their existing owners, and adapter retirement stays separate from server requests and application resources. A decoded message, a bound callable and a client-side prerequisite authorize nothing; the application server stays authoritative. Upstream A2UI action forms are wire semantics, and the adapter states how one reaches a bound callable without implying where the work executes. This is the implemented Lit integration; React qualification is recorded separately, and Lynx delivery is retired.

The historical Lynx Web investigation checked worker and resource-origin assumptions before VIEW1 finalized its neutral interfaces. Its bounded result is recorded in Status; the retired Lynx delivery chain creates no current implementation prerequisite or host-support claim.

## Failure and recovery

| Trigger | Visible result and cleanup |
| --- | --- |
| Unsupported version, malformed envelope, rejected component or update | The affected current view clears with a safe saga a2ui fallback; supplied markup stays inert and no invalid server action is dispatched. Application components stay responsible for rendering their own content safely. |
| A valid result replaces an earlier answer or item | Only the current result is visible; old bindings and resources do not persist as another active view. |
| Result arrives during connection | Handled once after the owning view is ready; initialization does not repeat the business request. |
| Results out of order after selection or account change | The current request and session generation wins; retired data and client work started by a retired invocation (in the example, the player Play started) cannot be restored. |
| Authentication lost or new sign-in observed | Private content clears immediately when observable; acquired resources and requests are cleaned up per the lifetime contract. An invisible host account change is not claimed detectable. |
| Callback fails, processing exceeds a bound, or the view disconnects | Safe failure or teardown retires work and releases owned listeners and sessions. Application cleanup stays explicit. The [connector's failure contract](reusable_mcp_connector.blueprint.md#failure-and-recovery) covers the bounded request. |
| Standard and Strict instances share a page | Trusted policy and callbacks stay instance-owned; one instance cannot permit another's links or images. |

Host navigation uses only a supported advertised capability; when unavailable, links stay readable and inert. Image requests obey trusted exact-host configuration and the host's CSP. Content cannot change policy, and an authored protected action keeps its own server authorization and resource rules under both content levels.

## Verification outcomes

| Condition | Observable result |
| --- | --- |
| Core exercised without a DOM or renderer | Valid envelopes, cases, field preservation and partial updates work; malformed, unsupported and state-invalid input fails explicitly. |
| Synthetic app uses installed public core and Lit exports | Read, content and protected action keep their authorization, policy, disclosure and visible behavior with the application's catalog. |
| Two catalogs and policy instances mounted | Neither's catalog, data, callbacks or policy changes the other. |
| Two catalogs register one tag in one registry | Different constructors fail explicitly without changing the first definition; the exact same tag and constructor repeats harmlessly. |
| Early, repeated, reversed, account-changing and cancelled results | Each accepted result renders once; no duplicate operations or listeners; no restoration of stale private data or retired-invocation work. |
| Mounted view disposed then reconnected | Old subscriptions and sessions released; late results ignored; the new instance starts fresh. |
| Built resource under the declared CSP | Bindings, host-navigation callbacks, allowed and blocked image requests, keyboard use and narrow layouts behave as required. |
| Server and browser entry points imported independently | Core has no renderer, MCP or DOM dependency; the browser artifact has no server module or credentials. |
| Own-catalog consumer installs packed artifacts | Uses public exports without FaithfulCard, components or a parser in the emitted view, workspace aliases or copied SDK code. A stack installation includes components; that differs from its emitted own-catalog view. |

Run the full VIEW2 lifecycle matrix and the complete connector CORE3 checks before calling the joined SDK ready for packaging. Browser evidence proves built adapter behavior; independent actual-host runs remain required for host claims, promptly on integrated candidates. A pending maintainer decision does not require idle implementation, but no missing observation becomes a pass.

## Implementation sequence

[Status](#status) owns the standing of each slice. The original sequence followed the shared dependency recipe and CORE1 view contract (the first of the three [connector](reusable_mcp_connector.blueprint.md#implementation-sequence) extraction steps): [VIEW1](https://github.com/MachineWisdomAI/saga-a2ui/issues/17) extracted core and Lit together using the synthetic app's catalog, after the Lynx Web investigation and before freezing neutral interfaces. It has no dependency on finished React or Lynx implementation.

**Sequencing amendment (approved 2026-10-17).** The operator approved starting preparation slices that do not need the proposed lifetime or action-binding designs ([#69](https://github.com/MachineWisdomAI/saga-a2ui/pull/69), [#73](https://github.com/MachineWisdomAI/saga-a2ui/pull/73)): "don't wait on #69 or #73 for work that doesn't need them." It changes start order only. It approves neither design nor implementation, and adds or claims no compatibility with them. Both designs have since been approved on their own (see Status), which does not change what this amendment authorized and does not establish their implementation.

The delivered preparation scope preserves authentication, result correlation, cancellation and disposal while rendering a synthetic public answer through installed core, Lit and MCP exports. Its checks cover exact question/answer binding, early and late delivery, invalid-current-result fallback and catalog isolation.

The joined qualification keeps the complete [VIEW2](https://github.com/MachineWisdomAI/saga-a2ui/issues/18) account, selection, cancellation and teardown matrix and CORE3's failure, deadline, callback, projection and transport matrix. STATE1 and STATE2 are accepted for their bounded scope in the [lifetime Status](request_view_lifetimes.blueprint.md#status), including [PR #126](https://github.com/MachineWisdomAI/saga-a2ui/pull/126); their preparation hold is historical.

[PACK1](https://github.com/MachineWisdomAI/saga-a2ui/issues/21) and [PACK2](https://github.com/MachineWisdomAI/saga-a2ui/issues/22) join own-catalog and optional-card consumers, protected behavior, external installation, matched resources and upgrade/rollback evidence. Advancing preparation does not waive required actual-host evidence, public source/npm installation or destination maintainer authority. [Ansari adoption](ansari_adoption.blueprint.md) can use pinned candidates during development; directory approval and publication tooling are not prerequisites.

## Open decisions

**Settled.**

- **Lifecycle reporting and release.** VIEW2 ([#18](https://github.com/MachineWisdomAI/saga-a2ui/issues/18), [#131](https://github.com/MachineWisdomAI/saga-a2ui/issues/131)) qualified the adapter lifecycle through installed public exports; [Status](#status) gives its scope and limits, including that server processes used workspace exports.
- **Lynx Web investigation.** VIEW1 recorded its bounded result (the default upstream module Worker path failed cross-origin in both actual web hosts; not Lynx renderer acceptance). The owner retired the Lynx delivery chain on 2026-10-19, so neutral interfaces carry no Lynx requirement.

**Still open.**

- **Which core/Lit peer recipe preserves both catalogs?** The original comparison concerned saga a2ui on A2UI 0.13.0 and Ansari on 0.9.1, both using `/v0_9`. It is a historical migration question, not a statement of Ansari's current dependencies. Version differences alone do not show wire incompatibility; the [Ansari adoption design](ansari_adoption.blueprint.md) owns destination qualification.

The Lit-specific action-attachment choices (how much of the basic Button to reuse, how a Lit mount identifies its owner, where an action dependency enters `A2uiAppDependencies`, what an unbound control shows) are adapter choices recorded in the [action binding decisions](../modules/action_binding.blueprint.md#open-decisions), not decided here.
