## Problem and current behavior

Developers can create a clean application with `saga init`, attach MCP delivery to an existing backend using generated recipes, or explore the separate synthetic demo. All three use maintained templates and qualified SDK interfaces; the application keeps authentication and domain authorization. [Status](#status) records the exact delivered revisions and evidence limits.

The server side uses official `@modelcontextprotocol` middleware, checked against the upstream typescript-sdk `packages/middleware` source on 2026-10-16. Available source is not proof that an adapter installs or works with saga a2ui. The [reusable MCP connector](reusable_mcp_connector.blueprint.md) selects Node integration 2.1.1 with MCP Apps 2.0.3, split MCP SDK 2.3.1 and Zod 4.2+; the framework slices below pin the tested Express, Fastify and Hono recipes. The design makes no wider version promise.

| Server target | Integration |
| --- | --- |
| `node` | Official `@modelcontextprotocol/node` adapter |
| `express` | Official `@modelcontextprotocol/express` adapter |
| `hono` | Official `@modelcontextprotocol/hono` adapter |
| `fastify` | Official `@modelcontextprotocol/fastify` adapter |
| `hapi` | No official adapter; saga a2ui maintains the Hapi bridge in its template over the official Node/server SDK |

saga a2ui owns the Hapi integration in `templates/lit-hapi`; its bridge (`server/bridge.ts`) was adapted from an earlier proof of concept that is not part of this repository, not a production deployment and not an external repository, maintainer, package or runtime prerequisite. saga a2ui qualifies the bridge's identity handoff and transport protections itself. The template is the single maintained source for exported applications and generated attach recipes. Route authentication alone does not show identity reaches saga a2ui's handlers. Framework adapters, HTTP handling and authentication remain application or template integration, not saga a2ui packages.

## Behavior

**New project.** `saga init --a2ui-stack <renderer>-mcp --server <target> DIR` (for example `lit-mcp` with `hono`) creates a new directory. The stack value selects a renderer and MCP delivery; the matching package uses the flat `@saga-a2ui/*` name. All five targets above are qualified, with Hapi using the maintained template bridge. Init refuses to overwrite files, follow unsafe symlinks, install dependencies or run remote hooks, and never modifies an existing application. It offers only CI-qualified pairs; any other pair is refused with the supported list. The starter is clean: no demo content, synthetic identity or media, and no test verifier.

**Existing backend.** A developer with a running server follows the attach recipe in the guides (including Hapi). Its authentication and server snippets are generated from the same maintained, CI-qualified template files init uses, so both paths share qualified pairs and glue but not business fixtures.

**Identity handoff.** In both paths the application authenticates and gives saga a2ui its verified identity through the connector's verified-identity hook; it keeps authentication and domain authorization. For Hapi, the authentication strategy snapshots and freezes the identity before any body wait. The bridge starts and owns the admission lifetime before authentication (reached through `mcpRequestLifetime(request)`), and its factory receives `{ authInfo, lifetime, request }`; the official Node transport carries request-local auth to the hook. The bridge owns bounded parsing, deadlines and connection cleanup, scoped to its registered endpoint. Identity is per request. A protected operation without verified identity fails closed; a declared public operation needs none and gets none fabricated.

**Demo.** One qualified pair is the separate demo. It matches the standalone release download and keeps the full synthetic allowed, denied, expired and recovery semantics, reusing shared glue with its own fixtures. There is no demo per pair.

## Responsibilities and interfaces

The SDK owns the shared template files, tested in CI, as the single source for init output and guide snippets. `scripts/saga.ts` owns command parsing and supported pairs; maintained templates own starter output, `scripts/build-demo.ts` builds the demo, and `scripts/guide-recipes.ts` generates attach recipes. The application owns authentication, domain authorization and business fixtures. No new runtime API is introduced; the identity hook is the connector's. The CI harness may supply a test identity from outside, but test verifiers never enter production starter output.

## Failure and recovery

| Trigger | Observable result and recovery |
| --- | --- |
| Requested pair not qualified | Init exits without writing, names the pair unsupported and lists supported pairs. |
| Target directory exists or contains an unsafe symlink | Init refuses and writes nothing; the developer picks a new path. |
| Init interrupted while copying | Only output this run created is cleaned up; the developer reruns with a clean path. |
| Protected operation without authentication | Fails closed, no handler runs. A declared public operation is unaffected. |
| Overlapping requests with different identities | Each handler sees only its own request's identity. |
| Template change makes a pair fail CI | The pair is withdrawn from the supported list until it passes. |

## Qualification

Each additional offered pair must still pass allowed, denied, missing-auth, public and concurrent-identity qualification, and Hapi's additional proof that authenticated identity reaches its hook is covered by `scripts/starter-hapi-identity.test.ts`. Overwrite, unsafe-symlink, implicit-install, remote-hook, unsupported-pair and interrupted-copy behavior is covered through the actual command paths of CLI1 and CLI2. Each check qualifies its own boundary independently of the first starter.

## Implementation sequence

The original delivery order preserved these dependency edges: the starter and demo followed PACK2 ([#22](https://github.com/MachineWisdomAI/saga-a2ui/issues/22)), the package release-readiness ticket. GUIDE1 followed the starter and demo, GUIDE2 followed GUIDE1, CLI1 followed the starter, and CLI2 followed CLI1 and the demo. Status records their landed implementations. The first pair needs only itself qualified; other combinations are not preconditions, and Ansari adoption is not gated on React, Lynx or a complete matrix. The public source and npm gate, required host runs, deferred final signoff, ownership and license checks and optional publish tooling (see [host publication](host_publication.blueprint.md)) are unchanged.

## Open decisions

**Settled.**

- **Demo pair.** STARTER1 and DEMO1 settled it: Lit/MCP on Node 2.1.1. No other server pair is implied.
- **Hapi identity handoff.** The Hapi authentication strategy snapshots and freezes the identity before any body wait, and the bridge passes `{ authInfo, lifetime, request }` to the factory (Behavior; the Hapi lifecycle amendment, PR #215, in [Status](#status)). `scripts/starter-hapi-identity.test.ts` and `scripts/starter-hapi.test.ts` check it in source.
- **Qualified adapter versions.** Node, Express, Fastify, Hono and Hapi, each for its scoped Lit/MCP pair at the exact tested recipe (historical pins in the [framework evidence](application_setup.evidence.md) and current pins in `templates/*/package.json`). No untested version or pair inherits this.

**Still open.** None recorded here. Publication, actual-host acceptance and the broader renderer matrix stay outside this Blueprint's scopes (see Status).
