## Problem and current behavior

Episode descriptions need ordinary Markdown formatting without letting supplied content execute code, navigate the assistant or fetch arbitrary images. The application owner also needs a stricter mode that can hide blocked fragments and lets the reader decide whether to load permitted images.

At the design baseline, [`SagaPanelElement`](../../apps/lit-host/src/lit/integration.ts) showed descriptions through inert Lit text bindings. Its [catalog contract](../../apps/lit-host/src/saga-panel/contract.ts) accepted a bindable description string with no Markdown interpretation or selectable policy, and the [public resource](../../apps/lit-host/src/mcp/server.ts) declared empty connection and resource allowlists. This design adds formatting and controlled effects in that working application. FaithfulCard and the reusable packages were later work at that point; [Status](#status) records which scopes are now implemented.

## Proposed behavior

The application resolves one trusted policy when it creates a view.

- **Standard** (default): absolute HTTPS links may open through a supported host callback, and HTTPS images may load only from explicitly configured exact hosts under the image restrictions below. The image allowlist defaults to empty.
- **Strict**: links stay inert and no content image loads automatically. Blocked fragments (links, image references, unsupported markup) appear by default as accessible placeholders in their original positions; the trusted application may instead choose readable inert text. Either way the reader can reveal or hide the source as text. Revealing changes visibility only: raw HTML, scripts, invalid URLs and unallowlisted images still cannot execute, navigate or fetch.

**Show images** and **Hide images** are local actions in the shared [action vocabulary](../README.md#action-vocabulary). The view owns them, and the consent they change is revocable view state. Show images lets the reader load otherwise-permitted images for the current description revision in the current live view; offer it only when the host path demonstrably qualifies, otherwise show blocked or unavailable feedback. It cannot widen the exact-host allowlist or bypass image restrictions. Content, policy or selection changes, view replacement or disposal, identity or session retirement (where the view receives such a signal; the public episode view has none today, see [Status](#status)) and any invalidation by the consent owner revoke consent. Revalidation cannot restore it. Hide images removes displayed images and revokes consent but cannot undo requests already sent. There is no extra content level or persistent trust setting, and the action module adds no second consent lifetime.

Example: a description holds a paragraph, a quotation, a link and an image. Both modes keep text, order and formatting without changing the input. Standard shows the parsed link hostname, visibly and accessibly, before sending the validated URL through the host callback. Strict initially shows placeholders for the link and image; revealing source activates neither. Only Show images can load the image, and only if its destination is otherwise permitted. A missing or denied link callback leaves an explicit readable inert state, never direct navigation.

The policy governs description visibility, link activation and image requests, and the same value drives the content-related CSP declared in the resource. The application owns the surrounding A2UI tree; this feature does not sanitize arbitrary A2UI components.

Two other decisions are separate. *Delivery policy* belongs to the [MCP connector](reusable_mcp_connector.blueprint.md): which recipient gets which projection and which host capabilities a protected operation needs. *Domain authorization* belongs to the application: an authored protected action (Play, in the playback example) has its own server-checked authorization and media policy. Strict therefore leaves an authorized authored action available where the host supports it, and a content link never acquires an authored control's binding or authority. Neither the description, an MCP tool result nor an A2UI property can change the content policy.

## Responsibilities and interfaces

| Owner | Responsibility and boundary |
| --- | --- |
| Application composition | Select Standard or Strict, the exact-host HTTPS image allowlist and Strict's blocked-fragment presentation (hidden or readable inert text). Reject invalid configuration before rendering. |
| Application-local policy module | Build one validated immutable policy value; decide link, image and resource-policy effects. Independent of any card, renderer or host name. API names are open. |
| Application-local Markdown module | Keep the original string; use a maintained parser to produce restricted tokens in order. Raw HTML and unsupported markup stay source text. Reject over-limit input explicitly. |
| Lit renderer | Map tokens to fixed templates and text bindings. Own accessible reveal and image controls, consent for the current description and view, events and cleanup. |
| MCP resource and host adapter | Derive content-related resource restrictions from the same policy; expose only the supported link-opening callback. A host may be stricter; application policy cannot expand host permissions. |
| Authored action/media flow | Keep the separate protected operation, capability routing, origin rules and server authorization from the playback design. Content policy neither creates nor authorizes business actions. |

Description text and parser-generated HTML must never reach `unsafeHTML`, `unsafeSVG`, `innerHTML` or equivalent paths. Fixed templates render only the restricted token cases, and revealed source is still a text binding. Ordinary prose stays text even if it resembles instructions.

One policy value determines both resource configuration and view behavior. MCP Apps [`resourceDomains`](https://github.com/modelcontextprotocol/ext-apps/blob/v2.0.3/src/spec.types.ts) is a broad origin permission covering images, scripts, stylesheets, fonts and media. POL1 must show an additional restrictive resource CSP, or an equivalent supported path, so adding an image host grants no script, style, font or media permission and authored media policy survives. If that cannot be enforced, images stay inert even after Show images. The resource declares its bounded image origins before mounting; consent cannot relax CSP; Strict sends no content-image request before consent. Tests inspect the built resource's effective restrictions and real requests, not declared metadata alone.

Each view receives its immutable policy and callback explicitly. Consent is separate view state and cannot mutate the policy. There is no module-wide "current policy", host-name switch or callback registry, and interleaved views cannot share consent. Resource identity must distinguish policy variants whose host metadata differs, so a cached resource cannot supply another policy.

URLs are parsed with platform APIs and validated before any effect; only absolute HTTPS destinations can activate. Exact-host image matching rejects suffix tricks, unlisted subdomains, credentials and malformed input; wildcards are outside the contract. If the host cannot enforce the image destination boundary, the image stays inert. Authored media permissions are derived separately and cannot be borrowed by content images.

The Markdown and policy modules stay renderer independent. Lit registration, templates, styling and host callbacks stay at the existing integration boundary, so later extraction needs no placeholder packages and Markdown is not required of unrelated catalog components.

## Trusted embedded artwork

A self-contained card can carry application-owned artwork without an external fetch. The shared [FaithfulCard policy](../../packages/components/src/faithful-card/policy.ts), inspected at SDK revision `78820dfce3d119d4c82d3d12020af65bef1e2fb1`, derives `img-src 'none'` for an empty image host list, which blocks bundled raster artwork encoded as data URLs even when it belongs to the trusted template. The amendment fixes that without a new flag.

**Images.** Build one `img-src` list from the mode's baseline plus the validated exact HTTPS origins, never emitting `'none'`. Configured origins extend the baseline and never replace it:

| Configured image hosts | Standard | Strict |
| --- | --- | --- |
| Empty | `img-src data: blob:` | `img-src data:` |
| One exact host | `img-src data: blob: https://images.example.com` | `img-src data: https://images.example.com` |
| Several | `img-src data: blob: https://a.example.com https://b.example.com` | `img-src data: https://a.example.com https://b.example.com` |

`data:` and `blob:` are scheme sources, not hosts, and must not be added to broad resource-domain permissions. Other directives, including connection policy, keep their restrictions. Rebuilding the policy from `policy.configuration` reproduces the same restrictions. Standard's `blob:` supports application-owned browser objects such as generated images or local previews; it permits no network fetch (bytes fetched first still need connection permission), and the application owns creating and revoking its object URLs. It is a convenience, not proof the bytes are trusted. Strict omits `blob:` even for application-created URLs and never regains it from configured origins. See the [CSP image directive](https://www.w3.org/TR/CSP/#directive-img-src) and [File API object URLs](https://www.w3.org/TR/FileAPI/#url).

### Trusted fonts

Standard derives `font-src data: blob:`; Strict `font-src data:`. No opt-in flag exists, and Strict cannot regain `blob:` through font origins. Trusted application CSS may embed WOFF2 as a data URL or, in Standard, use an application-owned blob URL in `@font-face`; system-font fallback remains. Answer text, tool results and A2UI properties cannot supply font URLs, inject CSS or select a font policy, and fonts do not use Show images consent.

Trusted resource configuration may add `fontOrigins`, a separate exact HTTPS origin list defaulting to empty. Normalize and validate before building the immutable policy: reject wildcards, non-HTTPS schemes, credentials, non-root paths, queries and fragments; keep an explicit non-default port; deduplicate. Serialization and reconstruction preserve the list. Image hosts never authorize fonts, and font origins never authorize images. Adding origins cannot drop `data:` or Standard's `blob:`. One origin gives `font-src data: blob: https://fonts.example.com` in Standard and `font-src data: https://fonts.example.com` in Strict. Authored `@font-face` URLs load automatically in both modes. Redirects must stay inside declared font origins under the effective host and document policies; otherwise use the readable fallback instead of broadening permissions.

Font requests carry ordinary network metadata, and paths, queries or `unicode-range` subset selection can reveal data. Application font URLs must not be built from answer text, credentials or private request data; static version parameters are fine. An origin allowlist does not validate URL content. The resource builder emits one `font-src` directive whose baseline survives reconstruction. Where the host needs broad resource-domain metadata, declare font origins there while keeping a restrictive document CSP so they grant font access only. A remote font stylesheet is a stylesheet request and is not authorized by allowing its font-file origin. Font loading follows browser fetch and CORS rules, so CSP permission alone does not guarantee a load; a failed font uses the authored fallback and verification must show the intended font actually loaded. See [CSP font sources](https://www.w3.org/TR/CSP/#directive-font-src) and [CSS font fetching](https://www.w3.org/TR/css-fonts-4/).

### Artwork and answer images take separate paths

The consumer imports static artwork at build time and references the bundled bytes from its trusted template or CSS; the shared policy supplies the matching CSP before mounting. Bundled decoration displays in both modes without consent, and Hide images does not remove it. Answer text still goes through the restricted Markdown reader. `decideImage` and `offerImages` keep their meaning: content images need an absolute HTTPS URL, an exactly allowed host, established enforcement and, in Strict, current consent. Markdown `data:` and `blob:` URLs stay rejected even with consent. The content wire contract stays exactly `contractVersion` and `markdown`; answers cannot select assets, CSS, templates or policy.

CSP cannot establish the provenance of data-URL or (in Standard) blob bytes, and removing `blob:` from Strict narrows permissions without making `data:` a trust check. The boundary therefore rests on fixed authored templates and the shared content decisions: untrusted MCP content must never reach trusted template or CSS asset slots, or be turned into a data or blob URL to bypass those decisions. Every renderer must verify this through its public content-binding path. The allowance is not a sanitizer, and adds no HTML injection path, inline SVG, image proxy or renderer-specific policy fork.

Example: an application with an empty external-image allowlist builds a card with decorative raster artwork. It displays from the immutable resource. An answer containing a data image, a blob URL or an external HTTPS image still shows a placeholder or source text, and neither Strict nor source reveal changes that.

### Enforcement, caching and failure

Resource and view rebuild the same policy through public SDK exports. `establishImageEnforcement` keeps requiring the exact derived document policy; baseline schemes cannot manufacture enforcement when it is missing or mismatched. Consumers must not hand-edit a looser CSP. A host may be stricter, and blocked artwork is a visible qualification failure, not a reason to relax directives or fetch a remote asset. Resource identity covers compiled code, policy, CSS and embedded font and artwork bytes; changing them changes identity, while a new answer reuses the resource and updates only validated data. Remote fonts are optional; the self-contained recipe embeds required font bytes and works with no external runtime asset.

### Amendment scope and delivery

Approval replaces only the earlier assumption that an empty image host list forbids every image (data sources in both modes, blob only in Standard) and `font-src 'none'` (baseline `data:`, `blob:` only in Standard, plus the exact HTTPS font-origin list). An empty host list still forbids every content image. Markdown fidelity, link rules, image consent, lifetime ownership, delivery policy and server authorization are unchanged. Earlier source-implementation records do not establish these baseline permissions.

## Failure and recovery

| Trigger | Reader-visible result and effect |
| --- | --- |
| Invalid level, malformed image host or wildcard in trusted configuration | Fail explicitly before mounting a permissive view; never guess a looser policy. |
| Oversize description | Explicit content-limit failure, no silent truncation; the supplied string is unchanged at its owner. |
| Embedded HTML or script, unsupported markup | Source stays inert, visible or collapsed; revealing it cannot execute code, change configuration or alter action arguments. |
| Non-HTTPS or invalid link | Source stays inert; no callback or direct navigation, even after reveal. |
| Missing or denied host link callback | Show the destination and an explicit inert state; no `window.open` or direct navigation. |
| Image unallowlisted, disallowed by CSP, or lacking demonstrated image-only enforcement | Placeholder or inert text and no request, even after consent. A CSP block does not excuse a forbidden fetch attempt. |
| Strict content with an allowlisted link or image | Links stay inert. Images need current consent plus destination and resource permission; source reveal grants neither. |
| Description, policy or selection change; view replacement or disposal; identity or session retirement where observed; any consent-owner invalidation | Revoke consent and remove images; stale controls and callbacks cannot load or restore them. Release owned state and handlers on teardown. |

Image redirects follow the same destination discipline as the first request; a redirect to an undeclared destination must not become a way around the exact-host policy. The chosen host and CSP path must demonstrate this, otherwise the image stays a placeholder. This authorizes no media proxy or content-fetching service.

## Verification outcomes

Use the same ordinary and hostile descriptions in both modes. Browser tests load the built resource and observe the actual host callback and network path, not source strings or declared CSP alone.

| Condition | Required result |
| --- | --- |
| Ordinary text, formatting, blocked fragments | Original input and order preserved. Strict placeholders, optional inert text and keyboard-accessible reveal and hide cause no execution or network effect. |
| Standard, default configuration | Empty allowlist, no content image loads. The parsed hostname is visible and accessible before a validated HTTPS link invokes the callback. |
| Standard, one exact image host | Only permitted HTTPS destinations load; suffix tricks, unlisted subdomains, credentials and non-HTTPS are rejected. Image-only restriction and redirect enforcement shown without widening script, style, font or media. |
| Host callback absent or denying | Explicit readable inert feedback, no direct navigation. |
| Strict before and after Show images | Before consent, even after reveal: zero image requests and link callbacks. After consent only permitted images load; invalid destinations stay unfetched; links stay inert. With no qualifying image, show unavailable feedback instead of enabling the control. |
| Hide images; stale consent | Hide removes images. Content, policy or selection change, replacement, disposal, observable identity or session retirement and consent-owner invalidation reject old controls and late results. Revalidation cannot restore consent; new content needs fresh consent; another view cannot inherit it. |
| Content tries to inject HTML, scripts, policy or actions | Stays inert, including after reveal; configuration and action arguments unchanged. |
| Standard and Strict views interleave updates and disposal | Each keeps its own policy and callback; one cannot enable effects or break the other's cleanup. |
| Resources rebuilt, cached or replaced | Resource metadata and renderer behavior agree; test the built resource and its identity. |
| Authored protected action under either level | Current authorization and applicable resource and delivery policy still apply (for Play: capability, recipient separation, media checks). Strict does not disable it, and content destinations do not inherit its permissions. |
| Empty image host list | Standard `img-src data: blob:`, Strict `img-src data:`. Trusted data images display in both; trusted blob images only in Standard. Answer-supplied data, blob and HTTPS images stay inert, including after reveal and consent. |
| One or several exact hosts, both modes | The mode baseline stays beside every normalized origin; data images display in both, blob images only in Standard. Exact-host, redirect and image-only rules apply; Strict needs current consent. |
| Invalid trusted configuration; attempted answer configuration | Explicit failure. Answer data cannot mutate policy or reach template or CSS control. |
| Policy round-trip; missing or mismatched document policy | Baseline and origins retained; Strict never gains `blob:`; missing enforcement leaves content images inert. |
| Embedded and blob fonts | A data-URL WOFF2 loads in both modes; a trusted blob font only in Standard (Strict falls back readably); invalid font input falls back readably. |
| Font source composition | Empty, one and several origins keep `data: blob:` (Standard) or `data:` (Strict) and add declared origins; normalization, deduplication and round trip preserve origins and ports; invalid entries fail explicitly. |
| Remote font loading and isolation | With working CORS a font loads from its declared origin; unlisted origins and redirects are blocked. Image permission grants no font access and font permission no image, script or stylesheet access; fallback stays readable. |
| Supplied content versus asset slots, every renderer | Content cannot reach template or CSS asset slots directly or by data/blob conversion. Verify with hostile input through real content binding; CSP alone does not prove it. |
| Hostile answer text and font requests | Cannot inject `@font-face`, change font configuration or become a request path or query; application font URLs carry no answer, credential or private data. |
| Attempted external runtime loads | Script, stylesheet, frame and connection restrictions unchanged; embedded assets create no external dependency. |
| Artwork or policy change versus answer change | Artifact changes give a new resource identity; answer-only changes reuse it. |

Local checks establish policy and browser behavior. The authenticated ChatGPT web and Claude web runs still exercise both levels, Strict visibility and image-consent controls and authorized and denied playback with the built resource, recording exact policy, source and resource identity, host and observed callbacks and requests. Deferring final signoff does not defer these runs; failed or unavailable evidence stays an open acceptance result.
