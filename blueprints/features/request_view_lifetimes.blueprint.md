# Request and view lifetimes

Draft awaiting human design review.

## Problem and current behavior

A user who performs a protected action through an assistant host touches two programs that each decide, separately, when a piece of work stops mattering. The embedded view, a page that talks to the host through the MCP Apps bridge, decides when it stops caring about a question: the user selects another item, the sign-in label changes, a request takes too long, or the host asks the view to tear down. The application's HTTP listener decides how long it waits on its own dependencies (credential verification, the authorization lookup, protected storage) before it answers. This document asks whether each side stops acting at the moment it decides to, for the two views, the two protected tool endpoints and the protected resource route of [authorized playback](authorized_playback.blueprint.md).

It supersedes the rejected [account and session isolation proposal](https://github.com/MachineWisdomAI/saga-a2ui/blob/427257e207b4bb8dbcec8dbf38ea466a98209024/blueprints/features/account_session_isolation.blueprint.md) with a narrower question about ordinary lifecycle correctness, and it preserves the safeguards the code already has: authentication on every protected request, the immutable per-request identity, opaque labels used only for freshness, safe fault distinctions, the read bound and the resource acquisition checks. It adds no live account switching, retained-state expiry, focus or resume revalidation, authentication for the public route, lifecycle framework or cross-request registry.

Current behavior was first inspected at `19fb26c` and reconciled on 2026-10-17 against main [`6d3916d`](https://github.com/MachineWisdomAI/saga-a2ui/tree/6d3916da15a6207a5a546f06a86f772fd31b9ce3), including the MCP SDK migration and Standard/Strict description rendering. The pinned recipe is MCP Apps 2.0.3 with client/core/server 2.3.1 and the Node transport 2.1.1. Each gap below remains a source-inspection candidate, not a reproduced fault; none is shown to expose another user's data. Existing regression checks do not establish the proposed fixes or actual-host acceptance. Repair of any candidate should begin with a reproduction.

### Terms

This document uses the shared [action vocabulary](../README.md#action-vocabulary). A **server action** is an operation the view sends to the application server through the host and waits on; in the pinned recipe it is a server tool call made with `App.callServerTool`, and the server authenticates and authorizes every one. A **client action** is handled entirely in the view by a JavaScript function and makes no request. A server action's result may start a **client continuation**: client-side work the view performs before it presents the outcome, such as acquiring a protected resource with a capability the result carried and starting a **client-held resource** with it. An **attempt** is one server action with its continuation, from the user's activation to a terminal view state. A **resource request** is the direct HTTP request the continuation makes to the application's protected resource route; it carries the capability and a proof, and the host does not proxy it.

The example application has two views. Its **read view** (the subscriptions view) issues a read server action and shows the rows for the signed-in account. Its **action view** (the playback view) offers a protected server action on the selected item and client actions on the client-held resource that the continuation starts. In the example, Play is the protected server action: the server authorizes the request and issues a media capability, then the continuation acquires the bytes and starts the player. Pause and Resume are client actions on that player. The design below is written for any view with this shape; the example's controls are named only where inspected source is described.

The **sign-in label** is the opaque `viewSession` value carried in tool results. It tells a view whether the data on screen still comes from the sign-in the view started with, and it never grants access, because the server authorizes every call from the verified request. To **pin** the label is to remember the first one a view accepts and compare later results against it. An **opener** is the `toolresult` notification that tells the action view which item is selected; a **correlated response** is the value returned to a server action the view itself makes. Notifications carry no request id, so an opener can be a delayed copy of an earlier one.

A view **retires** an attempt by advancing its generation number so a late answer is recognized as obsolete, stopping the attempt's timer, aborting its resource request and releasing the client-held resource (stopping the player, in the example). Retiring is a client decision and says nothing about whether the server stopped. On the server, a request is **committed** once its status line and headers are written and **finished** once the application has handed its final result or error to the transport.

### What exists today

On the server, the listener builds a fresh MCP server and `NodeStreamableHTTPServerTransport` for each POST to a tool endpoint and answers in JSON; the resource route is a plain HTTP handler. Verified identity reaches each handler through `ctx.http.authInfo`, and its cancellation signal is `ctx.mcpReq.signal`. The read server action races a bound (`readBoundMs`) and the handler's abort signal in `readWithinBound`, so a retired read never becomes the tool result. The resource service limits how long a credential is accepted when an acquisition begins, not how long an accepted request may wait.

In the view, the shared bridge closes the connection once on `dispose()` and, when the host asks for teardown, calls the view's optional `onTeardown` once before it answers and before delivery stops, leaving closing to the host. The public content view pins no sign-in label and issues no server action. It now owns description effects: it revokes image consent before every delivered result, including repeats and errors, and permanently retires consent on host teardown and disposal. Description elements discard obsolete link and image callbacks and revoke their grants on content change or disconnect. These POL1/POL2 safeguards stay with the content owner; this proposal preserves them rather than adding a second consent lifetime.

The read view accepts the host's opening result, which it treats as the answer to the call that created the view (a documented bootstrap assumption, not correlation), and later unsolicited results under the same label while it is not invalidated and no read is in flight. After a loss, an unsolicited positive result is ignored and only a correlated response from a read started after the loss recovers the view. Each read has a never-reused generation and a timer, so a read past its bound is retired, the view shows a retry state, and the late answer is dropped.

The action view pins the label from the first opener. Activating the server action retires anything earlier, unlocks the client-held resource inside the user's activation, and starts one attempt with a generation number: create a recipient key, call the server action through the host, check that the grant names the selected item, the pinned label and a resource URL for that item, acquire the resource with the capability and a fresh proof, and start the client-held resource. The server authorizes the action; the view validates the returned grant. The view checks its generation after key creation, after the server action, after acquisition and after the client-held resource answers. Acquisition itself (proof signing, the resource request and the body read) has several awaits with no check between them and relies on the request's abort signal and the check that follows. A late server-action result, a late grant, or a late acquisition completion finds a different generation and is dropped before the continuation produces anything the user can perceive. A stale completion of the client-held resource's `start` is different: its effect may already have begun, and the view currently calls `stop` on it, as the candidate below explains.

### Candidate gaps

On the server, the read is the only application-facing wait with a deadline. In the inspected code the credential verifier, the body read (byte limit only), the authorization check on the protected server action and on each resource acquisition, and the protected storage read have no bound of their own. A request can therefore wait on a dependency as long as the dependency takes, and a request nobody wants can still start work: a server action abandoned during the authorization wait would still issue a capability, and an abandoned acquisition would still read protected storage. The listener registers its own close handler only inside `serve`, after authentication and the body read, and what Node reports to the body reader when a caller disconnects earlier is not established. The public `/mcp` route was not inspected beyond its lack of limits, so this document says nothing about it.

In the view, five candidates came from reading the controllers.

- **The read view registers no `onTeardown`.** After teardown the controller can still hold an armed read timer and an active generation. If either settles, it presents rows, the retry state or sign-in-required, and `retry()` can start a new read. Whether that is visible depends on whether the host removes the page and whether an in-flight proxied call settles at close.
- **The action view can leave `session-changed` through the old label.** An opener under a different label clears the selection and presents `session-changed`; a grant under a different label presents `session-changed` but keeps the selected item. Both keep the old pin, so a later opener under the old label returns the view to `ready` and makes the server action available again, while an opener under the new label is never accepted. Given a delayed copy of an old opener, the view would report a changed sign-in and then show the old item as ready. This grants nothing by itself, since the server authorizes the next server action, and whether a host produces that sequence is unobserved.
- **Action-view teardown releases the client-held resource but does not retire the controller.** `onTeardown` is `retire`, which sets no flag, so until the host closes the connection the server action can pass its guards from a state such as `ready`, the client actions can call a released resource and present the result, and the resource's end event can present `ended`.
- **A late `start` can reach a newer attempt.** One client-held resource is shared across attempts, and when a `start` settles after its attempt was retired the controller calls `stop()`, which would stop a newer attempt's continuation. The resource's documentation says `stop()` during `start` makes the start reject, which covers the usual ordering, but the controller does not guarantee it.
- **A pending attempt has no controller-owned bound spanning the whole attempt.** The view waits on key creation, host forwarding, proof signing, the resource request, the body read and `start`, and ignores further activations meanwhile. The pinned `App.callServerTool(params, options)` accepts a signal and timeout options, but this controller passes none. That call has a 60-second default timeout which `App` resets on progress, with no maximum total timeout supplied. A silent stalled call therefore rejects through the existing failure path; progress can extend it. Neither that call timeout nor the resource request's cancellation bounds the whole attempt, including key creation and the continuation's start.

## Proposed behavior

Everything in this section is proposed. It gives the server and the view each a small, locally owned lifetime and keeps the two independent: retiring an attempt in the view never claims to stop the server, and a server deadline never depends on the view noticing.

### Server request lifetime

The listener creates a request lifetime when it accepts a request for a protected endpoint or the resource route, before authentication. It consists of one finite deadline, one abort signal, a watch on the response for an early close and a one-shot terminal gate, built from `AbortSignal` (handlers already receive one as `ctx.mcpReq.signal`), the response `close` event and timers. The deadline covers all asynchronous application work until the request is finished, and committing headers does not end it. The gate is closure state held by whichever owner settles the request; in the handlers it is the race `readWithinBound` already runs. The first of three events decides the terminal outcome: the work produces its final result or error, the deadline expires, or the caller closes the connection. A disconnect produces no response, matching the MCP cancellation guidance that a receiver should stop processing and not respond, and a deadline expiry on a usable channel produces exactly one. No path writes a second.

Before commit the server still chooses the outcome, so each stage reuses the answer it already gives a dependency fault, because an expired wait shows that a dependency was slow, not that the caller was refused. A verifier wait gives the existing 500 `server_error`, since a 401 would claim the credential is invalid. A tool handler's authorization, storage or read wait gives that tool's fixed unavailable failure, and the resource route's authorization or storage wait gives the existing 503 `unavailable`. A body wait has no suitable answer today; the proposal is a request-timeout status followed by destroying the request as the 413 path does, with the status and error name open. After commit the status cannot change and written bytes cannot be retracted, so on expiry or disconnect the response is ended or closed with no second status, and the deadline keeps applying to the work that produces the rest of the response.

The post-commit rule applies to any path that commits before its work completes. In the inspected JSON path commit and finish normally nearly coincide, and the source does not show how the pinned SDK transport writes its JSON response, so the proposal assumes it writes only after the handler settles and the implementation must confirm that. A streamed (SSE) response commits before the work ends, so the rule matters most there. Progress and delayed completion for JSON and SSE belong to the reusable connector, CORE3 ([#16](https://github.com/MachineWisdomAI/saga-a2ui/issues/16)), and a passing JSON-listener test neither qualifies SSE nor proves cross-POST cancellation.

The protected server action and each resource acquisition are separate requests with separate lifetimes. The capability the server action issues lives by its own clock after that request finishes, and each acquisition starts a new deadline that does not inherit what remains of the action's. The resource service checks capability expiry and proof age only when an acquisition begins, so the request deadline, not the capability, ends a wait on the lookup or the storage read.

### View attempt lifetime

Each attempt gets a bound timer armed when the view shows `pending`, independent of the server deadline because it must also cover the host's forwarding and the client continuation. Every way the attempt leaves `pending` clears the timer. A successful continuation (`playing`, in the example) clears it without retiring the attempt, because retiring would release the client-held resource that just started. A blocked continuation (`gesture-needed`) goes through the existing `clearWith`, which retires the attempt. The other outcomes (`unsupported`, `unavailable`, a denial, an error, a continuation that ends before its start is confirmed, and retirement by a new opener, a new activation, label loss, disposal or teardown) clear it too.

On expiry, if the attempt is still current and the view is still `pending`, the controller calls `clearWith` with `unavailable` for the selected item. That advances the generation, aborts the resource request and releases the client-held resource, so a hanging `start` rejects and finds a different generation, and the server action stays available. The timer ends the waiting. The generation checks only suppress the effects of obsolete results, so they do not shorten key creation or proof signing, which cannot be cancelled. Use the pinned `App.callServerTool` options: supply the attempt signal when initiating the server action and abort it on expiry or retirement. Retain generation checks for late completions. Its existing request timeout remains a narrower safeguard; the attempt timer provides one maximum across all client stages, regardless of progress. A local abort does not establish that the host forwards cancellation to the server. Client actions get no bound, because they act on the client-held resource, a released resource makes them reject, and retirement drops the answer.

On host teardown the action view's controller retires the attempt and enters a retired state separate from `disposed`, in which the server action and the client actions do nothing and no late callback presents or restarts the continuation. A retired attempt must not stop, suspend or alter a newer attempt's continuation; the retirement that already released the client-held resource is what ends the old one. The read view's controller registers `onTeardown`, marks itself disposed, retires its reads and drops its private state. Neither calls the bridge's `dispose()` at teardown, because the host closes the connection after answering.

### One selection, a late server action and teardown

1. A user opens the action view and the host sends an opener for item A under label L1. The view pins L1 and shows `ready`.
2. The user activates the server action. The view starts an attempt, shows `pending` and arms its bound. The listener accepts the request, starts the request lifetime, authenticates and builds the per-request server with the lifetime's signal. The handler races its authorization check against that signal, and the lookup does not answer.
3. The user selects item B and the host sends a new opener under L1. The view retires the attempt for A and shows `ready` for B. The server is not told, and its request for A is still waiting.
4. The deadline expires. Nothing is committed and the connection is open, so the gate records the expiry, the handler stops waiting and returns the existing fixed unavailable failure, and the SDK transport writes it. No capability is issued. The listener clears the timer, removes its listeners and closes the transport and server.
5. The lookup answers later, permitted or denied. The answer is ignored and starts no further stage. If the response reaches the view, the view finds a newer generation and drops it before any resource request.
6. The user activates the server action for B, a new attempt, and the host's forwarding stalls. If the attempt bound expires first, the view retires the attempt and shows `unavailable` for B with the action available; if the SDK call timeout rejects first, the existing failure path settles the attempt and clears its timer. Progress cannot extend the whole-attempt maximum. A later activation starts a new server action with a new key and reuses no saved authorization.
7. The user activates the server action again and, while it is pending, the host asks the view to tear down. The controller retires the attempt and stops the timer. Nothing is presented from then on, a late `start` cannot restart the continuation, and the later `dispose()` retires again harmlessly and closes the connection once. The server's request still ends by completion or its own deadline.

The read view follows the same shape: if the host tears the view down while a filtered read is in flight, nothing is presented when that read's answer arrives or its timer fires, `retry()` and `select()` do nothing, and the later `dispose()` closes the connection once.

### Recovery where upstream gives no correlation

The read view keeps its existing recovery: unsolicited results are accepted before any loss, and after a loss only a correlated read recovers the view. The action view has no equivalent, because an opener has no request id and the inspected source defines no safe read that returns the opened item. The host's supported initial bootstrap stays as it is, and this proposal does not invent a correlation key, require one from the host or add a read on every mount.

The proposed policy for the action view is conservative. Once the view has presented `session-changed`, from an opener or from a grant, it treats the loss as final for that view instance: no selected item on either path, every later opener ignored whichever label it carries, and the server action unavailable. Recovery is a new view whose opening result pins a fresh label, or a reload. This keeps today's rejection of an opener under a new label and removes the revival through the old label. The cost is that a user whose host reuses one view for a later tool call stays on `session-changed` until reload, and the sources do not say which the host does. This policy needs human design approval.

One limit has no proposed repair. While the label stays the same, the view takes the last opener delivered, so a delayed copy of an earlier same-label opener can replace a later selection, and without a request id the view cannot detect it. Because the view sends the server action for whichever item it shows as selected, a stale selection can change which item a later explicit activation asks for. The server still authorizes that request on its own and the view refuses a grant naming another item or label, so this is not an authorization bypass. A host-supplied correlation key or a read that returns the opened item would remove the limit; these are examples a future design might evaluate, not the only possible repairs, and neither has been tried in a real host.

## Responsibilities and interfaces

| Owner | Holds | Proposed change |
| --- | --- | --- |
| Listener | Deadline values, request lifetime, terminal gate, its own answers (413, authentication refusals, resource-route answers) | Create the lifetime at acceptance; race verifier and body waits; add the body-timeout answer |
| Tool handlers and resource service | Fixed failure sentences; per-request server factory; capability issue and ordered acquisition checks | Receive the signal; race the authorization and storage waits; start no later stage after the request ended |
| Application callbacks | Verifier, read, authorization lookup, storage read | Lookup and reads accept the signal; the verifier does not |
| Read view controller (the example's subscriptions controller) | Pin, rows, selection, read generation, read timer | Register `onTeardown`; release reads and private state |
| Action view controller (the example's playback controller) | Pin, selection, generation, abort controller, client-held resource, pending timer | Retire on teardown; make label loss final; add the pending bound; keep a retired attempt from touching a newer one |
| Bridge and public content view | Connection delivery and closing; per-view image consent and obsolete description callbacks | Preserve existing revocation on result replacement and terminal consent retirement on teardown/disposal; no new lifetime mechanism |
| Host | Notification delivery and server action proxying | None; cancellation forwarding and other host behavior remain to be observed |
| Reusable connector (CORE3) | Reusable callback cancellation and deadline contract; progress; delayed JSON and SSE completion | None here; neither implemented nor reshaped |

The application owns the deadline values and the answers written on expiry. STATE2 ([#13](https://github.com/MachineWisdomAI/saga-a2ui/issues/13)) keeps its own obligation to bound and cancel the waits of this application's listener, handlers and resource service, and neither it nor the connector defers its semantics to the other. Authentication stays in the application, outside the connector, and still runs on every protected request, now inside the deadline; a verifier result that arrives after the request ended is dropped before any identity snapshot is made.

The design reuses existing interfaces: the SDK's `ctx.mcpReq.signal`, `readWithinBound` with `readBoundMs`, the per-request server factory, the 413 answer followed by `req.destroy()`, and the 503 answer with the fixed failure sentences. New ones are a request lifetime passed to the server factories the way `readBoundMs` is today; a finite deadline setting for the protected endpoints and another for the resource route; an abort signal on the authorization lookup, storage read, read and resource acquisition; the request-timeout answer; and, in the action view controller, a retired state and an optional pending-bound dependency with an application default. The callbacks are internal and unreleased, so they change directly. The verifier takes only the token string, so the listener can stop waiting for it but cannot stop its work.

### Rationale and tradeoffs

One deadline for the whole request is the smallest design that answers how long a caller can wait, because per-stage budgets would have to be summed to answer it. The tradeoff is that a slow verifier uses time the handler could have used. The read keeps its tighter `readBoundMs` inside the request deadline. Racing each wait is the guarantee; passing the signal to a callback only asks for cooperative cleanup, because a callback that ignores it still cannot hold the request open. Where the SDK's own `ctx.mcpReq.signal` can carry the deadline and a cancellation the pinned SDK delivers, handlers should rely on it rather than a parallel facility.

Distinguishing server actions from client actions is what lets the view's lifetime stay small. Only the server action and its continuation need a bound, a generation and a signal, because only they wait on something outside the view. A client action is a local function on a resource the current attempt owns, so retirement, which releases that resource, is already its complete lifecycle: a late or stale client action rejects or is dropped, and it needs no timer of its own. The attempt bound is deliberately wider than the server deadline, because the server cannot see the host's forwarding or the continuation, and the two bounds never depend on each other.

The action view controller's retired state is separate from `disposed` because its `dispose()` returns early when `disposed` is set, so reusing that flag would skip the close; the read view controller's `dispose()` has no such early return. The generation checks stay at their existing points, with no new check after every `await`. When an attempt is retired during proof signing, the resource request that follows receives an aborted signal and is expected to reject without a network request, which a planned check confirms. MCP cancellation is optional, and because the listener builds a fresh server and transport per POST, a `notifications/cancelled` posted separately is not guaranteed to reach the handler it names. The proposal adds no registry or session state to change that; the deadline is the server's own maximum, not a client cancellation.

## Failure and recovery

Cancellation here is cooperative. The proposal bounds the waiting, guards each stage the application owns so it does not start, and asks callbacks to stop. JavaScript cannot preempt running code, a callback may ignore the signal and keep working, and a synchronous callback that blocks the event loop prevents the deadline timer from firing until it returns. In the view, a retired attempt, an expired bound or a host teardown leaves the server free to finish its own work, and bytes already buffered or effects already made are not recalled. Whether the page stays visible after teardown is host behavior.

| Trigger | What the caller or user sees | Cleanup and recovery | Residual limit |
| --- | --- | --- | --- |
| Server deadline expires before commit, or the caller disconnects | Expiry: the stage's existing safe failure. Disconnect: nothing is written | Request stops waiting; timer and listeners removed; transport and server closed; recovery is a fresh request | A callback that ignores the signal still runs; its result is ignored |
| Deadline expires after commit, on any path that commits before its work completes | A truncated or ended response, no new status | Response ended or closed | Written or buffered bytes stay. The current JSON path normally commits near completion; the pinned SDK's behavior is to be verified |
| Result and deadline arrive together, or a result arrives late | At most one response | First to reach the gate decides; a close after the response finished is not a cancellation (`res.writableFinished` already distinguishes it on the 413 path); a late result starts no storage read, capability or second response | See the residues below |
| The label differs from the pin, in an opener or a grant | Today: `session-changed`, with the selection cleared on the opener path and kept on the grant path. Proposed: `session-changed` with no selection on both | Today both keep the pin, so a later old-label opener returns the view to `ready`. Proposed: later openers are ignored; recovery is a new view or reload | A host that reuses the view leaves the user on `session-changed` until reload |
| Same-label delayed opener (no repair) | The delayed item replaces the later one; a later server action asks for it | The server authorizes that request; the view refuses a mismatched grant | Stale selection; no request id to detect it |

Three server-side residues remain. A capability already issued is not retracted; if the connection closes between issue and the response write, the capability, which is bound to the view's key, goes unused and expires on its own. A proof identifier recorded before the authorization lookup is not un-recorded, so that proof is spent. And a late `denied` answer from a lookup that was in flight when the request ended does not delete the grant. The grant stays until its time limit, but every later acquisition asks the lookup again, so a revoked authorization still refuses new bytes. A denial that arrives before the terminal outcome still deletes the grant, as today.

## Verification outcomes

The lifetime changes below are proposed, not implemented or verified. Existing regression checks against the merged SDK and content code establish only preserved behavior, not these proposed outcomes. Server checks would use the real listener, handlers and resource service with fake verifier, backend, store and clock, and show JSON-path behavior only. Controller checks would use a fake `App`, a fake client-held resource (the example's player) and fake timers, with teardown invoked through `app.onteardown`. They assert what a user could observe, not what a controller still holds, and none asserts that the server stopped. "No resource request" means no network request; the proof-signing path may still call `fetch` with an already aborted signal. The view state names below (`pending`, `playing`, `ready`, `unavailable`, `session-changed`, `ended`) are the example's observable states; an adopter's view substitutes its own.

| --- | --- | --- |
| The verifier never settles; or headers arrive and the body stalls | 500 `server_error`, not 401, with no body read or server built; or a request-timeout answer (status proposed) and a closed connection. No tool runs, and a late valid identity is dropped | Listener, fake verifier and clock, raw socket client |

| A request completes before its deadline; a result and the deadline in the same tick; a result after the response closed; a caller disconnect; a separately posted `notifications/cancelled` | Today's response, one write, one terminal outcome, no pending timer, no escaping error; expiry writes one answer and a disconnect none. The disconnect and cancellation cases record what the pinned runtime and SDK actually do | Existing tests with fake timers; listener with the pinned SDK; raw socket client, two clients |
| Read view: host teardown with a read in flight, then rows, rejection or the bound; then `retry()`, `select()` and `dispose()` | No `show` and no `callServerTool` after teardown; the connection closes once. | Action view: host teardown with an attempt pending, then the late server-action response, bytes and `start`; then the server action, each client action, an end event and `dispose()`; or retirement during proof signing | No `show`, no network resource request and no `prepare`; no new `start` and no client action reaching the resource, no late presentation or revival of the continuation, and no interference with a newer attempt (idempotent cleanup by a later `dispose()` remains permitted, including a repeated `stop`); the resource request's signal is aborted; `ended` is not presented; the connection closes once. For proof signing, no network request is made whether or not `fetch` is invoked with the aborted signal | Action view controller |
| Action view: a late response for A after a same-label opener for B; or A's `start` settling after B's continuation is running | B is `ready` and the next server action names B; B's continuation keeps running and nothing from A is presented, restarted or stopped | Action view controller |

### Required actual-host and integrated acceptance

Controller and listener checks do not close the following. They need the real `App` and `AppBridge`, a built browser and the real listener, and runs in the named hosts ChatGPT web and Claude web. They are owned separately from this proposal and are separate from final signoff and from SSE qualification.

- The host's sequence at teardown: whether the page is removed, whether an in-flight proxied call settles or rejects at close, whether a `toolresult` can arrive after teardown, and whether closing or replacing a view closes the connection of an in-flight request.
- Whether the host creates a new view for a later tool call or reuses the existing one; whether its forwarding of a server action can hang while the server is healthy; what it does on the unavailable failure and the request-timeout answer; and whether it sends `notifications/cancelled`.
- Two views open at once, where retiring or tearing down one leaves the other unchanged; reversed selections in a built page, where A's answers or A's `start` settle after B's continuation has begun; and pending, retry and recovery controls that stay reachable and announced to assistive technology at narrow widths, at browser zoom and with long item titles.

## Implementation sequence

STATE1 ([#12](https://github.com/MachineWisdomAI/saga-a2ui/issues/12)) is recorded as depending on BROWSE2 ([#9](https://github.com/MachineWisdomAI/saga-a2ui/issues/9)) and PLAY1 ([#10](https://github.com/MachineWisdomAI/saga-a2ui/issues/10)), and STATE2 ([#13](https://github.com/MachineWisdomAI/saga-a2ui/issues/13)) as depending on STATE1 and PLAY2 ([#11](https://github.com/MachineWisdomAI/saga-a2ui/issues/11)). Whether the slices below become one ticket or several is a breakdown decision.

STATE1 takes the view-side cleanup: teardown release in the read view controller; retirement of the action view controller on teardown, with its separate retired state and the rule that a retired attempt cannot affect a newer one; and final label loss for both the opener and grant paths. Teardown retirement of the action view is the ordinary cleanup the bridge already documents, so it belongs here and not in an optional follow-up. Each slice lands with its controller checks.

STATE2 takes the bounds. The attempt bound comes first, using the pinned `App.callServerTool` signal option and preserving its existing request timeout. Test both SDK-timeout-first and attempt-expiry-first outcomes, and progress that would otherwise keep the call alive. The server side follows: the listener lifetime with its raced verifier and body waits and the body-timeout answer; the lifetime and signal passed to the tool handlers and resource acquisition, so no later stage starts after the request ended; and the in-process evidence runs. Neither item closes the actual-host acceptance above. The reusable connector, packaging and adapters, and the actual-host runs stay with their current owners.

## Open decisions

Design decisions for the approver:

- **Recovery after label loss in the action view.** The recommendation is to make loss final for the view instance, with recovery by a new view or reload. One alternative drops the pin and accepts the next opener, which accepts a delayed copy and restores the behavior this proposal removes. Another is a correlated read that returns the opened item, a new interface the inspected source does not have. The approver decides whether a stuck reused view is acceptable, informed by host observation of view reuse.
- **Deadline values.** The protected-endpoint deadline, the resource-route deadline and the attempt bound are not chosen. The application owner proposes them and the approver confirms them; the inputs are measured verifier, authorization, storage and host-forwarding latencies that the inspected material does not provide.
- **Answers on expiry.** Should the attempt's expiry end in the existing `unavailable` state? Should a verifier timeout stay indistinguishable from a verifier fault (500) or get its own 5xx status, avoiding 401 either way? Is 408 with a new error name right for the body timeout, with the connection closed afterward as after the 413?
- **Slow reader after completion.** Nothing here bounds draining of a response after the application finishes. Is that acceptable on the JSON route, with any streaming policy settled through CORE3?

Missing verification evidence (observations needed before relying on an assumption, not choices for the approver):

- How the pinned SDK transport writes its JSON response and whether it tolerates a result returned after the response closed, which decides whether the handler's return path through the gate is safe.
- Whether `ctx.mcpReq.signal` aborts when the pinned SDK closes the transport, and what a separately posted `notifications/cancelled` does there. The design does not depend on either, since the listener supplies its own signal.
- Whether the pinned Node runtime reports an early client disconnect to the body reader. Default HTTP server header and request timeouts, which the listener neither sets nor relies on, are connection-level backstops rather than an application deadline, and their values are not established.
- Whether the real client-held resource can settle a retired `start` after a newer attempt has begun, and the host behaviors listed under required acceptance.
