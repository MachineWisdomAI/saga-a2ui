## Problem and current behavior

A user who performs an action through an assistant host touches two programs that each decide, separately, when a piece of work stops mattering. The embedded view, a page that talks to the host through the MCP Apps bridge, decides when it stops caring about a question: the user selects another item, the sign-in label changes, a step takes too long, the control is replaced, or the host asks the view to tear down. The application's HTTP listener decides how long it waits on its own dependencies (credential verification, the authorization lookup, protected storage) before it answers. This document asks whether each side stops acting at the moment it decides to, for the two views, the two protected tool endpoints and the protected resource route of [authorized playback](authorized_playback.blueprint.md).

The question is general. Any action with a protected operation, a local effect, or a resource that outlives the step that obtained it has the same lifetimes, and the action binding module gives them one vocabulary. Playback is the example application's most demanding case and is used to ground the inspected source, but it does not define the contract. A non-playback flow, archiving a note, is followed through the same lifetimes below.

The proposal replaces the rejected [account and session isolation proposal](https://github.com/MachineWisdomAI/saga-a2ui/blob/427257e207b4bb8dbcec8dbf38ea466a98209024/blueprints/features/account_session_isolation.blueprint.md) with a narrower question about ordinary lifecycle correctness, and it preserves the safeguards the code already has: authentication on every protected request, the immutable per-request identity, opaque labels used only for freshness, safe fault distinctions, the read bound and the resource acquisition checks. It adds no live account switching, retained-state expiry, focus or resume revalidation, authentication for the public route, lifecycle framework, action registry or cross-request registry.

Current behavior was first inspected at `19fb26c`, reconciled against `6d3916d` for the MCP SDK migration and Standard/Strict description rendering, and refreshed on 2026-10-17 against main [`c3eecaad89fcefc540ee7816a8b41731cb65e9d0`](https://github.com/MachineWisdomAI/saga-a2ui/tree/c3eecaad89fcefc540ee7816a8b41731cb65e9d0). CORE1 landed the private, unreleased `@saga-a2ui/mcp` package at `6c268cc924886d4f7dfeb1668d83d0e17324f00b`; the bridge and bounded operation helper now live there, while the protected playback operation and resource service remain application-owned. VIEW1 added private, unreleased `@saga-a2ui/core` and `@saga-a2ui/lit` packages at `c3eecaad89fcefc540ee7816a8b41731cb65e9d0`: the protocol/session and Lit surface lifecycle moved there, and the public answer now renders through its own catalog. The protected read and playback controllers remain application-owned, and this preparation slice adds none of the lifetime changes proposed here. Merging PR #73 added the approved module and no lifetime implementation. The pinned recipe is MCP Apps 2.0.3 with client/core/server 2.3.1 and the Node transport 2.1.1.

Each gap below is a source-inspection candidate, not a reproduced fault, and none is shown to expose another user's data. Nothing in this document was run: reading source is not running it. Existing regression checks do not establish the proposed fixes or actual-host acceptance, and repair of any candidate begins with a reproduction.

### Terms

This document uses the shared [action vocabulary](../README.md#action-vocabulary), which follows the [action binding module](../modules/action_binding.blueprint.md). The module's [lifetimes table](../modules/action_binding.blueprint.md#lifetimes-and-owners) is the single definition of the following terms, which are used here without being restated.

- *Definition*: the reusable builder product (parameter extraction, prerequisites, handler, hooks, limits, busy policy). It holds no pending flag, timer or resource.
- *Rendered component instance* (or *instance*): one component created and managed by a renderer, accessed directly or through its renderer-owned handle. A template can create many instances; each instance is distinct from the data item it currently displays.
- *Binding*: one definition attached to one event of one instance, with its own observable state.
- *Semantic subject*: the application item the instance shows now, when the application supplies a `subject` reader.
- *Invocation*: one activation of a binding that was not ignored, from the user's event through prerequisites, handler, required hooks and cleanup.
- *Acquired resource*: what an invocation obtained and the application must release, such as a capability a server action issued or a player holding decoded media. Its ownership ends only through release or an explicit transfer to a longer-lived owner. A transfer changes who owns the resource and keeps it alive; a release ends the owned acquisition.
- *Server request*: the request a server action's handler sends. The function that serves it lives on the server and is never referenced from the browser.
- *Discovery* (`watchById`): a setup-time subscription that delivers handles so setup code can bind to them. It is never consulted to route an activation, which reaches its callable through the instance's own event path.

Two kinds of action matter in the examples. A **local action** has a handler that runs in the view. The handler may be synchronous or asynchronous, and it may do asynchronous work of its own, such as the media fetch in the module's local play sketch. It does not receive the runtime's transport-aware `call`. A **server action** has the same shape, and its handler additionally receives `call`, through which it initiates a server request with the invocation's signal and the time left in the work deadline. In both kinds the runtime runs the prerequisites, which may be synchronous or asynchronous, before the handler. The module does not equate local and server actions with A2UI's wire forms, and neither does this document.

In the example application, Play is the action whose handler issues a protected request and then performs client work: it acquires the bytes with the capability the result carried and starts a player. The player is an acquired resource, and Pause and Resume are local actions on it. Archive is a server action in the non-playback flow below. The **read view** (the subscriptions view) shows rows for the signed-in account and is started by the host's tool input, not by an event on a rendered instance. The **action view** (the playback view) offers Play, Pause and Resume on the selected item. The design is written for any view with this shape, and the example's controls are named only where inspected source is described or a mapping is proposed.

Four terms from this feature's pre-module vocabulary keep their meaning because they name application behavior and not the module's concepts. The **sign-in label** is the opaque `viewSession` value carried in tool results. It tells a view whether the data on screen still comes from the sign-in the view started with, and it never grants access, because the server authorizes every call from the verified request. To **pin** the label is to remember the first one a view accepts and compare later results against it. An **opener** is the `toolresult` notification that tells the action view which item is selected, and a **correlated response** is the value returned to a server request the view itself makes. Notifications carry no request id, so an opener can be a delayed copy of an earlier one.

On the server, a request is **committed** once its status line and headers are written and **finished** once the application has handed its final result or error to the transport. The **capability** is the grant a server action issues for the protected resource route, and the **proof** is the signed statement a recipient presents with each acquisition.

The pre-module vocabulary's other terms map onto the module's as follows.

| Pre-module term | General term | What changes in meaning |
| --- | --- | --- |
| Server action | Server action | A definition, bound to an instance. It is no longer a bare call |
| Client action | Local action | Sync or async. For asynchronous work a `deadlineMs` is recommended, not required, because without one only cancellation, replacement or disposal ends a handler that never settles |
| Attempt | Invocation, plus any resource it hands off | An invocation ends at settlement. A started player does not |
| Client continuation | The handler's steps after `call` returns, and the owner's work after a transfer | Handler steps run under the work deadline. The owner's work does not |
| Client-held resource | Acquired resource, owned by the application's resource owner | Held by a token, not by a shared whole-player |
| Resource request | A second server request with its own lifetime | A direct HTTP request to the application's resource route, not proxied by the host |
| Retire | Cancel or become obsolete (invocation), dispose (binding), end or release (resource lease), controller retired state (today's code) | One word covered four owners; the four are now separate |

### What exists today

**The server.** The listener builds a fresh MCP server and `NodeStreamableHTTPServerTransport` for each POST to a protected tool endpoint and answers in JSON; only the public answer endpoint can choose an event stream. The resource route is a plain HTTP handler. The MCP callback receives verified identity through `ctx.http.authInfo` and cancellation through `ctx.mcpReq.signal`. The subscriptions operation uses `registerProtectedOperation`: the application converts that identity into its immutable value, and the connector passes it and `OperationRequest.signal` to the application handler. Its `withinBound` helper in `packages/mcp/src/server/operation.ts` races the operation's `boundMs` (supplied from `readBoundMs`) and the request signal, ignoring a settlement that loses, so a retired read never becomes the tool result.

For a protected endpoint the listener first refuses a declared body that is too large, with 413, before reading any credential. It then authenticates the bearer credential with the application's verifier, checks transport headers, reads the body within a byte limit, classifies the body against the endpoint's tool list, attaches the verified context to the request and only then builds the server and transport for that one POST. The response-close handler that closes the transport and server is registered inside `serve`, so only after authentication and the body read.

A missing or malformed credential gives 401 with a challenge, and so does a verifier that throws the SDK's invalid-token error. Any other verifier failure gives 500 `server_error`, so a dependency fault never claims the credential is invalid. An expired credential gives 401, and a missing scope or a credential naming no account gives 403. The accepted authorization is copied and frozen, with the validated account and sign-in identity written last, because a verifier may reuse an object and the transport reads `req.auth` only after the body arrives.

The verifier call, the body read, the authorization lookup in the playback handler, the entitlement lookup and the storage read in the media service have no bound of their own. The subscriptions operation is the only protected wait with one. The playback tools are registered directly with `registerAppTool`: they take no request signal and have no bound.

In the playback handler a verified-identity check, a recipient-key check and field validation come before any protected work. A lookup that returns anything other than `entitled`, or an unknown episode, gives the fixed denied sentence. A throw from the lookup, or from any later step except a contract fault, gives the fixed unavailable sentence, and a contract fault gives the fixed invalid-result sentence. The capability is issued synchronously after the last awaited step, so nothing in the handler stops it from being issued after a request has been abandoned.

The resource route has no person-level authentication. The capability and the recipient's proof decide each acquisition, and the service checks them in a fixed order, stopping at the first failure with a refusal that names no check: the capability is known and not expired on the service's clock, the episode scope, the proof's signature, type, age, method, target URL, capability binding and recipient-key thumbprint, a proof identifier not already used, and then the current entitlement lookup. Only after all pass does it read storage and interpret the `Range` header. The proof identifier is recorded before the entitlement lookup. A denial from the lookup deletes the grant, and a lookup that throws never does. The listener maps a throw from the lookup or storage to 503 `unavailable`, a refusal to 403 `forbidden`, and an unsatisfiable range to 416 for a caller who passed every check. The URL the proof must name is built from the listener's own origin, never from the `Host` header. The answers carry `private, no-store` and a `Vary` list, and the route allows any origin to read the response because no ambient credential authorizes it. That is not an origin allowlist, and nothing in this proposal adds or describes one.

The capability expires on the media service's clock (the inspected default is 60 seconds from issue, adjustable by `capabilityTtlSeconds`), and nothing about the request that issued it extends or shortens it. A proof is accepted only if it is recent and unused (the inspected maximum age is 60 seconds with a 5-second clock tolerance), and each acquisition needs a fresh one. The immutable verified identity is a frozen copy of the accepted request's authorization, made for exactly one request and never read from tool arguments.

On the resource route a successful answer calls `writeHead(...).end(bytes)` in one step, so commit and finish coincide from the application's side. That is the application's call, not proof that the response has drained to a slow reader. On a protected tool endpoint the source does not show when the pinned SDK transport writes its JSON response, so that remains unobserved.

**The bridge.** The shared bridge, `connectToolResultView` in [`packages/mcp/src/view/index.ts`](https://github.com/MachineWisdomAI/saga-a2ui/blob/c3eecaad89fcefc540ee7816a8b41731cb65e9d0/packages/mcp/src/view/index.ts), keeps two flags with different meanings. `disposed` means delivery has stopped. `closed` means the transport close has been requested. On host teardown it calls the view's optional `onTeardown` once if delivery has not already stopped, then releases its listeners and sets `disposed`, and it answers the host without closing the connection, because the host closes it after the answer. The connection's `dispose()` closes once, even after teardown, and also runs when `connect` fails. After teardown, therefore, no further `toolresult` or `toolinput` reaches a view, but nothing stops the view's own controls, timers or player callbacks.

**The read view.** The subscriptions controller is started by the host's `toolinput`, not by a user event on a rendered instance. It accepts the host's opening result as the answer to the call that created the view, which is a documented bootstrap assumption and not correlation. After a loss of the label, an unsolicited positive result is ignored and only a correlated response from a read started after the loss recovers the view. Each read has a never-reused generation and a timer set to `readBoundMs`, so a read past its bound is replaced by a retry state and its late answer is dropped.

**The action view.** The playback controller ([`playback-view.ts`](https://github.com/MachineWisdomAI/saga-a2ui/blob/c3eecaad89fcefc540ee7816a8b41731cb65e9d0/apps/lit-host/src/playback/playback-view.ts)) pins the label from the first opener. A press on Play first checks its guard: it does nothing when no item is selected, when a request is pending, when audio is playing, paused or resume-blocked, or when the view shows `session-changed`. Otherwise it retires anything earlier, calls the player's `prepare()` synchronously inside the user's event to unlock audio, presents `pending`, and starts one attempt. The attempt creates a recipient key, calls the play tool through the host with the key in the request metadata, validates the grant (it must name the selected item, the pinned label, an `http:` or `https:` URL, and the item's own path), acquires the bytes with the capability and a fresh proof, and starts the player. The grant check is a scheme, item and path check and is not an origin allowlist. Acquisition uses `credentials: 'omit'`, `cache: 'no-store'` and `redirect: 'error'`, so a redirect cannot carry the capability or proof to another destination. The controller checks its generation after key creation, after the server request, after acquisition and after `start`. Proof signing, the resource request and the body read have no check between them and rely on the abort signal and the check that follows. If audio ends before the player confirms the start, the end is remembered for that attempt and wins over the late `started` result.

Pause and Resume are called synchronously in the user's event, because the audio-context call is made before the player's first `await`. Their pending state is tracked by a counter in the controller, which a retirement or an end of audio clears.

The player's own waits are bounded. The Web Audio player gives the clock-advance check after a start or resume a fixed constant of 1,500 ms, and wraps a context suspend or resume in a call bounded by the same constant. Decoding the bytes has no bound of its own. These are player-level limits on single steps and say nothing about a maximum over the whole attempt.

**The content view.** The public content view keeps its own safeguards, which this feature does not touch: it revokes image consent before every delivered result, including repeats and errors, and retires consent permanently on host teardown and disposal. It pins no sign-in label and issues no server request. The description elements discard obsolete callbacks and revoke their grants on content change or disconnect. These POL1/POL2 safeguards stay with the content owner, and this proposal adds no second consent lifetime.

### Candidate gaps

Each of the following is a source-inspection candidate, not a reproduced fault, and each repair begins with a reproduction.

**On the server.**

1. **No whole-request bound.** A request can wait on the verifier, the body, the lookup or storage as long as the dependency takes. A server action abandoned during its authorization wait could still issue a capability, and an abandoned acquisition could still read protected storage.
2. **The close handler is registered late.** The listener learns of an early disconnect only after authentication and the body read. The body reader listens for `data`, `end` and `error`, and does not listen for `close`. Whether Node reports an early disconnect to it as an error, or leaves the promise unsettled, is not established. The 413 path already uses `res.writableFinished` to tell a finished response from a cancellation.
3. **A pre-aborted request may still start its handler.** In `execute`, the handler's promise is created before `withinBound` checks `signal.aborted`, so a request that is already aborted would still start its handler, whose result is then discarded. Whether the pinned SDK ever calls the callback with an already-aborted signal is unobserved. If this is confirmed, the owner (the connector with CORE3) settles whether the handler starts at all or only its result is discarded.
4. **No answer exists for a stalled body.** There is no status today for a body that never completes.

The public `/mcp` route was not inspected beyond its lack of limits. CORE1 also added a bounded public-answer operation and JSON/SSE preparation checks; that public path is outside this proposal's protected-request scope.

**In the views.** There are seven candidates.

1. **The read view registers no `onTeardown`.** Its `dispose()` sets `disposed` and retires reads, but teardown alone does neither. After teardown the armed read timer can fire and present the retry state, a late answer can present rows or sign-in-required, and `retry()` and `select()` can still run, because every guard tests `disposed`, which teardown does not set. Whether any of that is visible depends on whether the host removes the page and whether an in-flight proxied call settles at close.
2. **The action view can leave `session-changed` through the old label.** An opener under a different label clears the selection and presents `session-changed`. A grant under a different label presents `session-changed` but keeps the selection. Both keep the old pin, so a later opener under the old label returns the view to `ready` and Play becomes available again, while an opener under the new label is never accepted. The sequence needs a delayed copy of an old opener, grants nothing by itself because the server authorizes the next request, and whether any host produces such a copy is unobserved. This describes the baseline inspected before the 2026-10-19 decision; the decision removes the revival (see Status), and the baseline text above stays as historical context.
3. **Action-view teardown releases the player but does not retire the controller.** `onTeardown` is `retire`, which advances the generation, clears the pending Pause or Resume, aborts the request and stops the player, and sets no flag. Until the host closes the connection, a press on Play passes its guards from `ready`, calls `prepare()`, presents `pending`, and calls the host through a torn-down `App`. Pause and Resume can reach a released player. An `ended` presentation after teardown is possible for the `AudioPlayer` interface. In the inspected Web Audio player, `release()` sets the source's `onended` to null, so it is not obviously reachable with this player. Other `AudioPlayer` implementations are unexamined, and the real ordering is unverified.
4. **A late `start` can reach a newer attempt.** When `start` settles after its attempt was retired, the controller calls `stop()`, and `stop()` is the whole-player operation. The player's own protections make this unlikely in the usual ordering: `prepare()` and `stop()` both release the context, a pending start rejects when its context is no longer current, and decoded audio is checked against context identity. Whether a retired `start` can still resolve after a newer attempt has begun is unobserved, and the controller does not guarantee it.
5. **A pending attempt has no controller-owned bound over the whole attempt.** The controller waits on key creation, host forwarding, proof signing, the resource request, the body read and `start`. It passes no options to the pinned `App.callServerTool`, which accepts a signal and timeout options and has a 60-second default timeout that `App` resets on progress. A silent stalled call therefore rejects through the existing failure path, and progress can extend it. The player's 1,500 ms limits cover single steps only.
6. **Host-call rejections are presented as a sign-in problem.** The playback controller treats any rejection of `callServerTool` as the host refusing the call, with a comment attributing it to the listener's 401 or 403, and presents `sign-in-required`. The read view does the same for its host read: a rejection clears private state and shows sign-in-required. The module states that the pinned `callServerTool` throws for timeouts, a lost connection and a host rejection alike, so a stalled or aborted call would be shown as a sign-in problem. Whether a named host rejects with an error that tells a timeout, an abort and a refusal apart is unobserved. In the read view the controller's own timer produces the retry state for an unanswered read, so the misclassification concerns a rejection that arrives before it. Neither the read bound's value nor the order in which the two would fire was in the inspected material.
7. **A malformed opener leaves the old selection actionable (additional source observation, requires reproduction).** When an opener is an error or fails its schema, the controller retires and presents `unavailable` for the previous selection without clearing it, so the Play guard accepts a later press. It is recorded as a baseline for verification and adds no approval gate and no new fix to this feature.

## Proposed behavior

Everything in this section is proposed. It uses the module's contract as written, adds no exported name and gives no deadline value. It gives the server and the view each a small, locally owned lifetime and keeps them independent: ending a client invocation never claims to stop the server, and a server deadline never depends on the view noticing.

### One lifetime per owner

The module's [lifetimes table](../modules/action_binding.blueprint.md#lifetimes-and-owners) defines the lifetimes and who decides each ending. For the Play control the mapping is short.

| Lifetime | Play control | Ends when | Does not imply |
| --- | --- | --- | --- |
| Definition | The play definition | Never | Anything about a binding |
| Instance | The rendered Play control | The renderer destroys or recreates it | Cancellation, unless the adapter disposes its bindings |
| Binding | The play binding on that control | `dispose()`, or the adapter retires the instance, surface or session | That a request already sent has ended |
| Semantic subject | The selected item | `subject()` returns a different value | That the binding is removed. Only an undecided invocation is canceled |
| Invocation | One Play, from the press to settlement | Settlement. Cancellation or the work deadline fixes the outcome and ends the work wait, and the invocation then still runs bounded outcome hooks, releases and finalization | That the server stopped, or that a retained resource ended |
| Acquired resource | The player lease and the capability | Release, expiry, or the media ending. A transfer changes the owner and does not end the resource | That the invocation that obtained it is still running |
| Server request | The play call, and each resource acquisition | The server's own completion, deadline or disconnect | That the view noticed |

The host-triggered read of the subscriptions view is a controller operation, not a row of this table. It is not a module invocation, and the view has no binding's semantic-subject reader. The controller keeps its generation and its timer, and the server request the read sends keeps the independent server lifetime in the last row.

Two points follow and are easy to lose. First, a lease the invocation transferred to the application's owner outlives its invocation, so settlement of Play never means that playback stopped. Second, the server's request lifetime is separate from every client one: a canceled invocation, a disposed binding and a torn-down view each end the client's wait and make no claim about the server. Cancellation is cooperative. It does not recall a request already sent, and it does not undo a remote effect.

### What a view must decide, and what it must not

**Setup finds, activation routes.** An application locates instances at setup, by identifier through discovery or from the adapter's own setup, and binds a definition to each handle. A component identifier is a diagnostic and a discovery key, not an instance key, because a list can render one identifier once per item. Nothing at activation looks a callable up by name.

**`before` is for prerequisites.** A prerequisite is reusable work that may stop the handler: session validity, consent, a durable audit record. It is not spinner preparation. The view's pending presentation is a function of the binding's runtime state: `running` from admission, through the synchronous activation prefix, prerequisites, handler and the required success hook, and `settling` while the outcome hook, releases and `onFinally` (when configured) are active. It needs no separate pending flag of the controller's own and does not run a prerequisite to draw something.

**Gesture-sensitive synchronous preparation belongs to `atActivation`.** Where an API needs its call in the event's own call stack, as `prepare()` unlocking audio does, the action puts it in `atActivation`. The callback is synchronous by type and by rule, and a thenable result ends the invocation as `activation-error`. Work in `atActivation` and `input` cannot be preempted by a timer, so a synchronous callback that blocks the event loop prevents every bound from firing until it returns. The module promises no portable activation property, and a prerequisite that awaits promises nothing about activation.

**Each callback checks its own `current()` after an await, immediately before a synchronous presentation write.** The signal asks work to stop. `scope.active` says whether the outcome has been decided. Only a callback's own `current()` says whether it may still change what the instance shows, and it is false for good once that callback finished, exceeded its budget, or was made obsolete. The handler also stops starting network work or taking a resource when its signal has aborted or `scope.active` is false. A presentation write that cannot be conditioned on `current()` must be idempotent or be done in a prerequisite.

**An obsolete presentation is not a different outcome.** The runtime decides an outcome once and keeps it. When an invocation becomes obsolete after the decision, for example because the selected item changed while `onFailure` awaits, the outcome stays as decided, the hook's signal aborts and its `current()` is false, and no message about the old item appears on the new one. Cleanup and releases still run, and `onFinally`, when configured, receives `obsolete: true`.

**Bounds.** The activation prefix is part of `running` but precedes the work timer. `deadlineMs` starts when the synchronous prefix has finished and covers every prerequisite and the handler. It expires as `failed(timeout)` in the stage that was running: in `prerequisites` the handler never started, and in `running` the effect is unknown. `hookMs` is a separate timer for each of the required success hook, the outcome hook, each release and `onFinally` when configured. These are the runtime's own timers. Neither is a whole-invocation maximum and neither is a universal third timer, and the clocks of the controller's read, the player's single steps, the resource service and the listener stay with their existing owners. Local and server actions may omit explicit limits: each setting resolves independently from a per-action override, then the owning SDK instance's application configuration, then 30,000 ms work or 5,000 ms per bounded hook/cleanup step. Explicit invalid values fail early. The work budget is shared by prerequisites and handler, cannot be extended by progress, and a longer override cannot extend a host, gateway or server deadline. Separate cleanup budgets mean the default profile is not a 35-second whole-invocation maximum.

**Result-stage-aware outcomes.** What a failure may say depends on how far the handler got, which the runtime reports through `stage` and `failure.kind`. A failure before the handler started says the handler's protected request was not sent, although a prerequisite may itself have contacted a session or audit service. A handler that returned shows that the handler returned. The typed result and the operation's contract then establish which effect completed, including local effects, and not that every server request succeeded. Any later failure is the client's required work. A throw, a timeout while running, or a cancellation before a result says only that the client stopped waiting, so the effect is unknown, the message must not invite a retry, and nothing retries automatically.

**Finalization, token-scoped cleanup and transfer.** Finalization always occurs, and `onFinally` runs only when configured. Every resource the invocation holds through its scope is released in reverse order, each within `hookMs`, and a late handler that acquires after the invocation ended has the resource released at once. A resource held through an invocation's scope token survives a successful start only by explicit transfer to the application's owner. The owner's `end(token)` affects only the acquisition it names, is idempotent, and is a no-op for a token the owner has since superseded. Stopping everything the owner holds is the owner's own teardown and never an invocation's operation.

### A non-playback flow: archiving a note

This follows the module's approved archive example through the lifetimes above; the full rules, declarations and renderer columns are in the module. A note list renders an attachable control once per note, so two notes give two instances. Lit and React report the shared component identifier for both, and Lynx gives the expanded clones distinct `componentId` values with a shared `sourceComponentId`. Setup binds the archive definition to each instance's own handle and supplies a subject reader that asks that same handle which note it shows now.

The user presses the control on note A. Admission checks that the event belongs to the current installation and that the binding is idle. The synchronous prefix copies A's identifier out of the event. The binding shows `running` from admission, which the application draws as a busy control, and the work deadline starts when the prefix finishes. A session prerequisite, a confirmation prerequisite and a durable audit prerequisite run in that order, each able to refuse, and each counts against the deadline. The handler then calls the server through `call`, which gives the transport the invocation's signal and the time left in the work deadline. The server's own handler, its authorization and its own limits run on the server and are not referenced from the view.

Three things can then happen, and each follows from a rule above and not from the example.

- **The row now shows note B while the confirmation is open.** At the next checkpoint or adapter wake-up the runtime finds the subject changed and decides `canceled(subject-changed)` at stage `prerequisites`. No archive request was sent. The binding stays attached. A press on B first revalidates the old invocation, then applies the busy policy. A mismatch nobody observes cancels nothing yet.
- **The server archives the note, and the required success hook that records it overruns `hookMs`.** The outcome is `failed(success-hook-timeout)` with the result attached, so the failure hook can say the note was archived and the client's required work failed. The old hook's own `current()` is false for good, although binding, instance, installation and subject are unchanged, and the failure hook has its own eligibility and may present. If the row meanwhile shows another note, the failure hook's signal aborts and it writes nothing, the outcome stays `failed`, and `onCanceled` does not run.
- **The control unmounts during the request.** The adapter disposes the binding, the runtime decides `canceled(disposed)` at stage `running`, and the application may say only that the archive status is unknown. The server may still finish and archive the note. Cancellation did not undo it.

At no point does the view assume the server stopped, and at no point does a retry happen automatically.

### The server request as its own lifetime

The approved module names the server request as a lifetime that sits outside the module. A server action's definition holds a function that sends a request, and the function that serves it lives on the server. An invocation that ends, whether it settles, is canceled, or fails by its own deadline, therefore says nothing about whether this request stopped. In the other direction, a server deadline does not decide the invocation's outcome. The invocation's `deadlineMs` over prerequisites and handler, the per-step `hookMs`, and any host timeout belong to the client contract. STATE2 also retains an application-owned requirement to bound whole-playback pending work; how it maps onto those two module bounds, or onto an application-owned maximum where stages remain split, is not yet decided (see playback below). No action is assumed to have a playback continuation, and the module defines no third shared timer. The server request has its own clock, its own owner and its own answers.

This section is about the ordinary request: one POST to a protected tool endpoint, or one GET to the protected resource route. Both are owned today by the application listener, the per-request tool handlers and the media service. The reusable callback, progress and delayed-completion contract for such requests belongs to the reusable connector, CORE3 ([#16](https://github.com/MachineWisdomAI/saga-a2ui/issues/16)), and nothing here defines that contract.

**One lifetime, created before authentication.** The listener creates a request lifetime when it accepts a request for a protected endpoint, or an acquisition on the resource route. It has one finite deadline, one abort signal, a watch on the response for an early close, and a one-shot terminal gate, built from `AbortSignal`, the response `close` event and timers. The gate is closure state held by whichever owner settles the request, like the race `withinBound` already uses. The deadline covers all asynchronous application work until the request is finished, so it includes the verifier wait and the body wait, and committing headers does not end it. The first of three events decides the terminal outcome: the work produces its final result or error, the deadline expires, or the caller closes the connection. A disconnect produces no response, following the MCP cancellation guidance that a receiver should stop processing and not respond. A deadline expiry on a usable channel produces exactly one answer. No path writes a second.

**This deadline is the server's own.** It is not derived from the invocation's `deadlineMs`, a per-step `hookMs`, the application-owned playback bound or the host's timeout, and no client outcome is read from it. The proposal does not create a whole-invocation timer, and it does not make the server wait for the client to notice anything. The deadline value is open.

**Before commit, the server still chooses the answer, and it reuses the answer it already gives a dependency fault.** An expired wait shows that a dependency was slow, not that the caller was refused.

| Where the wait expires | Answer |
| --- | --- |
| Verifier | 500 `server_error`, not 401, because 401 would claim the credential is invalid |
| Body, headers already received | A request-timeout status, then the request is destroyed as on the 413 path. The status and error name are open |
| Tool handler's authorization, storage or read wait | That tool's fixed unavailable failure, never the denied sentence |
| Resource route's lookup or storage wait | The existing 503 `unavailable` with the existing headers |

**After commit, the status cannot change and bytes cannot be retracted.** On expiry or disconnect the response is ended or closed with no second status, and the deadline keeps applying to the work that produces the rest of the response. The rule applies to any path that commits before its work completes. It matters most for a streamed response, which commits before the work ends, but today no protected path streams. On the inspected JSON path commit and finish are expected to nearly coincide, but the SDK's write behavior has to be confirmed before relying on that. The resource route's `writeHead(...).end(bytes)` is one call, and the physical draining of that response to a slow reader is a separate matter this proposal does not bound.

**No stage begins after the terminal outcome.** Once the gate has decided, a late result is dropped without effect. This applies to every stage the application owns: a late verifier result reaches neither `req.auth` nor a server build; no body is classified; no capability is issued; no storage read starts; and no second response is written. The application checks the gate before each later stage. It does not rely on the callback stopping.

**Racing is the guarantee. Passing a signal asks for cooperation.** The listener stops waiting for each step. A callback that is given the signal is asked to stop its own work, but one that ignores it still cannot hold the request open. The verifier takes only the token string, so the listener can stop waiting for it and cannot stop its work. The new application interfaces are a signal on the authorization lookup, the storage read and the acquisition.

**Each request has its own clock, and no clock is inherited.** The protected server action and each resource acquisition are separate requests with separate lifetimes. Each acquisition starts a new deadline that does not inherit what remains of the action's. The capability keeps its own expiry. The media service checks that expiry and the proof's age only when an acquisition begins, so it is the request deadline that ends a wait on the lookup or the storage read, not the capability. The protected acquisition deadline is therefore separate from the capability and proof lifetime, and neither stands in for the other.

**Cancellation is cooperative and local.** The proposal adds no registry, session state or shared table. The listener builds a fresh server and transport for each POST, so a `notifications/cancelled` posted as a separate request is not guaranteed to reach the handler it names. MCP cancellation is optional, and the deadline is the server's own maximum, not a client cancellation. Cancellation never undoes remote effects. It stops waiting and prevents later stages.

![Flowchart of the server request lifetime, independent of the client invocation. The client invocation optionally sends a request through call. **A server request, step by step.** The example is a protected server action whose authorization lookup stalls, followed by the acquisition it would have led to. The client side of this flow is the invocation described above and is only referred to here.

1. The listener accepts a POST to the protected endpoint. The request lifetime begins before authentication, and the verifier answers within the deadline. The authorization is frozen and the body is read and classified.
2. The handler waits on the authorization lookup. The caller retires its invocation, and in this example nothing forwards a cancellation to the server (whether a host forwards one is unknown). The request is still waiting.
3. The deadline expires. Nothing is committed and the connection is open, so the gate records the expiry. The handler stops waiting and returns the tool's fixed unavailable failure, and the SDK transport writes it. No capability is issued. The timer and listeners are removed and the transport and server are closed.
4. The lookup answers later, permitted or denied. The answer is ignored and starts no further stage, so no capability is issued and no grant changes.
5. Separately, if a capability had already been issued by an earlier request, it is not retracted. It expires on its own clock. An acquisition made with it is a new request with a new deadline, new checks and a fresh proof.

If the caller closes the connection at step 2 instead, the gate records a disconnect, the handler stops waiting, nothing is written and the same cleanup runs.

### Playback on the module: one proposed mapping

This subsection is this feature's mapping choice. The module settles neither the choice nor the evidence behind it. It leaves the placement of playback's stages open and records that, if the stages cannot fall inside one interval, the controller keeps a bound of its own.

**The stages.** Playback has these stages after the user's press: `prepare()` inside the event, creating a recipient key, the host call to the play tool, validating the grant, signing a proof, the resource request, reading the body, decoding and starting the player, and presenting `playing`.

**Option A, one invocation.** The activation prefix holds `input` (the selected item) and `atActivation`, which begins a lease in the player owner and takes it into the scope; the owner's `begin()` ends the previous lease's audio and prepares the player. Key creation and the host-capability check are prerequisites, so that a failure of either is a prerequisite-stage failure and the host call never starts. The handler calls `call` for the play tool, validates the grant with the existing scheme, item, path and label checks, signs the proof, acquires the bytes, starts the player through the owner with the lease, and, on `started`, transfers the lease to the owner with no `await` between the start and the transfer. A blocked start returns a gesture-needed result without a transfer, and the scope still releases the lease.

**Option B, split invocations.** The play invocation ends at the validated grant, and a later controller step, with a bound owned by the application, performs the acquisition and the start. Option A makes the host call and the resource request two server requests inside one invocation. Option B makes them separate invocations or controller steps, and that difference decides which stages one budget can cover. Several requests inside one invocation are distinct from controller work outside it, and a binding's lack of a public `invoke()` does not prohibit such controller work.

| | Option A: one invocation | Option B: split under an application bound |
| --- | --- | --- |
| Where the stages sit | Key creation in prerequisites, everything from the host call to the start in one handler | Key and host call in the first invocation. Acquisition and start outside it, in controller code |
| Bound over the stages | The work deadline covers key creation through start. The success hook is under `hookMs` | The first invocation has its own deadline. The second needs a controller-owned maximum, which is the timer the module declined to add to the runtime |
| What cancels the later stages | The same cancellation as the earlier ones: a new selection, disposal, replacement | The runtime no longer sees them after the first invocation settles, so application continuation code keeps generation checks and aborts for them |
| Busy policy | `ignore` or `replace` covers the whole sequence until settlement | The binding is `idle` while acquisition is pending. A second press is not ignored by the runtime |
| Pending presentation | A function of the binding's `running` phase | Two sources of truth: binding state, then a controller flag |
| Lease ownership | One scope owns it from `atActivation` to a transfer at start | The lease must transfer to the controller before the first invocation settles, so ownership passes while acquisition has not begun |
| What the approved module says | The play sketch puts the fetch and the start in one handler | Open decision 5 and the corrections by owner retain this path: if the stages stay split, the controller keeps its own bound and the runtime provides none. A binding has no public `invoke()`, so the continuation is application code and not a module feature |

**Status of the two mappings.** Both options are candidates the approved module leaves open (its [open decision](../modules/action_binding.blueprint.md#open-decisions) on how the playback whole-attempt bound maps onto the two bounds). Neither has been checked against the real controller, and the check that every stage falls inside the work interval has not been made.

**Recommendation: Option A.** It is supported by the module's own sketch and by the property that matters, a single place where a user's selection, a disposal or a replacement ends the whole sequence and releases the lease. Option B stays viable as the application-owned continuation fallback. Its costs are ownership and coverage: the lease must change owner before the first invocation settles, the binding reads `idle` while acquisition is pending so the runtime's busy policy does not cover the slowest stages, and the controller keeps the generation, abort and timer code for work the runtime has not taken over. This is this feature's mapping choice, not a design the module approves, and it is unverified. If the check of the stages shows that one cannot sit inside the work interval, the controller keeps its own bound and the shared runtime provides none.

**What each budget bounds under Option A.**

| Phase the user sees | Binding phase | Bounded by |
| --- | --- | --- |
| The press, `prepare()`, and the extraction of the selected item | `running`, the activation prefix, before the work timer starts | No timer. A timer cannot interrupt synchronous code, so only the callbacks finishing bounds it |
| Creating the key | `running`, stage `prerequisites`, after the prefix | The work deadline. A timeout here means the handler never started |
| The host call, proof signing, the resource request, the body read | `running`, stage `running` | The work deadline, and the runtime-built `call` timeout, which is the time left in it. A progress notification cannot extend the deadline |
| Decoding and starting the player | `running`, stage `running` | The work deadline. The player's own 1,500 ms limits on the clock check remain narrower safeguards on single steps |
| Presenting `playing` or `gesture-needed` | `running`, in the required success hook | `hookMs` |
| Presenting a failure, ending the lease, final reporting | `settling` | `hookMs` for the outcome hook, `hookMs` for each release and `hookMs` for `onFinally` |

The longest the invocation can run after the prefix is `deadlineMs + hookMs` for `running`, and `hookMs` times the number of owned tokens plus two for `settling`, while the event loop turns. The whole-playback-pending requirement kept under STATE2, that the view does not stay pending beyond a maximum that progress cannot extend, **remains an application requirement**. Both module bounds and any application playback maximum that is still required stay separate from the listener, read, resource and player-step clocks. This mapping is intended to meet the requirement, but it is not described as met until a check places every stage inside the work interval and the success hook inside `hookMs`. The stage coverage is a proposed mapping and not an implemented protection.

**Until the playback path migrates, the controller keeps a bound of its own.** The pre-migration correction is as follows. The controller arms a timer when the view shows `pending`, independent of the server deadline because it must also cover the host's forwarding and the client's later steps. Every way the attempt leaves `pending` clears the timer. A successful start clears it without retiring the attempt, because retiring would release the player that just started. A blocked start goes through the existing `clearWith`, which retires the attempt. The other outcomes (`unsupported`, `unavailable`, a denial, an error, audio that ends before its start is confirmed, and retirement by a new opener, a new press, label loss, disposal or teardown) clear it too. On expiry, if the attempt is still current and the view is still `pending`, the controller calls `clearWith` with `unavailable` for the selected item. That advances the generation, aborts the resource request and releases the player, and Play stays available. The controller's bound ends the pending wait and invalidates and releases the attempt independently of whether `start` ever settles. The player's `release()` rejects the wait on a clock advance only when a start cancellation has been installed, and `start` first awaits `decodeAudioData` before installing it, so release cannot be claimed to settle every pending start. A start that settles later finds a different generation and is obsolete. The timer ends the waiting. The generation checks only suppress the effects of obsolete results, so they do not shorten key creation or proof signing, which cannot be canceled. The controller supplies the attempt's signal through the pinned `App.callServerTool` options and aborts it on expiry or retirement, keeping the generation checks for late completions. The call's own request timeout remains a narrower safeguard, and the controller's timer provides one maximum across all client stages regardless of progress. A local abort does not establish that the host forwards cancellation to the server. If the stages stay split after migration, that bound remains application code. Its value is not chosen.

**Where Option A leaves open work.** Three points are unsettled and none is decided here.

- The module's `call(name, args)` shows a name and arguments only. The current play request carries the recipient key in request metadata, not in the arguments. Whether `call` can carry metadata, or whether the key moves into the arguments and changes the server's contract, is a decision for the module's implementation review and for the application owner. This document does not choose.
- The existing `AudioPlayer` has a whole-player `stop()`. The owner conditions require a wrapper that knows which lease is current, ends only that lease, rejects a `start` for a superseded lease, and makes `end(token)` idempotent for a lease that never started. Whether the real player's ordering allows that without changing the player is the module's open decision, and it is the same evidence the stale-`stop()` candidate waits on.
- Resume calls the audio context synchronously in the user's event because the browser can require a gesture. A local action whose gesture-sensitive start is inside an `await`-able handler needs either an owner operation that begins the context call synchronously in `atActivation` and returns a non-thenable value, or an adapter that guarantees the handler runs in the event's call stack, which the module does not promise. The mapping does not choose between them. Where the event-turn ordering of Resume falls is likewise open.

**Failure mapping under Option A.** The mapping below is also this feature's choice. The existing presentation states are reused, and introducing a new state is a separate approval.

| Condition | Stage and kind | Presentation | What the application may say |
| --- | --- | --- | --- |
| `prepare()` throws | `activation-error` | `unsupported` | Nothing protected was requested. `atActivation` may have had effects, such as an earlier lease ending |
| Host lacks server tools, or key creation fails | `prerequisites`, `refused` or `prerequisite-error` | `unsupported` | The protected play request was not sent |
| The host call rejects | `running`, `handler-error` | Not `sign-in-required` until a host is shown to distinguish a refusal. The nearest existing state is `unavailable` | Effect unknown. A capability may have been issued |
| The tool answers with an error | `running`, `handler-error` with the handler's typed cause | `denied`, `unsupported` or `unavailable`, by the existing text mapping | The typed error and the operation's contract establish what completed. At the pinned source the play handler issues the capability before it parses the projection and labels the view session ([`playback-server.ts` lines 97 to 123](https://github.com/MachineWisdomAI/saga-a2ui/blob/c3eecaad89fcefc540ee7816a8b41731cb65e9d0/apps/lit-host/src/playback/playback-server.ts#L97-L123)), so an arbitrary tool error does not show that nothing was issued. Precise early refusals before the issue step do. Messages stay fixed and safe |
| The grant fails validation | `running`, `handler-error` with a typed cause | `session-changed` if the label differs, otherwise `unavailable` | The malformed grant does not show whether a capability was issued. No resource request was made |
| The media service says no (403) | `running`, `handler-error` | `expired` | The body was not read |
| Another acquisition failure | `running`, `handler-error` | `media-failed` | |
| The bytes arrive and starting the player fails | `running`, `handler-error` if the handler throws | `media-failed`, a safe presentation distinct from a server denial | Acquiring the bytes succeeded, but the player did not start. No successful handler result exists to report, so no effect is attributed from a result |
| The browser withholds audio | `running`, returned without a transfer | `gesture-needed` | Nothing is playing. The scope releases the lease. A gesture-needed result is never reported as playing |
| The work deadline expires | `prerequisites` or `running`, `timeout` | `unavailable`, with the retry not invited when the handler started | The existing state is a proposal for approval, see the open decisions |
| The success hook fails after a transferred start | `running`, `success-hook-error` or `success-hook-timeout`, result `playing` | The audio keeps playing under the module's chosen policy. An application that prefers silence ends exactly that lease in the failure hook | The handler returned, and the typed result shows which effect completed. The client's required work failed |
| Cancellation (`replaced`, `subject-changed`, `disposed`) | By stage | None from a failure hook. `onCanceled` ends exactly the activation's lease | Effect unknown if the request was sent |

A short audio that ends before the start is confirmed presents `ended`, not `playing`. That is today's behavior and a sourced safeguard, so the owner's `start` result must be able to say it, as the module's sketch, which shows only `started` and `blocked`, does not. How the owner preserves this early `ended` is an open question.

**Pause and Resume.** They are local actions whose asynchronous work acts on the player's current lease, and today's controller guards them with a counter. Under the module they have a busy policy and the resolved work budget, optionally overridden for the application; the player's own 1,500 ms limits remain narrower single-step safeguards. Pause and Resume act only on the lease the owner currently holds, so a lease the owner has since superseded makes them no-ops. A control that stays disabled once playback has begun is application state and not a binding's busy policy, because the binding settles when Play does.

**What the label and selection do.** A new opener for item B, a loss of the label, host teardown and disposal each end the lease through the owner's own teardown, because the module never calls whole-owner `stop` from an invocation. A new opener also changes the subject, which cancels an undecided Play invocation at its next checkpoint, and the lease the owner ended makes a late `start` reject.

### The read view stays controller-owned

The read is started by the host's `toolinput`, not by an event on a rendered instance, so it is not an instance-bound action, and this feature does not make it one. The controller keeps its generation, its timer and its correlated-recovery rule. `retry` and `select` are user controls and could later adopt the module as a bound server action and a bound local action. That would be a separate decision with its own conflict to resolve: an invocation's result and the controller's read generation would both claim to settle the same state. No such change is proposed here. The one correction the read view needs from this feature is teardown: it registers `onTeardown`, marks itself disposed, retires its reads and drops its private state, and leaves the bridge's `dispose()` to close the connection later. If the host tears the view down while a filtered read is in flight, nothing is presented when that read's answer arrives or its timer fires, `retry()` and `select()` do nothing, and the later `dispose()` closes the connection once.

### Teardown, disposal and four things called dispose

Four different objects carry a word like disposal, and they must stay distinct.

1. **The bridge's `disposed` flag** means that delivery has stopped. Teardown sets it.
2. **The bridge connection's `dispose()`** closes the connection once and is idempotent. It is not called from teardown.
3. **`ActionBinding.dispose()`** ends one binding: it cancels an undecided invocation with cause `disposed`, detaches the callable, and ends notifications after one final `disposed` state. It does not release a lease the owner deliberately holds.
4. **Today's playback controller** has `retire`, which releases the player and sets no flag, and `disposed`, which makes its `dispose()` return before it reaches the bridge's. Reusing `disposed` for teardown would skip the later close. The read view controller's `dispose()` has no such early return.

On host teardown, the application's `onTeardown` disposes each binding, ends the owner's retained lease through the owner's own teardown, and, in controller code that has not migrated, enters a retired state that differs from `disposed`. A retired attempt must not stop, suspend or alter a newer attempt's lease. It does not call the bridge's `dispose()` and does not close the connection. The later `dispose()` closes it once. Setup-time discovery is not a binding's lifetime either: unsubscribing discovery leaves bindings installed. In the pre-migration controller, the generation checks stay at their existing points, with no new check after every `await`; migrated callbacks make their own `current()` check before a post-await write.

### What retires an instance depends on the renderer

A view does not assume that its instance ends the same way on every renderer, and this feature does not flatten the three into a DOM instance.

- **Lit.** The proposal maps inspected upstream lifecycle events (disconnect, a same-identifier type change, a data-path change, a list shrink, and surface or session end) to instance retirement. Under `a2ui-surface` the rendered element has no node, and handle and retirement would come from a binding-aware catalog element. The upstream events were read in source. No SAGA retirement adapter was inspected, and nothing has run in a browser.
- **React.** The instance is the committed lifetime of a boundary for one node, delimited by a layout effect's setup and cleanup. A discarded render opens no instance. The timing is inspected at the 0.14.0 commit, and whether the published 0.13.0 runtime behaves the same is unresolved.
- **Lynx.** The handle comes from setup inside a catalog component, and cleanup runs as an effect cleanup. Between the native node's removal and that cleanup, `current()` can still be true. The module does not claim to prevent a stale write inside that interval and does not promise that native retirement precedes the observed background cleanup. Its recommendation is a narrower support contract: a hook's presentation write goes to a target that tolerates a retired instance, which means keying presentation state by item and not by a handle to a rendered view. Measuring the interval on a device sizes the window and does not close it.

Host teardown is renderer-independent, because it arrives through the bridge. Which adapter disposes the bindings on it is the adapter's own responsibility.

### Recovery where the host gives no correlation

The read view keeps its existing recovery: unsolicited results are accepted before any loss, and after a loss only a correlated read recovers the view. The action view has no equivalent, because an opener has no request id and the inspected source defines no safe read that returns the opened item. The host's supported initial bootstrap stays as it is, and this proposal does not invent a correlation key, require one from the host or add a read on every mount.

For the action view the proposal was conservative and was a decision for the approver, who selected it on 2026-10-19. Once the view has presented `session-changed` from an opener or a grant, the loss is final for that view instance. It shows no selected item on either path, ignores every later opener whatever its label, and keeps Play unavailable. Recovery is a new view whose opening result pins a fresh label, or a reload. This keeps today's rejection of an opener under a new label and removes the revival through the old label. Under the module this means the application ends the lease, disposes the Play binding and, because the label is application meaning, owns that decision. The shared runtime only carries the refusal of a prerequisite. The cost is that a user whose host reuses one view for a later tool call stays on `session-changed` until reload, and the sources do not say which behavior any host has.

One limit has no proposed repair. While the label stays the same the view takes the last opener delivered, so a delayed copy of an earlier same-label opener can replace a later selection, and without a request id the view cannot detect it. The subject reader cannot help, because the stale opener is itself what sets the subject. A press then asks for whichever item the view shows, the server still authorizes that request on its own, and the view refuses a grant naming another item or label, so the limit is not an authorization bypass. A host-supplied correlation key or a read that returns the opened item would remove it, and these are examples a future design might evaluate, not the only possible repairs. Neither has been tried in a real host.

The application owns the deadline values and the answers written on expiry. STATE2 ([#13](https://github.com/MachineWisdomAI/saga-a2ui/issues/13)) keeps the obligation to bound and cancel the waits of this application's listener, handlers and resource service. Neither STATE2 nor the connector defers its semantics to the other. Authentication stays in the application, outside the connector, still runs on every protected request, and now runs inside the deadline; a verifier result that arrives after the request ended is dropped before any identity snapshot is made.

**The two kinds of server request.** The play call and each resource acquisition are separate server requests with separate lifetimes. The capability the play call issues lives by its own clock after that request finishes, and an acquisition starts its own deadline, which does not inherit what remains of the call's. The client's `deadlineMs` never stands in for either one, and an invocation's expiry or cancellation does not claim that the server stopped. A server request ends by its own completion, its own deadline, or the caller's disconnect.

**Interfaces that exist and interfaces that do not.** The action builder, runtime, attachment, owner wrapper and any adapter are proposed and unimplemented. The `AudioPlayer` seam, the controllers and the bridge exist as inspected, and the migration changes owned callers and tests together, with no shim, alias or parallel implementation. Only mechanisms the migration actually replaces are removed.

The server design reuses existing interfaces:

- `ctx.mcpReq.signal`, exposed as `OperationRequest.signal`;
- the operation bound supplied from `readBoundMs` and enforced by `withinBound`;
- the per-request server factory;
- the 413 answer followed by `req.destroy()`;
- the existing fixed failure sentences and the 503 answer.

The new interfaces are the request lifetime passed to the server factories the way `readBoundMs` is today, a finite deadline setting for the protected endpoints and another for the resource route, the signal on the lookup and storage read, and the request-timeout answer. The application callbacks and private connector exports are unreleased, so owned consumers change together without compatibility shims.

**Open interface choice: how a listener-owned signal reaches handlers.** At main the connector's `OperationRequest.signal` is only `ctx.mcpReq.signal`, and the playback handlers use no request signal at all. The proposal says both that the listener's lifetime signal reaches the handlers and that handlers should rely on the SDK's signal where it can carry the deadline. The inspected source does not show how a listener-owned signal would reach `OperationRequest.signal`. Passing it through the server factory, the way `readBoundMs` is passed, is one option. A change to the connector is another, and that would be CORE3's. No such mechanism exists today.

### Rationale and tradeoffs

One deadline for the whole request is the smallest design that answers how long a caller can wait, because per-stage budgets would have to be summed to answer it. The tradeoff is that a slow verifier uses time the handler could have used. The read keeps its tighter `readBoundMs` inside the request deadline. Racing each wait is the guarantee, and passing the signal to a callback only asks for cooperative cleanup, because a callback that ignores it still cannot hold the request open.

Keeping the lifetimes separate is what lets each stay small. The module's runtime owns one invocation's work and hook timers, the listener owns the server request's deadline, and the application's resource owner owns whatever outlives an invocation. None of the three depends on another noticing. The cost is that the application must name the owner of each resource explicitly and that no single timer answers how long a user may wait across all of them, which is why the playback requirement stays an application one until a check places its stages inside the work interval.

## Failure and recovery

Cancellation is cooperative. The proposal bounds the waiting, guards each stage the application owns so it does not start, and asks callbacks to stop. JavaScript cannot preempt running code, so a callback that ignores its signal keeps running after the runtime stopped waiting and may still write if it never checks `current()`, and a synchronous callback that blocks the event loop prevents any timer from firing until it returns. A canceled or expired invocation leaves the server free to finish. Bytes already buffered, capabilities already issued and effects already made are not recalled. Whether the page stays visible after teardown is host behavior.

The module's [error categories and safe presentation](../modules/action_binding.blueprint.md#error-categories-and-safe-presentation) preserve inspectable causes without automatically showing raw server details, distinguish authentication from permission denial only with supporting evidence, and retain unknown/internal fallback. Timeout and cancellation prove no rollback. A returned result establishing write success remains known success if a later hook fails; a write without an established result remains uncertain. Application presentation and HTTP policy remain separate.

HTTP 408 concerns an incomplete incoming request ([RFC 9110 §15.5.9](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.9)); 504 concerns a gateway's upstream wait ([§15.6.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.5)). A frontend timeout alone establishes neither. This distinction does not choose STATE2's incoming-body or server-request response mapping.

### On the server

| Trigger | What the caller sees | Cleanup and recovery | Residual limit |
| --- | --- | --- | --- |
| Deadline expires before commit | The stage's existing safe failure | Waiting stops, timer and listeners removed, transport and server closed. Recovery is a fresh request | A callback that ignores the signal still runs. Its result is ignored |
| Caller disconnects before commit | Nothing is written | Same cleanup | Same as above |
| Deadline or disconnect after commit | A truncated or ended response, no new status | Response ended or closed | Written or buffered bytes stay. The JSON path normally commits near completion, and the SDK write behavior must be confirmed |
| Result and deadline arrive together, or a result arrives late | At most one response | The first to reach the gate decides. A close after the response has finished is not a cancellation. A late result starts no storage read, issues no capability and writes no second response | See the residues below |
| Body never completes | A request-timeout answer (status open), then the connection closed | The request is destroyed as on the 413 path | A slow body takes time from the whole-request deadline, so the handler gets less |
| Verifier never settles | 500 `server_error`, not 401 | No body read and no server built. A late valid identity is dropped | The verifier's own work cannot be stopped |
| Slow reader after the application has finished | Not bounded here | Nothing in this proposal drains or times out a finished response | Open for the JSON route and for any streaming policy settled under CORE3 |

Three server-side residues remain.

- A capability already issued is not retracted. If the connection closes between issue and the response write, the capability, which is bound to the recipient key, goes unused and expires on its own clock.
- A proof identifier recorded before the authorization lookup is not un-recorded, so that proof is spent.
- A late `denied` answer from a lookup that was in flight when the request ended does not delete the grant. The grant stays until its time limit. Every later acquisition asks the lookup again, so a revoked authorization still refuses new bytes. A denial that arrives before the terminal outcome still deletes the grant, as today. In current source the deletion follows the lookup unconditionally, so honoring this rule needs the service to know the request has ended.

Nothing here lets a client's retirement stand in for the server stopping. The invocation may end locally, the server request still ends by completion or by its own deadline, and a capability may outlive both.

### Observed evidence, and what it does not show

The only recorded evidence about disconnect is the test at `operation.test.ts` lines 246 to 276 at c3eecaa, titled "aborts the handler's signal when the caller disconnects, and its late record has nowhere to go". This is source inspection, not a new run. The test host answers in JSON by default (lines 130 to 135), and its helper (`http-host.test-support.ts` lines 27 to 42) passes `enableJsonResponse` to the real Node transport and closes the transport and server when the response closes.

The sequence is: a client `fetch` posts a public tool call whose handler records its signal and returns a pending promise; the test waits until one signal has been recorded; it aborts the `fetch`; and it waits until that signal reads aborted. It then releases the pending record, waits 20 ms, opens a new client, releases again and calls the tool a second time.

The assertions are these:

- the handler's signal becomes aborted after the client aborts;
- the fresh call returns the expected structured output;
- the recorded signal count is 2 at the end (line 276), which supports one handler invocation per call.

"Its late record has nowhere to go" is the test's title and intended reading. Releasing the late result is part of the exercised sequence, but no assertion checks that nothing was written to the closed response, so the transport's response-write behavior after close is unverified.

This narrows the broader open question of whether `ctx.mcpReq.signal` aborts when the connection closes. For a JSON test host that closes on response close, the inspected test asserts that it does and that the next request is served normally. The evidence stays narrow:

- The test host is test support in the connector package, not the application listener. It registers its close handler at the start of the request, not after authentication and the body read, and it has no verifier or body step. It does not stand in for the application listener's early-disconnect behavior.
- It exercises a public operation, not a protected one.
- It posts no separate `notifications/cancelled`, and covers no other close path and no streamed response.
- It involves no assistant host and no remote effect, and it is not a cross-POST registry test.

The assertions of only this test and of the Hide images browser spec were read. Whether the other existing tests cited as safeguards assert the behaviors they are cited for is not established, and the JSON, protected-route, SSE, cross-POST and actual-host evidence stay separate.

### Local listener, browser and renderer-runtime checks

These can be answered without a named assistant host. The first group needs the real listener and the planned raw-socket checks:

- whether the pinned Node runtime reports an early disconnect to the body reader, and what the reader then does;
- the values of Node's default header and request timeouts, which the listener neither sets nor relies on. They are connection-level backstops, not an application deadline.

The second group needs a built page with the real `App` and bridge, or a renderer runtime. It covers the integrated ordering of teardown, a late `start` for one lease after a newer lease began, and reversed selections; two views open at once, where tearing down one leaves the other unchanged; whether pending and recovery controls stay reachable and announced at narrow widths, at zoom and with long titles; the React 0.13.0 versus inspected 0.14.0 timing; and, on a Lynx device, the interval between native removal and effect cleanup with the other runtime conditions the module lists. No result of this feature applies to a Lynx renderer.

### Required actual-host and integrated acceptance

In-process and local checks do not close the following. They need the real listener behind a named assistant host (ChatGPT web, Claude web) and are owned separately from this proposal, from SSE qualification and from final signoff.

- The host's sequence at teardown: whether the page is removed, whether an in-flight proxied call settles or rejects at close, whether a `toolresult` can arrive after teardown, and whether closing or replacing a view closes the connection of an in-flight request.
- Whether the host creates a new view for a later tool call or reuses one; whether its forwarding of a server request can hang while the server is healthy; whether it forwards an aborted `App.callServerTool` or sends `notifications/cancelled`; and what error a rejected call carries (a timeout, an abort and a refusal distinguishably or not).
- What the host does when it receives the fixed unavailable failure, 503, 500 or the request-timeout answer, and how it handles the server's responses beyond those failures and closes.
- Whether the host enforces the declared connect policy on the built playback page.

## Open decisions

**Open decisions retained by the design approval.**

- **Playback placement.** Option A (one invocation) is recommended and unverified. It needs the check that every stage falls inside the work interval; if one cannot, Option B's application-owned bound applies and the runtime provides none. The cost of A is that key creation, the host call and the body read draw from one budget, so a slow stage uses time the others could have used.
- **Label loss in the action view: decided 2026-10-19.** The human owner selected the recommendation: loss is final for the view instance, with recovery by a new view or reload. The alternatives not chosen were to drop the pin and accept the next opener, which accepts a delayed copy and restores the behavior this proposal removes, and a correlated read that returns the opened item, a new interface the inspected source does not have. The bounded host observations in Status show recovery through fresh authenticated openers in both hosts. ChatGPT retained the old retired view separately from the fresh view; saved-chat reload could replay an old opener and did not guarantee recovery. These observations do not establish every host view-reuse path. A host that reuses a retired view still cannot reactivate it. A delayed opener under the same label is still not detected, because there is no request id, and nothing here claims invisible account-switch detection or that a host forwards cancellation.
- **Presentation after a host-call rejection and after a work-deadline expiry.** The proposal reuses `unavailable` and does not use `sign-in-required` for a rejection. The cost is that a real refusal also reads as unavailable until a host is shown to distinguish it. A new state is the alternative, and needs approval. Whether the attempt's expiry should end in the existing `unavailable` state is part of this decision.
- **Action defaults decided; application mapping remains open.** The module supplies 30,000 ms work and 5,000 ms per bounded hook/cleanup step with independent overrides. These are product defaults, not measured guarantees. The pre-migration controller bound, incoming-body policy, protected-endpoint and resource-route deadlines, response mapping and slow-reader policy still require their own explicit decisions. The playback placement check must establish full stage coverage before replacing its controller bound. Measurements can inform later tuning; they do not block the initial action defaults.
- **Whether the success hook should keep the audio playing when it fails.** The module's sketch keeps it playing. Silence is the alternative.
- **Answers on expiry.** Whether a verifier timeout stays indistinguishable from a verifier fault (500) or gets its own 5xx status, avoiding 401 either way. Whether the body timeout is 408 with a new error name and the connection closed afterwards, as after 413.
- **Slow reader after completion.** Nothing bounds draining after the application finishes. Is that acceptable on the JSON route, with any streaming policy settled through CORE3?
- **How a listener-owned signal reaches handlers.** The interface choice under Responsibilities and interfaces.
- **Passing the recipient key through `call`.** Whether `call` can carry metadata or the key moves into the arguments and changes the server's contract is a decision about the module's `call` shape or the server's contract, and is left to the module's implementation review and the application owner.
- **Where Resume's synchronous context call lives, and where its event-turn ordering falls.** An owner operation begun in `atActivation`, or an adapter guarantee.
- **Whether the player owner can preserve an early `ended`.** The owner's start result must be able to say that audio ended before the start was confirmed, and the module's sketch does not.

**Missing verification evidence** (observations needed before relying on an assumption, not choices):

- Whether the real player can settle a retired `start` after a newer lease began, and whether it can be wrapped as an owner of leases.
- Whether a named host rejects a call with an error that distinguishes timeout, abort and refusal.
- What each named host does at teardown, on view reuse, on a stalled forward and on an aborted call.
- Whether the React 0.13.0 runtime matches the inspected 0.14.0 commit, and the Lynx runtime conditions the module lists.
- Whether other `AudioPlayer` implementations clear their end callback on release; the inspected Web Audio release clears `onended`, and the real ordering is unverified.
- How the pinned SDK transport writes its JSON response, and whether it tolerates a result returned after the response closed.
- What a separately posted `notifications/cancelled` does, and what other close paths do, beyond the one narrow test.
- Local, not host: whether the pinned Node runtime reports an early disconnect to the body reader, and what the listener's body reader then does.
- Whether the pinned SDK ever calls a handler with an already-aborted signal, and whether `execute` starts the handler in that case.
- Whether the existing tests cited as safeguards assert the behaviors they are cited for.
- How each named host behaves toward the server's answers and closes.
