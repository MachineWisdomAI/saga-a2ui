# Request and view lifetimes

Draft awaiting human design review.

## Problem and current behavior

A listener who plays an episode through an assistant host touches two programs that each decide, separately, when a piece of work stops mattering. The embedded view, a page that talks to the host through the MCP Apps bridge, decides when it stops caring about a question: the user selects another episode, the sign-in label changes, a request takes too long, or the host asks the view to tear down. The application's HTTP listener decides how long it waits on its own dependencies (credential verification, the entitlement lookup, protected storage) before it answers. This document asks whether each side stops acting at the moment it decides to, for the subscriptions view, the playback view, the two protected tool endpoints and the media route of [authorized playback](authorized_playback.blueprint.md).

It supersedes the rejected [account and session isolation proposal](https://github.com/MachineWisdomAI/saga-a2ui/blob/427257e207b4bb8dbcec8dbf38ea466a98209024/blueprints/features/account_session_isolation.blueprint.md) with a narrower question about ordinary lifecycle correctness, and it preserves the safeguards the code already has: authentication on every protected request, the immutable per-request identity, opaque labels used only for freshness, safe fault distinctions, the browse read bound and the media acquisition checks. It adds no live account switching, retained-state expiry, focus or resume revalidation, authentication for the public route, lifecycle framework or cross-request registry.

Current behavior is described from the source at commit [`19fb26c`](https://github.com/MachineWisdomAI/saga-a2ui/tree/19fb26c84116b15a56fec31bfa358898fe96d791). Main has since advanced to `6785ae1` by a documentation-only change, so the runtime source is the same. Nothing was run. Each gap below is a candidate found by inspection, not a reproduced fault; none is shown to expose another user's data, and no real host was observed. Repair of any candidate should begin with a reproduction.

### Terms

The **sign-in label** is the opaque `viewSession` value carried in tool results. It tells a view whether the data on screen still comes from the sign-in the view started with, and it never grants access, because the server authorizes every call from the verified request. To **pin** the label is to remember the first one a view accepts and compare later results against it. An **opener** is the `toolresult` notification that tells the playback view which episode is selected; a **correlated response** is the value returned to a call the view itself makes through `App.callServerTool`. Notifications carry no request id, so an opener can be a delayed copy of an earlier one.

A view **retires** a Play attempt by advancing its generation number so a late answer is recognized as obsolete, stopping the attempt's timer, aborting its byte fetch and stopping the player. Retiring is a client decision and says nothing about whether the server stopped. On the server, a request is **committed** once its status line and headers are written and **finished** once the application has handed its final result or error to the transport.

### What exists today

On the server, the listener builds a fresh MCP server and transport for each POST to a tool endpoint and answers in JSON; the media route is a plain HTTP handler. The subscriptions read races a bound (`readBoundMs`) and the handler's abort signal in `readWithinBound`, so a retired read never becomes the tool result. The media service limits how long a credential is accepted when an acquisition begins, not how long an accepted request may wait.

In the view, the shared bridge closes the connection once on `dispose()` and, when the host asks for teardown, calls the view's optional `onTeardown` once before it answers and before delivery stops, leaving closing to the host. The episode view pins no label and starts no request, so it needs no change. The subscriptions view accepts the host's opening result, which it treats as the answer to the call that created the view (a documented bootstrap assumption, not correlation), and later unsolicited results under the same label while it is not invalidated and no read is in flight. After a loss, an unsolicited positive result is ignored and only a correlated response from a read started after the loss recovers the view. Each read has a never-reused generation and a timer, so a read past its bound is retired, the view shows a retry state, and the late answer is dropped.

The playback view pins the label from the first opener. A Play press retires anything earlier, unlocks audio inside the user's activation, and starts one request with a generation number: create a recipient key, call the Play tool through the host, check that the grant names the selected episode, the pinned label and a media URL for that episode, acquire the bytes with the capability and a fresh proof, and start the player. The server authorizes Play; the view validates the returned grant. The view checks its generation after key creation, after the Play call, after acquisition and after the player answers. Acquisition itself (proof signing, the fetch and the body read) has several awaits with no check between them and relies on the fetch abort signal and the check that follows. A late Play or grant result, or a late acquisition completion, finds a different generation and is dropped before audio starts. A stale completion of `player.start` is different: audio may already have started, and the view currently calls `stop` on it, as the candidate below explains.

### Candidate gaps

On the server, the browse read is the only application-facing wait with a deadline. In the inspected code the credential verifier, the body read (byte limit only), the entitlement check on Play and on each media acquisition, and the protected storage read have no bound of their own. A request can therefore wait on a dependency as long as the dependency takes, and a request nobody wants can still start work: a Play abandoned during the entitlement wait would still issue a capability, and an abandoned media acquisition would still read protected storage. The listener registers its own close handler only inside `serve`, after authentication and the body read, and what Node reports to the body reader when a caller disconnects earlier is not established. The public `/mcp` route was not inspected beyond its lack of limits, so this document says nothing about it.

In the view, five candidates came from reading the controllers.

- **The subscriptions view registers no `onTeardown`.** After teardown the controller can still hold an armed read timer and an active generation. If either settles, it presents rows, the retry state or sign-in-required, and `retry()` can start a new read. Whether that is visible depends on whether the host removes the page and whether an in-flight proxied call settles at close.
- **The playback view can leave `session-changed` through the old label.** An opener under a different label clears the selection and presents `session-changed`; a Play grant under a different label presents `session-changed` but keeps the selected episode. Both keep the old pin, so a later opener under the old label returns the view to `ready` and makes Play available again, while an opener under the new label is never accepted. Given a delayed copy of an old opener, the view would report a changed sign-in and then show the old episode as ready. This grants nothing by itself, since the server authorizes the next Play, and whether a host produces that sequence is unobserved.
- **Playback teardown stops the player but does not retire the controller.** `onTeardown` is `retire`, which sets no flag, so until the host closes the connection `play()` can pass its guards from a state such as `ready`, `pause()` and `resume()` can call a stopped player and present the result, and a player end event can present `ended`.
- **A late player start can reach a newer attempt.** One player is shared across attempts, and when a start settles after its attempt was retired the controller calls `player.stop()`, which would stop a newer attempt's audio. The player's documentation says `stop()` during `start` makes the start reject, which covers the usual ordering, but the controller does not guarantee it.
- **A pending Play has no client-side bound.** The view waits on key creation, the host's forwarding of the Play call, proof signing, the fetch, the body read and the player's start, and ignores further presses meanwhile. Only the fetch and the player offer a cancellation path. The code passes no signal to `callServerTool`, and the sources do not show whether the upstream `App` API accepts one. If host forwarding hangs while the server is healthy, the view stays pending until a new opener, disposal or teardown.

## Proposed behavior

Everything in this section is proposed. It gives the server and the view each a small, locally owned lifetime and keeps the two independent: retiring an attempt in the view never claims to stop the server, and a server deadline never depends on the view noticing.

### Server request lifetime

The listener creates a request lifetime when it accepts a request for a protected endpoint or the media route, before authentication. It consists of one finite deadline, one abort signal, a watch on the response for an early close and a one-shot terminal gate, built from `AbortSignal` (handlers already receive one as `extra.signal`), the response `close` event and timers. The deadline covers all asynchronous application work until the request is finished, and committing headers does not end it. The gate is closure state held by whichever owner settles the request; in the handlers it is the race `readWithinBound` already runs. The first of three events decides the terminal outcome: the work produces its final result or error, the deadline expires, or the caller closes the connection. A disconnect produces no response, matching the MCP cancellation guidance that a receiver should stop processing and not respond, and a deadline expiry on a usable channel produces exactly one. No path writes a second.

Before commit the server still chooses the outcome, so each stage reuses the answer it already gives a dependency fault, because an expired wait shows that a dependency was slow, not that the caller was refused. A verifier wait gives the existing 500 `server_error`, since a 401 would claim the credential is invalid. A tool handler's entitlement, storage or browse wait gives that tool's fixed unavailable failure, and the media route's entitlement or storage wait gives the existing 503 `unavailable`. A body wait has no suitable answer today; the proposal is a request-timeout status followed by destroying the request as the 413 path does, with the status and error name open. After commit the status cannot change and written bytes cannot be retracted, so on expiry or disconnect the response is ended or closed with no second status, and the deadline keeps applying to the work that produces the rest of the response.

The post-commit rule applies to any path that commits before its work completes. In the inspected JSON path commit and finish normally nearly coincide, and the source does not show how the pinned SDK transport writes its JSON response, so the proposal assumes it writes only after the handler settles and the implementation must confirm that. A streamed (SSE) response commits before the work ends, so the rule matters most there. Progress and delayed completion for JSON and SSE belong to the reusable connector, CORE3 ([#16](https://github.com/MachineWisdomAI/saga-a2ui/issues/16)), and a passing JSON-listener test neither qualifies SSE nor proves cross-POST cancellation.

Play and each media acquisition are separate requests with separate lifetimes. The capability Play issues lives by its own clock after Play finishes, and each acquisition starts a new deadline that does not inherit what remains of Play's. The media service checks capability expiry and proof age only when an acquisition begins, so the request deadline, not the capability, ends a wait on the lookup or the storage read.

### View attempt lifetime

Each Play attempt gets a bound timer armed when the view shows `pending`, independent of the server deadline because it must also cover the host's forwarding and the client's own steps. Every way the attempt leaves `pending` clears the timer. A successful start (`playing`) clears it without retiring the attempt, because retiring would stop the audio that just started. A blocked start (`gesture-needed`) goes through the existing `clearWith`, which retires the attempt. The other outcomes (`unsupported`, `unavailable`, a denial, an error, audio that ends before the start is confirmed, and retirement by a new opener, a new press, label loss, disposal or teardown) clear it too.

On expiry, if the attempt is still current and the view is still `pending`, the controller calls `clearWith` with `unavailable` for the selected episode. That advances the generation, aborts the fetch and stops the player, so a hanging `start` rejects and finds a different generation, and Play stays available. The timer ends the waiting. The generation checks only suppress the effects of obsolete results, so they do not shorten key creation or proof signing, which cannot be cancelled. If the `App` API accepts an abort signal on `callServerTool`, the controller supplies the signal when it initiates the call and aborts it on expiry or retirement; otherwise the generation check drops the late answer. Whether the upstream API accepts a signal is something to inspect, not a new interface to add. Pause and Resume get no bound, because a stopped player makes them reject and retirement drops the answer.

On host teardown the playback controller retires the attempt and enters a retired state separate from `disposed`, in which `play`, `pause` and `resume` do nothing and no late callback presents or restarts audio. A retired attempt must not stop, pause or alter a newer attempt's playback; the retirement that already stopped the player releases the old audio. The subscriptions controller registers `onTeardown`, marks itself disposed, retires its reads and drops its private state. Neither calls the bridge's `dispose()` at teardown, because the host closes the connection after answering.

### One selection, late Play and teardown

1. A user opens the playback view and the host sends an opener for episode A under label L1. The view pins L1 and shows `ready`.
2. The user presses Play. The view starts an attempt, shows `pending` and arms its bound. The listener accepts the request, starts the request lifetime, authenticates and builds the playback server with the lifetime's signal. The Play handler races `checkEntitlement` against that signal, and the lookup does not answer.
3. The user selects episode B and the host sends a new opener under L1. The view retires the attempt for A and shows `ready` for B. The server is not told, and its request for A is still waiting.
4. The deadline expires. Nothing is committed and the connection is open, so the gate records the expiry, the handler stops waiting and returns the existing fixed unavailable failure, and the SDK transport writes it. No capability is issued. The listener clears the timer, removes its listeners and closes the transport and server.
5. The lookup answers later, entitled or denied. The answer is ignored and starts no further stage. If the response reaches the view, the view finds a newer generation and drops it before any fetch.
6. The user presses Play for B, a new attempt, and the host's forwarding never answers. The bound expires, the view retires the attempt and shows `unavailable` for B with Play available. A later press starts a new Play with a new key and reuses no saved authorization.
7. The user presses Play again and, while it is pending, the host asks the view to tear down. The controller retires the attempt and stops the timer. Nothing is presented from then on, a late `start` cannot restart audio, and the later `dispose()` retires again harmlessly and closes the connection once. The server's request still ends by completion or its own deadline.

The subscriptions view follows the same shape: if the host tears the view down while a filtered read is in flight, nothing is presented when that read's answer arrives or its timer fires, `retry()` and `select()` do nothing, and the later `dispose()` closes the connection once.

### Recovery where upstream gives no correlation

The subscriptions view keeps its existing recovery: unsolicited results are accepted before any loss, and after a loss only a correlated read recovers the view. The playback view has no equivalent, because an opener has no request id and the inspected source defines no safe read that returns the opened episode. The host's supported initial bootstrap stays as it is, and this proposal does not invent a correlation key, require one from the host or add a read on every mount.

The proposed policy for the playback view is conservative. Once the view has presented `session-changed`, from an opener or from a Play grant, it treats the loss as final for that view instance: no selected episode on either path, every later opener ignored whichever label it carries, and Play unavailable. Recovery is a new view whose opening result pins a fresh label, or a reload. This keeps today's rejection of an opener under a new label and removes the revival through the old label. The cost is that a user whose host reuses one view for a later tool call stays on `session-changed` until reload, and the sources do not say which the host does. This policy needs human design approval.

One limit has no proposed repair. While the label stays the same, the view takes the last opener delivered, so a delayed copy of an earlier same-label opener can replace a later selection, and without a request id the view cannot detect it. Because the view requests Play for whichever episode it shows as selected, a stale selection can change which episode a later explicit Play asks for. The server still authorizes that request on its own and the view refuses a grant naming another episode or label, so this is not an authorization bypass. A host-supplied correlation key or a read that returns the opened episode would remove the limit; these are examples a future design might evaluate, not the only possible repairs, and neither has been tried in a real host.

## Responsibilities and interfaces

| Owner | Holds | Proposed change |
| --- | --- | --- |
| Listener | Deadline values, request lifetime, terminal gate, its own answers (413, authentication refusals, media answers) | Create the lifetime at acceptance; race verifier and body waits; add the body-timeout answer |
| Tool handlers and media service | Fixed failure sentences; per-request server factory; capability issue and ordered acquisition checks | Receive the signal; race the entitlement and storage waits; start no later stage after the request ended |
| Application callbacks | Verifier, subscription read, entitlement lookup, storage read | Lookup and reads accept the signal; the verifier does not |
| Subscriptions controller | Pin, rows, selection, read generation, read timer | Register `onTeardown`; release reads and private state |
| Playback controller | Pin, selection, generation, abort controller, player, pending timer | Retire on teardown; make label loss final; add the pending bound; keep a retired attempt from touching a newer one |
| Bridge, episode view, host | Listeners, teardown handler, closing; notification delivery and call proxying | None; host behavior is to be observed |
| Reusable connector (CORE3) | Reusable callback cancellation and deadline contract; progress; delayed JSON and SSE completion | None here; neither implemented nor reshaped |

The application owns the deadline values and the answers written on expiry. STATE2 ([#13](https://github.com/MachineWisdomAI/saga-a2ui/issues/13)) keeps its own obligation to bound and cancel the waits of this application's listener, handlers and media service, and neither it nor the connector defers its semantics to the other. Authentication stays in the application, outside the connector, and still runs on every protected request, now inside the deadline; a verifier result that arrives after the request ended is dropped before any identity snapshot is made.

The design reuses existing interfaces: the SDK's `extra.signal`, `readWithinBound` with `readBoundMs`, the per-request server factory, the 413 answer followed by `req.destroy()`, and the 503 answer with the fixed failure sentences. New ones are a request lifetime passed to the server factories the way `readBoundMs` is today; a finite deadline setting for the protected endpoints and another for the media route; an abort signal on the entitlement lookup, storage read, subscription read and media acquisition; the request-timeout answer; and, in the playback controller, a retired state and an optional pending-bound dependency with an application default. The callbacks are internal and unreleased, so they change directly. The verifier takes only the token string, so the listener can stop waiting for it but cannot stop its work.

### Rationale and tradeoffs

One deadline for the whole request is the smallest design that answers how long a caller can wait, because per-stage budgets would have to be summed to answer it. The tradeoff is that a slow verifier uses time the handler could have used. The browse read keeps its tighter `readBoundMs` inside the request deadline. Racing each wait is the guarantee; passing the signal to a callback only asks for cooperative cleanup, because a callback that ignores it still cannot hold the request open. Where the SDK's own `extra.signal` can carry the deadline and a cancellation the pinned SDK delivers, handlers should rely on it rather than a parallel facility.

The playback controller's retired state is separate from `disposed` because its `dispose()` returns early when `disposed` is set, so reusing that flag would skip the close; the subscriptions controller's `dispose()` has no such early return. The generation checks stay at their existing points, with no new check after every `await`. When an attempt is retired during proof signing, the fetch that follows receives an aborted signal and is expected to reject without a network request, which a planned check confirms. MCP cancellation is optional, and because the listener builds a fresh server and transport per POST, a `notifications/cancelled` posted separately is not guaranteed to reach the handler it names. The proposal adds no registry or session state to change that; the deadline is the server's own maximum, not a client cancellation.

## Failure and recovery

Cancellation here is cooperative. The proposal bounds the waiting, guards each stage the application owns so it does not start, and asks callbacks to stop. JavaScript cannot preempt running code, a callback may ignore the signal and keep working, and a synchronous callback that blocks the event loop prevents the deadline timer from firing until it returns. In the view, a retired attempt, an expired Play bound or a host teardown leaves the server free to finish its own work, and bytes already buffered or effects already made are not recalled. Whether the page stays visible after teardown is host behavior.

| Trigger | What the caller or user sees | Cleanup and recovery | Residual limit |
| --- | --- | --- | --- |
| Server deadline expires before commit, or the caller disconnects | Expiry: the stage's existing safe failure. Disconnect: nothing is written | Request stops waiting; timer and listeners removed; transport and server closed; recovery is a fresh request | A callback that ignores the signal still runs; its result is ignored |
| Deadline expires after commit, on any path that commits before its work completes | A truncated or ended response, no new status | Response ended or closed | Written or buffered bytes stay. The current JSON path normally commits near completion; the pinned SDK's behavior is to be verified |
| Result and deadline arrive together, or a result arrives late | At most one response | First to reach the gate decides; a close after the response finished is not a cancellation (`res.writableFinished` already distinguishes it on the 413 path); a late result starts no storage read, capability or second response | See the residues below |
| Playback label differs from the pin, in an opener or a Play grant | Today: `session-changed`, with the selection cleared on the opener path and kept on the grant path. Proposed: `session-changed` with no selection on both | Today both keep the pin, so a later old-label opener returns the view to `ready`. Proposed: later openers are ignored; recovery is a new view or reload | A host that reuses the view leaves the user on `session-changed` until reload |
| Same-label delayed opener (no repair) | The delayed episode replaces the later one; a later Play asks for it | The server authorizes that request; the view refuses a mismatched grant | Stale selection; no request id to detect it |

Three server-side residues remain. A capability already issued is not retracted; if the connection closes between issue and the response write, the capability, which is bound to the view's key, goes unused and expires on its own. A proof identifier recorded before the entitlement lookup is not un-recorded, so that proof is spent. And a late `denied` answer from a lookup that was in flight when the request ended does not delete the grant. The grant stays until its time limit, but every later acquisition asks the lookup again, so a revoked entitlement still refuses new bytes. A denial that arrives before the terminal outcome still deletes the grant, as today.

## Verification outcomes

No check below has been run, and there is no observed evidence yet beyond the source reading in this document. Server checks would use the real listener, handlers and media service with fake verifier, backend, store and clock, and show JSON-path behavior only. Controller checks would use a fake `App`, player and timers, with teardown invoked through `app.onteardown`. They assert what a user could observe, not what a controller still holds, and none asserts that the server stopped. "No media request" means no network request; the proof-signing path may still call `fetch` with an already aborted signal.

### Required actual-host and integrated acceptance

Controller and listener checks do not close the following. They need the real `App` and `AppBridge`, a built browser and the real listener, and runs in the named hosts ChatGPT web and Claude web. They are owned separately from this proposal and are separate from final signoff and from SSE qualification.

- The host's sequence at teardown: whether the page is removed, whether an in-flight proxied call settles or rejects at close, whether a `toolresult` can arrive after teardown, and whether closing or replacing a view closes the connection of an in-flight request.
- Whether the host creates a new view for a later tool call or reuses the existing one; whether its forwarding of a Play call can hang while the server is healthy; what it does on the unavailable failure and the request-timeout answer; and whether it sends `notifications/cancelled`.
- Two views open at once, where retiring or tearing down one leaves the other unchanged; reversed selections in a built page, where A's answers or A's player start settle after B has begun; and pending, retry and recovery controls that stay reachable and announced to assistive technology at narrow widths, at browser zoom and with long episode titles.

## Implementation sequence

STATE1 ([#12](https://github.com/MachineWisdomAI/saga-a2ui/issues/12)) is recorded as depending on BROWSE2 ([#9](https://github.com/MachineWisdomAI/saga-a2ui/issues/9)) and PLAY1 ([#10](https://github.com/MachineWisdomAI/saga-a2ui/issues/10)), and STATE2 ([#13](https://github.com/MachineWisdomAI/saga-a2ui/issues/13)) as depending on STATE1 and PLAY2 ([#11](https://github.com/MachineWisdomAI/saga-a2ui/issues/11)). Whether the slices below become one ticket or several is a breakdown decision.

STATE1 takes the view-side cleanup: teardown release in the subscriptions controller; retirement of the playback controller on teardown, with its separate retired state and the rule that a retired attempt cannot affect a newer one; and final label loss for both the opener and Play-grant paths. Playback teardown retirement is the ordinary cleanup the bridge already documents, so it belongs here and not in an optional follow-up. Each slice lands with its controller checks.

STATE2 takes the bounds. The pending-Play bound comes first, and its implementer's first task is to inspect whether the upstream `App` API accepts an abort signal on `callServerTool`. The server side follows: the listener lifetime with its raced verifier and body waits and the body-timeout answer; the lifetime and signal passed to the tool handlers and media acquisition, so no later stage starts after the request ended; and the in-process evidence runs. Neither item closes the actual-host acceptance above. The reusable connector, packaging and adapters, and the actual-host runs stay with their current owners.

## Open decisions

Design decisions for the approver:

- **Recovery after label loss in the playback view.** The recommendation is to make loss final for the view instance, with recovery by a new view or reload. One alternative drops the pin and accepts the next opener, which accepts a delayed copy and restores the behavior this proposal removes. Another is a correlated read that returns the opened episode, a new interface the inspected source does not have. The approver decides whether a stuck reused view is acceptable, informed by host observation of view reuse.
- **Deadline values.** The protected-endpoint deadline, the media deadline and the pending-Play bound are not chosen. The application owner proposes them and the approver confirms them; the inputs are measured verifier, entitlement, storage and host-forwarding latencies that the inspected material does not provide.
- **Answers on expiry.** Should the pending-Play expiry end in the existing `unavailable` state? Should a verifier timeout stay indistinguishable from a verifier fault (500) or get its own 5xx status, avoiding 401 either way? Is 408 with a new error name right for the body timeout, with the connection closed afterward as after the 413?
- **Slow reader after completion.** Nothing here bounds draining of a response after the application finishes. Is that acceptable on the JSON route, with any streaming policy settled through CORE3?

Missing verification evidence (observations needed before relying on an assumption, not choices for the approver):

- How the pinned SDK transport writes its JSON response and whether it tolerates a result returned after the response closed, which decides whether the handler's return path through the gate is safe.
- Whether `extra.signal` aborts when the pinned SDK closes the transport, and what a separately posted `notifications/cancelled` does there. The design does not depend on either, since the listener supplies its own signal.
- Whether the pinned Node runtime reports an early client disconnect to the body reader. Default HTTP server header and request timeouts, which the listener neither sets nor relies on, are connection-level backstops rather than an application deadline, and their values are not established.
- Whether the real player can settle a retired start after a newer attempt has begun, and the host behaviors listed under required acceptance.
