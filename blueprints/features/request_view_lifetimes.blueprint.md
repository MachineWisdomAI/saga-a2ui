## Problem and current behavior

A user who acts through an assistant host touches two programs that each decide when a piece of work stops mattering. The embedded view (a page talking to the host over the MCP Apps bridge) decides when it stops caring about a question: the user selects another item, the sign-in label changes, a step takes too long, the control is replaced or the host asks for teardown. The application's HTTP listener decides how long it waits on its own dependencies (credential verification, the authorization lookup, protected storage) before answering. This design asks whether each side stops acting when it decides to, for the two views, the two protected tool endpoints and the protected resource route of [authorized playback](authorized_playback.blueprint.md).

The question is general. Any action with a protected operation, a local effect or a resource that outlives the step that obtained it has these lifetimes, and the action binding module gives them one vocabulary. Playback is the most demanding example and grounds the contract, but does not define it; archiving a note is followed through the same lifetimes below.

The design replaces the rejected [account and session isolation proposal](https://github.com/MachineWisdomAI/saga-a2ui/blob/427257e207b4bb8dbcec8dbf38ea466a98209024/blueprints/features/account_session_isolation.blueprint.md) with a narrower question about ordinary lifecycle correctness. It preserves the safeguards the code has: authentication on every protected request, immutable per-request identity, opaque labels used only for freshness, safe fault distinctions, the read bound and resource acquisition checks. It adds no live account switching, retained-state expiry, focus or resume revalidation, public-route authentication, lifecycle framework, action registry or cross-request registry.

The lifetime scopes (STATE1, STATE2, CORE2, CORE3 and the React protected player) are implemented and accepted for the scopes in [Status](#status). The overall feature stays partially implemented, and this section describes the code at the cleanup baseline `2405c5d28f02a5b8d5fb70ed7a929e676cf78d43`. The original design-time source inspection (main `c3eecaad89fcefc540ee7816a8b41731cb65e9d0`, reconciled on 2026-10-17) is kept as history in the baseline text of [What exists today](https://github.com/MachineWisdomAI/saga-a2ui/blob/2405c5d28f02a5b8d5fb70ed7a929e676cf78d43/blueprints/features/request_view_lifetimes.blueprint.md#what-exists-today) and [Candidate gaps](https://github.com/MachineWisdomAI/saga-a2ui/blob/2405c5d28f02a5b8d5fb70ed7a929e676cf78d43/blueprints/features/request_view_lifetimes.blueprint.md#candidate-gaps). At that revision the bridge was `connectToolResultView` in [`packages/mcp/src/view/index.ts`](https://github.com/MachineWisdomAI/saga-a2ui/blob/c3eecaad89fcefc540ee7816a8b41731cb65e9d0/packages/mcp/src/view/index.ts) and the action view controller was [`playback-view.ts`](https://github.com/MachineWisdomAI/saga-a2ui/blob/c3eecaad89fcefc540ee7816a8b41731cb65e9d0/apps/lit-host/src/playback/playback-view.ts). The pinned recipe is MCP Apps 2.0.3, client/core/server 2.3.1 and Node transport 2.1.1.

### Terms

The shared [action vocabulary](../README.md#action-vocabulary) and the module's [lifetimes table](../modules/action_binding.blueprint.md#lifetimes-and-owners) define *definition*, *rendered component instance*, *binding*, *semantic subject*, *invocation*, *acquired resource* (ended only by release or an explicit transfer to a longer-lived owner), *server request* (served by a function that lives on the server and is never referenced from the browser) and *discovery* (`watchById`, a setup-time subscription never consulted to route an activation). Here, a **local action**'s handler runs in the view (sync or async, no transport-aware `call`); a **server action**'s handler also receives `call`, which starts a server request with the invocation's signal and the time left in the work deadline. In both kinds the runtime runs prerequisites before the handler. Local and server actions are not A2UI wire forms.

In the example, Play's handler issues a protected request, then acquires bytes with the capability the result carried and starts a player; the player is an acquired resource and Pause and Resume are local actions on it. Archive is a server action in the non-playback flow. The **read view** (subscriptions) shows rows for the signed-in account and is started by the host's tool input, not an instance event. The **action view** (playback) offers Play, Pause and Resume on the selected item. The design applies to any view of this shape.

Four older terms keep their meaning because they name application behavior. The **sign-in label** is the opaque `viewSession` value in tool results; it tells a view whether on-screen data still comes from its starting sign-in and never grants access, because the server authorizes every call. To **pin** it is to remember the first accepted label and compare later results. An **opener** is the `toolresult` notification that tells the action view which item is selected; notifications carry no request id, so an opener can be a delayed copy of an earlier one. A **correlated response** is the value returned to a server request the view itself makes. On the server, a request is **committed** once status line and headers are written, and a finite request is **finished** when the transport reports response `finish` or its documented equivalent; producing the application result does not end its delivery budget. The **capability** is the grant a server action issues for the resource route; the **proof** is the signed statement a recipient presents with each acquisition.

Older vocabulary maps onto the module's: server action stays a server action (now a definition bound to an instance); client action becomes a local action (a `deadlineMs` is recommended for async work); attempt becomes an invocation plus any resource it hands off (an invocation ends at settlement, a started player does not); client continuation becomes the handler's steps after `call` plus the owner's work after a transfer; client-held resource becomes an acquired resource held by a token, not a shared whole-player; resource request is a second server request with its own lifetime (a direct HTTP request to the resource route, not proxied by the host); and "retire", which covered four owners, is now four separate terms (cancel or obsolete, dispose, end or release, and the controller's retired state).

### What exists today

This is the code at the cleanup baseline `2405c5d28f02a5b8d5fb70ed7a929e676cf78d43`, read from source and not run for this cleanup. The accepted outcomes and their evidence are in [Status](#status).

**Server.**

- The listener starts one request lifetime at admission (`route.budgets.startRequest()` in `apps/lit-host/src/mcp/listener.ts`), before the first credential, header or body wait, and binds the response to it (`response-lifetime.ts`). A finite response is bounded through transport `finish`; if the deadline passes first the response is destroyed. A streaming route needs a finite idle policy (`StreamingPolicy`, default idle 30,000 ms when streaming is enabled without a choice).
- Budgets come from `createServerBudgets` in `packages/mcp/src/server/lifetime.ts`: 3,000 ms per operation and 10,000 ms per request by default, resolved per route, then per SDK instance, then default, field by field, and rejected before any callback runs when not finite and positive (`BudgetConfigurationError`).
- A verifier that does not settle answers 500 `server_error`, and an incomplete body answers 408 `request_timeout` followed by a closed connection (`listener.ts`).
- `registerProtectedOperation` and `registerPublicOperation` in `packages/mcp/src/server/operation.ts` run each handler as a bounded operation of the request's lifetime. The handler receives `OperationRequest.signal`, `within(stage, work, { limitMs })` for nested lookups inside its aggregate budget, and `reportProgress`. The adapter passes the lifetime through the per-request server factory (`lifetime`).
- The playback tools run each handler through `boundedHandler` in `apps/lit-host/src/playback/playback-server.ts` (`lifetime.run('handler', work, { upstream: ctx.mcpReq.signal })`). Expiry, caller cancellation or a call arriving after the request ended gives the fixed unavailable sentence, and each stage that could start an effect calls `throwIfEnded` first. The authorization lookup, storage read and acquisition take a signal.

**Safeguards the lifetime must keep.** These behaviors were inspected at the design baseline and are the preserved-behavior requirements below.

- A protected endpoint refuses a declared oversize body with 413 before reading any credential, then authenticates, checks transport headers, reads the body within a byte limit, classifies it against the tool list and attaches the verified context. A missing or malformed credential, or the SDK's invalid-token error, gives 401 with a challenge; any other verifier failure gives 500 `server_error`; an expired credential gives 401; a missing scope or a credential naming no account gives 403. Accepted authorization is copied and frozen with validated account and sign-in identity written last.
- The playback handler checks verified identity, recipient key and fields before protected work. A lookup returning anything but `entitled`, or an unknown episode, gives the fixed denied sentence; a throw gives the fixed unavailable sentence; a contract fault gives the fixed invalid-result sentence.
- The resource route has no person-level authentication. The capability and the recipient's proof decide each acquisition, in fixed order, stopping at the first failure with a refusal that names no check: capability known and unexpired; episode scope; proof signature, type, age, method, target URL, capability binding and recipient-key thumbprint; proof identifier unused; then the current entitlement lookup. Only then does it read storage and interpret `Range`. The proof identifier is recorded before the entitlement lookup. A denial from the lookup deletes the grant; a lookup that throws never does. A throw maps to 503 `unavailable`, a refusal to 403 `forbidden`, an unsatisfiable range to 416. The expected proof URL is built from the listener's own origin, never the `Host` header. Answers carry `private, no-store` and a `Vary` list, and the route allows any origin to read the response because no ambient credential authorizes it; that is not an origin allowlist. The capability expires on the service clock (inspected default 60 seconds, `capabilityTtlSeconds`); a proof must be recent and unused (maximum age 60 seconds, 5 seconds of tolerance).

**Bridge.** `runToolResultView` (`packages/mcp/src/view/run-tool-result-view.ts`) owns the view's lifetime. However the view ends (`dispose()`, a host teardown request or `pagehide`), delivery stops and held input is dropped, the caller's `onTeardown` runs once, and the listeners are removed and the connection closed whatever `onTeardown` did; on a teardown request the host is answered first. Retiring a view says nothing about server work started on its behalf. This replaced the earlier `connectToolResultView`.

**Read view.** `connectSubscriptionsView` (`apps/lit-host/src/mcp/subscriptions-view.ts`) is started by `toolinput` and registers `onTeardown`. It accepts the host's opening result as the answer to the call that created the view (a bootstrap assumption, not correlation). After a label loss an unsolicited positive result is ignored and only a correlated response from a read started after the loss recovers the view. Each read has a never-reused generation and a timer at `readBoundMs`; a read past its bound becomes a retry state and its late answer is dropped.

**Action view.** `connectPlaybackView` (`apps/lit-host/src/playback/playback-view.ts`) builds Play as one server action bound to the rendered control (mapping A below), with Pause and Resume as local actions. The synchronous prefix selects the item, takes a lease from the player owner (`player-owner.ts`) and unlocks audio inside the user's event. The handler makes the host call (with `resetTimeoutOnProgress: false`), validates the grant, signs the proof, acquires the bytes with `credentials: 'omit'`, `cache: 'no-store'` and `redirect: 'error'`, decodes and starts the player, and on a confirmed start transfers the lease to the owner with nothing awaited between. A grant is accepted only if it names the selected item, the pinned label, an `http:` or `https:` URL and the item's own path; this is a scheme, item and path check, not an origin allowlist. Host teardown disposes the bindings, stops the audio and retires the controller. An opener or grant under another label ends the view for good (`labelLost` is set last and never cleared): selection cleared, bindings disposed, player stopped, `session-changed` shown, every later opener ignored.

**Content view.** The public content view keeps its own safeguards, which this feature does not touch: it revokes image consent before every delivered result (including repeats and errors) and retires consent permanently on teardown and disposal; it pins no label and issues no server request; description elements discard obsolete callbacks and revoke grants on content change or disconnect. This design adds no second consent lifetime.

## Proposed behavior

This is the approved contract. [Status](#status) records which scopes are implemented and accepted; choices that were made or remain open are listed under Open decisions. The design uses the module's contract as written, adds no exported name and gives no deadline value beyond the defaults below. It gives server and view each a small, locally owned lifetime and keeps them independent: ending a client invocation never claims to stop the server, and a server deadline never depends on the view noticing.

### One lifetime per owner

| Lifetime | Play control | Ends when | Does not imply |
| --- | --- | --- | --- |
| Definition | The play definition | Never | Anything about a binding |
| Instance | The rendered Play control | The renderer destroys or recreates it | Cancellation, unless the adapter disposes its bindings |
| Binding | The play binding on that control | `dispose()`, or the adapter retires the instance, surface or session | That a request already sent has ended |
| Semantic subject | The selected item | `subject()` returns a different value | That the binding is removed; only an undecided invocation is canceled |
| Invocation | One Play, press to settlement | Settlement. Cancellation or the work deadline fixes the outcome and ends the work wait; bounded outcome hooks, releases and finalization still run | That the server stopped, or a retained resource ended |
| Acquired resource | The player lease and the capability | Release, expiry or the media ending. A transfer changes owner and does not end it | That the invocation that obtained it is still running |
| Server request | The play call and each resource acquisition | The server's own completion, deadline or disconnect | That the view noticed |

The host-triggered read of the subscriptions view is a controller operation, not an invocation or instance-bound action; the controller keeps its generation and timer, and the read's server request keeps the independent server lifetime. A lease the invocation transferred to the application's owner outlives the invocation, so settlement of Play never means playback stopped. A canceled invocation, a disposed binding and a torn-down view each end the client's wait and say nothing about the server; cancellation is cooperative and neither recalls a sent request nor undoes a remote effect.

### What a view must decide, and what it must not

- **Setup finds, activation routes.** The application locates instances at setup (by identifier through discovery, or from the adapter's setup) and binds a definition to each handle. A component identifier is a diagnostic and discovery key, not an instance key, because a list can render one identifier per item. Nothing at activation looks a callable up by name.
- **`before` is for prerequisites.** Prerequisites are reusable work that may stop the handler (session validity, consent, a durable audit record), not spinner preparation. Pending presentation is a function of binding state: `running` from admission through the synchronous prefix, prerequisites, handler and required success hook; `settling` while the outcome hook, releases and `onFinally` run. No separate pending flag is needed.
- **Gesture-sensitive synchronous work belongs to `atActivation`.** Where an API needs its call in the event's call stack (as `prepare()` unlocking audio does), `atActivation` is synchronous by type and rule, and a thenable result ends the invocation as `activation-error`. Work in `atActivation` and `input` cannot be preempted by a timer, so a blocking callback stops every bound from firing until it returns. The module promises no portable activation property.
- **Each callback checks its own `current()` after an await, immediately before a synchronous presentation write.** The signal asks work to stop; `scope.active` says whether the outcome is decided; only `current()` says whether a callback may still change what the instance shows, and it is false for good once the callback finished, exceeded its budget or became obsolete. Handlers also stop starting network work or taking a resource when the signal has aborted or `scope.active` is false. A write that cannot be conditioned on `current()` must be idempotent or done in a prerequisite.
- **An obsolete presentation is not a different outcome.** The outcome is decided once. If an invocation becomes obsolete after the decision (the selected item changed while `onFailure` awaits), the outcome stays, the hook's signal aborts and its `current()` is false, no message about the old item appears on the new one, cleanup and releases still run, and `onFinally` receives `obsolete: true`.
- **Bounds.** The activation prefix is part of `running` but precedes the work timer. `deadlineMs` starts when the prefix finishes and covers every prerequisite and the handler; it expires as `failed(timeout)` in the stage running (in `prerequisites` the handler never started; in `running` the effect is unknown). `hookMs` separately bounds each of the required success hook, outcome hook, each release and `onFinally`. Neither is a whole-invocation maximum, and the clocks of the controller's read, the player's single steps, the resource service and the listener stay with their owners. Each setting resolves independently from a per-action override, then the owning SDK instance's configuration, then 30,000 ms work or 5,000 ms per hook or cleanup step; invalid values fail early. The work budget is shared by prerequisites and handler, progress cannot extend it, and a longer override cannot extend a host, gateway or server deadline. The default profile is not a 35-second whole-invocation maximum.
- **Result-stage-aware outcomes.** A failure before the handler started says its protected request was not sent (a prerequisite may still have contacted a session or audit service). A handler that returned shows only that it returned; the typed result and operation contract establish which effect completed. Any later failure is the client's required work. A throw, a timeout while running or a cancellation before a result says only that the client stopped waiting: the effect is unknown, the message must not invite retry, and nothing retries automatically.
- **Finalization and transfer.** Finalization always occurs; `onFinally` runs only when configured. Resources held through the invocation's scope are released in reverse order, each within `hookMs`, and a late handler acquiring after the invocation ended has the resource released at once. A resource survives a successful start only by explicit transfer to the application's owner. The owner's `end(token)` affects only the acquisition it names, is idempotent and is a no-op for a token the owner has superseded. Stopping everything the owner holds is the owner's teardown, never an invocation's operation.

### A non-playback flow: archiving a note

A note list renders an attachable control once per note, so two notes give two instances (Lit and React report the shared component identifier for both; Lynx gives expanded clones distinct `componentId` values with a shared `sourceComponentId`). Setup binds the archive definition to each instance's handle with a subject reader asking that handle which note it shows now.

The user presses the control on note A. Admission checks the event belongs to the current installation and the binding is idle; the synchronous prefix copies A's identifier; the binding shows `running` (a busy control) and the work deadline starts. A session prerequisite, a confirmation prerequisite and a durable audit prerequisite run in order, each able to refuse and each counting against the deadline. The handler then calls the server through `call`.

- **The row now shows note B while the confirmation is open.** At the next checkpoint or adapter wake-up the runtime finds the subject changed and decides `canceled(subject-changed)` at stage `prerequisites`. No archive request was sent, and the binding stays attached. A press on B first revalidates the old invocation, then applies the busy policy. A mismatch nobody observes cancels nothing yet.
- **The server archives the note and the required success hook overruns `hookMs`.** The outcome is `failed(success-hook-timeout)` with the result attached, so the failure hook can say the note was archived and the client's required work failed. The old hook's `current()` is false for good; the failure hook has its own eligibility. If the row meanwhile shows another note, the failure hook's signal aborts, it writes nothing, the outcome stays `failed` and `onCanceled` does not run.
- **The control unmounts during the request.** The adapter disposes the binding, the runtime decides `canceled(disposed)` at stage `running`, and the application may say only that the archive status is unknown. The server may still archive the note.

The view never assumes the server stopped, and nothing retries automatically.

### The server request as its own lifetime

The approved module names the server request as a lifetime outside the module. An invocation that settles, is canceled or times out says nothing about whether the request stopped, and a server deadline does not decide the invocation's outcome. The invocation's `deadlineMs`, the per-step `hookMs` and any host timeout belong to the client contract. STATE2 keeps an application-owned requirement to bound whole-playback pending work; it maps onto the two module bounds through mapping A (see playback below); an application maximum would be needed only where stages stay split. The module defines no third shared timer.

This section covers one POST to a protected tool endpoint or one GET to the protected resource route, owned by the listener, per-request handlers and media service. The reusable callback, progress and delayed-completion contract belongs to the connector, CORE3 ([#16](https://github.com/MachineWisdomAI/saga-a2ui/issues/16)); the defaults, nesting and finite-delivery contract below apply to its reusable SDK boundary, and CORE3 keeps the complete transport matrix.

#### Configurable server budgets

The SDK supplies an **operation limit of 3,000 ms** and an **end-to-end request limit of 10,000 ms**: overridable product defaults, not latency guarantees, independent of the module's client defaults. A server SDK instance may override either field, and an operation or route definition may override either independently; each resolves as per-operation/route override, then SDK-instance setting, then SDK default, and omitting one field inherits it without changing the other. Validate before admitting work: non-numeric, non-finite, zero or negative values are rejected at configuration or registration, never after authentication or a handler starts. No implicit unlimited sentinel exists.

An operation is an explicitly owned unit of server work: admission and asynchronous header validation, credential verification, body ingestion and parsing, the whole tool handler including projection, authorization lookup, protected-storage read, or acquisition preparation. Synchronous JavaScript cannot be preempted, so the gate is checked before and after it. The handler has an aggregate budget spanning its nested callbacks; nested lookups may be narrower but cannot extend their parent. Authentication and body admission use SDK-instance or adapter settings because untrusted arguments cannot choose budgets; an operation-specific override applies only once the operation is safely identified, and route request settings come from trusted registration before authentication.

**One request lifetime starts before authentication.** At HTTP admission, before the first credential, admission or body wait, the listener sets one monotonic absolute deadline. The effective wait for any operation is the minimum of its operation limit, the remaining parent budget (when nested) and the remaining request budget. Advancing a stage, receiving progress, retrying a dependency, invoking another callback or revisiting a stage never resets an enclosing operation or request deadline; an internal retry stays inside its operation budget. A separately admitted HTTP request has its own budget and does not make repeating an unknown write safe. Example: a handler entered with 800 ms remaining gets at most 800 ms even with a 3,000 ms limit, two sequential storage attempts share that remainder, and raising an operation limit above the request limit extends nothing. The request budget is independent of client cancellation, action deadlines, capability expiry and proof age.

**Finite responses finish within the request budget.** The terminal owner races disconnect and deadline through authentication, body processing, handler and projection, serialization and delivery until the transport reports `finish` or its documented equivalent. Calling `end` or producing a result does not finish the request. A response is selected once and cannot be replaced after commitment. A slow reader cannot hold finite delivery beyond the remaining budget: the adapter closes or destroys the response on expiry, clears its listeners and timers and writes no further status. `finish` means the transport accepted the response, not that the peer consumed every byte, and buffered bytes cannot be recalled. An adapter may set a narrower finite drain limit but cannot extend the deadline. This adds no further SDK-wide timeout default.

**Streaming has a different endpoint.** The request budget bounds admission, authentication and setup through establishing a stream, not a legitimate long-lived stream; each later finite operation keeps its operation bound. The adapter documents a finite idle or backpressure policy for ongoing streams and closes stalled streams through transport-supported cleanup; the policy must be supplied before streaming is enabled, and its absence is a configuration failure, not an unlimited fallback. Idle resets need real transport activity, not a retry or a progress callback that delivered nothing. CORE3 keeps the SSE, progress and delayed-completion matrix, and STATE2 adds no cross-POST registry. This completion rule supersedes the earlier server diagram's application-result endpoint for finite responses; the diagram remains the pinned historical artifact, not evidence that delivery is bounded.

**Safe terminal outcomes.** The owner keeps a structured internal cause distinguishing operation timeout, whole-request timeout, caller cancellation or disconnect, authorization refusal and dependency failure, with failing stage and known or unknown effect where available. Public errors use the applicable HTTP, JSON-RPC or MCP tool envelope and never copy a raw exception, token, private metadata or internal cause.

| Expiry before commitment | Safe reference mapping |
| --- | --- |
| Verifier or admission dependency wait | 500 `server_error`; never 401 merely because the wait expired |
| Body ingestion | 408 `request_timeout`, then close the incomplete request |
| Tool handler, authorization or storage | The tool's fixed unavailable `isError` result, or the applicable protocol error if no valid tool invocation exists; never claim denied access |
| Protected resource lookup or storage | Existing 503 `unavailable` with its safe headers |

Real invalid credentials and authorization refusals keep their challenges and statuses. A malformed or unclassified request gets no invented tool result. Disconnect produces no response. Expiry on a usable uncommitted channel selects at most one safe answer and attempts immediate completion without renewing the exhausted deadline; if delivery cannot complete, close the transport. After commitment, end or close per protocol and write no replacement status. Never imply a timed-out or canceled write was rolled back: preserve a known returned result, otherwise report an unknown effect without automatic retry or retry invitation. Reference-application wording, narrower limits and adapter mappings are delegated within these constraints and are not new approval gates.

**No stage begins after the terminal outcome.** After the gate decides, a late result is dropped without effect: a late verifier result reaches neither `req.auth` nor a server build, no body is classified, no capability is issued, no storage read starts and no second response is written. The application checks the gate before each later stage and does not rely on a callback stopping. **Racing is the guarantee; passing a signal asks for cooperation.** The listener stops waiting for each step, and a callback that ignores its signal still cannot hold the request open. The verifier takes only the token string, so the listener can stop waiting for it but not stop its work. The new interfaces are a signal on the authorization lookup, the storage read and the acquisition.

**Each request has its own clock; none is inherited.** The play call and each acquisition are separate requests. An acquisition starts a new deadline and does not inherit what remains of the call's. The capability keeps its own expiry; the media service checks that expiry and the proof's age only when an acquisition begins, so the request deadline, not the capability, ends a wait on the lookup or storage read.

**Cancellation is cooperative and local.** There is no registry, session state or shared table. The listener builds a fresh server and transport per POST, so a `notifications/cancelled` posted as a separate request is not guaranteed to reach the handler it names. MCP cancellation is optional, and the deadline is the server's own maximum. Cancellation never undoes remote effects; it stops waiting and prevents later stages.

**A request, step by step** (a protected action whose authorization lookup stalls, then the acquisition it would have led to):

1. The listener accepts the POST; the lifetime begins before authentication; the verifier answers within the deadline; authorization is frozen; the body is read and classified.
2. The handler waits on the lookup. The caller retires its invocation; nothing here forwards a cancellation (whether a host does is unknown). The request is still waiting.
3. The deadline expires with nothing committed. The gate records the expiry, the handler stops waiting and returns the tool's fixed unavailable failure, which the SDK transport writes. No capability is issued. The exhausted budget is not renewed to deliver the error; if immediate delivery cannot finish, the transport is closed. Timers and listeners are removed.
4. The lookup answers later, permitted or denied; the answer is ignored and starts nothing, so no capability is issued and no grant changes.
5. A capability issued by an earlier request is not retracted; it expires on its own clock, and an acquisition with it is a new request with a new deadline, new checks and a fresh proof.

If the caller closes the connection at step 2, the gate records a disconnect, the handler stops waiting, nothing is written and the same cleanup runs.

### Playback on the module: mapping A

This is the feature's mapping, implemented by CORE2 (see [Status](#status)). The module leaves placement of playback's stages open and records that if the stages cannot fall inside one interval the controller keeps a bound of its own; the table below compares the two placements that were considered.

**Stages after the press:** `prepare()` in the event, creating a recipient key, the host call to the play tool, validating the grant, signing a proof, the resource request, reading the body, decoding and starting the player, presenting `playing`.

**Option A, one invocation.** The activation prefix holds `input` (the selected item) and `atActivation`, which begins a lease in the player owner and takes it into the scope (the owner's `begin()` ends the previous lease's audio and prepares the player). Key creation and the host-capability check are prerequisites, so a failure of either is a prerequisite-stage failure and the host call never starts. The handler calls `call` for the play tool, validates the grant (scheme, item, path and label checks), signs the proof, acquires the bytes, starts the player through the owner with the lease and, on `started`, transfers the lease to the owner with no `await` between start and transfer. A blocked start returns a gesture-needed result without a transfer, and the scope releases the lease.

**Option B, split invocations.** The play invocation ends at the validated grant, and a later controller step, with an application-owned bound, performs acquisition and start. Option A makes the host call and resource request two server requests inside one invocation; Option B makes them separate invocations or controller steps. A binding's lack of a public `invoke()` does not prohibit such controller work.

| | Option A: one invocation | Option B: split under an application bound |
| --- | --- | --- |
| Where the stages sit | Key in prerequisites; host call to start in one handler | Key and host call in the first invocation; acquisition and start in controller code |
| Bound over the stages | Work deadline covers key through start; success hook under `hookMs` | First invocation has its own deadline; the second needs a controller-owned maximum, the timer the module declined to add |
| What cancels later stages | The same cancellation as earlier ones: new selection, disposal, replacement | The runtime no longer sees them; application code keeps generation checks and aborts |
| Busy policy | `ignore` or `replace` covers the whole sequence | Binding is `idle` while acquisition is pending; a second press is not ignored by the runtime |
| Pending presentation | Function of the `running` phase | Two sources of truth: binding state, then a controller flag |
| Lease ownership | One scope from `atActivation` to a transfer at start | Must transfer to the controller before the first invocation settles |
| Module's position | The play sketch puts fetch and start in one handler | Open decision 5 retains this path: if stages stay split, the controller keeps its own bound |

Both options were candidates the module left open (its [open decision](../modules/action_binding.blueprint.md#open-decisions) on mapping the playback whole-attempt bound onto the two bounds). The comparison is kept as the rationale for mapping A.

**Mapping A was chosen and delivered by CORE2,** supported by the module's sketch and by the property that matters: a single place where a selection, disposal or replacement ends the whole sequence and releases the lease. Option B was the fallback; its costs are ownership and coverage (the lease changes owner before the first invocation settles, the binding reads `idle` while the slowest stages run, and the controller keeps generation, abort and timer code for work the runtime has not taken over). If one stage cannot sit inside the work interval, the controller must keep its own bound and the shared runtime provides none.

| Phase the user sees (Option A) | Binding phase | Bounded by |
| --- | --- | --- |
| Press, `prepare()`, extracting the selected item | `running`, activation prefix, before the work timer | No timer; only the callbacks finishing bounds it |
| Creating the key | `running`, stage `prerequisites` | Work deadline; a timeout means the handler never started |
| Host call, proof signing, resource request, body read | `running`, stage `running` | Work deadline and the runtime-built `call` timeout (time left in it); progress cannot extend it |
| Decoding and starting the player | `running`, stage `running` | Work deadline; the player's 1,500 ms limits remain narrower single-step safeguards |
| Presenting `playing` or `gesture-needed` | `running`, required success hook | `hookMs` |
| Presenting a failure, ending the lease, final reporting | `settling` | `hookMs` for the outcome hook, each release and `onFinally` |

After the prefix the invocation can run at most `deadlineMs + hookMs` in `running`, and `hookMs` times (owned tokens plus two) in `settling`, while the event loop turns. The STATE2 requirement that the view not stay pending beyond a maximum progress cannot extend is an application requirement that mapping A meets through the work deadline. Status records CORE2 and STATE2 acceptance for their scopes; no record names a separate check placing every stage inside the work interval and the success hook inside `hookMs`, so that coverage rests on the delivered design and the playback view's own stated structure.

**Before CORE2 the controller kept its own bound.** The interim design armed a controller timer while the view showed `pending`, cleared it on every exit from `pending` and, on expiry, called the existing clear path with `unavailable`, which advanced the generation, aborted the resource request and released the player. `playback-view.ts` at the baseline contains no timer: the work deadline of mapping A replaced it, and the call's own timeout stays a narrower safeguard (`resetTimeoutOnProgress: false`). The earlier description is kept in the [cleanup-baseline text](https://github.com/MachineWisdomAI/saga-a2ui/blob/2405c5d28f02a5b8d5fb70ed7a929e676cf78d43/blueprints/features/request_view_lifetimes.blueprint.md#playback-on-the-module-one-proposed-mapping). A local abort does not establish that the host forwards cancellation. If a future flow keeps stages split, the bound stays application code with its reference value delegated to the implementation team and no change to the server defaults.

**Points the design left open, and what the code does.**

- The module's `call(name, args)` shows only a name and arguments, but the play request carries the recipient key in request metadata. The playback view's server transport forwards `_meta` beside, not inside, the arguments, so the server contract is unchanged.
- The existing `AudioPlayer` has a whole-player `stop()`. The player owner wraps it: a lease from `begin()`, `start` that rejects with `LeaseEndedError` for a superseded lease, `retain` on transfer, a token-scoped idempotent `end`, and a whole-owner `teardown` called only from the application's own selection, label, teardown and disposal paths. Whether the real player's ordering holds when `stop()` and `prepare()` interleave with a pending `start` is not recorded as observed; CORE2 records lease tests as the ownership proof where the removed ChatGPT view was unobservable.
- Resume calls the audio context synchronously in the user's event because the browser can require a gesture. Pause and Resume are local actions that call the player inside the activation, and the Play gesture work (`prepare()`) sits in the synchronous `atActivation` prefix.

| Work deadline expires | `prerequisites` or `running`, `timeout` | `unavailable`, retry not invited once the handler started | Presentation delegated within the safe effect and recovery contract |
| Success hook fails after a transferred start | `running`, `success-hook-error` or `success-hook-timeout`, result `playing` | Audio keeps playing under the module's chosen policy; an application preferring silence ends exactly that lease in the failure hook | The handler returned and the typed result shows which effect completed; the client's required work failed |
| Cancellation (`replaced`, `subject-changed`, `disposed`) | By stage | None from a failure hook; `onCanceled` ends exactly the activation's lease | Effect unknown if the request was sent |

A short audio that ends before the start is confirmed presents `ended`, not `playing`. The module's sketch shows only `started` and `blocked`, so the owner remembers an end that arrives before the start is confirmed (`hasEnded(lease)`) and the invocation reports it.

**Pause and Resume** are local actions whose async work acts on the owner's current lease. Under the module they have a busy policy and the resolved work budget, optionally overridden; the player's 1,500 ms limits remain narrower safeguards. They act only on the lease the owner holds, so a superseded lease makes them no-ops. A control disabled once playback has begun is application state, not busy policy, because the binding settles when Play does.

**What the label and selection do.** A new opener for item B, a loss of the label, host teardown and disposal each end the lease through the owner's teardown, because the module never calls whole-owner `stop` from an invocation. A new opener also changes the subject, which cancels an undecided Play at its next checkpoint, and the ended lease makes a late `start` reject.

### The read view stays controller-owned

The read is started by `toolinput`, not an instance event, so it is not an instance-bound action and this feature does not make it one. The controller keeps its generation, timer and correlated-recovery rule. `retry` and `select` could later adopt the module as a bound server action and a bound local action, a separate decision with its own conflict (an invocation result and the read generation would both claim to settle the same state). The required correction was teardown, delivered by STATE1: the read view registers `onTeardown`, marks itself disposed, retires reads and drops private state, leaving `runToolResultView` to close the connection afterwards. If the host tears the view down while a filtered read is in flight, nothing is presented when the answer arrives or the timer fires, `retry()` and `select()` do nothing, and the runner closes the connection once.

### Teardown, disposal and four things called dispose

1. **The bridge's `disposed` flag** means delivery has stopped; teardown sets it.
2. **The bridge connection's `dispose()`** closes once and is idempotent. `runToolResultView` answers a host teardown request, runs `onTeardown`, then closes the connection through the runner, so a later `dispose()` does nothing further.
3. **`ActionBinding.dispose()`** ends one binding: cancels an undecided invocation with cause `disposed`, detaches the callable and ends notifications after one final `disposed` state. It does not release a lease the owner deliberately holds.
4. **The playback controller's retired state** (`ended`) is set after the bindings end and the audio stops, and it is separate from the bridge's close: however the view ends, the lifetime runner calls the controller's teardown once and then closes the connection.

On host teardown the application's `onTeardown` disposes each binding, ends the owner's retained lease through the owner's teardown and enters a retired state. A retired attempt must not stop, suspend or alter a newer attempt's lease. `onTeardown` does not close the connection; the runner does, after answering the host. Retiring a view is not server cancellation. Unsubscribing setup-time discovery leaves bindings installed. Migrated callbacks make their own `current()` check before a post-await write.

### What retires an instance depends on the renderer

- **Lit.** Inspected upstream lifecycle events (disconnect, same-identifier type change, data-path change, list shrink, surface or session end) map to retirement. Under `a2ui-surface` the rendered element has no node, so handle and retirement would come from a binding-aware catalog element. The events were read in source. The Lit adapter (`packages/lit/src/actions`) exists; its qualification is recorded in the [action binding Status](../modules/action_binding.blueprint.md#status) (local Chromium, not a named host).
- **React.** The instance is the committed lifetime of a boundary for one node, delimited by a layout effect's setup and cleanup; a discarded render opens none. Timing was inspected at the 0.14.0 commit; whether published 0.13.0, the version the baseline pins, behaves the same was unresolved at design time. The React adapter (`packages/react/src/actions`) exists and its qualification is in the [action binding Status](../modules/action_binding.blueprint.md#status).
- **Lynx.** The handle comes from setup in a catalog component and cleanup runs as an effect cleanup. Between native node removal and that cleanup `current()` can still be true; the module does not claim to prevent a stale write in that interval. Its recommendation is that a hook's presentation write goes to a target tolerating a retired instance, keying presentation state by item, not by a handle to a rendered view. Measuring the interval on a device sizes the window and does not close it. No result of this feature applies to a Lynx renderer, and no production Lynx adapter exists (the owner retired the Lynx delivery chain on 2026-10-19).

Host teardown is renderer-independent because it arrives through the bridge; which adapter disposes bindings on it is the adapter's responsibility.

### Recovery where the host gives no correlation

The read view keeps its recovery: unsolicited results are accepted before any loss, and after a loss only a correlated read recovers. The action view has none, because an opener has no request id and the inspected source defines no safe read returning the opened item. The host's initial bootstrap stays as it is; this design invents no correlation key, requires none from the host and adds no read on every mount.

For the action view the approver selected, on 2026-10-19, the conservative option. Once the view has presented `session-changed` from an opener or a grant, the loss is final for that view instance: no selected item on either path, every later opener ignored whatever its label, Play unavailable. Recovery is a new view whose opening result pins a fresh label, or a reload. This keeps the rejection of an opener under a new label and removes the revival through the old label. Under the module the application ends the lease, disposes the Play binding and, because the label is application meaning, owns that decision; the shared runtime only carries a prerequisite refusal. The cost is that a user whose host reuses one view for a later tool call stays on `session-changed` until reload; the sources do not say which behavior any host has.

One limit has no repair in this design. While the label stays the same the view takes the last opener delivered, so a delayed copy of an earlier same-label opener can replace a later selection and the view cannot detect it, since the stale opener itself sets the subject. A press then asks for whichever item the view shows, the server still authorizes it, and the view refuses a grant naming another item or label, so this is not an authorization bypass. A host-supplied correlation key or a read returning the opened item would remove it; these are examples for a future design, and neither has been tried in a real host.

CORE3 owns the reusable contract.

### Rationale and tradeoffs

One deadline for the whole request is the smallest design that answers how long a caller can wait, since per-stage budgets would have to be summed. The tradeoff is that a slow verifier uses time the handler could have used; the read keeps its tighter `readBoundMs` inside it. Racing each wait is the guarantee, and passing the signal only asks for cooperative cleanup.

Separate lifetimes keep each small: the module's runtime owns one invocation's timers, the listener owns the server request's deadline, and the application's resource owner owns whatever outlives an invocation, none depending on another noticing. The cost is that the application must name each resource's owner explicitly and no single timer says how long a user may wait across all of them, which is why the playback requirement stays an application one until a check places its stages inside the work interval.

## Failure and recovery

Cancellation is cooperative. The design bounds waiting, guards each stage the application owns so it does not start, and asks callbacks to stop. JavaScript cannot preempt running code, so a callback that ignores its signal keeps running and may still write if it never checks `current()`, and a blocking synchronous callback prevents any timer from firing. A canceled or expired invocation leaves the server free to finish; buffered bytes, issued capabilities and effects already made are not recalled. Whether the page stays visible after teardown is host behavior.

The module's [error categories and safe presentation](../modules/action_binding.blueprint.md#error-categories-and-safe-presentation) preserve inspectable causes without showing raw server details, distinguish authentication from permission denial only with evidence and keep an unknown fallback. Timeout and cancellation prove no rollback; a returned result establishing write success stays known success if a later hook fails, and a write without an established result stays uncertain. HTTP 408 concerns an incomplete incoming request ([RFC 9110 §15.5.9](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.9)) and 504 a gateway's upstream wait ([§15.6.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.5)); a frontend timeout establishes neither.

### On the server

| Trigger | What the caller sees | Cleanup and recovery | Residual limit |
| --- | --- | --- | --- |
| Deadline expires before commit | The stage's existing safe failure | Waiting stops; timer and listeners removed; transport and server closed; recovery is a fresh request | A callback ignoring the signal still runs; its result is ignored |
| Caller disconnects before commit | Nothing written | Same cleanup | Same |
| Deadline or disconnect after commit | A truncated or ended response, no new status | Response ended or closed | Written or buffered bytes stay; the SDK write behavior must be confirmed |
| Result and deadline arrive together, or a result arrives late | At most one response | A result selects its response once but delivery stays timed through transport finish; deadline or disconnect wins while delivery is pending; a close after finish is not a cancellation. A late result starts no storage read, issues no capability, writes no second response | See residues below |
| Body never completes | 408 `request_timeout` before commitment, then the connection closed | Request destroyed as on the 413 path | A slow body takes time from the whole-request deadline |
| Verifier never settles | 500 `server_error`, not 401 | No body read, no server built; a late valid identity is dropped | The verifier's own work cannot be stopped |
| Slow reader after the result is ready | Finite delivery stays under the request deadline | Close or destroy on expiry before finish; no replacement status | Buffered bytes are not recalled; streams use the separate idle policy |

Three residues remain. A capability already issued is not retracted: if the connection closes between issue and the write, the recipient-key-bound capability goes unused and expires on its clock. A proof identifier recorded before the lookup is not un-recorded, so that proof is spent. A late `denied` from a lookup in flight when the request ended does not delete the grant; it stays until its time limit, and every later acquisition asks the lookup again so a revoked authorization still refuses new bytes, while a denial arriving before the terminal outcome still deletes the grant as before (the media service honors the rule: once the request's scope has ended, a late denial deletes no grant, `media-service.ts`). A client's retirement never stands in for the server stopping.

### In the views

| Trigger | What the user sees | Cleanup and recovery | Residual limit |
| --- | --- | --- | --- |
| Host teardown with an invocation pending | Nothing from then on | Bindings disposed; undecided invocation canceled `disposed`; owner ends the retained lease; the runner answers the host, then closes the connection once | The server request ends by its own completion or deadline; page visibility is host behavior |
| Host teardown with the read in flight | Nothing presented | Read view registers `onTeardown`, retires reads, drops private state | An in-flight proxied call may or may not settle at close |
| Label loss from an opener or grant | `session-changed`, no selection | Lease ended, binding disposed, later openers ignored | A reused view stays on `session-changed` until reload |
| Delayed copy of a same-label opener | The stale item replaces the later one | The server authorizes the request; the view refuses a mismatched grant | No request id to detect it |
| A late `start` settles after a newer lease began | The newer playback continues | `end(token)` for the stale lease is a no-op for a superseded token | Whether the real player can produce the ordering is unobserved |
| Host call stalls past the work deadline | `unavailable`, not a sign-in message | `failed(timeout)` in the running stage; lease ends; signal aborts; a new press starts a fresh invocation once cleanup settles | Effect unknown; a local abort does not prove the host forwarded cancellation |
| Key creation stalls past the deadline | `unavailable` | `failed(timeout)` at `prerequisites`; nothing sent | Key creation cannot be canceled; the runtime stops waiting |
| A synchronous callback blocks | Nothing until it returns | None possible | No timer fires in the interval |
| Success hook fails or overruns after the start | Audio keeps playing; the view reports its own failure | Failure hook ends the lease only if the application prefers silence | The success policy is the author's |
| A late handler acquires after the invocation ended | Nothing | Token released at once; call rejects; no hook runs | A resource inside a dropped result is outside this protection, so the handler hands every resource to the scope before returning |

## Verification outcomes

This section is the verification matrix the design set. [Status](#status) records which checks ran for each accepted scope and what they do not show; the tables below state the expected observable result and boundary of each condition and are not a claim that every row has its own recorded run. The module's matrix covers shared runtime outcomes (outcome decision, per-callback eligibility, late settlement, hook budgets, busy policy, installation epoch); these tables add only what the server request and views contribute. Server checks use the real listener, handlers and media service with a fake verifier, backend, store and clock, show JSON-path behavior only, and qualify neither a streamed response nor cross-POST cancellation. Controller checks use a fake `App`, fake player and fake timers, with teardown through `app.onteardown`. A check asserts what a user could observe, never that a server stopped. Where a check says no request was made, it names which request or acquisition is counted: the protected play request and the acquisition are counted separately from requests a prerequisite may send to a session or audit service, and invoking `fetch` with an aborted signal is distinguished from an actual network acquisition. View state names are the example's; an adopter substitutes its own.

### Server-budget amendment checks

- Omitted configuration resolves to 3,000/10,000 ms; each per-operation or route field overrides only its matching SDK-instance field; two SDK instances and concurrent requests share no timers or configuration mutation; invalid settings fail before callbacks run.
- Delayed authentication and body ingestion consume the original request budget; a handler entered near expiry receives only the remainder; nested lookup and storage waits and retries cannot exceed the handler's aggregate cap; progress and repeated stages cannot reset it.
- An uncooperative callback is raced, its late result ignored and no later protected stage begins; concurrent unrelated requests continue; existing capability and proof residual rules are unchanged.
- A finite JSON or resource result ready before expiry whose delivery stalls is closed by the original deadline (`end` alone is not completion); successful `finish` clears the timer; finish, deadline and disconnect races yield one terminal decision and no second status.
- Each pre-commit stage uses the safe protocol envelope; committed responses cannot be replaced; timeout, cancellation and auth refusal keep distinct causes; a possibly completed write stays unknown, not retryable.
- A configured streaming response can continue beyond ten seconds after setup but stalls obey the adapter's finite idle or backpressure policy; a setup stall stays under the request budget; absence of a safe streaming policy fails configuration. Kept distinct from CORE3's complete SSE matrix.

### Observed evidence at the design baseline, and what it does not show

This is the evidence read at the design baseline. CORE3 later resolved the pre-aborted callback question and recorded the qualified JSON/SSE and stateless cancellation boundaries in the [connector Status](reusable_mcp_connector.blueprint.md#status), which owns those outcomes.

The only recorded evidence about disconnect is the test at `operation.test.ts` lines 246 to 276 at `c3eecaad89fcefc540ee7816a8b41731cb65e9d0`, "aborts the handler's signal when the caller disconnects, and its late record has nowhere to go" (source inspection, not a new run). The host answers in JSON by default (lines 130 to 135), and its helper (`http-host.test-support.ts` lines 27 to 42) passes `enableJsonResponse` to the real Node transport and closes transport and server on response close. A client `fetch` posts a public tool call whose handler records its signal and returns a pending promise; the test aborts the `fetch`, waits for the signal to read aborted, releases the pending record, waits 20 ms, opens a new client, releases again and calls the tool a second time. It asserts that the signal aborts, the fresh call returns the expected structured output, and the recorded signal count is 2 (line 276), supporting one handler invocation per call. No assertion checks that nothing was written to the closed response, so post-close write behavior is unverified.

This narrows the question of whether `ctx.mcpReq.signal` aborts on connection close, but only narrowly: the host is connector test support, not the application listener (it registers its close handler at request start and has no verifier or body step); it exercises a public operation, not a protected one; it posts no `notifications/cancelled` and covers no other close path or streamed response; it involves no assistant host or remote effect. Only this test and the Hide images browser spec had their assertions read. Whether other tests cited as safeguards assert what they are cited for is not established.

**Local checks needing no named host.** With the real listener and raw sockets: whether the pinned Node runtime reports an early disconnect to the body reader and what the reader then does; Node's default header and request timeouts, which the listener neither sets nor relies on (connection-level backstops, not an application deadline). With a built page, real `App` and bridge, or a renderer runtime: integrated teardown ordering, a late `start` after a newer lease began, reversed selections, two views open at once with one torn down, pending and recovery controls reachable and announced at narrow widths, zoom and long titles, React 0.13.0 versus 0.14.0 timing, and on a Lynx device the interval between native removal and effect cleanup.

**Required actual-host acceptance** (real listener behind ChatGPT web and Claude web; owned separately from this proposal, SSE qualification and final signoff):

- The host's teardown sequence: whether the page is removed, whether an in-flight proxied call settles or rejects at close, whether a `toolresult` can arrive after teardown, whether closing or replacing a view closes an in-flight request's connection.
- Whether the host creates a new view per tool call or reuses one; whether its forwarding of a server request can hang while the server is healthy; whether it forwards an aborted `App.callServerTool` or sends `notifications/cancelled`; what error a rejected call carries.
- What the host does on the fixed unavailable failure, 503, 500 or the request-timeout answer, and how it handles responses and closes.
- Whether the host enforces the declared connect policy on the built playback page.

## Open decisions

Each entry says whether the choice was made, by whom and where it is recorded, and what remains genuinely open. Nothing here is a new approval gate.

**Decided and implemented.**

- **Playback placement: Option A (mapping A), delivered by CORE2.** [Status](#status) records CORE2 (#15, PR #133) complete for mapping A with acquisition-scoped leases. The playback view's own header states that one invocation spans every pending stage, with the work deadline covering key creation through start. The comparison above is the rationale. A separate stage-coverage check naming every stage inside the work interval is not recorded in Status, so the cost of A (key creation, host call and body read draw from one budget) is accepted by the delivered design and not otherwise measured.
- **Label loss in the action view: decided 2026-10-19.** The human owner selected the recommendation: loss is final for the view instance, recovery by a new view or reload (PR #106). Not chosen: dropping the pin and accepting the next opener (accepts a delayed copy and restores the removed behavior), and a correlated read returning the opened item (a new interface the source lacks). The bounded host observations in Status show recovery through fresh authenticated openers in both hosts; ChatGPT retained the old retired view separately from the fresh one, and saved-chat reload could replay an old opener without guaranteeing recovery. They do not establish every host view-reuse path. A delayed same-label opener is still undetected, and nothing claims invisible account-switch detection or host forwarding of cancellation.
- **Reference-application presentation: delegated 2026-10-19.** The implementation team selects safe wording and recovery within the failure and effect contract. An indistinguishable host rejection must not assert invalid credentials; unknown effects must not invite blind retry (#122). A new presentation state within those semantics is not an approval gate.
- **Action defaults: decided** (30,000 ms work, 5,000 ms per hook or cleanup step, independent overrides; product defaults, not measured guarantees; #110).
- **Server defaults and response delivery: decided 2026-10-19** (3,000 ms operations, 10,000 ms requests, finite responses bounded through transport finish; adapter-configurable idle policy for streams; #112). Answers on expiry stay bounded by the selected contract: internal causes stay distinct and application mappings stay configurable without allowing timeout-as-authentication-failure or duplicate responses. CORE3 qualified the streaming boundary.
- **How a listener-owned signal reaches handlers: settled in code.** The adapter starts the lifetime at admission and passes it through the per-request server factory (`lifetime`); `OperationRequest.signal` aborts on caller cancellation, handler budget or request deadline.
- **Passing the recipient key through `call`: settled in code.** The playback view's server transport carries `_meta` beside, not inside, the arguments (`playback-view.ts`).
- **Ending a lease and preserving an early `ended`: settled in code.** The player owner in `player-owner.ts` offers `begin`, `start`, `retain`, a token-scoped `end`, `hasEnded` and a whole-owner `teardown` that only the application's own selection, label, teardown and disposal paths call. A start that confirms after audio already ended is reported as `ended` (`playback-view.ts`). Whether the real player's ordering holds under reversed selections in a built page is a verification item below, not an open design choice.
- **Resume's synchronous context call: settled in code.** Pause and Resume are local actions that call the player inside the user's activation (`playback-view.ts`).

**Still open.**

- **Whether the success hook keeps the audio playing when it fails.** The module's sketch keeps it playing; silence is the alternative. No decision is recorded.

**Missing verification evidence** (observations needed, not choices):

- Whether the real player can settle a retired `start` after a newer lease began, in a built page with reversed selections.
- Whether a named host rejects a call with an error distinguishing timeout, abort and refusal.
- What each named host does at teardown, on view reuse, on a stalled forward and on an aborted call. Status records bounded observations for STATE1, STATE2 and CORE2 only; the lists in [Required actual-host acceptance](#observed-evidence-at-the-design-baseline-and-what-it-does-not-show) remain outside them.
- Whether React 0.13.0 matches the inspected 0.14.0 timing. The baseline pins `@a2ui/react` 0.13.0 (`packages/react/package.json`); the ACT2 React qualification is recorded in the [action binding Status](../modules/action_binding.blueprint.md#status), and this document does not restate its outcome.
- The Lynx runtime conditions the module lists. The owner retired the Lynx delivery chain on 2026-10-19 and no production Lynx adapter exists, so these have no scheduled owner.
- Whether other `AudioPlayer` implementations clear their end callback on release (the inspected Web Audio release clears `onended`).
- How the pinned SDK transport writes its JSON response and whether it tolerates a result returned after the response closed. CORE3 records the qualified JSON/SSE and stateless cancellation boundaries in the [connector Status](reusable_mcp_connector.blueprint.md#status); that Status owns what is and is not shown.
- Locally: whether the pinned Node runtime reports an early disconnect to the body reader and what the body reader then does.
- Whether the existing tests cited as safeguards assert the behaviors they are cited for.
- How each named host behaves toward the server's answers and closes.
