## Purpose and boundaries

### Purpose

An application author needs to see, in ordinary typed code, which component invokes which callable, where its input comes from, what happens on completion or cancellation and who owns cleanup. A `dispatch(action, input)` function describes invocation after the connection exists; it does not show how an action is built, how it reaches one rendered component, or how event data, validated input, handler result and hook data relate in the type system. This module therefore starts from construction and attachment and derives the execution contract from them.

Application code builds an action value and attaches it to a component. For a directly attached control the markup supplies the component ID and layout and carries no action. Generated code or annotations emit the same public calls as hand-written code. Shared code owns the work around the callable: prerequisites, pending state, cancellation, settlement and cleanup.

The document covers, in order: how an author builds and attaches an action; what the shared runtime does once an event arrives; what Lit, React and Lynx must each supply; one complete non-playback flow; and how the design is verified, migrated and decided.

### What stays outside the module

The [coding standards](https://github.com/MachineWisdomAI/saga-a2ui/blob/c3eecaad89fcefc540ee7816a8b41731cb65e9d0/CODING_STANDARDS.md) say what the module does not own.

- The consumer application keeps domain values, backend calls, verified identity, authorization and authoritative effects. A client-side prerequisite is not authorization; the server stays authoritative for every protected operation.
- `@saga-a2ui/mcp` keeps MCP and MCP Apps delivery, the view bridge and its connection lifetime.
- `@saga-a2ui/core` keeps renderer-independent protocol processing.
- Renderer packages keep framework binding, events, mounting and disposal. A catalog or custom-element registration an upstream renderer requires stays at that renderer's adapter seam.

The module therefore cannot decide server authorization, close a connection or hold an upstream renderer's required registration. It adds no compulsory middleware, no generic retry and no handler-name table, typed or untyped. Existing upstream protocol actions remain available for controls that do not use direct attachment.

### Component terminology

A **component type** is a kind of control (`Button`, `List`). A **component definition** is the ID-bearing declaration in the layout. A **template** describes children to create for each data item. A **rendered component instance** (**instance**) is one component created and managed by a renderer; saga a2ui attaches actions through it or a renderer-owned handle, and the term implies neither a JavaScript class instance nor a single DOM element. A2UI calls repetition **dynamic children**: a container's `children` is a static array of IDs or a template with `componentId` and `path`, and each data item yields an instance of the template's tree with a data scope for relative paths, so a repeated row has its own instance of a child control such as Archive ([components](https://a2ui.org/concepts/components/#best-practices), [collection scopes](https://a2ui.org/specification/v0.9-a2ui/#collection-scopes-relative-paths)).

The **data item** is the application entity an instance currently displays. Rendering again does not necessarily create a new instance, and an existing instance may display a different item, so a `subject` reader tracks that semantic identity apart from the instance's lifetime (compare the [React list vocabulary](https://react.dev/learn/rendering-lists)). "Instance" is qualified with "rendered" because A2UI also uses "component instance" for an ID-bearing protocol declaration.

### Lifetimes and owners

An action involves lifetimes that end for different reasons. Keeping them apart lets one definition serve two components without shared pending state and stops a client decision from claiming something about the server. This table is the one place the lifetimes are defined.

| Lifetime | Covers | Owner | Ends when | Ending it does not imply |
| --- | --- | --- | --- | --- |
| Definition | What the builder produced: parameter extraction, prerequisites, handler, hooks, limits, busy policy. No pending flag, cancellation state, timer or resource | Application code | Never; reusable across any number of instances | Anything about a binding or invocation |
| Discovery (`watchById`) | A setup-time subscription delivering handles | Application setup code | It calls the returned unsubscribe | That any binding is disposed or callable removed |
| Rendered component instance | One component created and managed by a renderer, reached directly or through its handle | Renderer adapter | The renderer destroys or recreates it | That anything is canceled, unless the adapter also disposes its bindings |
| Binding | One definition attached to one event of one instance; applies the busy policy and exposes observable state | Application, or the adapter on its behalf | `dispose()`, or the adapter retires the instance or its surface or session | That requests already sent ended, or another binding of the definition is affected |
| Semantic subject | The item the instance shows now, when the application supplies a `subject` reader | Application data | `subject()` returns a different value | That the binding is removed; only an undecided invocation is canceled |
| Invocation | One activation not ignored: parameters, prerequisite values, abort signal, deadline and held resources, from the event through prerequisites, handler, required hooks and cleanup | Shared action runtime | It settles or is retired | That server work stopped; a local abort does not prove the host forwarded cancellation |
| Acquired resource | What an invocation obtained and the application must release: a capability, a player holding decoded media | Application resource owner | Released, expired on its own clock, or the media ends | That the invocation that acquired it is still running |

One more lifetime sits outside the module: the server request. A server action's definition holds a locally callable function that sends a request; the function that serves it lives on the server and is never referenced from the browser. The listener, handlers and resource service own the request, and its reusable callback and deadline contract belongs to CORE3 ([#16](https://github.com/MachineWisdomAI/saga-a2ui/issues/16)).

An acquired resource may outlive its invocation: playback continues after Play settles, and Pause and Resume act on the player. Ownership ends only by release or explicit transfer to a longer-lived owner. A later selection, label loss, host teardown or disposal releases the player; retiring a pending invocation releases only what it had already acquired. "Application resource owner" is the application code that acquires, holds and releases what an invocation obtains and owns application meaning such as the sign-in label and selected item (in the example, the player, media service and view controllers).

### Vocabulary inherited from #69

[#69](https://github.com/MachineWisdomAI/saga-a2ui/blob/1e02dc6a67f3781344dd5c476cc6ea64073a37d3/blueprints/features/request_view_lifetimes.blueprint.md#terms) described the example with its own terms: a server action (an operation the view sends to the application server through the host, in the pinned recipe `App.callServerTool`), a client action (a function handled entirely in the view), a client continuation, a client-held resource, an attempt and a resource request. That vocabulary belongs to the earlier draft, with a [terminology review](https://github.com/MachineWisdomAI/saga-a2ui/pull/69#issuecomment-6232496379) attached. It is not an equivalence between execution location and A2UI wire forms: per [A2UI's actions concept](https://a2ui.org/concepts/actions/), an `event` is dispatched to the agent and a `functionCall` is executed by the renderer, while the MCP Apps server action is a tool call to the application's own server. This module claims no correspondence between those pairs; each renderer adapter states how an upstream wire form reaches a bound callable. In these terms the #69 attempt is the invocation of a server action together with its continuation, and its client-held resource is an acquired resource. #69's remark that client actions need no deadline holds for Pause and Resume only because their sole effect is on a player that retirement releases; it does not extend to an asynchronous local action whose work retirement does not release (see [Bounds](#bounds-the-work-deadline-and-the-hook-budget)). The approved [request and view lifetimes](../features/request_view_lifetimes.blueprint.md) revision now follows this module's vocabulary.

### Authoring

A **prerequisite** is reusable work that must finish before a handler and may stop it. It is defined by what it decides, not what it shows. saga a2ui supplies the way to declare and attach one; the check itself is application code. A client-side session check avoids pointless work but is not authorization, and saga a2ui does not require a session fetch before every action. A prerequisite answers only with `proceed(...)` (optionally providing values) or `refuse(reason)`; the string given to `prerequisite` is a diagnostic label that appears in failure records and never selects behavior, and a plain `{ label, run }` object is equally valid. A guard that provides nothing calls `proceed()` and passes earlier provided values through unchanged.

A **synchronous local action** needs no parameters, prerequisites, hooks, limits or telemetry. An **asynchronous local action** extracts a parameter at activation, requires the session, passes the invocation's signal to its work and states its bounds; its failure hook says only what the outcome establishes about the local effect, in three states: the handler never started (nothing was attempted), the handler returned (the effect completed and only view work failed), or anything else (the effect may or may not have happened, because the handler threw or a deadline or cancellation decided first). A "not saved" message would be false in the last two. The full examples (`requireSession`, `confirmArchive`, `auditIntent`, `toggleDetails`, `saveDraft`) are in the [companion, section E.1](./action_binding.evidence.md#e1-authoring-examples).

A **server action** reuses the session prerequisite, adds a prerequisite needing the session and the parameter and a guard recording audit intent, and sends its request through `call`. It attaches to a data-bearing control showing one note, and is the workflow the [representative flow](#representative-flow-archiving-a-note) follows on every renderer. Each renderer's event carries the note identifier differently, so the workflow is a function of one projection, `noteIdOf`, which reads and validates the identifier from that renderer's event; the adapter copied the underlying value from the exact instance when it admitted the event. Component ID alone cannot supply it, because a list can render one ID twice with different data behind each instance. The extractor validates the copied value as a nonempty string and keeps it, and no later step re-reads a position that may now show something else. Everything except the projection is renderer-independent.

The success hook does required client work (a durable record) and then calls its own `current()` immediately before the synchronous presentation write. The failure hook reports only what the outcome establishes: where the handler never started, no archive request was sent; where it returned, the server effect is complete; otherwise the effect is unknown and the message must not invite a retry.

```ts
function requireNoteId(value: unknown): string {
  if (typeof value !== 'string' || value === '') throw new Error('this row shows no note');
  return value;
}

// 3. Server action: the same prerequisite, a second one that needs it, a guard that provides nothing,
//    and a handler that initiates the request. The server's own handler is not referenced from here.
//    Only `noteIdOf` depends on the renderer's event shape.
export function archiveNoteWith<Event>(noteIdOf: (event: Event) => string) {
  return Action.server<Event>('archive-note', transport)
    .input((event) => ({ noteId: noteIdOf(event) }))
    .before(requireSession)
    .before(confirmArchive)
    .before(auditIntent)
    .run(async ({ params, call }) => {
      const reply = await call('archive_note', { noteId: params.noteId });
      // Tool-level failures arrive as a result with isError, not as an exception (pinned upstream doc).
      // This example's tool reports isError only when it changed nothing; that is the tool's contract, not MCP's.
      if (reply.isError) throw new ArchiveRejected('The server declined to archive the note');
      return parseArchived(reply);
    })
    .limits({ deadlineMs: 30_000, hookMs: 2_000 })
    // Required client work after the server effect, then this hook's own check right before the commit.
    // If `recordArchived` ignores the abort and outlasts `hookMs`, `current()` is false when it resumes.
    .onSuccess(async ({ result, signal, current }) => {
      await recordArchived(result.archivedAt, signal);
      if (current()) showArchived(result.archivedAt);
    })
    .onFailure(async (context) => {
      // Input or prerequisite stage: the handler never started, so no archive request was sent.
      if (context.stage !== 'running') {
        if (context.current()) showError('No archive request was sent');
        return;
      }
      const { failure } = context;
      // The handler returned, so the server effect completed; only client work failed. This failure hook
      // has its own eligibility, so its `current()` (unlike `scope.active`) stays true after the failure was
      // decided, while a late `current()` call from the abandoned `onSuccess` is false for good.
      if (failure.kind === 'success-hook-error' || failure.kind === 'success-hook-timeout') {
        await refreshArchiveList(context.signal);
        if (context.current()) showArchivedButViewFailed(failure.result.archivedAt);
        return;
      }
      if (failure.kind === 'handler-error' && failure.error instanceof ArchiveRejected) {
        if (context.current()) showError('The server declined the request');
        return;
      }
      // Timeout, transport failure, or an unreadable reply: the request may have been applied.
      if (context.current()) showArchiveStatusUnknown();
    })
    .whenBusy('ignore')
    .observe((event) => void event.phase)
    .build();
}

// The data-bearing example below: the adapter copied `noteId` from the exact instance that fired.
export const archiveNote = archiveNoteWith(({ noteId }: NoteActivation) => requireNoteId(noteId));
```

`parseArchived` throws `ArchiveReplyUnreadable` when the reply cannot be read, landing in the last branch on purpose: the server answered but the client cannot say what it said. The runtime picks the branch from `stage` and `failure.kind`, which it knows. Whether the server really did nothing after `isError` is a fact about this example's tool, not an MCP promise. The `observe` call and the labels passed to `Action.local`, `Action.server` and `prerequisite` are diagnostics, not semantics. The necessary pieces are the ordered `before` calls, `run`, `limits` where an asynchronous hook or server call needs a bound, and the hooks the application chooses.

```text
Action.local<Event>(label)                      Action.server<Event>(label, transport)

  .input(extract)                one, first       reads the event, returns Params; sync, effect-free
  .atActivation(perform)         one, then        sync event-turn work for a qualified adapter/API
  .before(prerequisite)          any number       in the order written; adds provided values
  .run(handler)                  required         fixes Result
  .limits({ deadlineMs?, hookMs? })               optional per-action overrides; each field resolves independently
  .onSuccess / .onFailure / .onCanceled / .onFinally    each at most once
  .whenBusy('ignore' | 'replace')  .observe(observer)   each at most once
  .build()                                        returns the reusable ActionDefinition<Event>

component.bindAction(eventName, definition, { subject? })     returns ActionBinding
binding.state   binding.subscribe(listener)   binding.dispose()   binding.id
prerequisite and handler contexts: signal, current(), scope (the activation callback gets own only)
hook contexts: signal, current(); no scope

Discovery used by the authoring, Lit and React examples (not required of every renderer):
view.getById(id, kind)    view.watchById(id, kind, onHandle)
Optional data capability of a data-bearing kind: getById/watchById return a handle that also has readData()
```

**How the types connect.** `Action.local<Event>(label)` and `Action.server<Event>(label, transport)` begin a draft whose `Event` is what the target component's adapter delivers, and each later call refines one type parameter.

- `input(extract)` runs at activation and fixes `Params`. It reads the event (which carries current values the adapter supplies for that instance) and whatever application state the author chooses, once, when the event occurs, and copies out what later work needs. It must perform no effects; if it throws, the invocation ends as `invalid-input`.
- `atActivation(perform)` fixes `Activation`, the value returned by work an API requires inside the event itself (see [Event-turn work](#event-turn-work)). It receives the event and an activation scope that can take ownership of a token but cannot await an acquisition (N22).
- Each `before(prerequisite)` adds to `Provided`. The compiler rejects an ordering where a need has not yet been provided (N2) or needs params the action does not extract (N3). A guard providing nothing leaves `Provided` unchanged (P1).
- `run(handler)` fixes `Result` from the handler's return type, sync or promise. The handler context carries `params`, `activation`, `provided`, an abort `signal`, `current()` and the invocation `scope`; server actions also carry `call` and a local handler context has none (N8).
- Hook contexts are narrowed by what exists when the hook runs. `onSuccess` sees `result`. `onFailure` is a union keyed by stage: an input failure has neither parameters nor `provided`, a prerequisite failure has parameters but no `provided`, a failure while running has all (N5). `onCanceled` has a `completing` variant carrying the result and no other variant does (N21). Every hook context has a `signal` and its own `current()`, none has a `scope`. `onFinally` receives the primary outcome, keeping its stage, and a separate list of cleanup diagnostics (N23).
- `bindAction(event, definition)` requires the definition's `Event` to accept what the component kind delivers for that event: a definition for a field's change does not attach to a button's activation (N6), one needing a data-bearing row's `noteId` does not attach to a plain button (N24), an unknown event name is rejected (N7), and a definition written against a supertype attaches where the adapter supplies a subtype.

**The synchronous boundaries.** Three callbacks must finish in the call that made them: `input`, `atActivation` and the adoption callback passed to `Held.transfer`. Each declaration takes a guard as a rest parameter that demands an extra, unsatisfiable argument when the callback's inferred return type has any thenable constituent, so a plain `async` callback (N16, N19, N20) and a union such as `Promise<number> | undefined` (N17) are compile errors. A callback that always throws returns `never` and stays valid (P4). The guard offers no diagnostic string to supply (N18). Types cannot see a promise returned through a declared `unknown` or `void` (L1), so each boundary also checks at runtime: a thenable from `input` ends the invocation as `invalid-input`, from `atActivation` as `activation-error`, and from an adoption callback makes `transfer` throw and leaves the token with the scope. In all three the runtime attaches a rejection handler so a late rejection cannot become unhandled. Nothing can stop a synchronous callback starting deferred work, keeping the event or reading it later; that stays the author's responsibility.

**Order and the immutable builder.** The order is the execution order: `input`, `atActivation`, any number of `before` calls, then `run`; after the first `before`, `input` and `atActivation` are no longer on the builder (N10, N11), so a chain cannot change `Params` after attaching a prerequisite checked against the old shape. Every builder value is immutable: each call returns a new builder, a retained alias is a branch, and two `onSuccess` calls on one alias give two separate definitions (P6). TypeScript has no linear ownership, so hiding a used method is a convenience, and the runtime rejects a repeated registration on any chain, including through an `any` cast or from JavaScript. Repeated registrations are rejected rather than appended or replaced: `input`, `atActivation`, each of the four hooks, `limits`, `whenBusy` and `observe` can each be called once (N11, N12), because silently replacing a recording success hook would lose required work and appending would leave ordering and budgets to guess. An author needing two pieces of success work calls both from one hook. `before` is the one repeatable step because its order is the point.

`limits`, when supplied, comes before the hooks and overrides either or both settings. Hooks and server `build()` need no `limits` call because resolved defaults give finite budgets, and resource ownership needs no explicit `hookMs`. `build()` snapshots per-action overrides; the SDK instance supplies its own application configuration. The configuration attachment API is an implementation detail but may not introduce mutable process-wide settings or an action registry, and no operation composition is offered as an alternative.

### Direct attachment

Attachment obtains a handle for one rendered instance, once, at setup, and binds the definition to one of its events. One definition gives independent bindings with their own state. Disposing a binding does not retire its handle: the same live handle takes a new attachment, so changing an action needs no remount and no new catalog type. The common obligation on every renderer is exact instance identity, a typed `bindAction` on that instance's handle, and owned disposal. `getById` and `watchById` are the discovery facade the authoring, Lit and React examples use; they are not required of every renderer (Lynx delivers the exact handle from its catalog component's setup), and `readData` is an illustrative optional capability of a data-bearing handle. Each adapter keeps the data reader its renderer supports.

`NoteRow` is a data-bearing control kind: one kind serves archive, star, open or any action with a compatible event, its event carries the data the adapter copied from the instance that fired, and its handle can read what that instance represents right now through `readData()`. Neither belongs to the generic `ComponentHandle`, which declares only `id` and `bindAction`; the companion declares `DataSurfaceView` for the stronger handle, a plain handle has no `readData` (N25), and nothing casts one into a data handle. Lit and React declare `InstanceView` (handles with `read(path)`), and Lynx hands its control's setup a handle with `read(prop)` and `itemKey(prop)`. A synchronous star action omits `subject` because no gap exists in which the row could change; every example holding a row across an asynchronous gap passes a subject whose reader is the exact handle's own data reader. Attachment, rebinding, and the `watchById` ownership pattern (keep every binding and subscription the callback creates, and end them all from the owning setup's cleanup even if the callback fails part way) are shown in [companion E.1](./action_binding.evidence.md#e1-authoring-examples).

`watchById` is setup-time discovery: it calls the callback once per instance and delivers handles only. Stopping it disposes no binding. The adapter may index handles by component ID to implement it, but the index never routes an activation, which reaches its callable through the instance's own event path. The instance retires its own bindings when its lifetime ends, and the `disposed` notification lets the application forget them. An internal collector that disposes exactly the bindings one registration created is adapter plumbing, not a second public watch operation. `handle.id` is the component ID as the adapter reports it, a diagnostic and discovery key, not an instance key.

#### Identity and disposal defaults

Repeated component IDs occur on inspected paths: in Lynx GenUI 0.7.0 the list-template branch renders one ID once per item with a different data path each ([`List/index.tsx` lines 73–87](https://github.com/lynx-family/lynx-stack/blob/bb2f9ba92c8fe936be39b882047ab94aae58809f/packages/genui/a2ui/src/catalog/List/index.tsx#L73-L87)), and the Lit/core 0.13.0 and React/core 0.14.0 resolution types keep the protocol component ID, a document-unique node ID and a data path as separate identities ([0.13.0](https://unpkg.com/@a2ui/web_core@0.13.0/src/resolution/component-node.d.ts), [0.14](https://github.com/a2ui-project/a2ui/blob/45633b97636daf89bafb43fa7db23e3cd916461d/typescript/core/web_core/src/resolution/component-node.ts#L54-L84)). The contract therefore never selects behavior or data by component ID. The proposed defaults, offered for adapter authors to challenge:

1. A binding is identified by (rendered component instance, event). The same component ID after the renderer recreates the component is a different instance.
2. `getById` throws when no instance, or more than one, has the ID in the surface, naming the ID; it never picks the first match. A surface repeating an ID in a template is reached through `watchById` or an explicit adapter operation addressing one instance.
3. A handle represents one instance. When the adapter destroys that instance it disposes every binding on it and the handle becomes stale: `bindAction` on it throws, and a handle obtained before recreation does not attach to the new instance. Disposing a binding does not make its handle stale.
4. A binding lives no longer than its instance, and the adapter also disposes it when it ends the surface or session containing the instance. The `disposed` notification tells setup code to attach again.
5. A second `bindAction` on the same instance and event throws while the first binding is live. Replacing behavior means disposing the first and binding again on the same live handle.
6. Binding an event the component kind does not offer throws at setup, naming the event.
7. A recreated instance starts with no binding and an idle state; a reused definition carries no pending or cancel state from the old instance.

At `c3eecaad89fcefc540ee7816a8b41731cb65e9d0` nothing in the Lit code identifies or reaches an instance. How a handle is obtained differs by renderer (a Lit 0.13 default descendant has a context and no node, so a binding-aware catalog element supplies it; a React 0.14 handle comes from committed setup on a node whose cleanup list cannot be unregistered; the Lynx handle comes from setup in a catalog component), so the common contract asks each adapter for outcomes, not mechanism: a handle per instance, disposal of its bindings at retirement, and a stale handle that throws.

When the application swaps a definition on a mounted node (a React prop carrying a different action), the adapter disposes the old binding first, which cancels an undecided invocation with cause `disposed`, and only then installs the new one. A disposal always detaches the callable its own binding installed and never one installed afterwards, so an old binding's late cleanup cannot remove its successor. Unsubscribing discovery alone leaves the old callable installed. Where a renderer's cleanup list cannot unregister an entry or run one registered after disposal (the inspected React node), the adapter makes disposal idempotent and refuses `bindAction` on a handle whose node was already disposed. A live node under a new host or model needs the liveness reader to report that change, since reading only "not disposed" misses it, and the adapter must not mutate published live state during an abandoned render. Event types in examples (`ButtonActivation`, `FieldChange`) are illustrative and adapter-defined; the contract assumes no pointer, keyboard or thread and no event shape beyond the component ID.

#### Binding state, subject and ending

`bindAction` returns an `ActionBinding` with an opaque `id`, a `state` snapshot, `subscribe(listener)` and an idempotent `dispose()`. `state.phase` is `idle`, `running` (from activation start until the outcome is decided, covering prerequisites, handler and the required `onSuccess`), `settling` (from the decision until `onFinally` settles or its budget expires, covering the outcome hook, releases and `onFinally`) or `disposed`. It returns to `idle` only for the invocation that owns the binding's state: under `replace` an older invocation's cleanup can finish beside a newer running one without setting `idle`, and a disposed binding stays `disposed`. The state object is replaced on every change and never mutated; it carries no settled result (presenting a result is the hooks' job). `subscribe` calls the listener synchronously after each change and returns an unsubscribe. The binding exposes nothing else (no event, input, invocation or way to find another binding), so it is not an action bus. A listener's synchronous exception is caught and a returned thenable gets a rejection handler. A synchronous action completing in the event's call stack moves through `running` and `settling` to `idle` before the handler returns. How a renderer turns a subscription into a rerender is the adapter's design.

Disposing cancels the running invocation with cause `disposed`, detaches the callable, ends notifications after one final `disposed` state and leaves other bindings of the definition untouched. Disposal during an outcome-specific hook does not rewrite the decided outcome; it aborts the presentation hooks' signals (`onSuccess`, `onFailure`) and the rest of cleanup continues.

An instance identified by structure or list position can stay the same while the item it displays changes, and an invocation started for item A may still be awaiting while the row shows B; a structural key or data path is not a semantic identity. The application can optionally say what the instance is about with `bindAction(event, definition, { subject })`, a function returning a primitive key for the item the instance now shows, reading current state through a supported API and never a view object captured by an earlier render. The runtime captures `subject()` at invocation start and compares a fresh read with `Object.is` at its decision points and on every `current()` call, applying the [outcome rule](#outcome-decision-and-obsolescence): a mismatch before a terminal decision cancels with cause `subject-changed` and keeps the callable and binding; after a terminal decision it only makes the remaining presentation hooks obsolete. A reader that throws at activation ends the invocation as `invalid-input`; one that throws later counts as a change. Without a `subject`, the target is the instance alone and no semantic replacement is detected, which is right for a fixed button and wrong for a recycled list row.

### Execution semantics

This section is the single normative home for ordering, outcomes, obsolescence, freshness and the runtime and adapter seam. Renderer sections, the flow, failure discussion and verification matrix refer here.

#### Order of events for one activation

1. **Admission (synchronous).** An event captured under an earlier installation is ignored with reason `stale-installation`. If the binding is `running` or `settling`, the runtime first revalidates the active invocation (see [the seam](#the-runtime-and-adapter-seam)) and applies the [outcome rule](#outcome-decision-and-obsolescence); only then does the busy policy apply. `ignore` (the default) drops the new activation: no hook runs, no invocation exists, and the observer sees `ignored` naming the busy invocation. The policy covers `settling`, so a second activation cannot overlap the release of resources the first holds, and revalidation never bypasses `ignore`; if revalidation canceled the old invocation and its bounded cleanup is pending, the new activation is dropped until that cleanup settles. `replace` cancels a running invocation with cause `replaced` and starts the new one at once; if the old one is already `settling`, its outcome stays and its remaining cleanup continues beside the new invocation with its presentation hooks made obsolete.
2. **Activation prefix (synchronous).** In the event's call stack the runtime calls `input`, then `atActivation`. A throw or thenable ends the invocation as `invalid-input` or `activation-error`; no prerequisite or handler runs and resources the prefix took into the scope are released.
3. **Prerequisites** run sequentially in written order, each after the previous proceeded.
4. **Handler** runs once every prerequisite proceeded.
5. **Required success work.** If the handler returned in time, `onSuccess` runs within `hookMs`; the binding is still `running`, because success is decided only when this hook completes.
6. **Outcome decision.** Every path fixes one outcome exactly once; the binding is `settling` from here.
7. **Outcome-specific hook.** `onFailure` or `onCanceled` runs, awaited within `hookMs`. A failed `onSuccess` decides `failed`, so `onFailure` follows it. `onCanceled` runs only for a canceled outcome and `onFailure` only for a failed one.
8. **Resource release.** Tokens owned through the scope and not transferred are released in reverse order, each within `hookMs`.
9. **Final hook.** Finalization always occurs. A configured `onFinally` runs last, once, for every invocation that began, receiving the outcome and cleanup diagnostics; when it settles, its budget expires, or at once if none, the invocation is settled and the binding returns to `idle` only if this invocation still owns its state.

The runtime awaits a step only when it returned a promise, so an action built only from synchronous pieces runs from event to `idle` without yielding (`toggleDetails` has completed when the event handler returns). Nothing makes a `before` hook cross an asynchronous boundary merely because the API can await one; a piece that sometimes returns a promise and sometimes a value changes when the invocation finishes, so neither timing should be relied on. The [diagram](#representative-flow-archiving-a-note) shows this order with cancellation and telemetry drawn apart.

#### Outcome decision and obsolescence

The runtime decides an invocation's primary outcome once; no later event changes it, reruns a hook or hands a value to a hook that already ran. Four things can decide it, first to occur wins: a stage failure, expiry of the work deadline, a cancellation (`replaced`, `disposed`, `subject-changed`) and completion of `onSuccess`. The decision keeps its stage: a failed outcome is `input`, `prerequisites` or `running`; a canceled one is `prerequisites`, `running` or `completing`. A timeout during prerequisites is therefore a failed outcome in `prerequisites` (the handler never started), and one while the handler runs is in `running` (effect unknown). `onFinally` receives the same outcome (P7).

| A cancellation arrives while | Outcome | What it contains |
| --- | --- | --- |
| Prerequisites are running | `canceled`, stage `prerequisites` | No result; the handler never started |
| The handler has not settled | `canceled`, stage `running` | No result; the handler may be doing anything |
| The handler returned and `onSuccess` has not finished | `canceled`, stage `completing` | The result the runtime already observed |
| The outcome is already decided | Unchanged | Remaining presentation hooks become obsolete; the outcome is never rewritten |

**Obsolescence** is a condition of the presentation hooks, not a second outcome. An invocation becomes obsolete when its binding is disposed, a newer activation replaces it, the `subject` reader returns a different value at a checkpoint, or the adapter's liveness reader reports the instance gone.

- **Before a terminal decision**, obsolescence is a cancellation (`replaced`, `disposed`, `subject-changed`); an instance no longer live is treated as disposal. A changed subject keeps the callable and binding installed; liveness loss retires the binding. When `onSuccess` is running, the table decides `canceled(completing)`.
- **After a terminal decision**, the outcome stays. The runtime starts neither `onSuccess` nor `onFailure` for an already-obsolete invocation, because those hooks present results and a stale presentation is wrong. If failure was decided and `onFailure` is running when the invocation becomes obsolete, that hook's signal aborts, its `current()` returns false, the runtime stops waiting and records an `obsolete` diagnostic; the outcome stays `failed` (not rewritten to `canceled`) and `onCanceled` does not run. If the decided outcome is `canceled`, `onCanceled` still runs.
- **Cleanup always finishes.** Releases and finalization run in every case, and `onFinally` receives `obsolete: true`. Work that must run even for an obsolete invocation belongs in `onFinally` or a release, not `onFailure`.
- **Without a `subject` reader** a replaced row alone makes nothing obsolete; disposal, replacement and liveness loss still apply.

*Cancellation before the result.* A handler ignores the signal and the user presses again under `replace`: the runtime decides `canceled(running)`, runs `onCanceled` and `onFinally`, and settles. When the old handler later resolves, that is a **late settlement**: the value is dropped, `onSuccess` is not called, no hook reruns, the delivered outcome does not change, and the observer is told a late settlement occurred (with no value). A result that arrived before the decision but was not yet observed is treated the same. *Cancellation during required success work.* The handler returned and `onSuccess` is awaiting a write when disposal arrives: the runtime had observed the result, so it decides `canceled(completing)` with that result; `onCanceled` receives it, the `onSuccess` signal aborts, and a later `onSuccess` settlement is a late settlement whose failure reaches no hook. The runtime cannot recall a write the hook already started, so a write that must survive cancellation has to be idempotent or a prerequisite.

For any late settlement: a late value or error is dropped; a late resource handed to the scope is released at once, within `hookMs`, with no hook involved (a failure reaches only the observer, as `cleanup-error` with step `release`); a resource a handler returns inside its result instead of handing to the scope is outside this protection, so a handler hands any resource to the scope before it returns.

#### Running prerequisites

A prerequisite may be asynchronous and may stop the handler. Its `run` receives the values earlier prerequisites provided, the extracted parameters, the abort signal, `current()` and the scope, and returns `proceed(values)`, `proceed()` or `refuse(reason)` or a promise of one. They run strictly in order; provided values merge into one invocation-local object visible to later prerequisites, the handler and later hooks, and a prerequisite providing a key an earlier one provided ends the invocation as `prerequisite-error` (the runtime catches the collision types may miss). A prerequisite object holds no per-invocation state and is safe to share. `refuse(reason)` ends the invocation `failed` with kind `refused`, recording the prerequisite's label and reason; the handler does not run (the ordinary result of an absent session, which the failure hook can treat differently from an error). If a prerequisite throws or rejects the invocation ends `prerequisite-error`, and the failure hook receives `stage: 'prerequisites'`, the failure and the parameters but no `provided` object (enforced by type, N5). Cancellation aborts the signal, the runtime stops waiting at once, starts no further prerequisite and ends the invocation canceled; a prerequisite ignoring the signal and resolving later is a late settlement. A record that must exist before the handler is a prerequisite (`auditIntent`): its refusal or error stops the handler and its time counts against the work deadline. A record that must exist after the work is the required success hook with its own `hookMs`; a record allowed to be lost is telemetry.

#### Event-turn work

`input` and `atActivation` run in the same call stack as the adapter's event delivery, before anything awaits. `input` is needed everywhere because it copies the event's values before anything awaits. `atActivation` is narrower: whether work must run in the event turn depends on the API. In the playback application `prepare()` is documented as called synchronously inside the user's activation so audio unlocks. Opening a window, requesting a permission and starting audio each have their own rules, and browser activation is limited by time and consumption rather than lost mechanically at the first `await`, so the contract states no portable activation property. `atActivation` is for work its author knows an API requires in the event's own stack; `before` promises nothing about activation, and there is no `requiresActivation` flag. `atActivation` is synchronous by type and rule: the callback receives a scope with `own` and no `acquire`, a callback whose type shows a thenable is a compile error (N16, N17, N18), and a runtime thenable or throw ends the invocation as `activation-error`. Anything taken into the scope with `scope.own` is released by the runtime, and a token owned after the invocation ended is released at once and `own` throws.

A definition exposes `eventTurn`, the phase names it uses, but not which environment each callback was written for. The adapter must run those callbacks in the event's own call stack, in the environment where the author wrote them, never late. On Lynx, ordinary `bindtap` delivery, `input` extraction and asynchronous prerequisites run on the background runtime and no function reference crosses between main thread and background, so under the proposed control both phases run in the background event stack. Not yet defined: how a definition records where its callbacks were written so `bindAction` can reject a mismatch and name the phase (candidates: a build-time tag from the compiler's directive handling, or an explicit author declaration; see [Open decisions](#open-decisions)). Until then "reject at bind time" is a requirement without a mechanism.

#### Handler and server calls

A local handler may return a value or promise; a synchronous throw and a rejection are both `handler-error`; it receives the invocation signal and should pass it to cancellable work. A server handler also receives `call(name, args)`, with transport options built by the runtime: the invocation signal and the time left in the work deadline as the timeout, which the handler cannot widen. `call` returns the upstream result unchanged, so a tool-level failure arrives as a result with `isError: true` and the handler decides what it means; the pinned `callServerTool` throws for timeouts, lost connections and host rejections, all arriving as `handler-error` with the server effect unknown. The `App.callServerTool` timeout covers one call, not the whole invocation. Aborting the signal ends the client's wait and passes cancellation into the request options but does not show the host forwarded it or the server stopped: a server action canceled after its request was sent reports `canceled` with the server effect unknown, and its canceled hook must be written that way. Local prerequisites and aborts prove neither server authorization nor remote cancellation.

#### Bounds: the work deadline and the hook budget

Two limits exist, each covering one thing; neither is a maximum for the whole invocation and no third universal timer is proposed.

- The **work deadline**, `deadlineMs`, starts when the activation prefix finishes and the first prerequisite is about to run, and covers every prerequisite and the handler, stopping at the first of handler settlement or an earlier decision. On expiry the runtime aborts the signal and decides `failed(timeout)` without waiting for a handler that ignores the signal (a late result is a late settlement). A timeout during prerequisites is a prerequisite-stage failure and the handler never started; audit that must precede the handler is prerequisite work and shares the deadline. It does not cover required success work. The timer is armed only when the runtime waits on a promise.
- The **hook budget**, `hookMs`, is a separate timer for each step after the handler settles: required `onSuccess`, the outcome hook, each release and `onFinally`. An overrunning step has its signal aborted, the runtime stops waiting and records a `budget-exceeded` diagnostic; for `onSuccess` the overrun is instead `failed(success-hook-timeout)` with the result.

| Phase | Steps | Longest (event loop permitting) |
| --- | --- | --- |
| `running` | Activation prefix, prerequisites, handler, required `onSuccess` | `deadlineMs + hookMs` from the start of the work timer (after the synchronous prefix; prefix time is under no timer because a timer cannot interrupt synchronous code) |
| `settling` | Outcome hook, one release per owned token, `onFinally` | `hookMs × (owned tokens + 2)` |

**Resolution and validation.** Each setting resolves independently: per-action override, then application configuration on the owning SDK instance, then SDK default. Omitting a setting inherits it and does not disable its timer. Local and server actions both receive resolved budgets.

| Setting | SDK product default | Coverage |
| --- | --- | --- |
| `deadlineMs` | `30_000` ms | Prerequisites plus handler, after the synchronous prefix; progress cannot reset or extend it |
| `hookMs` | `5_000` ms | Each awaited hook and each bounded cleanup or release step separately, including late scope-resource release |

Example: an instance configured with `deadlineMs: 45_000` and an action overriding only `hookMs: 2_000` resolves to 45,000 ms work and 2,000 ms per step; with no instance setting, 30,000 ms and 2,000 ms; a separate SDK instance keeps its own values. Inputs are validated when supplied, before any activation or effect, and explicitly invalid values are rejected even when another layer would override them: zero, negative, `NaN`, either infinity and non-numbers are errors, never an instruction to fall back or disable a bound, and TypeScript's `number` does not replace runtime validation. Resolved settings are stable for an invocation. These are documented product defaults, not measured guarantees; measurements may inform tuning without blocking initial defaults. The MCP TypeScript SDK documents a [60,000 ms request default](https://ts.sdk.modelcontextprotocol.io/v2/api/index/@modelcontextprotocol/client/#default_request_timeout_msec) (checked 2026-10-19); that transport interval differs from saga a2ui's prerequisites-plus-handler interval and does not establish saga a2ui's values.

The default profile does **not** promise a 35-second maximum for the whole invocation: required success work and cleanup keep separate per-step budgets, and host, gateway, server-request, resource and security clocks stay independent. A longer override cannot make another owner wait longer, and `call` cannot widen the remaining work budget or a narrower transport limit. For work that cannot fit the available request lifetime an application may use an existing background operation and later retrieve its outcome; no background-job framework or automatic retry is added. The invocation settles when `onFinally` settles or its budget expires; nothing in an application hook has to clear a timer, controller or pending flag, and a never-settling hook cannot extend `settling` past its budget. JavaScript cannot preempt running code, so a hook ignoring its signal keeps running after the runtime stopped waiting and may still write, and a synchronous callback blocking the event loop prevents every timer from firing, so the bounds hold only while the loop turns.

#### Hooks and cleanup

Hooks perform application work; they are not observers.

| Hook | Runs when | Phase | Awaited | Exception or overrun |
| --- | --- | --- | --- | --- |
| `onSuccess` | The handler returned before cancellation or the deadline and the invocation is not obsolete | `running` | Yes, within `hookMs` | Decides `failed` in `running` with kind `success-hook-error` or `success-hook-timeout`, carrying the result; `onFailure` follows |
| `onFailure` | A failed decision at any stage, unless obsolete | `settling` | Yes, within `hookMs` | Recorded as a cleanup diagnostic; outcome unchanged |
| `onCanceled` | A canceled decision at any stage | `settling` | Yes, within `hookMs` | Recorded as a cleanup diagnostic; outcome stays canceled |
| `onFinally` | Always, last, once | `settling` | Yes, within `hookMs` | Reported to the observer by step name only |

`onSuccess` is part of the outcome because it does required work (recording a result, updating a view the user depends on); if it fails the invocation did not succeed. The other three are responses and reporting, and their failures never rewrite how the invocation ended. The outcome is the single decision delivered unchanged to every hook; the diagnostics are a list the runtime appends to during cleanup (outcome-hook failures, overruns, release failures, obsolescence), which `onFinally` receives as `outcome` and `cleanupErrors`. `onFinally`'s own failure has no later hook, so the observer sees the step name and the application sees nothing unless it catches inside its hook; whether that is enough is an open decision. All hook signals abort when their budget expires; `onSuccess` and `onFailure` signals also abort on obsolescence, while `onCanceled` and `onFinally` do not, because they exist to answer it. An aborted signal only asks a hook to stop: a hook that awaited calls its own `current()` before a presentation write, and that cooperative check authorizes the write.

#### Freshness: three questions that look alike

- *Has the outcome been decided?* `scope.active`: true from invocation start until the outcome is decided; handlers and prerequisites use it to stop work. It is false while `onFailure` runs, so it cannot authorize that hook's write.
- *Has this work been asked to stop?* The `signal`. An unaborted signal says nothing about a subject that changed unobserved.
- *May this callback still change what this instance shows?* The callback's own `current()`, a separate predicate for every prerequisite, the handler and every hook, true only while all hold, read afresh each call: (1) **this callback is still eligible**: eligibility starts when the runtime starts the callback and ends permanently at the first of: the callback finishes (a synchronous callback returns or throws; an asynchronous callback's Promise settles, and merely returning a pending Promise does not end it), its budget expires (work deadline for a prerequisite or handler, `hookMs` for a hook), or deadline, budget, cancellation or obsolescence makes the runtime stop waiting; it is the runtime's own bookkeeping, not `scope.active` and not supplied by an adapter; (2) the binding is not disposed and the invocation not replaced; (3) the adapter's liveness reader says the instance and installation are the live ones (`AdapterInstance` in the [companion](./action_binding.evidence.md#a-authoring-declarations); adapter plumbing, illustrative shape); (4) the binding's subject, if given, equals the one captured at activation.

Because eligibility is per callback, a failure hook started after the immutable failure decision has its own eligibility and can still present, while an ended, timed-out or superseded callback never regains permission merely because binding, instance and subject are unchanged. Callback-budget bookkeeping stays in the runtime, never an adapter. After any `await`, a callback calls its own `current()` immediately before its synchronous presentation write (as `archiveNote` does). Calling it is also a checkpoint, but only while eligible; if it finds a mismatch or vanished instance the runtime applies the [outcome rule](#outcome-decision-and-obsolescence), and an ineligible callback gets `false` and changes nothing, so a late callback cannot cancel a newer invocation. Two cases a future runtime test must enforce, with binding, instance, installation and subject unchanged in both:

| Case | What happened | The late callback's `current()` | The callback the runtime awaits |
| --- | --- | --- | --- |
| Late `onSuccess` | `recordArchived` ignores abort and outlasts `hookMs`; the runtime decides `failed(success-hook-timeout)` and starts `onFailure`, which presents; the old record resolves | False for good | The running `onFailure` has its own eligibility and may present |
| Late handler, `onFailure` or escaped closure | The deadline expired and the handler ignores abort; or `onFailure` outlasted `hookMs`; or a finished callback scheduled `setTimeout(() => { if (current()) show(); })` | False for good; the late handler result is dropped and a later activation's presentation is not overwritten | None, or the running `onFailure` |

The check is cooperative: aborting does not roll back a write a late callback already started, and a callback that never calls `current()` is not suppressed.

#### The runtime and adapter seam

Adapters supply liveness and source notifications; the runtime supplies callback eligibility, decides outcomes and owns every timer. All members are internal and none an authoring method; the handle's `bindAction` returns a view hiding the runtime-facing ones.

| Member | Meaning | Supplied by |
| --- | --- | --- |
| `isLive()` | Is this still the instance that was bound, under the current host or model? A fresh pull each call, never a cached boolean | Renderer adapter |
| Installation epoch | Stamped on each event when admitted; an event under another epoch is ignored as `stale-installation` | Renderer adapter |
| `subject` | The application's optional reader for the item now shown | Application, via `bindAction` options |
| `watchScope(revalidate)` (optional) | Subscribes to changes the adapter can observe and calls `revalidate` after each; returns the unsubscribe | Renderer adapter |
| `detach()` | Removes this binding's own installation; a no-op when the slot holds a newer one | Renderer adapter |
| `deliver(event)` | Synchronous entry for an admitted event: runs `input` in the caller's stack and applies the busy policy (Lit and React call it `activate` on what `createBinding` returns) | Runtime |
| `recheck()` | Re-reads `subject()` and liveness now and applies the outcome rule | Runtime |

- **An incoming activation first revalidates the active invocation, then applies the busy policy.** Otherwise a press on B can be dropped as "busy" because of A's obsolete invocation, which would never end its presentation. Revalidation applies the outcome rule to A (an undecided A is canceled; an A whose failure is decided stays `failed` with its remaining presentation obsolete) and does not replace the policy: if A's bounded cleanup is still pending, `ignore` still drops B until A settles and `replace` starts B beside that cleanup.
- **Wake-ups are optional and invocation-owned.** While an invocation is not idle the runtime may subscribe through `watchScope`; each `revalidate` requests the same recheck any checkpoint performs and never a different outcome; the runtime unsubscribes when the invocation settles, is replaced or disposed, and an idle binding holds no subscription.
- **Checkpoints read liveness and subject** before each prerequisite, when the handler's result is observed, before `onSuccess` and `onFailure` start, at the busy decision and on every `current()` call, applying the outcome rule. A checkpoint finding the instance not live treats it as disposal, because the adapter's own retirement may not have run yet.
- **An adapter's own observation is separate.** It may observe its instance or key while idle (for example to maintain tap-admission epochs); settlement ends the runtime's wake-up subscription and must not erase the adapter's identity history.

The lazy comparison has limits. Between checkpoints and `current()` calls nothing runs, so an unobserved mismatch changes nothing yet, and a pull reader alone is not a reactive notification: a stale invocation's pending state changes only when the runtime checks or the adapter asks it to recheck through a supported seam. It cannot see history: equal keys cannot detect an unobserved A, B, A, and no universal counter exists because one bumped on every data change would cancel invocations on edits that do not change which item is shown. An application can put a revision into the subject (`` `${id}:${revision}` ``), or a renderer can maintain an explicitly qualified observed-key epoch (the Lynx proposal does); callback observation is not proof that a native runtime delivers every intermediate change, so that route stays conditional on evidence. When the key is the item's semantic identity, an invocation for A presenting on A again is correct. Separately, a queued event must not reach a current binding with props captured under an earlier installation: the adapter stamps the epoch, the binding admits only the current one, and matching subject strings are not enough. A control may disable itself while busy, but an adapter cannot replace the busy policy with unconditional refusal.

#### Resource ownership and handoff

A resource is anything an invocation acquires that someone must give back (a lock, a subscription, a running player). The runtime cannot make arbitrary cleanup safe, so the work is divided. It does not promise safety for a callback closing over shared state, and it does not release every resource at the end of the attempt, since that would stop a successfully started player.

**What the application's resource owner provides.** The scope releases a *token*, an application-defined value identifying one acquisition. The owner must satisfy:

1. The token identifies one acquisition, and `release(token)` and any token-scoped `end(token)` affect only that acquisition.
2. Release and end are idempotent and a no-op for a token the owner has superseded or already ended. A release calling a shared object's whole-object `stop()` without testing which acquisition is current does not satisfy this (the stale attempt's release would stop the newer attempt's audio). A guard comparing the exact lease with the owner's current lease immediately before `stop()` does, and a generation counter in the owner is one way to build it. The test must live where the stop is reached; a freshness check on the invocation in front of a callback that can still reach the shared player does not provide it.
3. Acquiring a new token from a single-resource owner supersedes the previous one (the owner's policy, at acquire time).
4. Stopping everything the owner holds is a separate owner operation, called from the owner's teardown and never from an invocation; saga a2ui does not call it on binding disposal or subject change.

Playback is the motivating case: its `AudioPlayer` has a whole-player `stop()`, and its controller calls it when a start settles after its attempt was retired ([`playback-view.ts` lines 257–271](https://github.com/MachineWisdomAI/saga-a2ui/blob/c3eecaad89fcefc540ee7816a8b41731cb65e9d0/apps/lit-host/src/playback/playback-view.ts#L257-L271)). That stale stop is a source-inspection candidate, and the real-player ordering is left to verification. The player's own `start` guards decoded audio by context identity ([`web-audio-player.ts` lines 79–94](https://github.com/MachineWisdomAI/saga-a2ui/blob/c3eecaad89fcefc540ee7816a8b41731cb65e9d0/apps/lit-host/src/playback/web-audio-player.ts#L79-L94)), the kind of identity check an owner-scoped token generalizes.

**What the scope provides.** `scope.own(token, release)` takes responsibility for a token the caller already holds, synchronously; `scope.acquire(acquire, release)` awaits an acquisition and then owns its result, available after the event turn. Both return a `Held`. If the invocation already ended, the token is released at once and the call throws or rejects, so a late handler stops there. At the end the runtime releases every token it still owns, in reverse order, each within `hookMs`, after the outcome hook and before `onFinally`; `release` receives the token and a context whose `signal` aborts when that step's budget expires. `held.transfer(adopt)` moves responsibility to a longer-lived owner: it calls `adopt(token)` synchronously (a thenable-typed callback is a compile error, N20) and returns true if `adopt` returned a non-thenable and the invocation was still active; false, adopting nothing, if the invocation had ended (the runtime has released or will release the token); if `adopt` throws, ownership stays with the scope; if it returns a thenable the types could not see, `transfer` throws a `TypeError`, ownership stays with the scope and the runtime attaches a rejection handler whose later rejection reaches the observer as a `cleanup-error` with step `adopt`. The work such a callback started cannot be recalled, which is why the owner's `end(token)` must be idempotent. `transfer` never reports a completed transfer for asynchronous adoption. Transfer is how a resource survives a successful start:

```ts
export const play = Action.local<ButtonActivation>('play')
  .atActivation(({ scope }) => scope.own(playerOwner.begin(), (lease) => playerOwner.end(lease)))
  .before(requireSession)
  .run(async ({ activation, provided, signal }) => {
    const bytes = await fetchMedia(provided.session.userKey, signal);
    const started = await playerOwner.start(activation.token, bytes, signal);
    // Not started: the scope still owns the lease and releases it. Started: hand it to the owner with no await in between.
    if (started === 'blocked') return { state: 'gesture-needed' } as const;
    return activation.transfer((lease) => playerOwner.keep(lease))
      ? ({ state: 'playing', lease: activation.token } as const)
      : ({ state: 'gesture-needed' } as const);
  })
  .limits({ deadlineMs: 20_000, hookMs: 1_000 })
  .onSuccess(({ result }) => (result.state === 'playing' ? showPlaying() : showGestureNeeded()))
  // Every cancellation stage carries the activation token. After a transfer the owner holds the lease, so
  // end exactly this lease, idempotently. Before a transfer the scope releases it too, which is a harmless repeat.
  .onCanceled(({ activation }) => playerOwner.end(activation.token))
  .onFailure((context) => {
    if (context.stage === 'input') return showPlaybackFailed();
    if (context.stage === 'running') {
      const { failure } = context;
      if (failure.kind === 'success-hook-error' || failure.kind === 'success-hook-timeout') {
        // Chosen policy: only a result that records a started, transferred lease stays owner-held.
        if (failure.result.state === 'playing') return showPlayingButViewFailed();
        // A blocked start never transferred the lease. Nothing is playing; the scope still releases it.
      }
    }
    // Every other failure ends exactly this lease; a repeat of the scope's own release is harmless.
    playerOwner.end(context.activation.token);
    return showPlaybackFailed();
  })
  .build();
```

`PlayerOwner` (declared in the [companion](./action_binding.evidence.md#a-authoring-declarations)) has `begin()` (ends the previous lease's audio and prepares the player), `start(lease, …)` (rejects for a superseded lease), `keep(lease)` (marks the owner's long-lived claim), `end(lease)` (affects only that lease, idempotent) and `endCurrent()` (the owner's teardown). `begin()` runs in the event turn and `atActivation` hands the new lease to the scope with `own`, so a later failure releases it. The paths:

- *Pressed again before the first start finishes (`replace`).* The second `begin()` supersedes the first lease; the first invocation is canceled and its scope's `end(lease1)` is a no-op; the newer lease's audio is untouched.
- *Canceled or failed before transfer.* The scope still owns the lease; release runs after the outcome hook and `end` stops only that lease. A `blocked` start follows the same path.
- *Canceled after transfer, at any stage.* Transfer happens inside the async handler before the runtime observes the returned result, so cancellation can still be classified `running` while the owner holds the lease. Every canceled context carries the activation token and `onCanceled` ends exactly it, so cancellation in `prerequisites`, `running` or `completing` is covered without a whole-owner `endCurrent()` that could stop a newer lease.
- *Success hook fails after the player started.* The failure hook reads the attached result first; only a `playing` result records a start and transfer, and only that branch applies the chosen policy: audio keeps playing, the lease stays owner-held, the hook reports the view update failed. An application preferring silence adds `playerOwner.end(failure.result.lease)`; the policy is the author's.
- *Success hook fails after a blocked start.* The handler returned `gesture-needed` without a transfer and `showGestureNeeded` threw: `failed(success-hook-error)` with that result, nothing playing, the scope still owns the lease; the failure hook skips the keep-playing branch and ends exactly this lease. A gesture-needed result is never reported as playing.
- *Failed or timed out while running.* The failure hook ends exactly the activation token, covering a lease transferred just before the failure was decided.
- *Owner teardown and retained leases.* Binding disposal and subject change cancel an undecided invocation and the paths above end its lease; they never rewrite a decided outcome or run `onCanceled` for it, and they leave alone a lease the owner deliberately holds (after a transfer, and under the chosen policy after `failed(success-hook-error)` or `failed(success-hook-timeout)` with a `playing` result). Stopping a retained lease is the owner's teardown (`endCurrent()`), a separate application responsibility.

This is an application-owned mechanism, not an existing one; whether the real player's ordering lets a wrapper track the current lease without changing the player is open (see [Open decisions](#open-decisions)).

**Stale writes.** saga a2ui does not suppress arbitrary side effects: a handler that ignores its signal can still write after cancellation. The runtime gives guarantees it can keep: it never starts `onSuccess` for an invocation whose cancellation or deadline came first, never starts `onSuccess` or `onFailure` for one it knows is obsolete, discards a late handler result instead of delivering it as success, and supplies each callback's `current()`, which application code calls immediately before each synchronous write that follows an `await`. That check is reliable when it runs, permanently false for a callback the runtime stopped waiting for, and says nothing about what a callback does after it returns true. A write that cannot be conditioned on it must be idempotent or a prerequisite.

#### Telemetry

An observer receives, per phase, the action's label, opaque runtime-generated `bindingId` and `invocationId` (unique within the page session, derived from no input, so a collector can pair `started` with `finished` across concurrent bindings; `binding.id` carries the same identifier and no API maps one back to a binding), elapsed time, status, failure kind and the name of a failed cleanup step. An `ignored` event has a `bindingId` and a reason (`busy`, with a `busyInvocationId`, or `stale-installation`) and no `invocationId`. Events carry no parameters, provided values, results, error objects or component text, and `ObservedEvent` has no such fields (N9). The runtime calls the observer synchronously, never awaits it, catches a synchronous throw and attaches a rejection handler to a returned thenable, so neither alters the outcome or becomes unhandled; subscription listeners get the same treatment. The label is a diagnostic name the runtime never uses to find behavior. Telemetry is observational and cannot be a required record: durable audit is a prerequisite and required client work is a hook.

### Renderer proposals

The contract above is renderer-neutral. This section says where each part attaches in Lit, React and Lynx, what each adapter adds and where they differ. This is the approved design. The Lit and React attachments are implemented (ACT1, ACT2) and a Lynx Web qualification fixture exists (ACT3); a production Lynx adapter is not implemented. [Status](#status) owns the outcomes and limits, and the source and declaration checks cited below do not by themselves show that an adapter built on them works. The complete printed declarations, schema, element, boundary, control and application sketches are in [companion section E](./action_binding.evidence.md#e-printed-renderer-proposals-moved-from-the-blueprint); this section keeps the reasoning.

The Lit and React proposals share one design: an instance host publishes an `InstanceHandle` per rendered instance, discovered through `watchById`. That is a Lit and React proposal, not a requirement on every renderer; Lynx obtains its handle differently. All three share the builder, typed handle attachment, busy policy, optional subject, `state`, `subscribe`, `dispose` and the seam above, and differ in how an instance's data reaches the event and in which thread or event path admits the activation.

#### The trace every renderer completes

Four identities stay apart because renderers conflate them: the **protocol component ID** (the layout string; a template renders it once per item and a parent can reference it more than once); the **instance** (one rendered place for that ID and data path; upstream says a template item's identifier "names a list position, not a data item" ([`component-node.d.ts`](https://unpkg.com/@a2ui/web_core@0.13.0/src/resolution/component-node.d.ts)), so structural identity is never business identity, which comes from data the application reads); the **framework lifetime** (how long Lit, React or ReactLynx keeps what draws the instance); and the **physical element** (the DOM node or native view pressed: Lit reuses one element across components, a React function component has no application-accessible instance object, and a Lynx `<list>` reuses native nodes while logical instances persist).

Every renderer: (1) the layout of a directly attached control names its ID and type and carries no action, and upstream actions on unrelated controls keep their behavior; (2) the renderer opens an instance from the component's model and data path and makes a handle available (the instance host in Lit and React, the catalog component's setup in Lynx); (3) application code selects handles at setup (`getById` for exactly one instance, `watchById` for every present and future one); (4) `handle.bindAction(event, definition, options?)` creates a binding with its own state and the adapter installs the callable in the instance's slot for that event; (5) the control's activating event calls `activate` on the same instance; (6) `activate` calls the installed callable with an event the adapter builds from the instance's current data, with no ID or name lookup in between. The host may index live instances by ID for setup, and nobody consults that index at press time.

#### What each renderer must supply

1. **The handle is an object with identity.** The ID selects a handle at setup and never routes an event. Upstream puts only `componentModel.id` in a dispatched action's `sourceComponentId`, and the same ID can render several times ([`component-context.js`](https://unpkg.com/@a2ui/web_core@0.13.0/src/resolution/component-context.js), [`surface-model.js`](https://unpkg.com/@a2ui/web_core@0.13.0/src/state/surface-model.js)); a listener filtering on that field is ID-based routing.
2. **Selection cardinality is explicit.** `getById` fails for no instance and for several; `watchById` handles instances that do not exist yet (normal at startup).
3. **Events are typed per kind and carry instance data**, valid only during delivery. The shape is the adapter's: Lit and React offer a path reader, Lynx a property reader; neither a DOM `Event` nor one reader shape is required.
4. **A handle for a template instance exposes a live data reader** so the application can write a `subject` without reaching into renderer internals (`dataPath` and `read(path)` in Lit and React; `read(prop)` and `itemKey(prop)` in Lynx). Fixed controls with unique IDs can stay simpler.
5. **The instance supplies a freshness pull as well as a signal.** An unaborted signal proves nothing about whether a continuation still belongs to its instance; `isLive()` re-reads the renderer's own state.
6. **Bindings are scoped and owned,** with a known owner and no silent replacement.
7. **The busy decision is a checkpoint** and the runtime accepts adapter wake-ups while an invocation is not idle.
8. **Attachability is opt-in per catalog entry.** Only an element or view written to open an instance is attachable; arbitrary third-party components are not promised an attach point and the basic upstream `Button` is not wrapped.
9. **No browser activation is promised.** An adapter runs the callable synchronously from the event handler and nothing more.
10. **`AbortSignal` must exist in every execution environment.** Whether it exists in the Lynx background runtime is unresolved; if not, a minimal one-shot substitute is needed.

#### Instance data and the host (Lit and React)

The Lit and React proposals extend the generic event and handle with an `InstanceEvent` (`dataPath`, the native event, and `read(path)` against this instance's data scope, answering only during delivery) and an `InstanceHandle` (`dataPath`, and `read(path)`, `undefined` once the instance is not live), and supply a stronger discovery view, `InstanceView`, assignable to the general `SurfaceView`, so an action written for the general view still attaches through it. A fixed control needs no subject. A row control copies the item's identity into the parameters when pressed and supplies a `subject` so the runtime can tell when the position starts showing another item: the archive workflow attaches with this renderer's projection `requireNoteId(event.read('id'))` and `subject: () => handle.read('id')`. The projection validates the identifier as a nonempty string so an absent value fails at extraction and never becomes the text `"undefined"`. `input` copies the identifier so a later `await` cannot turn the captured position back into whichever item occupies it now; `handle.read('id')` returns `undefined` once the instance retired, which differs from any captured key, so a retired position also reads as a subject change. Omitting `subject` on a control inside a template forfeits all of this (right for a fixed control, wrong for a row). Warning in development when a scoped handle binds without one is an optional developer-experience choice, not a condition of this design.

The host publishing handles has three members: `register` runs application setup against a view owned by that one registration, `open` is called by a renderer element for each instance, and `close` is terminal; `createBinding` is the declared seam to the shared runtime (the runtime's `deliver`). The slot holding the installed callable stores an installation token and `detach` compares it before deleting, so a late disposal of an old binding cannot remove a newer one. **How setup is owned:** `watchById` is discovery only, so bindings and state subscriptions created during setup need an owner. `register(setup)` is internal to the adapters: it records the discovery subscriptions its `watchById` calls made and every binding made through the handles it delivered, and ending it stops all of that and disposes all of those bindings; the instance also retires its own bindings at the end of its lifetime, so each binding has two idempotent paths to disposal. If the setup function throws, the registration ends and the error propagates, leaving nothing half attached. If one `watchById` callback throws, the registration disposes only the bindings that callback made, reports to the host's required `onSetupError` sink and leaves every other binding in place. After `close()` the host is terminal: `open` returns an already retired instance and `register` runs nothing.

#### Same-position replacement and work in flight

Lit and React both keep one instance per structural position. Lit's `bindsSameComponent` compares component model, data model and data path ([`a2ui-lit-element.js` lines 285–298](https://unpkg.com/@a2ui/web_core@0.13.0/src/universal/a2ui-lit-element.js)); the React resolver reuses a node when component ID, data path, repeat ordinal (upstream `occurrence`), type and model identity match ([`node-resolver.ts` lines 475–510](https://github.com/a2ui-project/a2ui/blob/45633b97636daf89bafb43fa7db23e3cd916461d/typescript/core/web_core/src/resolution/node-resolver.ts#L475-L510)). Neither compares the business item at the path, so when position 0 changes from item A to B the instance, element or node, binding and callable all survive.

An *activation* reads current data (the event carries `read`, evaluated against the instance's scope at that moment; the DOM click listener calls `activate` synchronously so no event waits holding values from an earlier render). A *continuation* is an invocation that started on A and is still running when the position shows B; it holds A's copied parameters, correct for the work it was asked to do, and must not act as though it still belongs to the position, which the subject check expresses.

1. The application replaces row 0's data. `DataModel.subscribe` calls its listener synchronously inside `set` (observed in a Node probe of `@a2ui/web_core` 0.13.0), and the adapter's listener queues a microtask that calls `revalidate`.
2. A microtask runs when the call stack that made the change empties, before the browser takes the next input task, so a press should not arrive between the change and the check (a Lit lifecycle test is the intended check; see [Renderer conditions](#renderer-conditions)). At that checkpoint the runtime reads `subject()` and applies the outcome rule: with a reader and an undecided invocation, finding B where it captured A cancels with `subject-changed` and the binding stays installed; if failure was already decided and `onFailure` is running, the outcome stays `failed` and that hook's presentation becomes obsolete; a binding without a reader sees no change.
3. While a canceled invocation's `onCanceled`, releases and `onFinally` run, each within `hookMs`, its cleanup is the only thing pending and the callable stays installed.
4. Presentation hooks do not start for the obsolete invocation; work that must happen anyway belongs in `onCanceled`, a release or `onFinally`, and the application's record that row A is being archived is keyed by the copied identifier, not position.
5. A press on B follows the busy policy after revalidation: under `ignore` it is dropped while A's cleanup is pending and accepted once A settled; under `replace` it starts at once beside A's cleanup. A control that should look idle for B while A's cleanup finishes derives its state from application data keyed by item, not `binding.state`.

The wake-up covers a `subject` reader depending on data under the instance's own scope (the row's path or an ancestor such as `/rows`, since `DataModel.subscribe` notifies the path, ancestors and descendants). A reader depending on something else (application state outside the data model) gets no wake-up; the check happens at the next checkpoint, `current()` call or busy decision, and a spinner driven by `binding.state` can keep showing until one runs, because `resolveDynamicValue` evaluates once and creates no subscription. *A, then B, then A:* a queued revalidation reads the value when its checkpoint runs, so two `set` calls in one call stack both read A and nothing cancels; when a checkpoint reads B the invocation is canceled then and a later return to A cannot revive it; a single `set` moving a position from A to a new object with A's key is not an identity change. A round trip between checkpoints needs an application generation in the subject, and these adapters add no version counter. *Detaching with work in flight:* `dispose()` cancels an undecided invocation with cause `disposed`, leaves a decided outcome, detaches the callable and leaves other bindings untouched, and a new `bindAction` for the same event on the same live handle then succeeds.

#### Lit (`@a2ui/lit` and `@a2ui/web_core` 0.13.0)

Full source reading, schema, element, host and composition code: [companion E.3](./action_binding.evidence.md#e3-lit-a2uilit-and-a2uiweb_core-0130). The requirements:

- **No `action`, one owner per press.** The basic upstream `Button` cannot take an ID-only layout (its schema requires `action`, and a placeholder would invent the handler name this design forbids and make the upstream closure dispatch a server event from a control meant to be local). The proposal is an application-owned catalog entry, `ActionButton`, whose schema has no `action`; its Lit element is an optional export of `@saga-a2ui/lit`, and the schema lives in its own renderer-independent module also imported by the React entry. Its single click handler is the only activation site, so application code must not add its own `click` listener. Upstream `event` and `functionCall` actions on components that do not open an instance are untouched. A catalog entry that keeps an upstream `action` beside the attach point keeps one owner per press (bound invocation when a binding exists, else `props.action?.()`, never both), and a conformance test counts effects. Reusing more upstream code (subclassing `A2uiBasicButtonElement`) needs a typed-controller interop assertion and makes an unbound press indistinguishable from a bound one; the recommended path duplicates about twenty lines of markup. Which duplication to accept is a review choice, and either covers only entries saga a2ui or the application writes.
- **Instance identity.** The instance belongs to an element together with the component model and data path it shows, not to the element alone (the directive reuses elements) and not to the `context` object (parents replace it every render). Under `a2ui-surface` the element has no `node`, so the supported seam is the overridable `createController()`, which learns that the element now shows a different component or path without copying upstream's private `bindsSameComponent` check; the element never reads the public `controller` getter there. `watchById` is the supported path because rendering happens after the initial input is ingested.
- **Lifetime events.** A parent re-render, same-ID same-type property change or data-context change at the same position keeps the instance (only the subject check protects work in flight). A same-ID type or catalog change, a data-path change, a list shrink, surface deletion and disconnect retire the instance and dispose its bindings; a reconnect opens a new instance and the application's callback fires again, so moving an element in the DOM cancels an in-flight invocation (deferring retirement would add machinery no measured case justifies). Each template item has its own element and `dataPath`, so `getById` fails with more than one row. Two identical references with the same ID and path under one parent have indistinguishable contexts at 0.13.0 and should be avoided. A custom descendant that supplies `element.node` needs a node-aware element (reopen on a changed node, retire through `node.addCleanup`, check `node.disposed` first); the default path never reaches that.
- **Host ownership.** `createA2uiAppElement` already owns the session, surface and their disposal; attachment adds one optional dependency and one host per presented surface, created in `onSurfaceCreated` and given its setup before `this.surface` is assigned (so every `watchById` registers before any element opens an instance; a throwing setup closes the host and the existing fallback renders). The terminal `close()` runs on `onSurfaceDeleted`, on disconnect (before `session.dispose()`) and on setup failure; a later `createSurface` with the same ID gets a fresh host and a fresh `attach`, which must be safe to run once per surface instance. A retained weak-map entry cannot reopen anything. **Mount ownership** cannot be keyed by `SurfaceModel` (two `<a2ui-surface>` mounts of one model share it): `hostOf` walks outward from the element through shadow roots and accepts only when the nearest surface element is the owner's own `#mount` and the owner's surface is the one the element holds, so a raw second mount stays unbound; an `ActionButton` in light DOM or slotted content is unsupported, and a runtime test must confirm the chain through nested catalog elements. `ActionButtonElement` cannot close over a per-session host (`defineElements` throws `ElementConflictError` for a tag bound to a different constructor), so it finds its host by DOM position. An unbound control renders but a press does nothing; whether it renders disabled is a presentation decision.
- **Freshness.** The signal is a push that aborts only at or after the next Lit update; `isLive()` is a pull over the registered model, element context, connection and host state, correct from the moment `removeComponent` or `SurfaceModel.dispose` runs, before any notification. The runtime's `current()` and checkpoints read it, so a running continuation finds the transition before a guarded write. Nothing suppresses an async callback that does not check.

#### React (`@a2ui/react`, source at commit `45633b97636daf89bafb43fa7db23e3cd916461d`)

Full source reading and the printed boundary, provider and application sketch: [companion E.4](./action_binding.evidence.md#e4-react-a2uireact-source-at-commit-45633b97636daf89bafb43fa7db23e3cd916461d). The requirements:

- **The instance is a committed boundary, not a function component.** React gives application code no object for a function component (no stable `this`; a render can re-run, be discarded before commit or mount twice), and nothing in the upstream view path publishes a handle. The instance is the committed lifetime of a boundary for one `ComponentNode`, delimited by a layout effect's setup and cleanup. A catalog entry supplies a node-aware `view` (an entry rendered through `render` instead gets no boundary and an inert button); the recipe wraps the entry `createComponentImplementation` builds and uses only exported React-renderer API and the shared schema module.
- **Commit-time ownership.** The layout effect is the only writer of the ref saying which instance is committed, and `isLive` reads that ref, set before `host.open` so a `watchById` callback binding inside `open` already sees a live instance. When a new host or node renders, the old pair's cleanup retires its instance and disposes its bindings and the new pair's setup opens another, in the same commit and before a passive effect. A running invocation therefore sees `isLive()` false as soon as the commit finishes, a press reaches only the committed entry, and a discarded render publishes nothing. Retirement also runs through `node.addCleanup` (synchronous at resolver disposal) and the host's `close()`; `retire` is idempotent so order does not matter. The documentation supports this timing; the tests that show the recipe behaves this way are pending.
- **Host and attachment ownership.** `InstanceHostProvider` creates the host in an effect, closes it in the cleanup and renders children only once a live host exists (Strict Mode's second setup creates another, so a reference retained to the first can no longer open an instance or register a setup); mount it once per surface view. The setup function must keep a stable identity per distinct definition (`useCallback`) because the registration is keyed to it. A change from definition A to B ends the registration, disposes every binding it made (an undecided invocation for A is canceled `disposed`) and binds every present instance with B within one effect flush, so the duplicate-attach rule never fires; an application not wanting A's in-flight work canceled keeps the definition's identity stable and passes changing values through what `input` copies. Two registrations binding the same instance and event make the second `bindAction` throw inside its callback, which the registration reports to `onSetupError` while leaving the first binding untouched.
- **Replacement and reuse.** A replaced node changes the `key`, so the old boundary unmounts and retires while the new opens (the unkeyed root re-runs the layout effect instead); upstream gives a replaced node a new `id`, including on sibling reorder. The resolver's reuse predicate omits the business item, so React has Lit's same-position behavior and subject rule. Each `A2uiSurface` mount builds its own resolver, so views under separate providers have separate scopes; two views under one provider are unsupported as one scope.
- **Version.** saga a2ui pins 0.13.0; the inspected source is the commit that moves React, Lit and core to 0.14.0. Published 0.13.0 exposes the same type names and the boundary type-checks against it, but whether its runtime renders `view` and reuses nodes as the commit does is unknown. The React lifecycle tests against published 0.13.0 decide between running the recipe on 0.13.0 and adopting 0.14.0 (a dependency change outside this Blueprint); if behavior differs, the commit-based claims need correcting before implementation cites them. This Blueprint changes no dependency.

#### Lynx (`@lynx-js/genui` 0.7.0)

Source facts, code sketches and the freshness mechanism: [companion E.5](./action_binding.evidence.md#e5-lynx-lynx-jsgenui-070) and [section D](./action_binding.evidence.md#d-lynx-freshness-and-admission-mechanism). No `@saga-a2ui/lynx` package exists and none is planned (the owner retired the Lynx delivery chain on 2026-10-19), no host is claimed to support Lynx, and this section supports design and source feasibility only. The renderer examined is `@lynx-js/genui` 0.7.0 at lynx-stack [`bb2f9ba92c8fe936be39b882047ab94aae58809f`](https://github.com/lynx-family/lynx-stack/commit/bb2f9ba92c8fe936be39b882047ab94aae58809f).

- **Identity.** A binding belongs to a logical component instance (one mounted ReactLynx component and its hook state), not to the component ID (a template renders one ID many times; clones get distinct `componentId` values with a shared `sourceComponentId`) and not to the physical node (`<list>` reuses native nodes while logical instances persist, so the binding survives scrolling). An *installation* is one open-to-close run of the adapter's slot inside a logical instance.
- **What the pinned renderer does** (the facts that shape the design): a custom control cannot reach the processor instance, so it cannot call `resolveDynamicValue`; props are resolved before a component renders and resolution executes function calls anywhere in them, including `action`, so an `action.functionCall` can run before the component receives props and more than once; the protocol `sendAction` discards its promise and cannot report completion; messages reach the processor through the `messageStore` prop in an effect, and replacing the store does not reset the processor; a data update writes the signal store before components re-expand; template clones are positional and a clone does not record its original's ID; the built-in `Button` requires a protocol `action` and `useChecks` counts an unrecognized condition as passing, so checks gate the interface and authorize nothing; a component update can replace a property's binding without changing the instance, and its resource is public.
- **The adapter supplies four things:** a `ControlActivation` event (component IDs, surface ID and `read(prop)`, the named property of the tapped instance as the data model holds it at the call, valid only while extraction runs); a `LynxInstanceHandle` (common handle plus `sourceComponentId`, a live `read(prop)` and `itemKey(prop)`, all background only); a reference-stable snapshot for rendering (`{ installation, binding, state, keyProp, epoch }`, where `binding` is a direct reference to the exact attached binding and `epoch` is the observed-key epoch, separate from the installation); and the runtime entry (`deliver(event)`, `recheck()`, with the slot's `activate(token)` as admission in front of `deliver`).
- **One generic control.** A single `ActionButton` component type serves every instance. Application setup code sees each mounted instance once after commit and binds an already constructed definition to it; after setup the control holds a direct reference to the binding and a tap calls it, with nothing looked up by name at activation and no type per action. Nothing is bound on first commit (`bindtap` is undefined until the mount effect has run setup and published a bound snapshot), an uncommitted render constructs only an inert slot, an unrecognized instance binds nothing and refuses every tap, `disableWhileBusy` is presentation only, and the item identifier is copied by `input` at the tap from the data model as it stands then. Business identity is data the application controls, never inferred from a component ID or path.
- **Bound-control action policy.** Because props resolve first, a wrapper cannot stop an agent-supplied `action` on a bound control from executing function calls. The proposed enforcement point is the message buffer: the adapter supplies the `MessageStore` that `<A2UI>` reads (`createAdmittingMessageStore`), which rejects whole, and reports with the component ID, any message putting an `action` key (either shape) on a bound control, so no protocol action reaches the processor for that control (an unbound `Button` keeps its path; removing the field and continuing is the alternative under open decisions). It stamps an adapter-set `sagaSourceId` on the admitted copy, because a clone's original ID is otherwise only an upstream naming convention (a plain string property survives the inspected path by source reading, runtime confirmation pending). It does not make rendering free of application code: other properties and `checks[].condition` can still contain function calls, and restricting those to pure expressions is a restriction on the application and its catalog functions enforced by review or a separate validator; this Blueprint proposes no change to GenUI. The adapter's live reader executes no function calls (literals and plain bindings only; `undefined` otherwise), refusal comes from the validating projection and `itemKey` returning `undefined` for an unreadable key, and an application building its own renderer on the exported `MessageProcessor` bypasses `<A2UI>` and this guard.
- **Event ownership.** A tap runs only the control's own `bindtap`; it never calls the `sendAction` it receives, so `useAction`, `processor.dispatch` and `onAction` are not reached through this control and one tap makes at most one `deliver`. That is narrow (other catalog functions can still be triggered through other properties or checks). Composing with the upstream path as an awaited stage is not available because the renderer discards the promise behind its callback.
- **Freshness.** A logical instance can present a different item without remounting, so a binding keyed only on surface, ID and path would leave A's pending invocation attached to a component now displaying B. The adapter supplies: a *live subject reader* (`itemKey(prop)` reads the raw component the surface holds now, its plain `{ path }` binding resolved against the instance's data context path, and the signal for that path; a literal is read as itself; a function-call binding, any other shape or an empty path is unreadable and the change to `undefined` counts as a change; after an item moves to a new path it reads the old path until `sync` runs and cancels conservatively); an *observed-key epoch* (the reader returns `"<epoch>:<key>"`, the epoch increasing whenever the adapter's subscription observes a different value, so an observed A, B, A changes the token; a change never visible to the subscription, such as B set and reverted in one batched update, is not claimed detected, and an application needing more joins a revision into the key; if delivery on a Lynx background runtime is coalesced or late the design degrades to the runtime's own checkpoint reader, and only an unobserved return to the same key goes undetected); a *subscription that follows the key's actual source* (recorded by signal identity and reconciled when setup asks for the key, from the commit effect `sync` and from the public component Resource's subscription, rejecting notifications from a retired signal); and *tap admission* (`activate(token)` checks, in order, that the installation is live and is the one the token captured, that the epoch has not moved since that render, that a binding is attached (`unbound` otherwise), that the token's binding is the attached one by direct reference (`stale` otherwise) and that the live key still equals the key the render showed; other inputs follow *current data*, read at the tap, and whoever needs the shown value in the contract binds a revision into the key). After a reorder A's request may still run on the server while row 0 shows B, so the server must tolerate a repeated request where that matters or the application should hold reorders while an action is pending.
- **Late completion and the unmount window.** A late result or error is dropped and a late resource handed to the scope is released. One window is unresolved: unmounting is detected by `close` in the effect cleanup, ReactLynx lifecycle hooks run asynchronously in the background, and between native removal and that cleanup `installation.live` and a hook's `current()` can still be true. Measuring the interval sizes the window and does not prevent a stale write inside it; closing it needs a supported logical-retirement seam earlier than effect cleanup (the sources name none) or the narrower support contract in open decision 4. A stale presentation write there is not assumed harmless.
- **Threads.** The component body, `tapToken`, `useChecks` and child lookup run on both runtimes (`tapToken` and the child lookup use only props and the published snapshot; `useChecks` can execute application functions in a check condition, so the body is pure only if the application's check expressions are). `useEffect` bodies (`open`, `sync`, `close`), `setup`, `handle.read`, `handle.itemKey`, `bindAction`, `reconcile`, the signal and resource subscriptions, the `bindtap` handler, `activate`, `deliver`, `input`, prerequisites, handlers, hooks, timers and network calls run in the background (ReactLynx has no `useLayoutEffect`; `setup` carries the `'background only'` directive); only imperative element operations such as `setStyleProperty` belong to the main thread. A render-time selector and a live reader are different functions that communicate through the published snapshot, never a shared function reference. Both event-turn phases run in the background event stack; a definition needing a main-thread phase cannot have a background function run there by reference, and the mechanism that would let `bindAction` reject such a definition does not exist yet (see [Event-turn work](#event-turn-work)). An optional `main-thread:bindtap` bridge over `runOnBackground` is sketched in the companion and uncompiled; the sources identify no operation needing it, the binding, installation, slot and token must never be captured by the main-thread function or cross threads, and three checks would qualify it (a build accepting `runOnBackground` over a function referencing the slot, a device run showing call order, and a named host API rejecting non-gesture calls).
- **Mount, session reset and failure.** The processor and surfaces live as long as one `<A2UI>` mount; a new session is a new mount, keyed by the application together with a fresh admitting store (one store per session, replaced only with the key; this adapter's own stricter rule because bound controls and the admission annotation assume one continuous history; `store.clear()` is not a session reset). A changed `key` closes every control, disposes its binding and cancels its invocation. The component type must stay stable (`createActionControl` called once at module scope, `catalogs` a module constant) or React remounts and disposes every binding. `activate` never throws into the renderer (a refused tap returns `'unbound'` or `'stale'`; a thrown `input` ends the invocation `invalid-input`). A setup exception leaves the instance unbound: the slot disposes what setup attached, drops the key watch it started, retires the handle, publishes the unbound snapshot, then calls `onSetupError`; cleanup is by identity so a later installation's valid binding is untouched.
- **Versions.** GenUI 0.7.0 depends on `@a2ui/web_core` at exactly 0.10.6 and ships its own `MessageProcessor`, resources and signal state (peers `@lynx-js/react >=0.121.0`, optional `@lynx-js/lynx-ui >=3.133.0`), while saga a2ui pins 0.13.0. In a scratch install both versions coexisted; `A2uiMessage` from each is assignable to the other by default, but under `exactOptionalPropertyTypes` the 0.13.0 type is not assignable to 0.10.6 (`createSurface.sendDataModel`). That is type-level only, and declared versions do not establish commit equivalence. Separately, `[actionButton, Button, Column, Text]` does not type-check under `strictFunctionTypes` because upstream built-ins declare narrower props than `ComponentType<GenericComponentProps>`, an observation about upstream's documented usage. This Blueprint upgrades neither dependency. Adopting GenUI means GenUI also interprets the protocol; whether `@saga-a2ui/lynx` wraps GenUI and accepts a second validation path or renders core-decoded values through its own catalog components is open (it changes where messages enter the admitting store, not where the binding attaches).

## Representative flow: archiving a note

This follows one non-playback action from layout to settlement on each renderer: the `archiveNoteWith` workflow from [Authoring](#authoring) with its session, confirmation and audit prerequisites, its `archive_note` request and its required `onSuccess` and `onFailure`. The layout renders an attachable control named `row-archive` once per note, so two notes give two instances with data scopes `/notes/0` and `/notes/1`. ## Failure and recovery

The decision rules for outcomes, cancellation, obsolescence and late settlement are in [Outcome decision and obsolescence](#outcome-decision-and-obsolescence). This section says what an application may report, who owns each failure path and what recovery the design does and does not provide.

### What each outcome says about the server effect

The runtime knows only how far the handler got, reported through stage and `failure.kind`, and an application derives its presentation from them, for a local effect as much as a server effect. Three states are distinguishable: known not to have started, known completed, unknown.

| Outcome | How far the handler got | What the application may say |
| --- | --- | --- |
| `invalid-input`, `activation-error` | Not started | No handler request was sent; `atActivation` may have had its own effects, so not a claim that nothing happened |
| `refused`, `prerequisite-error`, `timeout` during prerequisites, `canceled` during prerequisites | Not started | The handler's request was not sent; a prerequisite's own effects (an audit write, a session request) may have happened |
| `handler-error` | Threw | Unknown, unless the handler's own contract says otherwise (the example's tool-level `isError`); a transport failure, parse or other post-response error and an unreadable reply are unknown |
| `timeout` while running, `canceled` while running | Unsettled | Unknown; the request may have been applied and aborting does not recall it |
| `success-hook-error`, `success-hook-timeout`, `canceled` while completing | Returned | The handler completed; for a server action the effect may be reported done as far as the handler established it; only client work failed or was abandoned |
| `succeeded` | Returned and `onSuccess` completed | Done |

The server effect and the client's required work are separate facts. A prerequisite failure means no handler request was sent, not that nothing happened anywhere. A timeout or cancellation before any result says only that the client stopped waiting, and a stalled call produces an outcome distinct from a refusal so the application can stop presenting it as a sign-in problem.

### Error categories and safe presentation

The error contract distinguishes timeout, cancellation, authentication required, permission denied, transport or unavailable failures, and validation or application failures when the evidence supports them. Categories are extensible with an unknown or internal fallback; an unrecognized error is never guessed to be an authentication failure, and authentication required and permission denied are distinct only when the response or typed cause establishes it. They supplement the stage, primary outcome and `failure.kind` without rewriting a decided outcome or treating a tool `isError` result as transport success of the business operation. The original cause is preserved for programmatic inspection alongside any known result and stage; safe user-facing messages are a separate application choice (raw server messages, payloads, credentials and stack details are not displayed automatically; the observer's payload restrictions remain). A timeout or cancellation ends the wait and proves neither rollback nor that a remote write stopped. A known successful write followed by a hook timeout keeps that success and reports the client-step failure without inviting replay; a write with unknown outcome reports the uncertainty with no automatic retry or generic retry invitation. Frontend timeout categories assign no HTTP status: [RFC 9110 §15.5.9](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.9) describes 408 for an incomplete incoming request and [§15.6.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.5) 504 for a gateway waiting on an upstream server, and neither follows from an action timeout; STATE2's application HTTP mapping remains open.

### Recovery

Nothing says a generic retry is safe: only the "not started" rows leave the handler's request unsent, and a retry after any other row needs the application's knowledge of idempotency. The runtime does not retry. A completed server effect followed by failed client work is never replayed automatically, a prerequisite that passes locally is not authorization to repeat a request, and recovery is a new activation the user or application chooses, offered by a hook only for the states marked safe to describe.

### Failure paths owned by the adapters

- **Setup failure.** A throwing setup function leaves nothing half attached. In Lit and React the registration ends and the error propagates (or, for one `watchById` callback, only that callback's bindings are disposed and the error reaches `onSetupError`). In Lynx the slot disposes what setup attached, drops its key watch, retires the handle and publishes the unbound snapshot before reporting. Whether a later setup error should also clear the surface is a product choice, not something a test decides.
- **Host, surface and session end.** Closing the Lit host (surface deletion, disconnect or setup failure) retires every instance and ends every registration; the React provider's cleanup does the same for its subtree; a changed `key` on the Lynx `<A2UI>` mount closes every control. Bindings are disposed and undecided invocations canceled `disposed`, while a decided outcome stays.
- **Late or racing disposal.** Disposal detaches only the installation its own binding made and every retirement path is idempotent, so an old binding's late cleanup cannot remove a newer binding.
- **Native removal before cleanup (Lynx).** Between native removal and effect cleanup `current()` can still be true; the Blueprint claims no prevention of a stale presentation write there (see [Open decisions](#open-decisions)).
- **Teardown versus disposal at the bridge.** However a view ends (`dispose()`, a host teardown request or `pagehide`), `runToolResultView` stops delivery, calls the view's optional `onTeardown` once, then removes its listeners and closes the connection; on a teardown request it answers the host first. Binding teardown hangs off `onTeardown`, and each `ActionBinding.dispose()` must run there, because that is how the adapter retires its bindings. `onTeardown` must not call the connection's `dispose()` or close the connection; the runner does, and `dispose()` is idempotent. The two are different objects with the same method name.

## Verification outcomes

These are the conditions and expected results the design set; [Status](#status) records which slices ran their checks and what they do not show, and the design-time evidence is in [Evidence status](#evidence-status). A row is not a claim that it has its own recorded run. This section is a test matrix, not a second specification: each row names the trigger, expected result and boundary, and the rule it tests is defined once in [Execution semantics](#execution-semantics). Shared-runtime checks use fake timers, a fake clock and test doubles at the renderer and server seams and need no DOM. ### Renderer conditions

Each needs a real renderer; where a check ran renderer-free the text says so, and no result below has run in a browser or on a Lynx runtime. The outcome, cancellation and eligibility rows above apply to every renderer.

(2) A press starts one invocation and an unbound press none; a basic `Button` on the same surface keeps its `onAction`. **Activation tests.** Browser user activation is a window-level state with a timestamp and consumption rule. The [HTML specification](https://html.spec.whatwg.org/multipage/interaction.html#tracking-user-activation) defines transient activation as the interval after the last activation shorter than the user agent's transient activation duration, expected to be "at most a few seconds", and says it can end earlier through consumption. APIs fall into four classes (sticky-gated, transient-gated without consuming, transient-consuming, history-action-consuming), an `await` does not end activation by itself, and a Node test showing listener scheduling says nothing about any of this. Tests run in real browsers against the actual API an action calls, for Lit and React (both run the callable from a DOM `click`): for each API, record its class and fire the same click with the runner calling synchronously in the handler, after one resolved-promise `await`, after an await on a prerequisite shorter than the transient duration and after one longer, recording `navigator.userActivation.isActive` immediately before the call and the API's result (a case where a consuming API ran earlier in the prefix must not be misread as expiry). The result is a per-API, per-host table. The shared interface carries no `requiresActivation` flag, and Lit and React promise only that the callable starts synchronously from the event handler. A Lynx host is a separate case needing its own runtime and thread evidence, and may find the DOM notion does not apply.

## Open decisions

Settled decisions give their result and evidence at the cleanup baseline. Questions with no recorded decision are listed apart, then the evidence still missing. Two things are not open: `subject` is an optional, application-supplied reader, and a test can verify a chosen policy but cannot choose it. Adapter choices can be settled during implementation review and do not block approval of the common interface.

### Settled

1. **Work deadline and prerequisites.** One `deadlineMs` covers prerequisites and handler, so a stuck session check cannot hold a binding running (`packages/core/src/actions/limits.ts`). A confirmation prompt and a network call therefore draw from one budget, and an author waiting on a person sets a longer deadline. No measured prompt duration is recorded.
2. **Playback whole-attempt bound.** Play is one invocation under a single `deadlineMs` (mapping A, CORE2, PR #133), so the controller keeps no bound of its own; see [Corrections by owner](#corrections-by-owner). No separate record names a check placing every stage inside the work interval.
3. **Wrapping the player as an owner of leases.** The wrapper exists (`apps/lit-host/src/playback/player-owner.ts`) and no redesign is recorded. Whether the real player's ordering holds when `stop()` and `prepare()` interleave with a pending `start` is evidence still missing, below.
4. **Label loss in the action view.** Decided 2026-10-19 and delivered in PR #106: the #69 recommendation, loss final per view instance, recovery by a new view or reload. A user whose host reuses the view stays on `session-changed` until reload, and the sources do not say whether any host does. Not chosen: dropping the pin and accepting the next opener (restores the revival through a delayed copy) and a read returning the opened item (no such interface exists).
5. **Application deadline mapping, answers on expiry and slow-reader draining.** Decided with the server amendment (#112) and the 2026-10-19 delegation; see the [lifetime Status](../features/request_view_lifetimes.blueprint.md#status). Streaming policy is settled through CORE3.
6. **Breakdown.** The sequence divided into the issues listed in the [implementation sequence](#implementation-sequence).
7. **React version.** The baseline pins `@a2ui/react` 0.13.0 (`packages/react/package.json`); the React outcome is in Status (ACT2).
8. **Lit and React adapter choices.** How much of the basic Button to reuse, how a Lit mount identifies its owner, where `actions` lives (declared `private` in `lit` at the baseline), whether a watch-callback error after render clears the surface, whether an unbound `ActionButton` renders disabled, whether DOM moves defer retirement, and whether to warn in development when a scoped handle binds without a subject are embodied in the shipped adapters. They are not recorded individually here.

### Still open

1. **Where cleanup exceptions go.** Failures of `onFailure`, `onCanceled` and releases reach `onFinally` via `cleanupErrors`; `onFinally`'s own failure reaches only the observer, as a step name. The recommendation is to keep that, because a second application error channel is another concept and an application needing the object can catch inside its hook. The cost is that an uncaught error in the last hook is invisible to the application; a consumer that needs the object and cannot catch it would change the recommendation. No decision is recorded.
2. **How a definition records the execution environment of its event-turn callbacks (Lynx).** The contract requires an adapter to run `input` and `atActivation` in the event's call stack in the environment where written, or reject at bind time. A runtime function value carries no marker and `eventTurn` lists only phase names. Candidates are a build-time tag from the compiler's directive handling or an explicit author declaration; resolving needs a decision and a build check that the compiler's partition matches. No operation found needs main-thread gesture work, so the optional bridge is not needed for ordinary prerequisites. The recommendation is the bind-time rejection rule once a mechanism exists, with no common thread guarantee; the cost is that some definitions cannot be bound on some renderers.
3. **The Lynx window between native removal and effect cleanup.** Closing it needs a supported logical-retirement seam earlier than effect cleanup (the sources show none) or a narrower contract requiring a hook's presentation write to go to a target tolerating a retired instance. The recommendation is the narrower contract now, revisited if a seam appears; Lynx authors then key presentation state by item, not by a handle to a rendered view. Measuring the interval sizes the window and does not close it.
4. **Lynx versions, interpreter and adapter choices.** `@lynx-js/genui` 0.7.0 depends on `@a2ui/web_core` 0.10.6 while saga a2ui pins 0.13.0, and GenUI ships its own `MessageProcessor`; schema comparison and replaying recorded sequences through both decode paths would show whether runtime shapes agree. Open also: whether `@saga-a2ui/lynx` wraps GenUI and accepts a second validation path or renders core-decoded values through its own catalog components (this changes where messages enter the admitting store, not where the binding attaches); whether a message putting `action` on a bound control is rejected whole (proposed) or has the field removed with a reported warning; whether the adapter-set `sagaSourceId` is acceptable or the SDK asks GenUI to expose a clone's original ID; whether other inputs are read at the tap (proposed) or refused when any captured input changed; and package placement, since `@saga-a2ui/lynx` is planned with no consumer.
5. **Successor revisions of `authorized_playback` and `content_safety_levels`.** Their lifecycle records need their own human decisions; none is recorded here.

The owner retired the Lynx delivery chain on 2026-10-19, so items 2 to 4 have no scheduled owner.

#### Candidate gaps

The source-inspection candidates (none reproduced, none shown to expose another user's data) are listed in [request and view lifetimes, Candidate gaps](../features/request_view_lifetimes.blueprint.md#candidate-gaps), with each one's standing at the cleanup baseline. The table, written at design time, assigns each correction to the party owning the mechanism and keeps #69's identities: STATE1 ([#12](https://github.com/MachineWisdomAI/saga-a2ui/issues/12)) takes view-side cleanup in the controllers, STATE2 ([#13](https://github.com/MachineWisdomAI/saga-a2ui/issues/13)) the bounds, and CORE3 ([#16](https://github.com/MachineWisdomAI/saga-a2ui/issues/16)) the reusable connector contract. **Playback mapping to the bounds (mapping A, delivered by CORE2).** #69's attempt is a server action plus its continuation. The `play` sketch in [Resource ownership](#resource-ownership-and-handoff) puts the media fetch and player start inside one handler, so those stages share one `deadlineMs`; a session or consent check written as a prerequisite shares it too, and the server action's `call` is a handler step inside the same interval. The synchronous prefix is outside the interval, and anything in `onSuccess` or a release is under `hookMs`. The playback view at the baseline builds Play this way: key creation and the host-capability check are prerequisites, and the handler makes the host call, validates the grant, signs the proof, acquires the body and starts the player (`apps/lit-host/src/playback/playback-view.ts`). The alternative, separate invocations with a controller-owned maximum, was not taken, and this Blueprint adds no universal timer. A separate check that every stage falls inside the work interval is not recorded in Status.

### Migration rules

1. A controller migrates only when the module's behavior covers the verification outcomes above for that path. STATE1 and STATE2 may correct the controllers first, since they repair defects independent of the module's interface.
2. The change that moves a path also deletes the controller-local generation, abort and timer code it replaces, the unused exports and superseded tests, and keeps the safeguards covered by behavioral tests; the coding standards forbid old and new paths in parallel.
3. An upstream catalog or custom-element registration the renderer requires stays at that renderer's adapter seam (today `defineElements` and the application's catalog), and no saga a2ui handler-name table, typed or untyped, takes over routing.
4. Protected authorization, grant validation and resource ownership stay in the application, and `@saga-a2ui/mcp` keeps the connection, even where a migrated path reads shorter.

### Relationship of the lifetime corrections to this contract

This contract claims to fix none of the lifetime candidates by construction; it supplies the places where a fix would live. Standing is in the lifetime Blueprint's [Candidate gaps](../features/request_view_lifetimes.blueprint.md#candidate-gaps).

| Candidate | Where the contract supplies the mechanism | What stays outside |
| --- | --- | --- |
| Cleanup runs on teardown but late presentation or new reads follow | Binding `dispose()`: presentation hooks stop and their signals abort on disposal, and a disposed binding ignores later events | The adapter calling `dispose()` on its bindings at teardown |
| A controller releases its resource on teardown without marking itself retired | Disposal is a terminal state of the binding | The existing controller until migrated |
| A delayed old opener restores a stale selection | `current()` before each synchronous write, and the handler signal | Freshness and recovery rules for the session label |
| Cleanup after an old resource start affects a newer invocation | Owner-scoped tokens, scope ownership, token-scoped end on every cancellation stage, transfer on success | The player owner satisfying the token conditions, and any shared resource held outside the scope |
| No maximum across key creation, call, signing, acquisition and startup | `deadlineMs` over prerequisites and handler after the prefix, and `hookMs` over every step after; not a whole-invocation maximum | The mapping of playback's stages, and the server's own lifetime, which a client deadline cannot enforce |
