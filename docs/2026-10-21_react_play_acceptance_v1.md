# React protected-player acceptance

The application's React Play, Pause and Resume controls use the existing shared
actions, controller, player owner and server authorization. This record joins the
accepted installed/browser evidence to the remaining ChatGPT web observations.
It qualifies the protected player, not the combined description-card recipe or
full React renderer parity.

through [PR #172](https://github.com/MachineWisdomAI/saga-a2ui/pull/172).
This status record changes no approved design.

The application commits one typed control instance through a React layout effect,
retires it on host replacement/unmount and delivers activation synchronously
inside the native click. It subscribes to the existing controller state; it adds
no authorization handler, action runtime or player engine. It uses the
application's React runtime and installed `core`/`mcp` packages, without the
optional React card, Lit adapter or A2UI catalog.

## Bounded named-host observations

The retained Claude web sequence on 20 October opened synthetic episode `ep-1`,
received a private grant, refused `ep-2` without a grant, then opened a fresh
`ep-1` view and received a new grant. Three entitlement checks and zero media
reads were observed. This accepted sequence was not repeated.

On 21 October, ChatGPT web exercised the same sequence through supported OAuth
using synthetic data only. Each Play request carried episode-only arguments and
validated recipient metadata. Successful responses carried a private grant;
capability and media URL were absent from the model-visible result. The refused
response carried no private grant and a protocol/tool error. Its card displayed
“Playback could not be confirmed. Open this episode again to try playing it.”
A fresh `ep-1` card started Ready, then received its own private metadata after
Play.

One further fresh card used a 20-second synthetic entitlement delay with the
existing 40/45-second server budgets and 30-second action limit. Play visibly
showed “Checking access…” before the conversation was reloaded. After restoring
zero delay, a new opener created a fresh Ready player; its own Play received a new
private grant. The old request settled after reload with no observed server
abort. This is visible retirement/reload and fresh acquisition, not forwarded
cancellation or proof of invisible host-owned cleanup. Deterministic lifecycle
checks supply that separate application evidence.

The ChatGPT window made five entitlement checks in total and no fixture media
reads. Its resource was the reviewed installed HTML with an independently
inspected passive mapping observer appended, served SHA256
`9949d7efe575f994b094f0ef4f00a71d69167def0a5adc2a1fa619545ae31051`.
The observer reports presence/status only; it does not supply metadata or invoke
Play. The tested server adapter's SHA256 was
`2a2e2ba81ea3098767e94b3ce471b823843516992d4d683386dc978c6b840ea7`.
The execution runtime was Node 24.14.1 with MCP Apps 2.0.3. Historical fixture
URLs are intentionally omitted: they were bounded test endpoints.

Some new ChatGPT app containers initially failed to display. One explicit host
container Try again per affected view restored rendering. This is retained as a
host-loading limitation, separate from the card's refusal/fresh-view recovery.
It does not qualify a card-owned rendering-error path.

## Acceptance limits

The scoped React protected-player integration now has source, installed,
built-browser and required Claude/ChatGPT host evidence. The expected loopback
media failure (“The audio could not be played”) after a private grant is not
audible or remote-audio acceptance. No physical device, Alexa in-card round trip,
host account-switch signal, remote rollback or forwarded cancellation was
qualified. The combined subscriptions/description/Play recipe and optional-card
host recovery remain separate. No package publication or production deployment
follows from this acceptance record.
