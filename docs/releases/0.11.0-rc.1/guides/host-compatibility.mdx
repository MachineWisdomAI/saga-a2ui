SAGA delivers a rendered view and its data through an assistant using MCP Apps. One application serves ChatGPT, Claude and Alexa+ from the same server and the same view code.

| Interaction | ChatGPT web and Claude web | Alexa+ |
| --- | --- | --- |
| Display a SAGA view from a tool result | Lit and React views | Lit and React views |
| Render a FaithfulCard answer with attribution | Yes | Yes, including Ansari's answer card |
| Run a protected operation from an in-card control | Allowed and refused requests, including playback grants | Run it through the conversation |

## Renderer support and application evidence

React and Lit both provide an MCP stack for typed surfaces, actions and FaithfulCard applications. Ansari Faithful Answers runs on the React stack; its [public destination candidate](https://github.com/iaser-ai/ansari/pull/323) records the application's React stack recipe. The [React integration](https://github.com/MachineWisdomAI/saga-a2ui/pull/161) delivered answer cards in ChatGPT web, Claude web and Alexa+.

Lit supplies the generated starters and the standalone demo, on Node, Express, Fastify, Hono and Hapi. React supplies a generated starter on Hono. Choose either renderer: both stacks reach the same hosts.

## ChatGPT and Claude

The notes application runs in both hosts with a React view and the shared action runtime, and authenticates through each host's supported authentication path before the server applies its authorization. Mark read changes application state locally, without a backend call. Archive calls the authenticated server, displays the result and refuses before sending the request when its session prerequisite is missing. A fresh list shows the applied archives.

Protected playback grants work in both hosts: a control requests a grant, the server allows or refuses it for the verified account, and a newly opened view obtains a fresh grant. The public tool arguments carry the episode selection, while recipient metadata and grants travel in their separate delivery fields. The model-visible result carries no capability or media URL.

When you design feedback for a protected request:

- Show an uncertain outcome when the host stops waiting before the server answers; the request may already have taken effect.
- Do not retry a write automatically because the view stopped waiting.
- Let a reopened view request its own fresh grant rather than reuse an earlier one.

## Alexa+

Alexa+ displays SAGA views and FaithfulCard answers, including Ansari's answer card. Use conversation-driven delivery: the person asks, the assistant calls the tool and the resulting card displays the answer. Run consequential Alexa+ operations the same way, through the conversation.

SAGA also supplies a `readingProfile` helper. Alexa-like host names, an Echo Show device class or a mobile platform yield a device profile; the application maps that profile to its own font and layout tokens. See [card styling](/docs/releases/0.11.0-rc.1/guides/faithful-card-styling#custom-properties) for the application-owned mapping.

## Check your deployment

Before you launch on a host, check three things for your own application:

1. **Displayed content:** the expected result reaches the correct view, with its attribution and content policy.
2. **Protected operations:** authentication, server authorization and the allowed and refused outcomes for each real operation.
3. **End-of-view behavior:** late results, closing or replacing the view, and the resources your application owns. Cancellation ends a wait; it does not roll back a remote effect.
