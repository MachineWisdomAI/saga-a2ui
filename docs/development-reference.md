### Content safety

**Standard** permits validated HTTPS links through the host and images from explicitly allowed HTTPS hosts. **Strict** keeps every link inert, shows blocked fragments as accessible placeholders the reader can reveal as text, and loads a permitted image only after the reader chooses Show images. Both keep ordinary Markdown formatting and server authorization and data-sharing checks. The application chooses the policy; the optional FaithfulCard shows supplied Markdown without rewriting or silent truncation. Details are in [Content policy and the FaithfulCard](#content-policy-and-the-faithfulcard). Ansari-specific branding stays in Ansari.

## Set up and check your work

### Local development


Requires the Node version in `.nvmrc` (22.23.3; `engines` is `>=22.23.3`; run `nvm use`) and npm. No global tools are needed. The workspace has `packages/*` and `apps/lit-host`; `apps/lynx-fixture` has its own lockfile.

```sh
npm ci                              # install from the committed lockfile
npm ci --prefix apps/lynx-fixture   # the Lynx fixture's own lockfile; verify and CI need it
npm start                           # Vite dev server at http://127.0.0.1:5173
npm run build                       # the Lit app, example consumers, starters, demo, tour and installed builds
npm run typecheck                   # tsc across the root, packages, examples, templates and demo
npm run test:headless               # vitest in plain Node (no DOM, no browser)
npx playwright install chromium     # explicit browser install; verify does not download one
npm run test:browser                # Playwright specs against the built pages
npm run verify                      # guards, typecheck, build, tests, LFS, version enrollment
npm run test:docs                   # documentation checks only
```

`test:browser` needs a prior `npm run build`. The full CI route installs Chromium, then runs `npm run verify`, which already includes typecheck, build, headless tests and the browser check, so CI does not run those twice. `npm run serve:mcp` serves the local synthetic MCP endpoints on `http://127.0.0.1:3001` after a build (`PORT` overrides).

### Formatting and hooks

Formatting hooks are enabled for SDK development. Install and verify them before committing in each development checkout or worktree, including automated worker checkouts. Preserve existing Git safety guards.

```sh
npm ci --workspaces=false --ignore-scripts
npm run hooks:install
npm run hooks:check
```

`hooks:check` prints `SAGA formatter hook verified` with the effective hook path. Setup is idempotent, changes no Git configuration and installs no consumer lifecycle script. Consumers of the SDK do not install hooks; full SDK development still needs the workspace dependencies.

- **Where it installs.** In Git's effective hooks directory, including `core.hooksPath`. An existing executable pre-commit is kept as `pre-commit.saga-original`, runs first and its failure is respected; then pinned lint-staged and Prettier run from the committing worktree. The pre-push hook and its default-branch and force-push guards are untouched. Linked worktrees normally share hooks. The wrapper runs only the original guard when the committing checkout has no `scripts/format.mjs`; otherwise that checkout needs its own root dependencies. No global hook setting changes.
- **What blocks setup.** A symlinked or non-executable existing hook needs its owner to resolve it first. An existing backup plus an unknown hook needs inspection, not replacement. If another installer replaces the wrapper, `hooks:check` reports the drift; preserve the backup when you repair it.
- **Pinned tools.** Prettier 3.9.10 and lint-staged 16.2.7. One small wrapper composes the existing hook; a second hook manager would add another owner for the same file.
- **What is formatted.** Staged JS and TS (including JSX, TSX, MJS, CJS), JSON, CSS and YAML. `.prettierignore` excludes generated output, lockfiles, retained evidence, vendored material and Markdown or HTML source-quotation documents. The hook formats whole selected files, including lines outside the staged hunk. Formatting a touched source file can change quoted guide snippets: reconcile those quotes and run `npm run test:docs` before review. lint-staged owns index updates and restores unstaged portions; do not use `--no-stash` or `--no-hide-partially-staged`.
- **Manual runs.** `npm run format -- PATH...` formats selected files. `npm run format:check -- BASE HEAD --merge-base` checks a branch and never writes. The CI backstop uses the same selection and configuration on changed files; documentation-only changes select no formatter inputs. `npm run test:tooling` exercises real isolated commits, partial staging, preserved hooks and linked worktrees without building an application or opening a browser.
- **Troubleshooting.** If the hook cannot find Node, put the supported runtime on the Git process's PATH (including IDE and agent launches). If dependencies are absent, run the root installation command above. Fix formatting failures with the pinned formatter and retry the commit. After any lint-staged restoration conflict, inspect the index and worktree. The hook never downloads anything.

### Advisory correctness lint

`npm run lint` checks tracked JS, TS and workflow files. Pass paths to limit it (`npm run lint -- scripts/saga.ts`) or `npm run lint -- --base BASE HEAD --merge-base` for a PR. A dependency or analyzer configuration change rechecks all tracked inputs; deleted files are ignored; Markdown and artwork changes start no analyzer. The separate Advisory lint workflow is path-filtered, installs only root tooling and actionlint, and runs no SDK build, browser, fixture service or release rehearsal.

- **Tools.** ESLint 10.13.0 (needs Node 22.13+), typescript-eslint 8.72.0 and TypeScript 5.9.3, all pinned. The root TypeScript pin also controls root scripts and example typechecks. Package consumer engine requirements are unchanged. Install the workflow analyzer with Go: `go install github.com/rhysd/actionlint/cmd/actionlint@v1.7.12`; put Go's binary directory on PATH or set `ACTIONLINT`. `npm run lint:workflows -- .github/workflows/ci.yml` runs only that analyzer. Shellcheck and pyflakes integrations are disabled so the workflow rules are reproducible without extra tools.
- **Exit codes.** 0 means clean or warning-only, 1 means actionlint findings, 2 means an execution failure. A missing analyzer is an execution failure, never a clean scan.
- **Rules.** Seven ESLint rules, all warnings with no count threshold: `no-async-promise-executor`, `no-unsafe-finally`, `no-unreachable`, `no-sparse-arrays`, `use-isnan`, `valid-typeof` and `@typescript-eslint/no-non-null-asserted-optional-chain`. No recommended preset, type-aware build, formatting, naming, complexity or unused-variable policy is added. Unrelated suppression directives are left alone and unused-disable reporting is off.
- **Authority.** Findings are evidence to assess, not an automatic repair loop; do not clean unrelated code to quiet the report. No hook runs lint, and it is not a required check or branch protection. TypeScript, behavior, source-quote, version, artifact and Git safety checks keep their authority. The workflow uses `continue-on-error` and still summarizes analyzer outcomes when installation or execution fails.
- **Cost and license.** ESLint, typescript-eslint and actionlint are MIT-licensed with no per-seat fee, and send no code to a hosted analyzer. GitHub standard hosted runners are free for public repositories; private repositories use their plan's included minutes ([GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)).

References: [ESLint severities](https://eslint.org/docs/latest/use/configure/rules), [typescript-eslint setup](https://typescript-eslint.io/getting-started/), [actionlint usage and exit codes](https://github.com/rhysd/actionlint/blob/v1.7.12/docs/usage.md).

### CI checks and release qualification

CI (`.github/workflows/ci.yml`) runs on pull requests, pushes to main and manual runs. The **Documentation, artifacts, policy tests and CI routing** job always checks Git LFS pointers, version enrollment, Python version-policy integration and CI path routing, and runs `npm run test:docs`: guide commands, source snippets, generated recipes, local links and headings, tour references, third-party notices and the consumer boundary scan (`scripts/consumer-boundary.test.ts`, which reads documentation code fences and consumer source, so a prohibited fence in a documentation-only change fails here). It installs root tools only with `npm ci --workspaces=false --ignore-scripts`; no workspace, Lynx fixture, browser or pnpm dependency is installed. The separate **Version policy** PR check validates intended versions against the current base.

| Changes | Application types, builds, tests and release qualification |
| --- | --- |
| Root Markdown; Markdown in `docs/`, `blueprints/` or `diagrams/`; README and CHANGELOG files elsewhere; PNG, JPEG, GIF, WebP, AVIF, SVG or ICO under `assets/brand/`, `docs/` or `diagrams/` | Skipped; focused document and artifact checks run |
| Only those documents and the version-policy paths listed in `scripts/ci-scope.py` | Skipped; focused policy checks run |
| All other paths, including source and fixture Markdown, runtime images, executable files in `docs/`, retained evidence, dependencies and CI routing or workflow changes | Full qualification |
| Manual run, unavailable Git history, or an empty or unknown change set | Full qualification |

Extensions are case-insensitive. A rename checks both paths, so moving a runtime image into documentation still runs full qualification. A PR uses its merge-base diff; a main push checks its complete before and after diff. This routing is deliberately more conservative than the version-bump documentation exemption and exempts no whole directory. Run its real-Git cases with `python3 scripts/test-ci-scope.py`. A guide change stays on the fast path and must pass the focused document checks.

Full qualification runs the packed React pnpm consumer, `npm run verify`, `candidate:pack`, `candidate:rehearse`, and keeps the SHA-named candidate artifact for 14 days. The rehearsal rebuilds A and B from the same implementation at different versions; it proves the install, update and rollback procedure, not compatibility between different implementations.

Before any separately authorized release, run **CI → Run workflow** on the exact release ref (or `gh workflow run ci.yml --ref YOUR_RELEASE_REF`) and require the full check to pass. Manual runs bypass path exemptions, and a skipped documentation-only check is not release qualification. The workflow publishes and deploys nothing, holds no registry credential, and does not establish npm installation or assistant-host acceptance.

### Repository verification

`npm run verify` is the complete local and full-CI application route. In order, it runs the static guard, headless and browser discovery checks, typecheck, build, headless tests, browser tests, the Git LFS pointer check and the version-enrollment check, and stops at the first failure with that command's exit code. Git LFS must already be installed. Install the Playwright browser first (`npx playwright install chromium`); verify neither downloads nor substitutes one. CI runs `npx playwright install --with-deps chromium`.

- **Receipt.** Each run writes a disposable receipt to `.wise-agents/verify-receipts/` (ignored) and copies it to `latest.json`. It records the working directory, verify arguments, the Node and npm versions that ran, the commit and tracked dirty state at each command boundary, and each command's name, arguments, timestamps and exit code. It records no environment variables or output, so keep secrets out of command arguments. A run is `pristine-head` only when the commit and tracked state are clean at the start and unchanged through every command; otherwise it is `not-pristine-head`, which is not itself a failure. Detection happens at command boundaries only. `--exec` replaces the suite and labels the receipt `exec`; `npm run verify` does not pass it.
- **Static guard.** Reports `||` whose left operand, after removing parentheses and zero-argument `.trim()` calls, is a string or untagged template containing fixed non-whitespace text, with file and line, and exits nonzero. It does not flag identifiers, interpolation-only templates, whitespace-only text, nested interpolation, concatenation, `&&`, `??`, other `.trim()` forms or other methods. It parses authored `.ts`, `.tsx`, `.mts` and `.cts` files with the TypeScript compiler, skips `.d.ts`, dependencies and generated output, and does not typecheck.
- **Test discovery.** Vitest's file list (`vitest list --filesOnly`) is compared with authored `*.test.ts` files; Playwright `*.spec.ts` files are compared with `playwright test --list`. An authored file its runner omits fails the check, with no exclusions for fixture or `e2e` tests.
- **What a pass means.** It does not guarantee coverage, host compatibility or architecture. `apps/lit-host` is the only application; it declares no `version`, so it enrolls no owned version.

### Browser and installed-package checks

`apps/lit-host` renders developer-authored A2UI v0.9 surfaces from synthetic public data. Pinned and tested: `@a2ui/lit` and `@a2ui/web_core` 0.13.0, `zod` 3.25.76 (each A2UI package installs its own nested copy), `lit` 3.3.3. ## Contracts

### Package boundaries

<a id="consumer-boundary-scan-and-package-directions"></a>

Dependency direction points toward renderer-independent contracts. `scripts/package-direction.ts` states one row per package and each package's `exports.test.ts` asserts its row against its manifest and non-test source, with a deliberate wrong-direction import and manifest dependency proving the assertion can fail:

- core imports no delivery, renderer or DOM (only `@a2ui/web_core` and Zod);
- MCP delivery imports core only (types for the host-link and delivered-result contracts) and never components or a renderer;
- components import core only, no DOM, no MCP;
- the renderers import core and components, and name components only as an **optional peer** inside their `faithful-card` exports, so an application with its own catalog installs neither the components package, `markdown-it`, nor a FaithfulCard;
- a stack is the only place a renderer meets a delivery; server-only modules stay out of browser entry points.

**Consumer code holds application meaning only.** `scripts/consumer-boundary.ts` scans consumer code for the SDK's own glue, and `scripts/consumer-boundary.test.ts` (part of `npm run test:headless` and `test:docs`) judges the result. It guards against a duplicated integration rule; it does not forbid a supported lower-level interface used for a documented purpose.

- **Scanned.** `templates/*/src` and `templates/*/server` (all five templates must be present), `examples/*/src` and `server`, `demo/*/server`, the `apps/lit-host/src` view modules (`mcp/`, `answer-card/`, `playback/`, `lit/`, `react/`, `*-main`), the starter output each qualified template exports, and the code fences of the documentation.
- **Excluded, each with its reason in the configuration.** `apps/lit-host/src/main.ts`, `saga-panel/` and `lit/saga-app.ts` (host side), `apps/lit-host/e2e` and `apps/lynx-fixture` (fixtures that send wire messages by design), test files, the dated `docs/2026-*` observations, and a fence whose info string carries `before` or `historical`.
- **Prohibited glue.** The A2UI wire literals `createSurface:`, `updateComponents:`, `updateDataModel:` and `version: 'v0.9'`; imports of `@modelcontextprotocol/ext-apps` (every subpath), `@saga-a2ui/mcp/view` and `@a2ui/*`; and the `createMessageSession`, `a2uiV0_9Decoder` and `IngestResult` symbols. A raw `pagehide` listener is application behavior, not a rule.
- **Exceptions.** A server consumer takes its backend entry from `@saga-a2ui/mcp/server`. The `ext-apps` package's own `/server` subpath is real backend API, so a server that registers a tool or resource with it directly (the notes example's server and the playback server) keeps that import through one reviewed line, `// saga-boundary: <rule> <reason>`. Exemptions are not granted by pattern: a new use is reported until a reviewer accepts it; there is no file-wide disable; an unknown, reasonless or hit-less exemption is reported. The test also fails when a file under a `server` directory (or named `server.ts` or `*-server.ts`) in `templates`, `examples`, `demo` or `apps` is neither scanned nor excluded.
- **Stack imports.** An application that installs a stack takes its upstream catalog and schema names from the stack, so its view code carries no exemptions. `scripts/consumer-stack-imports.test.ts` checks that templates, the examples' stack views and their manifests name no upstream renderer or schema package and no lower SDK package the stack re-exports. The lower-level files are listed there with reasons: the notes example's renderer-neutral modules (shared by the Lit and React consumers), its optional-card consumer (`main-card.ts`, the FaithfulCard entry inside an own catalog) and the answer example's standalone page (no MCP host).
- **Reporting.** The test reports hit counts, fails when an include entry matches nothing or the scanned count falls below its floor, and proves with a known-bad line per rule and each near miss that the scan reports what it should and only that. `npx tsx scripts/consumer-boundary.ts --exempt` prints the report and every exemption.

### Core and Lit

<a id="core-and-lit-packages-view1"></a>

`@saga-a2ui/core` takes renderer-independent A2UI processing and `@saga-a2ui/lit` the Lit binding. Raw wire parsing exists only in core; renderer code receives validated messages.

| Export | Holds |
| --- | --- |
| `@saga-a2ui/core/protocols/a2ui/v0_9` | `a2uiV0_9Decoder` (the `MessageDecoder` strategy), validated message cases with `A2uiMessageVisitor`, `createMessageSession`, ingest result types, `defineSurface` with `SurfaceLayout`. Imports upstream `@a2ui/web_core` and Zod 3; no DOM, MCP or renderer |
| `@saga-a2ui/core/protocols/a2ui/zod3` | `z`, the Zod 3 copy upstream A2UI builds on, for authoring catalog component schemas |
| `@saga-a2ui/core/actions` | The action runtime ([Actions](#actions)) |
| `@saga-a2ui/core/host-links`, `/delivered-result` | Delivery-neutral contracts: `HostLinks`, `LinkOpenOutcome`, `NO_HOST_LINKS`, `describeLinkOutcome`; `DeliveredResult` |
| `@saga-a2ui/lit` | `createA2uiAppElement` (mounts one `SurfaceLayout` from a session, owns its lifecycle, exposes `updateData`) and `defineElements` (explicit custom-element setup). No MCP, no Markdown parser, no optional components |
| `@saga-a2ui/lit/actions`, `/faithful-card` | Opt-in action control and the Lit FaithfulCard |

The application keeps its catalog, component implementations, content policy, host links, the Play operation and the composition roots that choose the catalog and layout.

- **Surface authoring.** No consumer writes A2UI wire messages. `defineSurface({surfaceId, catalogId, data, root, components?, initial})` (the one place the version literal and message names live) returns a `SurfaceLayout<TData>` with `opening` (create, components and the first data model, as decoder input) and `update(data)`, which returns the single message that replaces the whole data model, or `{ ok: false, failure }`. `data` is a Zod 3 object schema; the schema is applied strictly and the result must equal the input, so `update` refuses an unknown or missing field at any depth, and any default, coercion or transform that would change a value, instead of dropping, filling or converting it. The scope is one root component over a flat data model plus an explicit list of other components passed through unchanged; `root.bind` maps a root property to a data field and `root.props` supplies plain values. It is not a binding engine and does not decide catalog support: every generated message still passes the decoder and the upstream processor, so a root the catalog lacks fails when the surface opens. `defineSurface` throws at definition time, naming the field, for an `initial` that fails the schema, a binding to an undefined field, a property both bound and valued, a property the layout owns (`id`, `component`) or repeated component ids. A change to one field in a nested scope, such as a row's status line, is still a whole-model replacement: `examples/pack1-consumer` keeps the rows it shows, replaces that row's status in its own copy and passes the full list to `surface.update({notes: shown})` on the stack's bound surface (`notes-controller.ts` `present()`; `notes-view.ts` hands the controller that surface). The application writes no protocol message for it.
- **Data updates.** `updateData(data)` validates against the layout and applies the replacement in place; mounted controls, action bindings and focus survive because nothing remounts. A rejected update (invalid data, an unconnected element, a disposed session) returns `{ ok: false, failure }` and changes nothing. The name is `updateData` because Lit's `ReactiveElement.update` is the render lifecycle method. `ingest(input)` remains only as a protected member for subclasses that relay protocol input they did not author.
- **Rejection.** `ingest` never throws for bad input. A rejected input (unsupported version, malformed envelope, upstream refusal) clears the surface and shows a safe fallback (`role="alert"`, inert text). Messages of a rejected batch applied before the refusal stay applied; there is no atomic rollback. The next accepted input removes the fallback. An application that wants a fresh surface sends `deleteSurface` and creates it again.
- **Registration.** `defineElements` defines free tags, leaves a tag already bound to the same constructor alone (repeating setup, or two catalogs sharing a component, is harmless), and fails with `ElementConflictError` for a different constructor on an existing tag; the first definition is kept and a failing call defines nothing. Nothing registers at import time. Decorator syntax is not transformed under a consumer's own toolchain, so `createA2uiAppElement` and the card declare reactive state with `static properties` and `declare`.
- **Lifecycle.** Connecting creates a session, subscribes to the surface and opens the layout. Disconnecting unsubscribes and disposes the session; a late `updateData` or `ingest` on a retired element is refused with an explicit failure, not a throw; a reconnected element opens the layout afresh.
- **Packing.** Unversioned packages cannot be packed by `npm pack`, so installed-package tests pack a copy that carries the candidate version ([Packaging](#packaging-starters-and-demonstrations)).

### MCP connector

<a id="reusable-mcp-connector-core1"></a>

`@saga-a2ui/mcp` owns MCP delivery. Three subpath exports keep server and view code apart; `packages/mcp/src/exports.test.ts` bundles each by name to show a server consumer pulls in no renderer and a view consumer no server module, and `e2e/view-bundle.spec.ts` repeats the check on built views.

| Export | Holds |
| --- | --- |
| `@saga-a2ui/mcp/server` | `registerPublicOperation`, `registerProtectedOperation`, `viewUriForHtml`, `operationViewFromHtml`, `OperationConfigurationError`, the request-budget seam (`createServerBudgets`, `RequestLifetime`, `LifetimeCause`, `StageFailure`), `attachRequestLifetime` and the declaration types. Imports MCP server helpers and Zod; no renderer or view code |
| `@saga-a2ui/mcp/view` | `runToolResultView` (handlers before connect, early results held, host context before the first result, teardown before the connection ends, disposal, callback failures reported), `ViewStartFailure`, `hostLinksFromApp`, `startOwnSizing`, `readingProfile`, `deliveredResultFromToolResult`. No server module, Node built-in or renderer |
| `@saga-a2ui/mcp/policy` | `ViewCsp`, `CLOSED_VIEW_CSP`, `DEFAULT_OPERATION_MS`, `DEFAULT_REQUEST_MS`, `startBoundedTimer` |

**What the application keeps:** the listener (hosting, Host-header protection, body bounds), authentication, request classification, domain authorization, backend calls and the renderer. The connector never reads a credential: for a protected operation the application supplies `identity(authInfo)`, which turns the transport's per-request verified context into its own immutable value.

**What the connector does** for each declared operation, in order:

1. *Registers* the tool and its `ui://` view on the application's `McpServer`. A protected registration without an identity resolver, sign-in failure text, projection, view or output contract throws `OperationConfigurationError` naming the missing requirement, as does a non-finite bound.
2. *Validates input* with the declared Zod contract before the handler runs. Undeclared fields (for example `accountId`) are dropped; a protected operation takes its identity only from the verified context.
3. *Resolves identity* (protected only). No acceptable identity gives the declared sign-in text and the handler does not run. A public operation resolves nothing.
4. *Waits for the handler and its projection* as one bounded `handler` operation of the request's lifetime. A result that loses the race is ignored; a throw or rejection gives the declared `unavailable` text with no message; a request already ended or cancelled never starts the handler.
5. *Projects explicitly.* `project(record)` builds the model-facing text and structured data field by field; the data is validated against the strict output contract before serialization, and a violation gives the declared `invalidOutput` text, not the validator's message.
6. *Links the result to its view.* Every result the operation returns, success or fixed-text failure, carries `_meta.ui.resourceUri` set from the trusted declaration, so a host can mount the view from the result alone. A tool argument, record or projection cannot select another resource. A request the MCP server rejects before the operation runs is answered by the server and is not stamped.

The handler returns `record`, `absent` (declared text) or `refused` (fixed safe text for well-formed but unaccepted input). Recipient mapping for Play stays in the application's `playback/` code; it depends on an actual-host measurement that has not been made.

**Callback contract.** `handle(input[, identity], request)` receives an `OperationRequest`: `signal` (aborts on caller disconnection, a cancellation reaching the request, the handler's budget, the request deadline, or once the operation finished), `within(stage, work, { limitMs })` for nested work inside the same aggregate budget (rejects with `StageFailure` carrying the typed cause), and `reportProgress(update)`, a quiet no-op after the operation ended. Anything other than `record`, `absent` or a `refused` with non-empty text is answered with the declared `invalidOutput` text. `project(record[, identity])` is synchronous and returns `{ text, data }`; a returned promise is refused with `invalidOutput` unawaited. Declared Zod contracts own every size, item and string bound (the connector adds none and never truncates), `Projection.text` is checked only for being a string (bound it in `project`), and the identity resolver is synchronous: a promise is answered with the unavailable text and recorded as the typed `authentication` cause.

#### Content identity for a served view (`viewUriForHtml`)

A host or proxy that caches `ui://` resources by URI cannot see that HTML changed if the URI stays. `viewUriForHtml(html, 'answer.html')` derives `ui://views/answer.<32 hex digits>.html` from the filename and the SHA-256 of the exact document, and the application uses it as `OperationView.uri`.

- Apply it to the **final** HTML after every build, inlining and stamping step. The same filename and bytes give the same URI; any changed byte gives a new one. It accepts a string (hashed as UTF-8; an unpaired surrogate throws `RangeError`) or a `Uint8Array`. It is a pure function with no registry or cache. It identifies bytes only: it does not authenticate the document or builder and does not cover the CSP declared beside it. A host that already holds the URI keeps what it cached, so the identity helps only once the application serves the new URI.
- `operationViewFromHtml({ html, filename, title, csp })` builds the whole `OperationView`: the URI from `viewUriForHtml` (a filename that is not a relative `.html` file throws), and `csp` starting from `CLOSED_VIEW_CSP` plus only the host permission arrays the caller names. A content policy supplies them through `resourcePermissionsOf(policy)` from `@saga-a2ui/components/faithful-card`, so neither package imports the other.
- A content policy travels in the same document: `embedContentPolicy(html, policy)` writes the policy-derived `Content-Security-Policy` meta and a configuration script (every `<` written `\u003c`), and `contentPolicyFromEmbedded(text)` rebuilds and re-validates the policy (`null` is the default Standard policy). Both are string operations, so a server calls them without a DOM. `embedContentPolicy` throws, and nothing is served, when the document has no `<head>`, has a `<script` or comment before the insertion point, declares its charset anywhere but as head's first element, or when the policy's CSP contains a `"`.
- `examples/answer-consumer` shows both from the installed packages alone. `scripts/answer-consumer.test.ts` builds it, serves it through the packed `@saga-a2ui/mcp` and checks over JSON and server-sent events that results, discovery and the resource read agree and that a changed page gets a different URI; `apps/lit-host/e2e/answer-consumer-mcp.spec.ts` mounts the page the consumer's server serves in the host fixture.

#### Public answer operation

`POST /answer/mcp` (`startEpisodeListener({ answer })`, off unless configured) is a synthetic, explicitly public question-and-answer tool, `answer_question`, with its own view. No credential is read and a presented `Authorization` header is not an identity. `responseMode` is `json` or `event-stream` (progress notifications, then the answer).

- **Binding.** The result repeats the question exactly (`{ question, answer }`, strict, bounded to 500 and 2,000 characters). If the host also announced the question (`toolinput`), a result shows only when its question is identical (no trimming or case folding); a late copy for another question is ignored.
- **Early, repeated, late.** A result before any input shows with its own question; an input for the already answered question keeps the answer; the same answer again is not shown again; a different answer to the same question replaces it. After teardown or dispose nothing is delivered. An error, malformed or undeclared-field result, or unreadable input clears the answer and shows a problem; only the server's three known safe texts are shown verbatim.
- **Progress and bounds.** The handler runs once per call. `request.reportProgress` sends `notifications/progress` only to a caller that supplied a progress token and while the operation is live. The wait is one operation of the request (`answerBoundMs` overrides the 3 s operation limit), and a dropped HTTP request aborts the handler's signal. Neither the connector nor the listener logs the question or answer.

### Request lifetime and failure paths

<a id="bounded-requests-and-playback-state2"></a><a id="the-server-request-contract-and-its-failure-paths-core3"></a>

**Configuration.** Two independent limits: an **operation limit** (`DEFAULT_OPERATION_MS`, 3,000 ms) and a **request limit** (`DEFAULT_REQUEST_MS`, 10,000 ms). Each field resolves as per-operation or per-route override, then SDK-instance setting, then default; an omitted field never changes the other. `createServerBudgets({ operationMs, requestMs })` is an SDK instance, `forRoute(...)` layers a route's overrides, and the listener takes `budgets` (instance) and a `budgets` per endpoint (route). `boundMs` on an operation declaration (and the listener's `readBoundMs` and `answerBoundMs`) overrides the operation limit; it is not a second timer. Every supplied value must be a finite positive number: zero, negative, `NaN`, infinite and non-number values, including values a more specific setting would shadow, are refused when the instance, route, listener or operation is configured, before any callback or port opens. Settings are copied when created.

**One lifetime per request** (`packages/mcp/src/server/lifetime.ts`, portable, no HTTP types). The Node listener starts it when it admits the request, before the first credential, header or body wait. The deadline is monotonic and absolute. Authentication, body ingestion, the complete handler with its projection, an authorization lookup, a storage read and a media acquisition are each a bounded stage whose wait is the least of its own limit, every enclosing operation's remainder and the request's remainder. Progress, retries, callbacks and revisited stages never renew a deadline. A timer is not the only witness: a result is checked against the absolute deadlines when work returns and when it settles, so work that blocked the thread past its limit is refused (JavaScript is not preempted; the result is dropped and nothing later starts). Every wait uses `startBoundedTimer`, which segments delays so a finite limit above the platform timer maximum (2^31-1 ms) is honored. Nested handler work goes through `request.within(stage, work)`. Racing is the guarantee and the signal asks for cooperation: an uncooperative verifier, lookup or storage read cannot hold the request open, its late result is dropped, and the gate is checked before later stages (no server built, no authorization snapshot taken, no capability issued, no storage read started, no grant deleted after it closes). Untrusted input cannot choose these settings; the route is chosen from the path.

**Failure map.** The HTTP status and challenge, the JSON-RPC error and the tool result's `isError` are separate observations.

| Trigger | HTTP | JSON-RPC | `isError` | Internal cause (for `observe`, never sent) |
| --- | --- | --- | --- | --- |
| No, malformed, unknown or expired credential | 401 + `WWW-Authenticate` | none | n/a | `auth-refused` 401 |
| Service-only credential or missing scope | 403 `insufficient_scope` + challenge | none | n/a | `auth-refused` 403 |
| Verifier throws, or its wait expires | 500 `server_error`, no challenge | none | n/a | `dependency-failure` or `operation-timeout`, stage `authentication` |
| Body over the limit, never completes, wrong `Accept` | 413, 408 (then closed), 406 | none | n/a | `request-timeout` for the 408 |
| Body is not JSON | 400 | `-32700`, id `null` | n/a | none |
| Malformed MCP call | 400 | `-32600` | n/a | none |
| Unknown tool | 200 | `-32602` | n/a | none |
| Business input refused, record absent | 200 | none | `true`, declared text | none |
| Handler throws, rejects, stalls or is cancelled; projection throws; identity resolver throws or returns a promise | 200 | none | `true`, declared `unavailable` text | `dependency-failure`, `operation-timeout`, `request-timeout` or `cancelled`, with the stage |
| Projection is not `{ text: string, data }`, `data` breaks the output contract, or is oversized | 200 | none | `true`, declared `invalidOutput` text, no `structuredContent` | none |
| Backend answers 401, 429 or 503 | 200 | none | `true`, declared `unavailable` text; no backend status, `Retry-After` or challenge | `dependency-failure` with the original error |
| Request deadline passes before anything is committed | the owned stage's answer, once | | | `request-timeout` |
| Caller disconnects or cancels | nothing written | | | `disconnected` or `cancelled` |

Media lookups or storage that fail answer `503 unavailable` with the existing safe headers. A verifier or admission wait that merely expires is `500`, never `401`. Real credential refusals keep `401` and `403` with the challenge. An expired request may attempt one immediate safe answer and gets no extra delivery time; a committed response is never given a replacement status. Causes are typed (`operation-timeout`, `request-timeout`, `cancelled`, `disconnected`, `auth-refused`, `dependency-failure`, each with a stage and whether an effect is possible); they may hold the original error, so the listener hands them only to the application's `observe` callback, never to a caller. A stage that never started is `effect: 'none'`; anything that began is `'unknown'`. A timeout proves no rollback: a possibly completed write stays unknown and is never offered a retry. Success output schemas stay strict.

**Cancellation, disconnection and resume are different facts.**

- *Disconnection of the same request* aborts the handler's `signal` and drops everything after it; the transport receives no write.
- *A `notifications/cancelled` in the POST that carried the call* is processed before the SDK reaches the tool callback, and the pinned SDK (server 2.3.1) then invokes the callback with an already-aborted signal. The connector does not start the handler or resolve an identity, and no JSON-RPC response is sent for the cancelled call; the exchange ends at the request deadline (JSON) or the stream idle policy (SSE).
- *A separately posted `notifications/cancelled`* names no running request on a stateless endpoint (each POST has its own server and transport, and the connector keeps no process-wide registry): it is acknowledged `202` and the running handler is not aborted. Cancellation reaches a handler only by closing its own HTTP request.
- *Resume and replay.* Endpoints are stateless: `GET` (with `Last-Event-ID`) and `DELETE` get `405`, an abandoned handler is not run again, and a retry is a new request with its own run and budget.
- *Host forwarding is not established.* Whether an assistant host forwards cancellation, closes the connection or keeps waiting is a per-host observation; a host cancellation notification was observed that did not abort the entitlement signal. Local abort proves no remote rollback.

**Per-request servers.** A stateless `createMcpHandler` factory builds one `McpServer` per request, and the request's lifetime must end when that server does. A server ends when its transport closes (`onclose`) or when the handler closes it before any transport connected (no `onclose` fires). `attachRequestLifetime(server, lifetime)` covers both:

```ts
const server = new McpServer({ name: 'status', version: '1.0.0' });
attachRequestLifetime(server, lifetime);   // before the factory returns it
registerPublicOperation(server, operation, { lifetime });
return server;
```

`lifetime.finish()` is called exactly once per server: on transport close, on `close()` with or without a transport, on a repeated `close()`, and when the upstream `close()` throws (the failure still reaches the caller). A close callback already on `server.server.onclose` keeps running first, so attach after installing your own. Attaching the same lifetime twice changes nothing; a different lifetime throws `RequestLifetimeAttachmentError` and leaves both untouched. The application still starts the lifetime at admission and passes it to the operations.

**Finite delivery and streaming.** JSON and media responses are bounded through the transport's `finish`, not through the result being ready. A reader that stops reading is closed at the original request deadline; bytes already buffered are not recalled. Only a `finish` on a response nobody destroyed counts as delivery, and `observe` reports `finished: false` for a response the deadline closed. Media grants keep their own expiry, a spent proof stays spent, an acquisition is a new request with a new deadline, and a denial arriving after the request ended does not delete the grant. The request deadline bounds setup up to an established `text/event-stream`; an established stream lives while the transport keeps accepting bytes, and `answer.streaming.idleMs` (default `DEFAULT_STREAM_IDLE_MS`, 30,000 ms) closes one that goes idle or backs up. Only bytes the transport accepts reset it.

**Cleanup responsibilities.** The connector stops waiting, ends the signal, drops late results and progress and refuses later stages. The application stops work it can on `request.signal` and `within`'s signal, owns idempotency and compensation for work it cannot interrupt, keeps per-request state in the request, and, as the listener, starts a lifetime per request, reports disconnects and `finish` to it, and closes the transport and server when the response closes. A client prerequisite never authorizes a protected handler, and an action's hooks and busy policy are not a request deadline.

### Views and stacks

<a id="mcp-tool-result-in-the-view-mcp1"></a><a id="mcp-result-lifecycle-in-the-view-mcp2"></a><a id="the-mcp-stacks-and-the-card-application-e1-e2"></a>

A view is a single-file page that connects the MCP Apps bridge, turns each tool result into an A2UI data-model update and hands it to a session. Decoding stays in core; rendering stays in the renderer package.

**Stacks.** `@saga-a2ui/react-mcp-stack` and `@saga-a2ui/lit-mcp-stack` each connect one renderer to the bridge. An application installs one stack and the renderer's framework peers, and imports from the stack only. The two have the same shape and the same lifecycle code, copied between them (`running-view`, `container-claim`, `host-connection`, `start-failure`, `faithful-card/document-policy`); a change to one is made in both, and each package's tests (`stack.test-support.ts` runs a real `AppBridge` over an in-memory transport) check it.

| Entry | Holds |
| --- | --- |
| `.` | `startA2uiView({ container, layout, catalog, actions, readyWhen, sizing, hostContext, onToolResult, onTeardown, onError })` and the names an own-catalog application writes its view against: the layout (`defineSurface`, `z`), the catalog (`Catalog`, `CommonSchemas`; Lit adds `A2uiLitElement`, `basicCatalog`, `LitComponentApi`; React adds `createComponentImplementation`, `ReactCatalogComponent`, `ColumnApi`, `ListApi`, `RowApi`), the actions (`Action`, `ActionBinding`, `ActionButton`, `ActionButtonActivation`, `createLitActions` or `createReactActions`; Lit adds the `HostLinks` type of `ViewHost`), the failures (`StartError` with `StartMisuse`, `StartFailure`, `ErrorPhase`), `readingProfile` and the delivery callback types. It imports neither `@saga-a2ui/components` nor Markdown, so an own-catalog bundle holds neither |
| `./faithful-card` | `FaithfulCardApp` (the definition builder of `@saga-a2ui/components/faithful-card`), `startFaithfulCardApp(definition, { container, readyWhen, sizing, hostContext, chrome, onError })` (Lit also takes `styles`, constructable stylesheets for its card), `CardResultOutcome`, `CardResultReader`, `DeliveredResult`, the card's host link (`useHostLink` in React, `bindHostLink` in Lit), `readingProfile`, and for Lit `contentPolicyFromDocument` and `documentContentSecurityPolicies` |
| `./content-policy` | `createContentPolicy` and `embedContentPolicy`: how a server states and embeds the policy the card application reads back from its document. No renderer or delivery code |
| `./server` | `createServerBudgets`, `registerPublicOperation`, `operationViewFromHtml`, `viewUriForHtml`, `attachRequestLifetime`, `OperationView`, `RequestLifetime`, re-exported from `@saga-a2ui/mcp/server`, which keeps their specification. Node only: no browser entry imports it |

Each stack's `exports.test.ts` bundles the entry's graph from workspace source to show that the browser graphs hold no server module and the server graph no renderer or components module; `scripts/pack1.test.ts` builds the own-catalog and card pages from packed copies and shows only the card page carries the parser.

**Lifecycle.** Both starts return a running view synchronously (`{ ready, dispose }`; the A2UI view also exposes `surface`). The layout is validated before the connection is made, results arriving during readiness are held and the latest is shown once it settles, host context applies before the first result, and the stack owns the view's size reports. Ending a view in any state (dispose, a host `ui/resource-teardown` request or `pagehide`) removes what it showed and frees its container before the connection closes, once; only a start that failed keeps its failure on screen until disposed. A second start on a container with a running view throws `container-busy` and leaves the first alone. However a view ends, `runToolResultView` stops delivery, runs the application's `onTeardown` once and closes the connection once (on a host teardown request it answers the host first); `dispose()` is idempotent. The application's teardown disposes its own bindings and does not close the connection.

**What the application's view decides.** The episode view's `createEpisodeView` decides what each delivered result means for its panel and nothing else: each valid public result replaces the one shown in place; an error result, a result that is not a public episode (including undeclared fields) or a rejected update empties the panel and shows a plain-text fallback, and the next valid result clears it; image consent is revoked before every result is applied, even a repeat, and retired for good by teardown. The page keeps what is its own: the policy it reads from its served document, the content view its descriptions run under and the problem line.

**The card application** is a pure value: `FaithfulCardApp.define({ name, version }).reader(...).policy('document').result(read).texts(...).build()`. `result(read)` takes the application's one `CardResultReader`: it receives the delivered result and returns `{kind: 'content', content}` or `{kind: 'rejected', text?}`, and it is the application's only decision about a result. A reader that throws, or returns anything else, is defensively rejected without wording, so the stack shows the definition's `texts.problem` ([Reading the whole result](#reading-the-whole-result)). Reuse by a delivery other than MCP is unqualified.

<a id="reading-the-whole-result"></a>**Reading the whole result.** Core's `@saga-a2ui/core/delivered-result` holds the delivery-neutral `DeliveredResult`: boolean `isError`, `content` (every block in delivered order; a text block carries `text`; any other block is opaque) and an optional, unchecked `structuredContent`. Absent, `null` and malformed `structuredContent` stay distinct (`'structuredContent' in result` tells absence from `null`). `deliveredResultFromToolResult` in `@saga-a2ui/mcp/view` maps an MCP tool result onto it and decides nothing: it neither rejects an error result nor reads structured content. Both stacks pass that value unchanged to the definition's one `result` reader, which returns `{kind: 'content', content}` or `{kind: 'rejected', text?}`.

```ts
import {FaithfulCardApp, type CardResultOutcome, type DeliveredResult} from '@saga-a2ui/react-mcp-stack/faithful-card';

// The application's own protocol: a result it cannot use is rejected with its own words.
const read = (result: DeliveredResult): CardResultOutcome =>
  usable(result)
    ? {kind: 'content', content: {markdown: textOf(result), heading: headingOf(result)}}
    : {kind: 'rejected', text: 'This answer needs a newer version of the app.'};
const definition = FaithfulCardApp.define(identity).reader(readerOptions).policy('document').result(read).texts(texts).build();
```

- There is no default reading and no second option. An application whose protocol is only `structuredContent` writes that reader. The reader receives the result whatever the delivery calls an error; what an error result means, and what it says, is the application's decision (return `{kind: 'rejected', text}` to show the error's own text as the problem).
- A rejection shows `text` when supplied and the definition's `texts.problem` otherwise. Either way the shown answer clears, image consent and the previous link outcome end, and the next accepted result recovers. A reader that throws, a result whose content cannot be mapped, or a return that is not an outcome is reported to `onError` with phase `result` and rejects the result without wording, with the same clearing; the stack does not undo anything the callback already changed. (A result that cannot be mapped does not reach the view through the bridge, whose schema rejects it first; the mapper's unit tests cover it.)
- Three owners each decide once. Core owns the neutral value and imports no delivery, renderer or DOM. The MCP view maps without interpreting. `readCardResult` in `@saga-a2ui/components/faithful-card` is delivery-neutral and shared by both stacks: it runs the mapping and the reader under one guard, checks the return and reports a throw, and never looks inside a result. Each stack keeps only the rendering of the outcome. The SDK names no application protocol, version or wording; the test matrices in `card-app.test.ts` and each stack's `start-faithful-card-app.test.ts` use a synthetic envelope.

<a id="the-reading-profile-and-the-applications-tokens"></a>**The reading profile.** `readingProfile(context, hostName)` answers `'device'` or `'desktop'` and is exported by both stacks. It recognises hosts the recorded observations read on a device (Alexa+), the historical `HTMLFragmentWrapper` host name, a host context whose `deviceClass` is an Echo Show class (`echo_show`, `echo_show_8`, `echo_show_15`, matched as a whole underscore-separated word) and a declared `mobile` platform. `deviceClass` is an extension beyond the MCP Apps host context schema, which accepts and passes it on. The names come from a consumer's fixtures, not fresh host evidence. The profile decides nothing about presentation: the application calls it from its `hostContext` callback and maps the answer onto its own tokens and `data-reading-profile` attribute, with no host-name test of its own.

### Content policy and the FaithfulCard

<a id="standard-descriptions-pol1"></a><a id="strict-descriptions-and-show-images-pol2"></a><a id="the-passive-faithfulcard-and-an-installed-second-consumer-card-prep"></a>

`@saga-a2ui/components/faithful-card` holds the versioned content contract and reader (`createFaithfulCardReader`, `describeContentFailure`), Markdown interpretation into restricted nodes, the trusted content policy (`createContentPolicy`, `establishImageEnforcement`, `embedContentPolicy`), image consent scopes (`createImageConsentScope`) and the A2UI catalog contract (`FaithfulCardApi`). It imports `markdown-it`, `zod`, upstream `@a2ui/web_core` and core; no MCP, renderer, DOM or server API (checked on the bundled graph). `@saga-a2ui/lit/faithful-card` and `@saga-a2ui/react/faithful-card` render it. `markdown-it` is used directly, not through A2UI's optional `@a2ui/markdown-it` peer, so the SDK controls the token set.

**Content contract.** Content is untrusted: `{ contractVersion: 1, markdown: string }`. The reader refuses anything else with an explicit failure kind and never repeats the content: `invalid` (not that shape, or an unknown field), `unsupported-version`, `too-long`, `too-nested`. The element then shows an alert and none of the earlier content; the next valid value recovers. A card with no enclosing view shows nothing of its content. The card's two A2UI properties are `contractVersion` and `markdown`, both bindable, and the schema is strict, so a layout cannot supply an action, handler name, dialect or bound. The card never rewrites, translates, summarises, moves attribution, numbers headings or truncates.

**Trusted settings, never content.** The reader is created from `{ dialect, maxLength }`, validated on its own with no defaults (`invalid-dialect`, `invalid-limit`, `invalid-config`). `maxLength` counts UTF-16 code units and is each application's own finite bound (the episode view keeps 2,000 as `EPISODE_CARD_SETTINGS`; the answer example accepts 50,000). The nesting safeguard `MAX_NESTING_LEVEL` is 20 for all (a block quote counts one level, a list item two); `markdown-it` would otherwise silently stop reading and drop text, so a description that reaches it is refused with a "nested too deeply" alert. Longer input is a "too long" alert. The episode tool contract (`mcp/episode.ts`) is stricter, at 500.

**Dialects.** `commonmark` is markdown-it's `commonmark` preset with linkify, typographer, tables and strikethrough off; pipe tables and `~~tildes~~` stay readable text. `commonmark-tables-strikethrough` enables the parser's maintained `table` and `strikethrough` rules and nothing else. The parser drops body cells beyond the header's column count, so the reader keeps the dropped cells after the parsed ones. Raw HTML, footnote syntax and task-list markers stay as written; the parser recognises raw HTML only so Strict can tell it from prose (its tags, comments and blocks become `raw-html` nodes rendered as text). A link reference definition nothing uses is not shown. Supported: paragraphs, headings, block quotes, bullet and ordered lists, fenced and indented code, rules, emphasis, strong, inline code, soft and hard breaks, links and images. HTML blocks follow CommonMark: a line that starts one keeps the rest of the block as raw source.

**Restricted tokens.** `markdown.ts` turns the parser's tokens into a closed, deeply frozen set of nodes in source order (`ParsedMarkdown.source` keeps the original string). Renderers use fixed templates and text bindings; no `unsafeHTML`, `innerHTML` or parser-generated HTML exists. React node switches end in an exhaustiveness check.

**Policy.** `createContentPolicy({ level?, imageHosts?, fontOrigins?, blockedPresentation? })` returns a frozen policy or an explicit failure (never mount on a guessed policy):

```ts
const created = createContentPolicy({ level: 'strict', imageHosts: ['images.example.com'] });
if (!created.ok) throw new Error(created.failure.message);
await startEpisodeListener({ viewHtml, catalog, contentPolicy: created.policy, port });
```

- `level` is `standard` (default) or `strict`; `blockedPresentation` is `placeholder` (default) or `inert-text` and is rejected for Standard. The listener defaults to Standard with no image host.
- `imageHosts` accepts only canonical lowercase DNS hostnames (letters, digits and interior hyphens, which includes canonical dotted IPv4) and rejects wildcards, schemes, ports, paths, credentials, uppercase or non-canonical hosts, any CSP delimiter (`;`, `,`, `'`, spaces), bracketed IPv6, more than 32 hosts and unknown settings. It defaults to empty.
- `fontOrigins` is a separate trusted list, default empty: `createContentPolicy({ fontOrigins: ['https://fonts.example.com', 'https://assets.example.org:8443'] })`. Each entry is validated and normalized (lowercase ASCII host, default port dropped, other ports kept), deduplicated and sorted. A wildcard, plain HTTP, credentials, a path other than `/`, a query, a fragment, whitespace, a CSP delimiter or a bracketed IPv6 literal is an explicit `invalid-font-origin` failure. The list is part of `policy.configuration`, so `createContentPolicy(policy.configuration)` and the embedded copy rebuild an equal policy.
- Link decisions allow only absolute HTTPS without credentials. Image decisions also need an exact `https://host` origin match (suffix tricks, unlisted subdomains, other ports and credentials fail) and demonstrated enforcement.

**Standard.** A validated HTTPS link is a button whose accessible name includes the parsed hostname (internationalized names appear in ASCII); activating it makes one request through `HostLinks.open`, backed by `App.openLink` (`ui/open-link`) when the host advertised `openLinks` (`mcp/host-links.ts`). Denial, failure or a missing capability leaves a polite status with the destination as text. There is no `window.open`, anchor, `href` or navigation fallback, and a result for a replaced description is ignored. Images from exactly listed HTTPS origins (same scheme, host and port) load without consent.

**Strict.** Under Strict, `decideLink` refuses every destination (valid HTTPS included) and every link, image reference and piece of raw HTML is a blocked fragment. By default each appears as readable placeholder text in place (`[Link blocked]` after the label, `[Image blocked: alt]`, `[Markup blocked]`); surrounding prose, order and formatting are unchanged. With `inert-text` the source is shown from the start. A keyboard-operable **Reveal source / Hide source** button switches between the two; it changes visibility only, so nothing revealed can execute, navigate or fetch. Revealed source is reconstructed from the parsed fragment, not copied byte for byte. A description with nothing to block gets no button. Syntax the dialect does not support (strikethrough, tables in `commonmark`) is ordinary text and stays visible.

**Show images.** Before consent, including after source reveal, no image request is made (`decideImage` answers `consent-required`). **Show images** is enabled only when `offerImages` finds an image that would qualify now (an exactly listed HTTPS host and demonstrated enforcement); it cannot widen the allowlist or relax the document's restrictions. With no qualifying image the button is disabled and a polite message says so; a description with no image has no button. Under Strict, images load eagerly once consented, so consent and request are one observable step. **Hide images** removes them and revokes consent; it cannot undo a request already sent.

**Consent is separate, revocable view state.** `createImageConsentScope()` makes one scope per view (`contentViewFromDocument`; React's `FaithfulCardView.consent`). A grant is live until revoked and never restored, so a later Show images is a new grant. The application owns the scope and is its **sole owner of view-wide revocation**: it calls `revokeAll()` when its selection changes or it observes another retirement signal, and `retire()` when the view ends. A card asks the scope for grants and gives back only its own; it never calls `revokeAll` or `retire`. Consent ends on Hide images, new content or a replaced trusted view, a card's disposal or disconnection, and `revokeAll` or `retire`. The MCP views revoke the scope before applying every delivered result (a new result is a new selection even with identical text, so a repeated identical result needs fresh consent) and retire it on host teardown and disposal; retirement is terminal, every later `grant()` is dead, and the control is disabled with a "view ended" notice. A control kept from replaced content or from before a disconnect does nothing, and a new view starts with no consent. No account, session or focus signal exists in the public episode view; `revokeAll` is where one would call.

<a id="trusted-artwork-and-fonts-react3-resources"></a>**Document restrictions.** MCP Apps `resourceDomains` is one broad permission (scripts, styles, fonts, media and images), so the server also inserts a second `<meta http-equiv="Content-Security-Policy">` derived from the same policy (`embedContentPolicy`, composed by `mcp/content-resource.ts`):

- `default-src 'none'`; `script-src` and `style-src` `'unsafe-inline'` only (the single-file view); `media-src`, `connect-src`, `frame-src` and `object-src` `'none'`.
- `img-src` and `font-src` each start with the mode's embedded baseline (`data:` and `blob:` in Standard, `data:` only in Strict; Strict never has `blob:`), then add exactly the configured image origins or font origins. An empty, single or multiple list extends the baseline and never replaces it. These schemes fetch nothing from the network, so trusted template or CSS can embed artwork and fonts as data URLs at either level. There is no embedded-asset opt-in.
- An image host never authorizes a font and a font origin never authorizes an image; a font origin gets no script, stylesheet, image, media, frame or connection access. A remote font stylesheet is a stylesheet request and is not authorized by its font origin. The resource declares the union of both lists once as `resourceDomains`.
- A document must satisfy the host's policy and this one, so a listed origin gains only its own resource type. Redirects are checked against the same `img-src`; a redirect to an unlisted origin is not followed.
- **Enforcement gate.** The view rebuilds the policy from the JSON in its own resource (an invalid one stops the view before anything mounts) and treats images as enforced only when the document carries exactly the restrictions that policy derives (`establishImageEnforcement`). Without them every image stays inert, even from a listed host. This is evidence about the document, not a host's own enforcement.
- **Font URLs are trusted authored inputs.** Font requests carry network metadata and `unicode-range` can reveal which subsets were needed, so never build a font URL from answer text, credentials or private data. A static asset-version parameter is fine; an origin allowlist does not validate a URL's content.
- Markdown `data:` and `blob:` images stay rejected, with or without consent. An answer cannot select assets, CSS, templates or policy.
- **Identity.** The episode view is served as `ui://views/view.<32 hex digits>.html`, the `viewUriForHtml` identity of the final document after the policy is embedded. A change to code, policy (including `fontOrigins`), CSS, fonts or artwork bytes is a new resource; equal filenames and bytes keep one. Strict and Standard never share a URI, because the embedded configuration differs, even with identical host metadata. The URI does not cover the CSP declared beside the document. `npm run candidate:identity -- --level strict [--blocked-presentation inert-text] --image-host HOST [--font-origin ORIGIN]` reports a configured resource's URI, bytes and SHA-256.
- **Authored Play is separate.** The playback resource and its capability, origin and entitlement rules are unchanged; a content image host is never added to them (`playback/content-policy-separation.test.ts`). The deployed player embeds no content policy, because the policy's `connect-src 'none'` would block the media fetch: its card runs the default Standard policy with an empty allowlist, loads no image, and opens links only through the host's `ui/open-link`.

Presentation renders into the light DOM and reads `--saga-card-font-family`, `--saga-card-line-height`, `--saga-card-text-color`, `--saga-card-accent-color`, `--saga-card-muted-color`, `--saga-card-border-color` and `--saga-card-code-background` (each with a neutral fallback). The card's own wording (placeholders, `image-not-loaded`, the hostname) is an element with `data-annotation` (`link-blocked`, `image-blocked`, `markup-blocked`, `image-not-loaded`, `link-host`), italic except the hostname; supplied labels and text that merely spells a placeholder are never marked. The shared styling surface, including the `data-saga-closing="paragraph"` marker, is in [faithful-card-styling.md](faithful-card-styling.md). The application owns the question, status text, branding, fonts and any footer or attribution semantics. Shared, renderer-neutral description fixtures live in `packages/components/src/faithful-card/description-fixtures.test-support.ts`; another renderer can import them, and nothing claims identical pixels.

- **One interpretation.** The card renders the typed nodes the components package produces (shared reader, one parser, unchanged wire contract) as fixed elements with text children; no raw-HTML escape hatch exists. Order, Unicode, right-to-left text, tables and failures behave as in Lit; failure sentences have one owner, `describeContentFailure`. Everything else (unlisted host or port, `http:`, credentials, relative address, `data:` or `blob:` Markdown reference, and every image when enforcement is not established) stays text in place with a `data-reason` (`host-not-allowed`, `not-https`, `credentials`, `malformed`, `enforcement-unestablished`, `consent-required`); an image that fails to load becomes the same text with `load-failed`. Reveal source makes no grant, loads no image and asks the host for nothing.
- **Committed requests only.** React fills elements before it knows a render is kept and a browser requests an image once an element has an address, so the image receives its address in a layout effect after commit (`image.tsx`); a discarded render or ended consent cannot start a request. Because consent can end between render and that effect, the effect asks the shared policy again (`imageStillPermitted`) and gives no address if it no longer agrees. A grant is made only by a press. The card learns of `revokeAll` and `retire` through `useSyncExternalStore`; cleanup of a committed revision revokes only that card's grants, so Strict Mode's replay finds none and a sibling's images stay.
- **Lifecycle.** Card state belongs to a content revision and starts over when content or the trusted view changes: source visibility, link outcomes and every earlier control. Rendering derives values only; the host is asked only from a press. A control applies to the revision it was rendered for, a late answer for replaced content is dropped, an answer after unmount is dropped without a React warning, and a card asks its A2UI node whether it still stands before asking the host for anything.
- **Styles.** Templates (`nodes.tsx`), lifecycle (`lifecycle.ts`) and the stylesheet are separate; every rule is scoped under `.saga-card`. The seven tokens keep names and fallbacks; `--saga-card-font-size` and `--saga-card-reading-width` (default `70ch`) are new. The semantic classes are documented in the stylesheet header and `styles.test.ts` fails if the card renders an undocumented one.

React 18, other 19.x and other A2UI releases are not claimed.

### Protected browse and Play

<a id="subscriptions-for-the-verified-request-identity-browse1"></a><a id="recovering-from-a-failed-subscription-read-browse2"></a><a id="play-an-episode-only-after-a-fresh-entitlement-check-play1"></a><a id="protected-media-expiry-and-delivery-constraints-play2"></a><a id="view-teardown-and-acquisition-scoped-cleanup-state1-partial"></a>

These endpoints use synthetic accounts, a generated tone and development-only verifier tokens (`mcp/dev-auth.ts`, which throws when `NODE_ENV=production` and is imported only by `mcp/serve.ts` and tests). A remote host passes its own `OAuthTokenVerifier` to `startEpisodeListener({ subscriptions })`; the listener has no default. Run them with `npm run build && npm run serve:mcp`. The [walkthrough](authorized-playback.md) shows the SDK and application split, the Play sequence, media checks and player states.

**Browse: `POST /subscriptions/mcp`.** Returns the signed-in user's own subscriptions.

- *Authentication* (`mcp/request-auth.ts`, application-owned). A bearer credential is checked by an `OAuthTokenVerifier` before any server is built or backend called. Missing credential: `401` with `WWW-Authenticate: Bearer realm=...`; malformed, unknown or expired: `401 invalid_token`; verified but not a user (service-only, no account or scope): `403 insufficient_scope`. The accepted credential is copied into a frozen, request-owned snapshot before it is attached to `req.auth`, so a verifier that reuses or mutates its own `AuthInfo` cannot change which account an earlier request used. It reaches the tool only as `ctx.http.authInfo`; an `accountId` argument is dropped; the optional `status` filter cannot name an account. There is no shared current-user state.
- *Projection* (`mcp/subscriptions.ts`, `subscriptions-server.ts`). Strict, bounded zod projection: each field is copied explicitly (no spreading) and validated before serialization; a record that breaks the contract yields a generic tool error and canary private fields never reach the wire.
- *View session.* The result carries an opaque label (`vs_` + 22 characters, an HMAC of the sign-in id under a per-process key). `subscriptions-view.ts` pins the opening host delivery; a different label, unknown shape or error clears the private view. A `toolinput` notification does not authenticate the next `toolresult` (they are not correlated). When the host proxies server tool calls, a new input starts `App.callServerTool`, and only that response may establish or recover the pin; the read carries the declared `status` filter, and a status the tool does not support clears the view instead of widening the read. A finished read does not recycle its identity. An unsolicited notification cannot open private rendering, but an error, changed label or unknown shape clears the view even while a correlated read is in flight and retires reads that started before the loss; only a correlated read started after the loss may recover. A host refusal of the proxied call (HTTP 401 or 403, before any handler) keeps the view cleared. The label controls freshness only; the server authorizes every call.
- *Reading a failure.* Read the HTTP status before the JSON-RPC body; none of these forwards a backend status or a raw `Error.message`.

| What you see | Class | Meaning |
| --- | --- | --- |
| `401` or `403`, `WWW-Authenticate: Bearer ...`, body `{ "error": "..." }`, no `jsonrpc` | Authorization | The credential is missing, invalid, expired or not a user. The tool did not run. Sign in again; `insufficient_scope` means it is not a user sign-in |
| `413`, `406` or `415`, body `{ "error": "..." }`, no `jsonrpc` | Transport | Body over the browse limit, or `Content-Type` or `Accept` missing. The tool did not run. A chunked body with no `Content-Length` is the same 413, sent before the connection closes |
| `400`, or `200` with `jsonrpc`, `id` and `error` and no `result` | Protocol | Malformed JSON (`id` is `null` when unreadable), malformed call, unknown tool or an argument over the input limit. A batch is classified before any element runs: a one-element batch keeps that element's error and id; a longer rejected batch is one invalid request and runs nothing. The tool name is not echoed. The tool did not run |
| `200` with `result.isError` and a fixed sentence | Tool failure | The tool ran, or rejected its business input, and returned a safe sentence. A backend read that does not finish within its limit, or is cancelled, is this failure (`Subscriptions are unavailable.`). The limit is the read's own `readBoundMs` when set, otherwise the route's or SDK instance's operation limit (3,000 ms by default); it never extends the request's lifetime; a later resolution is not sent. An empty `subscriptions` array is a successful read, not this |

- *States.* **Empty** (`data-state="empty"`): the read succeeded with no rows; Try again refreshes that read. **Retry** (`data-state="retry"`): the read could not complete; private rows and the selection are cleared and Try again calls `list_subscriptions` with no arguments, not the failed input. **Cleared** (`data-state="problem"`): the result was not a subscriptions result, the projected output was invalid or the input was rejected; private values are cleared. Backend text is never shown. A selection stays only when the next successful read still contains that subscription id. A delayed copy of an earlier result cannot restore a sign-in-required state.
- *Try it.* After `npm run build`: `curl -s -X POST http://127.0.0.1:3001/subscriptions/mcp -H 'authorization: Bearer <a development token printed in mcp/dev-auth.ts>' -H 'content-type: application/json' -H 'accept: application/json, text/event-stream' -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"list_subscriptions","arguments":{}}}'`. There is no separate diagnostic command.

**Play: `POST /playback/mcp`.** Lets the signed-in synthetic subscriber press Play in an embedded view and hear a protected episode.

- *Recipient binding: proof of possession.* The view creates a non-extractable ECDSA P-256 key and sends only its public half in the Play call's `_meta` (`saga-a2ui/recipient-key`); arguments stay `{ episodeId }`. The media service binds the capability to the verified account, the episode and that key's thumbprint. A media request must carry the capability **and** a fresh ES256 proof signed by that key naming the exact URL, method and capability; each proof is single-use. A copied capability, another user or episode, a missing, stale, replayed or mis-targeted proof, and an expired capability each get the same `403` with fixed body `{"error":"forbidden"}` and no protected read. A bearer URL alone is never enough.
- *App-only declaration and private channel.* `play_episode` declares `_meta.ui.visibility: ['app']`; the only model-visible tool is `get_playable_episode`, which mounts the view and checks no access. A successful Play puts the capability only in `result._meta['saga-a2ui/playback']`; `content` is a fixed sentence and there is no `structuredContent`. Both projections are strict, bounded zod schemas parsed before serialization. The static view resource is identical for every caller. Play's input is a strict object, so a forged `accountId` is rejected, not dropped.
- *Gesture and truth.* The press calls `player.prepare()` synchronously (creating and resuming the `AudioContext` inside the activation) and authorizes asynchronously. If the browser still holds audio back the view shows `gesture-needed` and a second explicit press plays; it never autoplays. Audio is fetched and decoded with Web Audio, so the view needs only `connect-src` for the media origin. `playing` is reported only after the audio clock advanced. `pause()` and `resume()` return promises, so `paused` or `playing` show only once the audio did that; a Resume the browser withholds shows `resume-blocked` and keeps the position; a Pause or Resume the player cannot perform is `media-failed`; audio that ends before start is confirmed shows `ended`. The other states are `denied`, `expired`, `unsupported` and `unavailable`.
- *Wire mapping.*

| Condition | Result |
| --- | --- |
| Missing, invalid, expired credential | HTTP `401` + `WWW-Authenticate`, before any tool |
| Service-only credential | HTTP `403 insufficient_scope` |
| Malformed call, unknown tool, oversized argument | JSON-RPC error from the request gate (`protected-request.ts`), tool not run |
| Known tool, invalid input (including a forged `accountId`) | `isError` with a fixed sentence; the rejected key and value are not echoed |
| Denial, unknown episode | `isError`, "Playback denied: this account does not have access to this episode." (identical for both) |
| No usable recipient key (host dropped `_meta`) | `isError`, "Playback is not supported here."; zero entitlement checks, zero media reads |
| Backend failure, projection that breaks its contract | `isError` with a different fixed sentence; no capability is disclosed and no backend text is exposed. Projection failure can occur after capability issuance, so this is not proof that no capability exists |

- *Server limits to know.* The MCP server package maps any handler failure to an `isError` result and copies the thrown message, which is why handlers catch everything and return fixed sentences; there is no JSON-RPC internal-error path for a registered tool, so a "sanitized internal error" is an `isError` result with a fixed sentence. The media origin answers any origin (`Access-Control-Allow-Origin: *`, no credentials) because a sandboxed iframe sends `Origin: null`; that is safe only because no cookie or ambient header authorizes media. Headless Chromium asserts only that the audio clock advanced; audible playback in a real host is an owner acceptance run.
- *Host feasibility, still open.* Recipient binding needs the host to forward `_meta` on the view's proxied `tools/call` and let a sandboxed iframe `fetch` the media origin with custom headers. The local fixture shows the mechanism works when it does and that Play fails closed (`unsupported`, no protected fetch) when it does not. Whether each named host carries the binding was decided only by its recorded receipts; nothing here weakens the binding for a host that cannot.

**Media acquisition rules.** Every acquisition, whole body or range, runs the same checks in order and stops at the first failure with the same `403` and no read of protected storage: capability known and unexpired on the **service's** clock, episode scope, proof from the bound key (single-use, so a range needs its own proof), then **current entitlement**. Only then is storage read and `Range` interpreted.

| Rule | Decision |
| --- | --- |
| Lifetime | 60 seconds from issue (`capabilityTtlSeconds` overrides); usable while `now < expiresAt`, and the view is told that same `expiresAt`. Using a capability does not extend it; a new Play issues a new one |
| Revocation lookup | The application's `checkEntitlement`, asked again on every acquisition for the capability's account and episode. A denial refuses the request **and drops the capability**, so access granted again later is reached only through a new Play |
| Lookup or storage fault | Never a grant and not a refusal: `503` with fixed body `{"error":"unavailable"}`, no dependency text on the wire or in logs, distinct from the `403` for expired, revoked or misused. A fault does not revoke the capability |
| In-flight response | A response that passed every check is not tracked or cancelled and finishes; every acquisition that starts after revocation or expiry, including a range issued while the first runs, gets no bytes |
| Bytes already delivered | Cannot be retracted. Stopping the player reduces continued use of held media; it does not erase what the browser or host buffered |
| Ranges | One `bytes=` range (`a-b`, `a-`, `-n`) is `206` with `Content-Range` and `Content-Length`; `Accept-Ranges: bytes` is sent on whole answers. A `bytes=` range that cannot be served as one slice (past the end, reversed, `-0`, `-`, several, non-numeric) is `416` with `Content-Range: bytes */<length>` and no body, sent only to a caller who passed every check; a range in another unit is ignored and the whole body is sent (RFC 9110) |
| Cache | Every answer that can carry bytes or a status (`200`, `206`, `403`, `416`, `503`) is `Cache-Control: private, no-store` with `Vary: Origin, Range, x-saga-capability, x-saga-proof`; the player also fetches with `cache: 'no-store'` |
| Origins | The only origin the view may reach is the one the resource declares in `connect-src`. A grant naming another origin is blocked by that policy in the built view: nothing, not even a preflight, reaches it, and the player reports a media failure |
| Redirects | The media service never redirects, and the player fetches with `redirect: 'error'`, so capability and proof headers never follow a redirect to an undeclared destination |

- *Recovery in the view.* Expiry or revocation between grant and fetch shows `expired`; any other media failure (network, `5xx`, redirect, undecodable bytes, blocked origin) shows `media-failed`. Both stop the player, clear the source and offer one explicit press, which is a brand-new Play (fresh authentication, fresh entitlement check, fresh capability). Nothing refreshes a capability from saved view state, nothing retries on its own, and no public MP3 or chat URL is substituted. The status line is the polite live region and the control keeps keyboard focus through `expired`.
- *Limits.* The built player fetches the whole body with one request and never sends `Range`; range behavior is exercised at the service's HTTP edge. The view does not compare a media URL's origin itself; the resource's `connect-src` rejects an undeclared destination, and a host that ignores the resource's CSP would not. The synthetic entitlement lookup and storage are in-memory seams; a real application owns revocation latency, and this service guarantees only that it asks on every acquisition. ChatGPT web and Claude web behavior (forwarding `_meta`, allowing the `connect-src` origin, focus and announcements) is owner acceptance work.

**Playback controller and teardown.** Play is one server action built with `Action.server('play', transport)` and bound to the rendered control. The synchronous prefix (`input`, `atActivation`) selects the item, takes a lease from the application's player owner (`player-owner.ts`) and unlocks audio inside the click. Two prerequisites run in order before the handler, the host-capability check and recipient-key creation: a failure of either is `unsupported`, a stall in either is plain `unavailable`, and the protected request is never sent. The handler makes the host call, validates the grant, signs the proof, acquires the body, decodes and starts the player, and on a confirmed start transfers the lease to the owner with nothing awaited between. The action's work deadline (30,000 ms by default, overridable through the action host's `limits`) bounds key creation through the start of audio; progress never extends it, a successful start ends it without stopping the audio, and a continuation delivered after it passed is dropped. The success hook is under the 5,000 ms hook budget. `App.callServerTool` gets the invocation's signal, a timeout no wider than what remains or the 60,000 ms transport safeguard (`HOST_CALL_SAFEGUARD_MS`, which only mirrors the MCP Apps client's own timeout), `resetTimeoutOnProgress: false`, and the recipient public key as request `_meta` through `call(name, args, { meta })`, never in arguments.

- A rejected, timed-out or aborted host call is `unavailable` with `requestOutcome: 'unknown'` (never "sign in" or "denied"): a capability may have been issued, so no retry is invited and the status asks the user to open the episode again, with focus on the status. A host call that resolves is classified before expiry or recovery are decided: only the server's two fixed early refusals (denied, unsupported, both made before a capability exists) and a valid grant for the selected episode and pinned sign-in establish a known outcome. A valid grant under another sign-in label ends the view for good. A proof, media, decode or start failure after a valid matching grant is plain `unavailable` or the matching state, with its permitted manual recovery. No attempt retries itself.
- A changed selection is a changed subject: the binding cancels an undecided Play at its next checkpoint, and every opener, valid or not, replaces the subject's identity. A Play whose control was retired while pending shows `ready` when nothing was sent, plain `unavailable` after a known grant, and `unavailable` with `requestOutcome: 'unknown'` once the request was sent. The protected media request is preceded by the invocation's own `current()` checkpoint, so an overdue proof or retired Play dispatches nothing. Pause and Resume are local actions that call the player inside the click and present what it reports for the lease it still holds.
- **Label loss (decided 2026-10-19, [#105](https://github.com/MachineWisdomAI/saga-a2ui/issues/105)).** The controller pins the sign-in label of its first opener. An opener or grant under a different label ends the view for good: it clears the selection, stops the player and shows `session-changed` ("Your session changed. Open a new view or reload to continue.", no control). From then on every opener is ignored, and Play, Pause and Resume send no request, prepare no audio and acquire no media. A new view or reload pins its own label. A same-label opener for another item before any loss replaces the selection. The label is freshness only; the server still authorizes every request.
- **Host teardown.** The subscriptions controller retires the read in flight, stops its timer and drops private rows and selection; late answers present nothing and `retry()` and `select()` do nothing. The playback controller releases the player, aborts the byte request and retires itself through its `ended` state (label loss has its own terminal flag): Play, Pause, Resume, the player's end event and every continuation of an earlier press present nothing, prepare no audio and send no request. A late `start` settling for a retired Play releases the player only while no later Play has taken it over, and never touches a newer Play's audio. On host teardown `runToolResultView` invokes the controller's teardown once, answers the host, then closes the connection once; `dispose()` is idempotent. Late cleanup is scoped to its own lease, so an old acquisition's release or start cannot stop a newer player. With the Web Audio player in Chromium, `stop()` rejects a start that is decoding or waiting for the audio clock.
- **Left open on purpose.** A same-label delayed opener cannot be detected (no request id; the server still authorizes every request). ChatGPT web and Claude web teardown order, view reuse, whether a late `toolresult` follows teardown and whether an aborted call is forwarded are unobserved beyond the recorded receipts. Hide images cannot retract a request already sent.

### Actions

<a id="direct-action-attachment-act1"></a><a id="asynchronous-local-actions-act4"></a><a id="resource-ownership-in-the-invocation-scope-act5"></a><a id="server-actions-and-the-joined-contract-act6"></a><a id="configurable-action-defaults-and-error-categories"></a><a id="the-action-contract-across-the-current-codebase-act7"></a><a id="qualifying-the-shared-action-seam-in-react-act2"></a>

One runtime in `@saga-a2ui/core/actions` serves every renderer: no registry, handler-name table, global bus, retry layer or second API. It imports no renderer, DOM or MCP module. The [action binding design](../blueprints/modules/action_binding.blueprint.md) holds the vocabulary: a *component type* is a kind of control; a *definition* is the ID-bearing layout entry (a *template* repeats it per *data item*); a *rendered instance* is one component a renderer created; a *binding* is one action definition attached to one event of one instance; an *invocation* is one activation of a binding, which may hold *resources* and make a server *request*. The [action guide](actions.md) walks a complete example.

| Export | Holds |
| --- | --- |
| `@saga-a2ui/core/actions` | `Action.local`, `Action.server`, `prerequisite`, `proceed`, `refuse`, `componentKind`, `createInstanceHost`, `ActionError`, the types |
| `@saga-a2ui/core/actions/action-button-schema` | `ActionButtonApi`, the renderer-neutral contract of the opt-in control, shared by Lit and React |
| `@saga-a2ui/lit/actions` | `ActionButton` (kind token), `actionButtonEntry`, `ActionButtonElement`, `createLitActions`. The main `@saga-a2ui/lit` entry imports no action code |
| `@saga-a2ui/react/actions` | `ActionButton`, `ActionButtonEntry`, `InstanceHostProvider`, `useActionSetup`, the activation types. Imports React and upstream `@a2ui/react`; no Lit, no MCP |

The shipped surface is exactly what `packages/{core,lit,react}/src/actions/index.ts` export; declarations in the Blueprint that are not exported there are design illustrations.

**Application code follows three steps.**

```ts
// 1. The layout names the control by ID and type. It carries no action and no handler name.
{ id: 'save', component: 'ActionButton', child: 'save-label' }

// 2. Build the action once. Immutable; one definition serves any number of controls.
const save = Action.local<ActionButtonActivation>('save-draft')
  .input((event) => ({ text: String(event.read('/draft')) }))        // copies what the handler needs
  .before(requireSession)                                            // reusable prerequisites, in order
  .run(({ params, provided, signal }) => saveLocally(provided.user, params.text, signal))
  .limits({ deadlineMs: 10_000 })                                    // optional override for this action
  .onSuccess(({ result, current }) => { if (current()) showSavedAt(result.savedAt); })
  .onFailure((context) => { /* context.stage, context.failure and context.failure.category */ })
  .whenBusy('ignore')
  .build();

// 3. Opt in once: list the entry in the catalog and give the app element its setup.
createA2uiAppElement({
  /* catalog, layout */
  actions: createLitActions({
    attach: (view) => view.watchById('save', ActionButton, (handle) => handle.bindAction('activate', save, { subject: () => handle.read('id') })),
    onSetupError: reportSetupProblem,
  }),
});
```

For React, list `ActionButtonEntry`, mount one `InstanceHostProvider` per rendered surface and run setup under it with `useActionSetup(setup)` (a stable-identity function). Use `watchById` there: `A2uiSurface` 0.13.0 renders a placeholder in the first commit, so no instance exists while the first setup effect runs and `getById` finds none.

**Discovery and routing.** IDs select handles during setup only: `getById` for exactly one instance (it throws for none or several, naming the ID) and `watchById` for every present and later instance, such as each row of a template. An activation never looks anything up: the control's own click calls the callable installed in that instance's own slot, keyed by the event names its kind declares. Repeated IDs give separate instances with separate data scopes; `event.read(path)` answers only during delivery, and `handle.read(path)` is the live reader (`undefined` once retired). Replacing the item at a position keeps the instance and binding; the next press sees the new item.

**Binding rules.** One instance and event admit one live binding, so a second `bindAction` throws. `dispose()` is idempotent and detaches only its own installation, after which the handle can bind again. Binding an event the instance does not offer, or through a handle whose instance was retired or whose setup ended, throws. A recreated component is a new instance that starts unbound and idle; handles for the old one are stale.

**Execution.** A press runs `input`, then (optionally) the activation prefix, prerequisites, the handler and the hooks. A synchronous action runs in the click's own call stack and is `idle` again before the click handler returns. Failures decided synchronously for a definition with no `onFailure` are rethrown to the event caller after the binding returned to `idle`, but only failures that carry an error (`invalid-input`, `prerequisite-error`, `handler-error`, `success-hook-error`); a refusal is not an error and is not thrown; an asynchronous failure has no caller to return to. A local action makes no MCP request.

**Strict opt-in control.** `ActionButton` has a strict schema with `child` and optional `checks` and no `action`, so a layout that adds an upstream action, a `functionCall` or a handler name is rejected when ingested, before any property resolves or any function runs. The element is the only click site. A control with no attached action does nothing; a failing `checks` rule disables it as it does the upstream Button. Upstream `Button`s and their protocol actions are untouched and deliver exactly once.

**Ownership.** `createLitActions` gives each presented surface its own host before it first renders, so every `watchById` is registered before any control opens an instance. It ends (disposing bindings and discovery subscriptions) when the surface is deleted or replaced, when setup fails, and when the element disconnects. A reconnected element gets a new host and a fresh `attach`. Unsubscribing a `watchById` stops later handles only. A setup that throws leaves nothing bound and shows the safe fallback (Lit) or reports to `onSetupError` and propagates to the nearest error boundary (React); a discovery callback that throws loses only its own bindings. `ActionButtonElement` finds its host from its place in the DOM, crossing shadow roots outward and accepting only an app element whose own `<a2ui-surface>` is the nearest surface above the control; a second surface for the same model, or a control in light DOM outside the app element's shadow tree, is unbound. In React an instance is the span of one layout effect for one committed `(host, node)` pair, so a render React never commits publishes nothing; it retires through the effect's cleanup, `node.addCleanup` (the upstream resolver disposes a node synchronously) and the host's `close()`, each idempotent. `InstanceHostProvider` creates its host in an effect and closes it in cleanup (Strict Mode's simulated unmount closes the first host and makes another); closing is terminal.

**Prerequisites** are application work before the handler, not authorization and not pending UI. They run strictly in order, may answer synchronously or with a promise, and see `provided`, `params`, `signal` and their own `current()`. `refuse(reason)` ends the invocation as `failed` in the `prerequisites` stage and the handler never runs; a throw, a key two prerequisites both provide, or an answer that is neither `proceed` nor `refuse` is `prerequisite-error`. A prerequisite that passes locally never stands in for the server's check.

**Bounds.** Each setting resolves on its own: the action's `limits` override, then the configuration of the SDK instance that owns the binding, then the default (`deadlineMs` 30,000 ms, `hookMs` 5,000 ms). Omitting a setting inherits it; it never disables a bound; no limit needs to be declared. An instance is the `InstanceHost`: pass `limits` to `createInstanceHost`, to `createLitActions({ attach, onSetupError, limits })` or to the React `InstanceHostProvider` (fixed for the provider's lifetime). Supplied values must be finite and greater than zero; anything else throws a `TypeError` where it is supplied, before any binding, even when another layer would override it. Supplied objects are copied, and an invocation's limits are resolved once, when its binding is made. `deadlineMs` starts when the synchronous activation prefix ends and covers prerequisites and handler together; progress never extends it and a late result cannot revive the invocation. `hookMs` is a separate budget for `onSuccess`, the outcome hook, each resource release and `onFinally`. There is no whole-invocation timer, so an invocation whose failure hook, release and `onFinally` all stall settles about 45 seconds after it started under the defaults. A timer is armed only when a step returns a promise; timers cannot interrupt blocked JavaScript; limits longer than one platform timer (about 24.8 days) are waited out in consecutive timers. `onSuccess` is awaited before success is decided: its exception or overrun is `failed` (`success-hook-error` or `success-hook-timeout`) in the `running` stage and carries the handler's result. A hook past its budget is no longer waited for, is recorded as a `budget-exceeded` diagnostic reaching `onFinally`, and cannot hold the binding in `settling`.

**Currentness.** Every prerequisite, the handler and every hook gets its own `current()`, which ends for good when the callback finishes, its promise settles, its budget or the work deadline expires, or cancellation or obsolescence makes the runtime stop waiting. It also needs the binding live, the invocation not replaced, the adapter's `isLive()` and an equal subject. A late settlement is dropped (the observer sees `late-settlement` and no value); a late callback cannot start `onSuccess`, change a decided outcome or write over a newer invocation, provided it asks `current()` first. Effects a callback already started are not recalled. Outcomes are decided once: an obsolete failure stays `failed`, does not run `onCanceled`, does not start `onFailure` and still finalizes; an older invocation settling beside a newer one cannot return the newer to `idle`; the runtime never continues an invocation inside one of its own callbacks' call stacks.

**Busy policy and `subject`.** An activation arriving while the binding is `running` or `settling` first rechecks the active invocation, then meets the policy: `ignore` (default) drops it and tells the observer which invocation was busy; `replace` cancels a running invocation with cause `replaced` or, for one already settling, keeps its outcome and makes its presentation obsolete. `bindAction(event, definition, { subject })` takes an optional reader of the item the instance shows, because component or model identity alone cannot tell two items at one position apart. The runtime captures it when the invocation starts and compares a fresh `Object.is` read at its checkpoints (before each prerequisite, when the handler's answer is observed, before a presentation hook, at the busy decision and on every `current()`). A reader that throws at activation ends the invocation as `invalid-input`; one that throws later counts as a change. Adapters may supply `watchScope(revalidate)` so the runtime subscribes only while an invocation is unsettled; Lit and React wire it to `DataModel.subscribe`. An unobserved A, B, A cannot be detected (put a revision into the subject if a row can be deleted and recreated under one key), and once an observed B has canceled an invocation a return to A does not revive it.

**Resources in the invocation scope.** The runtime owns invocation-scope cleanup; the application's resource owner stays responsible for what a token means.

```ts
const play = Action.local<ActionButtonActivation>('play')
  .atActivation(({ scope }) => scope.own(owner.begin(), (lease) => owner.end(lease)))   // the event's own call stack
  .run(async ({ activation }) => {
    const started = await owner.start(activation.token);
    if (started === 'blocked') return { state: 'gesture-needed' } as const;             // the scope still owns the lease
    return activation.transfer((lease) => owner.keep(lease))                            // synchronous adoption, no await between
      ? ({ state: 'playing', lease: activation.token } as const)
      : ({ state: 'gesture-needed' } as const);
  })
  .onCanceled(({ activation }) => owner.end(activation.token))
  .build();
```

- *Three ways in.* `atActivation(({ event, scope }) => value)` runs synchronously after `input` in the adapter's event delivery; its value reaches the handler and every hook as `activation`, and its scope offers `own(token, release)` only. `scope.own` on a handler or prerequisite scope takes a token the caller already holds. `scope.acquire(acquire, release)` awaits an acquisition after the event turn and owns the token on arrival. `Held<Token>` carries `token` and `transfer`.
- *Release at the end.* Every token the invocation still holds is released newest first, after the outcome hook and before `onFinally`, each as its own step with its own `AbortSignal` and `hookMs` budget; a release that never settles has its signal aborted and is not waited for. A release that throws or overruns is a `release` cleanup diagnostic in `cleanupErrors` and to the observer; it never changes the decided outcome or stops later releases. Releases run for an obsolete invocation too.
- *After retirement.* `own` after the outcome was decided releases the token at once and throws `InvocationEndedError`; `acquire` on an ended invocation does not start and rejects with the same error; a token arriving after the end is released at once. `scope.active` is work activity, not freshness (that is `current()`).
- *Transfer.* `held.transfer(adopt)` calls `adopt(token)` synchronously while the invocation is active and returns true only if `adopt` returned a non-thenable and the invocation was still active; the scope then no longer releases it. It returns false once the outcome is decided or the token is no longer held; if `adopt` itself ended the invocation, it returns false and the scope releases the token in its ordinary place. A throw from `adopt` propagates and ownership stays with the scope. A thenable the types could not see throws `TypeError`, keeps ownership with the scope and reports a later rejection to the observer as `cleanup-error` with step `adopt`. Compile time: `Synchronous<Returned>` rejects an `async` adoption callback and an `async` `atActivation`.
- *Activation failures.* A throw or hidden promise from the event-turn callback ends the invocation as `failed`, stage `input`, kind `activation-error`; the handler never runs and tokens already taken are released after the failure hook. A disposal from inside the callback is noted, the scope stops being active at once, and cancellation is decided when the callback returns. If it disposes and then throws, the throw is the outcome, the failure hook does not present, and the scope releases what it owned. Cleanup the failure started still runs to completion.
- *What the owner provides.* `release(token)` and any token-scoped `end(token)` affect only that acquisition and are idempotent, a no-op for a token the owner has superseded. The SDK never calls an owner's stop-everything teardown on binding disposal, subject change or session reset, so a deliberately retained resource outlives a successful invocation. `activation` is typed in the handler and every later hook, and `failure.result` is the handler's own result type, so a result like `playing` is distinct from `gesture-needed` before a hook presents.

**Server actions.** `Action.server<Event, Reply = ServerReply>(label, transport)` starts the same chain as `Action.local`; the handler context also has `call(name, args, options?)` with `options` `{ timeoutMs?, meta? }`. Core stays free of MCP: the application supplies a `ServerTransport`, and in the examples the transport is the MCP Apps `App`. A local handler context has no `call`, by type and at run time.

```ts
Action.server<Event, CallToolResult>('archive-note', app)
  .input((event) => ({ noteId: noteIdOf(event) }))
  .before(requireSession(environment))
  .before(confirmArchive(environment))
  .run(async ({ params, call }) => {
    const reply = await call('archive_note', { noteId: params.noteId });
    if (reply.isError === true) throw new ArchiveRejected('The server declined to archive the note');
    return parseArchived(reply);
  })
  .onSuccess(...).onFailure(...).onCanceled(...)
  .build();
```

- *What `call` sends.* The runtime builds the request options: `signal` is the invocation's signal and `timeout` is the time left on the work deadline counted from the start of the prerequisites. The handler's third argument can only narrow: `timeoutMs` (finite, positive) is clamped to the time left and fields such as `signal` or `timeout` smuggled through a cast are not forwarded. `meta` (a plain object, copied and frozen at call time, otherwise `TypeError` before anything is sent) becomes the request's `_meta` beside, never inside, the arguments. `call` returns the transport's reply unchanged: a tool-level `isError: true` is a result the handler interprets. A transport that rejects (timeout, lost connection, host refusal, abort) rejects `call` and reaches the runtime as `handler-error`, unless the deadline or a cancellation decided first. It is invoked as a method of the transport so an `App` keeps its state. Pinned types: `App.callServerTool(params, options?): Promise<CallToolResult>` from `ext-apps` 2.0.3 and `client` 2.3.1; a transport whose reply has no `content` is a compile error.
- *When nothing is sent.* A `call` after the runtime stopped waiting, after cancellation or the work deadline, or after a checkpoint found the subject changed or the instance gone, rejects without calling the transport. The handler never runs while a prerequisite refuses, throws, times out or is canceled.
- *What an outcome says about the effect.* A failure or cancellation in the input or prerequisite stage: no protected request was sent. A returned tool-level failure the handler throws on: whatever that tool's contract says. `handler-error` from a rejected transport, `timeout` in the running stage and `canceled` in the running stage: the effect is **unknown**, with no retry and no invitation to retry. `success-hook-error`, `success-hook-timeout` and `canceled` in the completing stage: the reply was returned, the result is kept on the outcome, and only client work failed or was abandoned; a known write followed by a client-step failure is reported as such and is never replayed. An abort ends the client's wait; it does not show that the host forwarded it, that the server stopped, or that anything rolled back.

**Error categories.** Every `failure` carries `category` beside `kind`, `stage` and any kept `result`. Known names: `timeout`, `canceled`, `authentication-required`, `permission-denied`, `unavailable`, `validation`, `application`, `unknown`; the type is open, so handle names you do not know. A category comes from evidence only: the runtime's own decisions (a deadline or hook overrun is `timeout`, a refusal is `application`, unreadable input is `validation`), the platform's own `DOMException` named `TimeoutError` or `AbortError` (an ordinary `Error` carrying that name is not one), or an `ActionError(category, message, { cause })` the application throws when it knows (a 401, a typed server error). Anything else is `unknown`; an unfamiliar error, its message or a `status` field is never read as authentication. The original thrown value stays on `failure.error`. The SDK shows none of it: choosing a safe message is the application's.

**Telemetry.** `observe(observer)` receives phases with the label, opaque binding and invocation ids, elapsed time, status, failure kind and the failed cleanup step's name, and nothing else: no parameters, provided values, results or error objects. A throwing observer or listener changes nothing.

### Lynx action attachment qualification (ACT3)

The owner retired the Lynx delivery chain on 2026-10-19. `apps/lynx-fixture` (`@saga-a2ui/lynx-fixture-app`, private) remains in the repository as a retained qualification fixture, not an adapter: it consumes `@saga-a2ui/core/actions`, builds no second runtime, and declares no `@saga-a2ui/lynx` package. ### Candidates, installed consumers and release checks

<a id="installing-the-sdk-and-the-lit-example-from-packed-artifacts-pack1"></a><a id="release-candidate-update-and-rollback-pack2"></a>

A **candidate** is an auditable, private build of the seven SDK packages (`SDK_PACKAGES` in `scripts/release-candidate.ts`: the five release-set packages plus the private `lit` and `lit-mcp-stack`) plus the views and servers built from them. The public release set stays the five packages in the Packages table. It is not a release, a registry install or host acceptance. The maintainer guide is [candidate installation, updates and rollback](candidate-update-and-rollback.md); `docs/release-packages.md` covers release preparation.

- **One place packs packages.** `scripts/packed-consumer.ts` (`installPackedSdk`) installs the same candidate tarball for every consumer in the repository: version `0.0.0-candidate.g<12 hex of the commit>` (`.dirty` when tracked files differ), every SDK dependency and peer pinned to exactly that version, `LICENSE` in every tarball and `THIRD_PARTY_NOTICES.md` in `components`. Repository manifests are untouched, so no owned version is introduced.
- **Commands.** `npm run candidate:pack -- --out DIR` (CI runs it after `verify` and uploads the artifact) packs the seven SDK packages, requires every consumer identity under `apps/lit-host/dist*` to name exactly those digests and this revision, installs them into a clean directory, runs `npm ls --all`, and writes `candidate.json`, `CANDIDATE.md` and the consumer lockfile. `npm run candidate:verify -- --candidate FILE --modules DIR --combination own|card [--page FILE]` reports each installed package that is not the candidate, a combination package that is not installed, a `--modules` location with no `@saga-a2ui` package, a sibling at the wrong version, a built view that is not the recorded resource, and any carried check the record predates (exit 1; a missing or unknown combination is exit 2). `npm run candidate:rehearse -- --candidate FILE` rehearses install of A, update to B and rollback to A as built applications: each stage installs the consumer from that stage's tarballs, rebuilds page and server, connects a real MCP client to confirm the server serves the rebuilt page, and runs the ten `pack1-consumers.spec.ts` cases in a real browser (`SAGA_PACK1_DIR` points the spec at the stage's files). A and B are one revision with different version strings, so it shows the procedure and per-stage behavior, not an upgrade between two versions of the code.
- **Carried cases.** `CARRIED_CASES` in `scripts/release-candidate.ts` names the 15 checks each claimed combination (`notes-own`, `notes-card`, the browse and Play application) rests on, by file and exact title: disclosure and per-request authorization (including after a withdrawn permission), known versus unknown effect, one definition bound to two rendered instances, prerequisite, subject freshness, disposal and page teardown, the installed listener's authentication, scoping, entitlement and media binding, a layout naming an action or handler being refused with a press sending nothing, and a result from a server of another build being refused with guidance. A headless test fails if a listed title no longer exists, and `candidate:verify` reports a record that lacks one as `floor-missing`, so a rollback cannot silently undo an authorization fix.
- **`private` does not stop `npm publish`.** npm 12.0.2 accepted the private candidate manifest in `npm publish --dry-run`, so candidate manifests also name `https://candidate-artifact.invalid/` in `publishConfig.registry` (a host that cannot resolve, RFC 6761). Neither field is the safeguard on its own: no CI job holds a publish credential, and the release recipe builds from a reviewed release change. A mixed set is refused at install (`E404` for the sibling at an exact version not among the tarballs named beside it).

### Starters

<a id="the-clean-lit-and-node-starter-starter1"></a><a id="the-clean-lit-and-express-starter-starter-express"></a><a id="the-clean-lit-and-hono-starter-starter-hono"></a><a id="the-fastify-starter-starter-fastify"></a>

`templates/` holds one maintained starter per qualified pair of the `lit-mcp` stack and a server target. [`templates/README.md`](../templates/README.md) describes the layout and each starter's own README is what a developer reads first. `scripts/qualified-starters.ts` (`QUALIFIED_STARTERS`) lists the templates CI qualifies; `scripts/starter-template.test.ts` fails for a template directory that is not listed, so a pair is not offered before its evidence exists. A qualified pair joins `saga init` only through `SUPPORTED_PAIRS` in `scripts/saga.ts`, and the existing-backend recipes in [attach-to-existing-backend.md](attach-to-existing-backend.md) are generated from the qualified templates (never edit that file by hand; `npm run guide:recipes` renders it).

| `templates/lit-express` | `express` | `express` 5.3.0, `@modelcontextprotocol/express` 2.0.2 (peers `express ^4.18.0 \|\| ^5.0.0`, `server ^2.3.0`), `@types/express` 5.0.6; Express 4 satisfies the peer range but is not the tested recipe |

All pins are exact in each template's manifest and in `apps/lit-host`, from which the qualification links them; tests read the installed adapter's manifest and fail if an installed package falls outside its peer ranges or a starter promises an older Node than the adapter supports. Starters require Node 22.12 or newer (`engines`); CI uses `.nvmrc`.

**What a starter is.** A new project, not a demo: no account, token, media or business record, and no test verifier. One Node listener serves a public `get_status` and a protected `get_account` that shows the verified account of that request. Everything that decides identity or access is a file the application owns and the starter leaves refusing: `server/verifier.ts` rejects every credential (the protected endpoint fails closed until an identity provider is configured) and `server/authorization.ts` is the placeholder policy asked again for every request. The view composes its own catalog (`src/catalog.ts`, no forced FaithfulCard), builds one local action (`src/actions.ts`) and attaches it directly to the rendered Clear control (`src/view.ts`); the layout names no action. The view ends its discovery subscription, bindings and element in one idempotent `retire()` that host teardown and `pagehide` both call; ending a binding does not prove that work a server action started has stopped.

**One source for init, guides and CI.** `scripts/starter-template.ts` exports a template into a directory that does not exist (it never overwrites or follows a symbolic link, installs nothing and runs nothing; a failure removes only what that call created), pins every `@saga-a2ui/*` dependency to one SDK build (templates declare `*`; any other range is an error) and cuts the existing-backend snippets out of the same files: `prepare-view`, `register-protected-operation`, `identity-handoff` and `bind-action`, marked with `// #region saga-snippet:<name>` comments that are not in the exported starter. `npm run starter:snippets [-- --out DIR] [--template NAME]` lists or writes them; an unclosed, unopened, nested or repeated region is an error, and a test fails if a snippet differs from the starter's text.

**Per-framework listener rules.** The templates share the view, operations, identity, policy and verifier source; the Hapi reuse test compares it after formatting. Framework-specific files include the listener, request authentication, manifest, metadata and README. Hapi also supplies `server/bridge.ts` in place of Node's `server/endpoint.ts`. In each, authentication and authorization stay in the application's `verifier.ts`, `authenticate.ts`, `identity.ts` and `authorization.ts`; the framework adds no verifier, session or "current user"; the request's clock (3 s operation, 10 s request, resolved per field and validated before the port opens) starts in the first middleware or hook, before authentication; and the verified `AuthInfo` is copied and frozen per request. Each deliberately avoids the adapter's convenience body parser, because a parser with no deadline would hold a stalled body open outside the request lifetime:

- **Express.** Uses `localhostHostValidation()` and `localhostOriginValidation()` (403 before anything else) and an `identify` middleware (the `identity-handoff` snippet). Not used: `createMcpExpressApp` (installs `express.json()` ahead of every route) and `requireBearerAuth` (would take authentication out of the request's lifetime and decide the required scope for the application).
- **Hono.** Uses `hostHeaderValidation` and `localhostOriginValidation`, the Web Standard Streamable HTTP transport, and reads each POST body with the SDK's own `readRequestBody` as the lifetime's `body` stage. Not used: `createMcpHonoApp`, which parses the body before the routes run.
- **Fastify.** `createMcpFastifyApp` validates Host and Origin (`ALLOWED_HOSTS` is the application's list). Authentication is an `onRequest` hook of the protected route only (the `identity-handoff` snippet), running before the body is read. Fastify's own body parsers are replaced with one that passes the unread stream on, `readJsonBody` reads it as the lifetime's `body` stage, and the route handler hijacks the reply so the transport and deadline answer it. An application that attaches the SDK to existing routes keeps its own parsers by registering the two MCP routes in a plugin of their own.

- **Hapi.** The maintained `server/bridge.ts` starts admission and validates Host and Origin before authentication, bounds streamed body reads and owns transport cleanup. The application's Hapi authentication strategy supplies the verified request snapshot through `request.auth.credentials.authInfo`; the bridge passes it to the per-request factory and Node transport. `scripts/starter-hapi-identity.test.ts` qualifies that identity handoff.

**How a pair is qualified.** `scripts/build-starter.ts` (`npm run build:starter`, part of `npm run build`) exports each qualified template as a developer receives it, installs the packed candidate tarballs beside it, type-checks both projects and builds the single-file view and the server bundle into `apps/lit-host/dist/starters/<template>` with an `identity.json`. `scripts/starter-qualification.ts` is the one headless suite (called by `scripts/starter.test.ts`, `starter-express.test.ts`, `starter-hono.test.ts`, `starter-fastify.test.ts` and `starter-hapi.test.ts`) and `apps/lit-host/e2e/starter.spec.ts` runs six browser cases per pair. They cover: the public operation answering with no credential and serving exactly the built page's bytes; an allowed account seeing only its own; a denied one getting a fixed sentence that names no account; no, malformed, unknown, expired, wrong-scope and account-less credentials refused at HTTP (401 or 403 with a challenge) before any protected work (missing or malformed credentials are refused before the verifier); two overlapping requests each seeing their own account; a verifier that rewrites the object it returns not changing a request whose body is still arriving; a verifier that never answers cut off at the operation limit with a 503 while the public endpoint keeps working; an invalid budget failing before the port opens; the body and delivery boundary (a stalled body is one 408 and a closed connection, a response the deadline overtakes is destroyed); the server refusing to start without the built page; a refusing asynchronous prerequisite sending no protected request; the shipped `server/main.ts` run as its own process refusing every credential; and no test identity, demo verifier or copy of an SDK implementation in the output. Framework-specific cases add foreign Host and Origin refusal (403 before any credential is read), bare 404s that do not name the framework, and authentication of a protected request of any method. The test identities and policy exist only in the specifications, supplied through the listener's public options by a qualification entry the harness adds outside the exported starter.

### The `saga` command

<a id="creating-a-project-with-saga-init-cli1"></a><a id="creating-the-demonstration-with-saga-demo-cli2"></a>

`scripts/saga.ts` is run from a checkout (`npx tsx scripts/saga.ts --help` lists usage and the supported pairs); it is not a package and nothing is published. Exit status: 0 created, 1 refused or failed, 2 command line not understood, 130 interrupted.

```sh
npx tsx scripts/saga.ts init --a2ui-stack lit-mcp --server node ./my-app
npx tsx scripts/saga.ts demo --a2ui-stack lit-mcp --server node ./my-demo
cd my-demo && npm install --omit=dev && npm start
```

- **`init`.** `--a2ui-stack <renderer>-mcp` and `--server <target>` name a pair; `init` copies that pair's maintained template (`exportTemplate`, shared with the starter, snippets and qualification) into the new directory, with every `@saga-a2ui/*` dependency pinned to the build of the checkout it ran from (`0.0.0-candidate.g<12 hex>`; a candidate identity, not a release). It prints the ordinary next commands and says the candidate is not published, so the install comes from that build's tarballs. `SUPPORTED_PAIRS` is a plain list of the pairs CI qualifies: `lit-mcp` on `node`, `express`, `fastify`, `hono` and `hapi`; each row names its template. A template directory existing does not add a pair, a pair whose template stops declaring its stack and server is refused, and any other pair is refused before anything is written, with the supported ones listed. The owner of a further pair adds one row when its qualification passes and removes it while that fails.
- **`demo`.** Creates the standalone demonstration download as a new directory: `server.mjs`, the five built pages under `views/`, `package.json`, `README.md`, `LICENSE`, `THIRD_PARTY_NOTICES.md` and `release.json` (commit, candidate version and digests). It is not a starter: synthetic accounts, fixed development credentials and media live only in this output, and `init` still exports the clean `templates/lit-node`. `SUPPORTED_DEMO_PAIRS` is the entries of `SUPPORTED_PAIRS` whose template is `DEMO_TEMPLATE`: today `lit-mcp` on `node` only; a qualified starter alone adds no demonstration. `stageDemo` in `scripts/build-demo.ts` runs the demo build in a scratch directory outside the repository and the destination, and `createDirectoryInterruptibly` in `scripts/starter-template.ts` writes the files.
- **What it will not do.** Create more than one new directory. A target that exists (directory, file, or symbolic link, dangling or not) is refused and left as it was; a missing parent is refused rather than created; a symbolic-link parent is resolved first. It starts no process: no install, package manager, script or lifecycle hook (`demo` runs only `npm pack` and `npm --version`). The directory is created only if it does not exist at that moment. If a write fails, the directory this run created is removed and nothing beside it is touched; "this run created" is identified by device and inode from the exclusive creation, not by path, and checked before every file and before removal. If another process replaced the path, the command stops, removes nothing there and says so. Node has no directory-relative file calls, so a replacement landing between a check and the call after it is narrowed, not excluded. The copy yields to the event loop before each file, so SIGINT or SIGTERM is seen before the next write: the created directory is removed, the created message is not printed and the exit is 130. During the `demo` build a signal ends it before its next stage, removes the scratch directory and exits 130 with nothing created. SIGKILL or power loss can leave a partial directory, which the developer deletes and re-creates with the same command.
