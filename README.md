TypeScript middleware for connecting existing services to assistant experiences, with renderer choice, explicit data-sharing rules, and server authorization hooks.

## Status

Five private, unreleased SDK packages exist: `packages/core`, `packages/lit`, `packages/mcp`, `packages/components` (the passive FaithfulCard preparation slice), and `packages/react` (a qualification slice of direct action attachment, and the optional FaithfulCard text and image-consent slices). The shared action contract (`@saga-a2ui/core/actions`, with the opt-in Lit and React controls) is implemented as local and server actions, and the Lit application's Play runs on it; "The action contract across the current codebase (ACT7)" below says what it supports, what retained owners keep and what is unqualified. This repository starts private and is intended to become public after a separate publication decision.

Host observations are specific to the tested flow. A Lit consumer displayed host-delivered answers in Alexa+. A separate self-contained React/A2UI probe displayed initial server data in ChatGPT, Claude and the Alexa+ web simulator. Its in-card server-tool update passed in ChatGPT and Claude and timed out in Alexa+; the accepted Lit flow did not exercise that interaction. See the [dated host observations and limits](docs/2026-10-19_host-compatibility-observations_v1.md). These results do not establish the timeout's cause or repair location. The notes browse and its row actions also run through a React consumer of the same contract, server and actions (see "Browsing the notes workflow through React (REACT1)"; experimental, local fixture host only), and the protected Play through a React control of the same controller and actions (see "Playing through React (REACT2)"; also experimental and local). The installed SAGA React card is qualified separately, as a minimal passive card from packed packages in a local fixture host (see "The installed React card as one self-contained resource"); that is not actual-host acceptance, the authenticated browse/Play recipe or a package release.

## Content safety

**Standard** permits validated HTTPS links through the host and images from explicitly allowed HTTPS hosts. **Strict** keeps every link inert, shows blocked fragments as accessible placeholders the reader can reveal as text, and loads a permitted image only after the reader chooses Show images. Both preserve ordinary Markdown formatting and retain server authorization and data-sharing checks. Application code controls the policy.

The optional FaithfulCard component displays supplied Markdown without rewriting or silent truncation. Its passive preparation slice exists as private, unreleased packages (see "The passive FaithfulCard and an installed second consumer"); the complete CARD1 integration is not done. Ansari-specific branding and presentation rules remain in Ansari.

Verify includes typecheck, build, the headless tests and the browser check, so CI does not run that suite a second time.

### Repository verification

`npm run verify` is the one local and CI route. It runs the static guard, headless and browser discovery checks, typecheck, build, headless tests, browser tests, Git LFS pointer check, and version-enrollment check, in that order. It stops at the first failing command and uses that command's exit code. Git LFS must already be installed; the pointer check calls `git lfs`.

Browser installation is an explicit prerequisite. Install the Playwright browser this repository already depends on before verify. Verify does not download a browser and does not substitute a different one:

    npx playwright install chromium

CI runs `npx playwright install --with-deps chromium` before `npm run verify`.

Each invocation writes a disposable receipt to `.wise-agents/verify-receipts/` (ignored) and copies it to `latest.json` in that directory. The receipt records the working directory, the verify process arguments, the Node and npm versions that actually ran, the git commit and tracked dirty state at each command boundary, and each command's name, arguments, timestamps, and exit code. It does not record environment variables or command output, so do not put secrets in command arguments. A run is labeled `pristine-head` only when the commit and tracked dirty state are clean at the start and unchanged through every command that ran. A dirty tracked file or a commit created during verification is recorded as `not-pristine-head`. That label is not itself a failure. Detection is at command boundaries, not a continuous watch. `--exec` replaces the repository suite and marks the receipt `exec`; `npm run verify` does not pass it.

The static guard is not a general truthiness analysis and does not prove a policy is correct. It reports `||` whose left operand, after removing parentheses and zero-argument `.trim()` calls, is a string or untagged template that contains fixed non-whitespace text. It reports the file and line and exits nonzero. It does not flag identifiers, interpolation-only templates, whitespace-only fixed text, `||` nested inside an interpolation, concatenation, `&&`, `??`, non-zero-argument `.trim()`, or other methods. It parses authored `.ts`, `.tsx`, `.mts`, and `.cts` files with the TypeScript compiler and skips `.d.ts`, dependencies, and generated output (`node_modules`, `dist`, `coverage`, `test-results`, `playwright-report`). It does not typecheck.

Test discovery asks Vitest for its file list (`vitest list --filesOnly` against `vitest.config.ts`) and compares that with authored `*.test.ts` files. Playwright `*.spec.ts` files are compared separately with `playwright test --list`. An authored file omitted by its runner fails the check. The file walk does not exclude fixture or `e2e` tests. Discovery does not run the tests, measure coverage, or prove an architectural boundary.

Passing verify does not guarantee coverage, host compatibility, or architecture.

The only application is `apps/lit-host` (private, not published). It deliberately declares no `version`, so it introduces no owned version to enroll; add one only through the repository's version-policy bootstrap when that tooling exists. The workspace root stays private; `packages/core`, `packages/lit` and `packages/mcp` are the SDK packages so far (private, unreleased, no version).

### MCP result lifecycle in the view (MCP2)

`connectEpisodeView` (`apps/lit-host/src/mcp/view.ts`) applies each result to the A2UI session over the bridge connection that `connectToolResultView` from `@saga-a2ui/mcp/view` owns, and nothing else: A2UI decoding stays in `protocols/a2ui`, and the session and surface lifetime stay with `saga-app`. It uses only the upstream `App` API from `@modelcontextprotocol/ext-apps`; there is no extra host handshake and no second fetch of the answer (the host delivers the result it already has).

- Initialization: the `toolresult` listener (`addEventListener`) and `onteardown` are registered before `app.connect`, so a result the host sends right after the handshake is rendered exactly once.
- Replacement: each valid public result is applied as a data-model update and replaces the one shown.
- Failure: an error result, a result that is not a public episode (including undeclared fields) or an ingest failure removes the panel surface and shows a plain-text fallback in `[data-testid="view-problem"]`. The next valid result recreates the surface and clears the fallback.
- Teardown: the resolved `EpisodeViewConnection.dispose()` removes the listener and closes the `App`; it also runs if `connect` fails. A host `ui/resource-teardown` request releases the listener and answers the host, which then ends the connection. Results arriving afterwards are ignored. Connecting the same `App` again starts with exactly one listener, so delivery is not duplicated.

Tests: `src/mcp/view.test.ts` (`npm run test:headless`) joins a real `App` and `AppBridge` over an in-memory transport with a real A2UI session. `e2e/mcp-view.spec.ts` (`npm run test:browser`) controls delivery order through the test-only host fixture's real `AppBridge` against the built view: a result sent during initialization, replacement, each failure kind with recovery, delivery after teardown, and remount. Account or selection isolation is a separate, later concern.

### Subscriptions for the verified request identity (BROWSE1)

A second, protected MCP endpoint, `POST /subscriptions/mcp`, returns the signed-in user's own subscriptions from a synthetic account fixture. Synthetic data only; no real Patreon access, no actual-host (ChatGPT/Claude) acceptance. No new dependencies. (This section describes the slice as built; its MCP delivery now runs through `@saga-a2ui/mcp`, see "Reusable MCP connector (CORE1)".)

- `mcp/request-auth.ts`: application-owned authentication. A bearer credential is checked by an `OAuthTokenVerifier` (the MCP server package's own interface; an unknown credential is an `OAuthError` with `OAuthErrorCode.InvalidToken`) before any server is built or backend called. Missing credential: `401` with `WWW-Authenticate: Bearer realm=...`; malformed, unknown or expired: `401 invalid_token`; verified but not a user (service-only, no account or scope): `403 insufficient_scope`. The accepted credential is copied into a frozen, request-owned snapshot of the validated claims before it is attached to `req.auth`: the transport reads that context only after the body arrives, so a verifier that reuses or mutates its own `AuthInfo` cannot change which account an earlier request was authenticated as. The snapshot reaches the tool only as the SDK's per-request `ctx.http.authInfo`, read inside each invocation; an `accountId` argument is dropped. An optional `status` filter is the only declared argument, and it cannot name an account. There is no shared current-user state.
- `mcp/dev-auth.ts`: **development-only** verifier with fixed public tokens (`DEV_TOKENS`). It throws when `NODE_ENV=production`, is imported only by `mcp/serve.ts` (the loopback demo) and tests, and is kept out of the browser bundles (checked by `e2e/view-bundle.spec.ts`). A remote host must pass its own configured `verifier` to `startEpisodeListener({ subscriptions })`; the listener has no default.
- `mcp/subscriptions.ts`, `mcp/subscriptions-server.ts`: strict, bounded zod projection. Each field is copied from the backend record explicitly (no spreading) and the result is validated before serialization; a record that breaks the contract yields a generic tool error. Canary private fields never reach the wire.
- View session: the result carries an opaque label (`vs_` + 22 characters, an HMAC of the sign-in id under a per-process key). `mcp/subscriptions-view.ts` pins the opening host delivery; a different label, an unknown shape, or an error clears the private view. A `toolinput` notification does not authenticate the next `toolresult` — those notifications are not correlated. When the host proxies server tool calls, a new input starts `App.callServerTool`, and only that response may establish or recover the pin. That read carries the declared `status` filter from the input's business arguments, so a filtered read stays filtered: an undeclared field such as `accountId` is dropped, and a status the tool does not support clears the view instead of widening the read. A finished read does not recycle its identity, so an older in-flight response cannot satisfy a later read or restore private rendering after a later refusal. An unsolicited notification cannot open private rendering, but an error, a changed label, or an unknown shape still clears the view while a correlated read is in flight and retires reads that started before that loss. Only a correlated read started after the loss may recover. A refusal of the proxied call (the listener's HTTP 401/403, before any tool handler) keeps the view cleared. The label controls freshness only; the server authorizes every call.
- `subscriptions.html`, `src/subscriptions-main.ts`: the view, built to `dist/subscriptions-view/subscriptions.html`. States: subscriptions, empty, sign-in required, retry, problem. Values are written with `textContent`.
- `connectToolResultView` (bridge lifetime) is the `@saga-a2ui/mcp/view` export that the episode, subscriptions, answer and playback views share.

Try it locally (`npm run build` first): `curl -s -X POST http://127.0.0.1:3001/subscriptions/mcp -H 'authorization: Bearer dev-only-token-alice' -H 'content-type: application/json' -H 'accept: application/json, text/event-stream' -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"list_subscriptions","arguments":{}}}'`.

### Recovering from a failed subscription read (BROWSE2)

Install and run the same way as the rest of the app: `nvm use`, `npm ci`, `npm run build`, then `npm run serve:mcp`. The protected path is `POST /subscriptions/mcp`. Sign in with a bearer token the configured verifier accepts. The loopback demo accepts only the development tokens printed in `mcp/dev-auth.ts`; it refuses to start that verifier when `NODE_ENV=production`. A remote host passes its own `OAuthTokenVerifier` to `startEpisodeListener({ subscriptions })`. There is no separate diagnostic command.

Read the HTTP status before the JSON-RPC body. They are different failures, and none of them forwards a backend status or a raw `Error.message`.

| What you see | Class | Meaning |
| --- | --- | --- |
| `401` or `403`, `WWW-Authenticate: Bearer ...`, body `{ "error": "..." }` and no `jsonrpc` | Authorization | The credential is missing, invalid, expired, or not a user. The tool did not run. Sign in again. `insufficient_scope` means the credential is not a user sign-in. |
| `413`, `406` or `415`, body `{ "error": "..." }` and no `jsonrpc` | Transport | The body is over the browse limit, or `Content-Type` / `Accept` is missing. The tool did not run. Fix the request. A chunked body with no `Content-Length` is the same 413, sent before the connection is closed. |
| `400` or `200` with `jsonrpc`, `id` and `error`, and no `result` | Protocol | Malformed JSON (`id` is `null` when none can be read), a malformed call, unknown tool, or an argument over the input limit. A JSON-RPC batch is classified the same way before any element runs: a one-element batch keeps that element's error and id; a rejected longer batch is one invalid request and does not run the other elements. The tool name is not copied into the error. The `id` matches the request when one was present. The tool did not run. |
| `200` with `result.isError` and a fixed sentence | Tool failure | The known tool ran, or rejected its own business input, and returned a safe sentence. A backend read that does not finish within five seconds, or whose request is cancelled, is this failure (`Subscriptions are unavailable.`); a later resolution is not sent. An empty `subscriptions` array is not this: it is a successful read. |

The view then shows one of three subscriber states, and never the backend text:

- **Empty** (`data-state="empty"`): the read succeeded and there are no rows. Try again refreshes that same read.
- **Retry** (`data-state="retry"`): the read could not be completed. Private rows and the selection are cleared. Try again calls `list_subscriptions` with no arguments; it does not resend the failed input.
- **Cleared** (`data-state="problem"`): the result was not a subscriptions result, the projected output was invalid, or the business input was rejected. Private values are cleared. Try again is still only the safe read.

A selection stays only when the next successful read still contains that subscription id. A host refusal of the proxied call (HTTP 401/403, before the tool handler) keeps the sign-in-required state; a delayed copy of an earlier result cannot restore it.

Tests: `src/mcp/subscriptions.test.ts` (wire classes, limits, batch classification, chunked 413, a bounded backend read that does not emit late, and the failure fixture), `src/mcp/subscriptions-view.test.ts` (empty, retry, cleared, selection, the declared status filter through a real `App`/`AppBridge`, and a bounded read that does not emit late), `e2e/subscriptions-view.spec.ts` (the same wire results in the sandboxed view).

Tests: `src/mcp/subscriptions.test.ts` (real listener and bearer credentials over HTTP: concurrent users, forged account argument, canaries, bad backend data, every credential failure and its status/challenge, and a paused request whose verifier reuses one mutable `AuthInfo`), `src/mcp/subscriptions-view.test.ts` (session pinning, clearing, recovery only through the correlated `callServerTool` response, an older in-flight read that cannot reuse a later read's identity after a refusal, and session loss that clears while a read is pending), `e2e/subscriptions-view.spec.ts` (built view in the sandboxed host fixture: authorized, changed sign-in, a proxied tools/call whose listener 401 clears the view, a delayed prior result, and recovery from that call's response).

### Play an episode only after a fresh entitlement check (PLAY1)

A third protected MCP endpoint, `POST /playback/mcp`, lets the signed-in synthetic subscriber press Play in an embedded Lit view and hear a protected episode. Synthetic accounts and a generated tone only; no real Patreon access, no actual-host (ChatGPT/Claude) acceptance. One new runtime dependency: `jose` 6.2.12 (MIT) for JWT proofs and RFC 7638 key thumbprints; no MCP-UI, CopilotKit, AG-UI or Ora package is used. The [v0.1.0 playback walkthrough](docs/authorized-playback.md) shows the current SDK/application split, Play sequence, media checks, player states and teardown behavior, with the limits of the observed host support.

    npm run build && npm run serve:mcp   # also prints the playback URL; dev tokens only (see mcp/dev-auth.ts)

Mechanisms chosen for the Blueprint's open decisions (the evidence is the tests named below, run through the real listener and the built view):

- **Recipient binding (decision 1): proof of possession.** The view creates a non-extractable ECDSA P-256 key and sends only its public half in the Play call's `_meta` (`saga-a2ui/recipient-key`); the arguments stay `{ episodeId }`. The media service binds the issued capability to the verified account, the episode and that key's thumbprint. A media request must carry the capability **and** a fresh ES256 proof signed by that key naming the exact URL, method and capability; each proof is single-use. A copied capability, another user, another episode, a missing, stale, replayed or mis-targeted proof and an expired capability each get the same `403` with a fixed `{"error":"forbidden"}` body and no protected read (`playback/media.test.ts`, `e2e/playback-view.spec.ts`). A bearer URL alone is never enough.
- **App-only declaration and private result channel (decision 3).** `play_episode` declares `_meta.ui.visibility: ['app']`; the only model-visible tool is `get_playable_episode`, which mounts the view and checks no access. A successful Play puts the capability **only** in `result._meta['saga-a2ui/playback']` (MCP Apps documents `_meta` as not intended for model context); `content` is a fixed sentence and there is no `structuredContent`. Both projections are strict, bounded zod schemas parsed before serialization. The static view resource is identical for every caller.
- **User gesture (decision 4).** The press calls `player.prepare()` synchronously (creating and resuming the `AudioContext` inside the activation), then authorizes asynchronously. If the browser still holds audio back, the view shows `gesture-needed` and a second explicit press plays; it never autoplays. Audio is fetched with `fetch` and decoded with Web Audio, so the view needs only `connect-src` for the media origin and no media element, URL or `media-src`.
- **Playing means the audio clock advanced.** The view reports `playing` only after that signal; `denied`, `expired`, `unsupported`, `unavailable`, `media-failed` and `gesture-needed` are distinct states, and pending work is retired so a late success cannot restore cleared media. PLAY1 did this with a generation number and an `attemptLimitMs` bound inside the controller; CORE2 replaced both with the shared action runtime: a changed `subject` and the action's work deadline (30,000 ms by default) retire the press, and one deadline covers every client stage until audio advances. See "Bounded requests and playback (STATE2)" below.
- **Pause, Resume and a short episode tell the truth.** `pause()` and `resume()` return promises, so the view shows `paused` or `playing` only once the audio did that. A Resume the browser withholds (`NotAllowedError`, or a clock that does not advance) shows `resume-blocked`, keeps the position, and the next explicit press retries it without a new authorization. A Pause or Resume the player cannot perform is `media-failed`. Audio that ends before the start is confirmed shows `ended`: the end is remembered for the request that was waiting, and the late `started` result cannot replace it, while a retired request still cannot restore anything.

Wire mapping, verified against `@modelcontextprotocol/server` 2.3.1 and `ext-apps` 2.0.3 (see the MCPV2 recipe below):

| Condition | Result |
| --- | --- |
| Missing, invalid, expired credential | HTTP `401` + `WWW-Authenticate`, before any tool |
| Service-only credential | HTTP `403 insufficient_scope` |
| Malformed call, unknown tool, oversized argument | JSON-RPC error from the request gate (`protected-request.ts`), tool not run |
| Known tool, invalid input (incl. a forged `accountId`) | `isError` result with a fixed sentence; the rejected key and value are not echoed |
| Denial, unknown episode | `isError`, "Playback denied: this account does not have access to this episode." (identical for both) |
| No usable recipient key (host dropped `_meta`) | `isError`, "Playback is not supported here."; zero entitlement checks, zero media reads |
| Backend failure, projection that breaks its contract | `isError` with a different fixed sentence; no capability, no backend text, nothing in logs |

Limits worth knowing:

- The MCP server package maps **any** handler failure to an `isError` result (and copies the thrown message into it, which is why handlers catch everything and return fixed sentences); it has no JSON-RPC internal-error path for a registered tool. The ticket's "sanitized internal error" is therefore an `isError` result with a fixed sentence and no success data. A distinct JSON-RPC `-32603` would need a change upstream or a custom dispatcher, which this slice does not add.
- Play's input is a strict object, so a forged `accountId` is rejected instead of dropped. MCP Apps 2 accepts that schema in `registerAppTool`, which also writes the legacy flat `ui/resourceUri` key, so Play and its opener use the helper like every other app tool.
- **Feasibility gap kept open:** recipient binding needs the host to forward `_meta` on the view's proxied `tools/call` and to let a sandboxed iframe `fetch` the media origin with custom headers. The local host fixture shows the mechanism works when it does and that Play fails closed when it does not (`unsupported`, no protected fetch). Neither ChatGPT web nor Claude web has been tried; their result decides whether each can carry the binding. Nothing here weakens the binding for a host that cannot.
- The media origin answers any origin (`Access-Control-Allow-Origin: *`, no credentials) because a sandboxed iframe sends `Origin: null`. That is safe only because no cookie or ambient header authorizes media; the capability and proof decide every request.
- Expiry, revocation, ranges, redirects, origins and caches are decided together in PLAY2 below. [Request and view lifetimes](blueprints/features/request_view_lifetimes.blueprint.md) proposes STATE1/STATE2 scope for selection races, teardown, cancellation and bounded request completion, replacing the [rejected account/session proposal](blueprints/features/account_session_isolation.blueprint.md). Design and breakdown approval remain pending; existing authentication and isolation safeguards and prerequisite edges remain.
- Audio device output is not asserted by headless Chromium beyond the audio clock advancing; "audible playback" in a real host is a Captain acceptance run.

### Protected media expiry and delivery constraints (PLAY2)

The same example media service and foreground player, no new dependency and no general media proxy. The rules below are decided together and each one is pinned by a test named after the behavior. The media checks are drawn in [How authorized playback works](docs/authorized-playback.md#what-the-media-service-checks). They build on PLAY1's recipient binding (capability plus a fresh single-use proof from the bound key); none of them weakens it.

Every acquisition, whole body or byte range, runs the same checks in this order and stops at the first failure with the same `403` (fixed body `{"error":"forbidden"}`) and no read of protected storage: capability known and unexpired on the **service's** clock, episode scope, proof from the bound recipient key (single-use, so a range needs its own proof), then **current entitlement**. Only then is storage read and the `Range` header interpreted.

| Rule | Decision |
| --- | --- |
| Lifetime | 60 seconds from issue (`capabilityTtlSeconds` overrides). Usable while `now < expiresAt`; the view is told that same `expiresAt`. Using a capability does not extend it. A new Play issues a new capability. |
| Revocation lookup | The application's own `checkEntitlement`, asked again on every acquisition for the account and episode the capability was issued for. A denial refuses the request **and drops the capability**, so access granted again later is reached only through a new Play, never by reviving an old copy. |
| Lookup or storage fault | Not a refusal and never a grant: a `503` with the fixed body `{"error":"unavailable"}` and no dependency text on the wire or in logs, distinct from the `403` that means expired, revoked or misused. A fault does not revoke the capability. |
| In-flight response | A response that already passed every check is not tracked or cancelled and finishes. Every acquisition that **starts** after the revocation or expiry, including a range request issued while the first is still running, gets no bytes. |
| Bytes already delivered | Cannot be retracted. Stopping and clearing the player reduces continued use of held media; it does not erase what the browser or the host already buffered or downloaded. This is the explicit buffered-byte limit. |
| Ranges | One `bytes=` range (`a-b`, `a-`, `-n`) is answered `206` with `Content-Range` and `Content-Length`; `Accept-Ranges: bytes` is sent on whole answers. A `bytes=` range the service cannot serve as one slice (past the end, reversed, `-0`, `-`, several ranges, non-numeric) is `416` with `Content-Range: bytes */<length>` and no body, sent **only to a caller who passed every check**, so the length is not a probe. A range in another unit is ignored and the whole body is sent (RFC 9110). |
| Cache | Every answer that can carry bytes or a status (`200`, `206`, `403`, `416`, `503`) is `Cache-Control: private, no-store` with `Vary: Origin, Range, x-saga-capability, x-saga-proof`, so neither a shared cache nor the browser keeps it and a cache that ignores `no-store` still cannot answer one user with another's bytes. The player also fetches with `cache: 'no-store'`. |
| Origins | The only origin the view may reach is the one the resource declares in `connect-src` (the listener's own). A grant naming any other origin is blocked by that policy in the built view: nothing, not even a preflight, reaches the other destination, and the player reports a media failure. |
| Redirects | The media service never redirects. The player fetches with `redirect: 'error'`, so a redirect is a failed acquisition and the capability and proof headers never follow it to a destination the application did not declare. |

Recovery in the view: expiry or revocation between grant and fetch shows `expired`; any other failure of the media request (network, `5xx`, a redirect, undecodable bytes, a blocked origin) shows `media-failed`. Both stop the player, clear the source and offer one explicit press. That press is a brand-new Play (fresh authentication, a fresh entitlement check, then a fresh capability) and ends in playing or the safe denial. Nothing refreshes a capability from saved view state, nothing retries on its own, and no public MP3 or chat URL is ever substituted. The status line is the polite live region and the control keeps keyboard focus through `expired`.

Limits worth knowing:

- The built player fetches the whole body with one request and never sends `Range`. Range behavior is exercised at the service's HTTP edge (real listener, real proofs), not through the player.
- The view controller does not compare a media URL's origin itself; the resource's declared `connect-src` is what rejects an undeclared destination. A host that ignores the resource's CSP would not reject one, which is part of the host feasibility check, not something this service can enforce.
- The redirect rule is exercised in the headless controller test against a real redirecting origin, not in the browser spec.
- The synthetic entitlement lookup and storage are in-memory seams. A real application owns revocation latency; this service guarantees only that it asks on every acquisition.
- `Access-Control-Allow-Origin: *` remains (see PLAY1): a sandboxed iframe sends `Origin: null`. Nothing ambient authorizes media, so this discloses nothing to a page without the capability and a proof from the bound key.
- Neither real host has been tried. Whether ChatGPT web or Claude web forward `_meta`, allow the `connect-src` origin and keep the player's focus and announcements is Captain acceptance work, as is the dependency on STATE1/STATE2 and both content-policy levels.

Tests: `src/playback/media.test.ts` (revocation of an issued capability, sticky revocation, fault versus revocation, in-flight characterization, lifetime boundaries, every range case, `416`, `503`, cache and `Vary` headers, log capture), `src/playback/playback-view.test.ts` (redirect not followed, expiry versus media failure, retry as a new Play, no automatic loop, only the declared origin fetched), and `e2e/playback-view.spec.ts` (the same behavior in the built view: revoked mid-Play with keyboard focus kept and announced recovery, media-service outage, no self-retry, an undeclared origin receiving nothing, headers sent only to the declared origin, no media request after a denied Play, no capability in model-visible fields or the static resource).

### View teardown and acquisition-scoped cleanup (STATE1, partial)

This slice implements the teardown part of [Request and view lifetimes](blueprints/features/request_view_lifetimes.blueprint.md). It adds no dependency and changes no server code. It is **not complete**: the action-view label-loss policy and the actual-host observations remain open (below), so the issue stays open.

What changed:

- **Subscriptions view.** The controller registers `onTeardown`. Teardown retires the read in flight, stops its timer and drops the private rows and selection. A late answer, a late rejection or the read bound then presents nothing, and `retry()` and `select()` do nothing and start no read. Teardown is not disposal: the bridge connection stays open until `dispose()`, which closes it once. The correlated-recovery rule is unchanged (an unsolicited positive result cannot recover label loss; a correlated read started after the loss can).
- **Playback view.** Teardown still releases the player and aborts the byte request, and now also retires the controller: Play, Pause and Resume, the player's end event and every asynchronous continuation of an earlier press present nothing, prepare no audio and send no request. This `tornDown` state is separate from `disposed`, which makes `dispose()` return before it reaches the bridge. Host teardown does not call the connection's `dispose()`, and a later `dispose()` closes it once.
- **Action-view label loss (decided 2026-10-19, [#105](https://github.com/MachineWisdomAI/saga-a2ui/issues/105)).** The playback controller pins the sign-in label of its first opener. An opener or a grant under a different label ends the view for good: it clears the selection, stops the player and shows `session-changed` ("Your session changed. Open a new view or reload to continue.", with no control). From then on every opener is ignored whether it carries the old label, the new label or is unreadable, and Play, Pause and Resume send no request, prepare no audio and acquire no media. A new view or a reload pins its own label and bootstraps normally. A same-label opener for another item before any loss still replaces the selection. The controller tests (`playback-view.test.ts`, "final loss of the pinned sign-in label") and the built-page tests (`playback-view.spec.ts`, "after the sign-in label is lost") pin this. The label is freshness only; the server still authorizes every Play and media request.
- **Late `start` cleanup.** A start that settles for a retired Play releases the player only while no later Play has taken it over; it never stops or otherwise touches a newer Play's audio. The release for the latest retired Play is kept, because a player that does not reject a pending start on `stop()` would otherwise leave audio running.

Real-player ordering (Chromium, Web Audio player, `e2e/web-audio-player.spec.ts`): `stop()` rejects a start that is decoding or waiting for the audio clock, and a start made before the next `prepare()` is rejected by that `prepare()` and cannot end the newer start. The whole-player `AudioPlayer` seam stays: with a player that honors that contract, a stale start never resolves, so the controller's guard matters only for a player that does not. This is not a claim about any other player or about a named host, and it is not a lease wrapper. *Current reading: that per-lease owner now exists (`apps/lit-host/src/playback/player-owner.ts`, delivered with CORE2); this paragraph records STATE1's own behavior.*

Left open, deliberately:

- **Same-label delayed opener.** The view takes the last opener delivered and has no request id to detect a delayed copy; the server still authorizes every request. No mandatory read or host correlation field is added.
- **Actual hosts.** ChatGPT web and Claude web teardown order, view reuse, whether a late `toolresult` follows teardown and whether an aborted call is forwarded are unobserved. The synthetic fixtures here do not establish them.
- **Content consent.** Unchanged. Replacement, error, invalidation, teardown and disposal already revoke or retire it (`packages/components/src/faithful-card/image-consent.test.ts`, `e2e/description-strict.spec.ts`); Hide images cannot retract a request already sent.

Tests: `src/mcp/subscriptions-view.test.ts` ("host teardown of the subscriptions view"), `src/playback/playback-view.test.ts` ("host teardown of the playback view", "late player-start cleanup is scoped to its own acquisition"), `e2e/playback-view.spec.ts` ("the built player after host teardown") and `e2e/web-audio-player.spec.ts`.

### Standard descriptions (POL1)

Episode descriptions are read as Markdown under one trusted, immutable content policy chosen by the application. This section is Standard (POL1); Strict and the reader's Show images control follow in [POL2](#strict-descriptions-and-show-images-pol2). One new runtime dependency: `markdown-it` 15.0.2 (MIT; notices in [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)). No MCP-UI, CopilotKit, AG-UI or Ora package is used. A2UI's optional `@a2ui/markdown-it` peer stays uninstalled; SAGA uses `markdown-it` directly so it controls the token set.

    npm run build && npm run serve:mcp   # the default policy; PORT=… overrides the port

Decisions made here (the Blueprint left them open):

- **Parser and dialect.** `markdown-it`'s `commonmark` preset with linkify, typographer, tables and strikethrough off. Supported: paragraphs, headings, block quotes, bullet and ordered lists, fenced and indented code, rules, emphasis, strong, inline code, soft and hard breaks, links and images. Everything else, including raw HTML (`<b>x</b>`), stays as the characters written. The parser recognises raw HTML only so POL2 can tell it from prose: its tags, comments and blocks become `raw-html` and `raw-html-block` nodes that carry their characters and are rendered as text, never as elements.
- **Input bound.** 2000 UTF-16 code units (`EPISODE_CARD_SETTINGS.maxLength`, the episode consumer's trusted setting; see the FaithfulCard section). Longer input is an explicit "too long" alert, never truncated. The MCP tool contract (`mcp/episode.ts`) is stricter, at 500; the renderer bound covers other data sources too.
- **Nesting bound.** `markdown-it` silently stops reading once open block containers reach its ceiling, which would drop the rest of the text. The ceiling is fixed explicitly (`MAX_NESTING_LEVEL`, 20; a block quote counts one level, a list item two) and a description that reaches it is refused with an explicit "nested too deeply" alert, never partly rendered. Inline nesting (brackets, emphasis) does not drop text and is not limited.
- **Restricted tokens.** `@saga-a2ui/components/faithful-card` (`markdown.ts`) turns the parser's tokens into a closed, deeply frozen set of nodes in source order (`ParsedMarkdown.source` keeps the original string). `@saga-a2ui/lit/faithful-card` renders each node with a fixed template and text bindings; no `unsafeHTML`, `innerHTML` or parser-generated HTML exists.
- **Policy.** `@saga-a2ui/components/faithful-card` (`policy.ts`, `createContentPolicy`) validates `{ level?, imageHosts?, blockedPresentation? }` (see POL2) and returns a frozen policy or an explicit failure; it accepts only canonical lowercase DNS hostnames (labels of letters, digits and interior hyphens, which also covers canonical dotted IPv4) and rejects wildcards, schemes, ports, paths, credentials, uppercase or non-canonical hosts, any character that is a delimiter in a Content-Security-Policy (such as `;`, `,`, `'`, spaces) and bracketed IPv6 literals, more than 32 hosts and unknown settings, and never falls back to something looser. `imageHosts` defaults to empty; `fontOrigins` is a separate trusted list (see "Trusted artwork and fonts"). Link decisions allow only absolute HTTPS without credentials. Image decisions additionally need an exact `https://host` origin match (so suffix tricks, unlisted subdomains, other ports and credentials fail) and demonstrated enforcement.
- **Links.** A link is a button whose accessible name includes the parsed hostname (shown as `(docs.example.com)`; internationalized names appear in ASCII). Activation calls only `HostLinks.open`, backed by the pinned upstream `App.openLink` (`ui/open-link`) when the host advertised `openLinks` (`mcp/host-links.ts`). Denial, failure or a missing capability shows a polite status with the destination as text. There is no `window.open`, anchor or navigation fallback. A result that arrives after the description changed is ignored.
- **Resource restrictions.** MCP Apps `resourceDomains` is one broad permission (scripts, styles, fonts, media and images). The server therefore inserts a second `<meta http-equiv="Content-Security-Policy">` derived from the same policy into the served document (`content/embedded-policy.ts`, `mcp/content-resource.ts`): `default-src 'none'`, `script-src`/`style-src` `'unsafe-inline'` only (the single-file view), `img-src` and `font-src` (each the mode's embedded baseline plus its own exact origins, see "Trusted artwork and fonts" below), and `media-src`, `connect-src`, `frame-src`, `object-src` `'none'`. A document must satisfy the host's policy and this one, so a listed origin gains nothing but its own resource type. Redirects are checked against the same `img-src`, so a redirect to an unlisted origin is not followed.
- **Enforcement gate.** The view rebuilds the policy from the JSON embedded in its own resource (an invalid one stops the view before anything is mounted) and treats images as enforced only when the document carries exactly the restrictions that policy derives (`establishImageEnforcement`). Without them every image stays inert, even from a listed host. This is evidence about the resource document, not about a host's own enforcement; the host fixture shows the effect with a host policy as broad as the spec describes.
- **Identity.** The episode view is served as `ui://sha256/<64 hex digits>.html`, the `viewUriForHtml` identity of the final document after the policy is embedded, with the image origins and font origins as the only `resourceDomains`. A cached resource therefore cannot supply other bytes under the same URI: a change to the application code, CSS, fonts, artwork or policy is a new resource, and equal bytes keep one. A Strict policy never shares a URI with a Standard policy that declares the same origins, although both declare identical host metadata, because the embedded configuration differs. The URI does not cover the declared CSP served beside the document. `createEpisodeServer` and `startEpisodeListener` take the policy explicitly (the listener defaults to Standard with no image host); the view receives its own policy and `HostLinks` through its `saga-app`, never through module state.
- **Authored Play is separate.** The playback resource and its capability, origin and entitlement rules are unchanged; a content image host is never added to them, and choosing one does not change Play's authorization (`playback/content-policy-separation.test.ts`).

Limits worth knowing:

- Neither real host (ChatGPT web, Claude web) has been tried. Whether each keeps the document's second policy when it mounts the resource, forwards `ui/open-link` and applies `resourceDomains` as described is Captain acceptance work. A host that rewrote the document's policy away would make the view treat every image as inert, because the derived restrictions are missing (covered by the stripped-policy browser test).
- Image-only enforcement is demonstrated in the local host fixture's sandboxed iframe in Chromium only. The `securitypolicyviolation` directives and the absence of requests at the network boundary are the evidence.

Tests: `packages/components/src/faithful-card/policy.test.ts` (configuration failures, link and image decisions, derived restrictions, immutability, enforcement), `packages/components/src/faithful-card/markdown.test.ts` (order, preservation, inert HTML and unsupported syntax, the bound), `src/mcp/content-resource.test.ts` and `src/mcp/server.test.ts` (identity, declared origins, embedded configuration), `src/mcp/host-links.test.ts` (a real `App`/`AppBridge`: opened, denied, failed, no capability), and `e2e/description.spec.ts` (the built view in the sandboxed fixture with real `ui/open-link`: order and formatting, hostile input, hostname disclosure, keyboard activation, denial and missing capability without navigation, inert links, stale results, empty and exact-host allowlists, suffix/subdomain/credential/port/non-HTTPS images, redirect, the missing-restriction fallback, a no-restriction control proving scripts, styles, fonts and media would otherwise load, and invalid embedded configuration).

### Strict descriptions and Show images (POL2)

Strict is chosen by the application, like Standard: `createContentPolicy({ level: 'strict', imageHosts?, blockedPresentation? })`, where `blockedPresentation` is `placeholder` (the default) or `inert-text` and is rejected for Standard. The same policy value drives the resource restrictions and the view's decisions. No new dependency.

    const created = createContentPolicy({ level: 'strict', imageHosts: ['images.example.com'] });
    if (!created.ok) throw new Error(created.failure.message); // never mount on a guessed policy
    await startEpisodeListener({ viewHtml, catalog, contentPolicy: created.policy, port });

Behavior (`packages/components/src/faithful-card/policy.ts` and `image-consent.ts`, `packages/lit/src/faithful-card/faithful-card-element.ts` and `blocked-fragment.ts`):

- **Blocked fragments.** Under Strict every link, image reference and piece of raw HTML is a blocked fragment. By default each appears as readable placeholder text in its original position (`[Link blocked]` after the link's label, `[Image blocked: alt]`, `[Markup blocked]`); surrounding prose, order and formatting are unchanged. With `inert-text` the source is shown from the start. In either case a keyboard-operable **Reveal source / Hide source** button switches between the two. It changes visibility only: nothing revealed can execute, navigate or fetch. Revealed source is reconstructed from the parsed fragment (`[label](destination)`, `![alt](source)`, the HTML's own characters), not copied byte for byte; `ParsedDescription.source` still holds the supplied string. A description with nothing to block gets no button.
- **Links stay inert.** `decideLink` refuses every destination under Strict, valid HTTPS included, and image consent does not change that.
- **Show images.** Before consent, including after source reveal, no image request is made (`decideImage` answers `consent-required` for an image that otherwise qualifies). **Show images** is enabled only when `offerImages` finds an image that would qualify now: an exactly listed HTTPS host and demonstrated enforcement, the same test as Standard. It cannot widen the allowlist or relax the document's restrictions, which Strict declares before mounting exactly as Standard does. When no image qualifies the button is disabled and a polite message says images cannot be shown; a description with no image has no button. Under Strict the images load eagerly once consented, rather than lazily, so consent and request are one observable step. **Hide images** removes them and revokes consent; it cannot undo a request already sent.
- **Consent is separate, revocable view state.** `createImageConsentScope()` creates one scope per view (`contentViewFromDocument`); a grant is live until revoked and is never restored, so a later Show images is a new grant. The description element revokes its grant on Hide images, when its description changes, when its view's scope is revoked, and on disconnection, and ignores image load results from before. The view revokes the scope before it applies any delivered tool result (a new result is a new selection even when its description is identical, which also means a repeated identical result needs fresh consent; the view is still live, so the reader can consent again, `mcp/view.ts`, `revokeImageConsent`). When the host asks it to tear down, and when its connection is disposed, the view retires the scope instead (`retireImageConsent`, `ImageConsentScope.retire()`): that is terminal, every later `grant()` is already dead, and the Show images control is disabled with a "view ended" notice. Show/Hide images controls are also bound to the description revision they were rendered for, so a control kept from a replaced description (or from before a disconnect) does nothing when invoked. A new view replacing an old one, or a second view, starts with no consent and cannot inherit it. This slice adds no retention TTL, account switching or focus/resume revalidation, and no observed identity or session signal exists in the public episode view; the scope's `revokeAll` is where such a signal would call once a lifetime design is approved.
- **Identity.** See POL1: the Strict configuration is part of the resource URI and is embedded in the document, so Standard and Strict resources are never confused. `npm run candidate:identity -- --level strict [--blocked-presentation inert-text] --image-host HOST` reports the Strict resource's URI, bytes and SHA-256.
- **Authored Play is unchanged in both modes.** The player resource, capability, origin and entitlement rules are untouched; `playback/content-policy-separation.test.ts` runs its cases under Standard and Strict.

Limits worth knowing:

- Neither real host (ChatGPT web, Claude web) has been tried; the local fixture is not evidence of host enforcement. Final signoff and the integrated authenticated runs stay open acceptance work, as does integration with the separately held lifetime design (STATE1/STATE2).
- Only raw HTML is treated as "unsupported markup". Other syntax the episode's CommonMark dialect does not support (strikethrough, tables) is ordinary text and stays visible under Strict; the answer dialect reads both.
- HTML blocks follow CommonMark: a line that starts an HTML block keeps the rest of that block as raw source, so Markdown inside it is no longer interpreted (Standard shows it as text too).

Tests: `packages/components/src/faithful-card/policy-strict.test.ts` (configuration, link and image decisions, Show images offers), `packages/components/src/faithful-card/image-consent.test.ts` (grant, revoke, view-wide revoke, isolation between views), `packages/components/src/faithful-card/markdown.test.ts` (raw HTML nodes, fragment inventory), `src/mcp/content-resource.test.ts` (Strict identity and embedded configuration), `src/mcp/view.test.ts` (revocation before each result, on teardown and dispose), `src/playback/content-policy-separation.test.ts` (Play under both levels), `scripts/candidate-identity.test.ts`, and `e2e/description-strict.spec.ts` against the built resource in the sandboxed fixture (placeholders, keyboard reveal and hide, hostile input before and after reveal and consent, zero requests before consent, only the permitted image after, disabled states, redirects, Hide images, late results, description change, new selection, teardown, view replacement, failure results, two concurrent views and interleaved Standard and Strict views, resource identity and restrictions). Helpers shared with `e2e/description.spec.ts` live in `e2e/description-harness.ts`.

### Trusted artwork and fonts (REACT3-RESOURCES)

Design: [content safety and resource permissions](blueprints/features/content_safety_levels.blueprint.md#trusted-embedded-artwork). This slice changes only the shared resource policy (`@saga-a2ui/components/faithful-card`, `policy.ts`) and its owned consumers; it adds no package, dependency, registry or configuration flag, and no React code.

- **Baseline.** The document's `img-src` and `font-src` each start with the mode's embedded schemes: `data:` and `blob:` in Standard, `data:` only in Strict. They fetch nothing from the network and are not origins. Trusted template or CSS can therefore embed artwork and fonts as data URLs at either level, and use an application-owned object URL in Standard. Strict never has `blob:`, whatever else is configured. There is no embedded-asset opt-in.
- **One directive per type.** `img-src` is the baseline plus the exact image origins, `font-src` the baseline plus the exact font origins; an empty, single or multiple list extends the baseline and never replaces it (no `'none'` remains in either directive). `script-src`, `style-src`, `media-src`, `connect-src`, `frame-src`, `object-src` are unchanged.
- **`fontOrigins`.** A separate trusted list, default empty: `createContentPolicy({ fontOrigins: ['https://fonts.example.com', 'https://assets.example.org:8443'] })`. Each entry is validated and normalized (lowercase ASCII host, the default port dropped, any other port kept), then deduplicated and sorted. A wildcard, plain HTTP, credentials, a path other than `/`, a query, a fragment, whitespace, a CSP delimiter or a bracketed IPv6 literal is an explicit `invalid-font-origin` failure, never dropped. The host rule is the image-host rule, so a canonical dotted IPv4 address is accepted as an exact host. The list is part of `policy.configuration`, so `createContentPolicy(policy.configuration)` and the embedded copy rebuild an equal policy; the baseline follows from the level.
- **Separation.** An image host never authorizes a font and a font origin never authorizes an image: they are different directives. The resource declares the union of both lists once as `resourceDomains` (the host permission is not per type); the document's own policy keeps each origin to its type, and a font origin gets no script, stylesheet, image, media, frame or connection access. A remote font stylesheet is a stylesheet request and is not authorized by its font origin.
- **Unchanged.** `decideImage`, `offerImages`, Strict consent, link rules and `establishImageEnforcement` (which still requires the exact derived document policy) are untouched. Content images still need an absolute HTTPS URL on an exact image host; Markdown `data:` and `blob:` images stay rejected, with or without consent. The content wire contract is still `contractVersion` and `markdown`; an answer cannot select assets, CSS, templates or policy.
- **Font URLs are trusted authored inputs.** Font requests carry ordinary network metadata, and `unicode-range` can reveal which subsets were needed, so an application never builds a font URL from answer text, credentials or private data. A static asset-version parameter is fine; an origin allowlist does not validate a URL's content.
- **Identity.** The URI of `contentResource` is `viewUriForHtml` (`@saga-a2ui/mcp/server`) of the final document returned by `embedPolicy`, the only identity mechanism, so a change to code, policy (including `fontOrigins`), CSS, font or artwork bytes is a new resource, equal bytes keep the URI, and a new answer reuses it. Runtime assets stay embedded in the self-contained document.
- **Candidate report.** `npm run candidate:identity` accepts `--font-origin ORIGIN` (repeatable) beside `--image-host`.

Evidence (this change; Node 26.7.0, Chromium 1248 through Playwright 1.64.0):

- `packages/components/src/faithful-card/policy-resources.test.ts`: baseline and composition for both modes with empty, single and multiple lists; font origin validation, normalization, ports and rejection of each forbidden form; separation of image and font permissions; round-trip of the configuration; unchanged content decisions. Mutating Strict to carry `blob:` fails 10 of these and 6 browser cases.
- `apps/lit-host/e2e/trusted-assets.spec.ts` drives the built episode view in the sandboxed host fixture, in both modes and with empty and nonempty lists. The document carries exactly the derived `img-src` and `font-src`. A trusted data image and data font written into the served document load (measured natural size and font advance, no network request); a blob image and a blob font load in Standard and are blocked in Strict (security-policy violation, readable fallback text). ### Reusable MCP connector (CORE1)

`packages/mcp` (`@saga-a2ui/mcp`) takes over MCP delivery from the application. It is a **private, unreleased workspace package** with no version (nothing is published, and the version policy has nothing to enroll). The Lit application consumes it through its package name and its three separate subpath exports. This is a preparation slice: the interfaces may change until CORE3, and owned callers migrate together.

| Export | Holds | Imports |
| --- | --- | --- |
| `@saga-a2ui/mcp/server` | `registerPublicOperation`, `registerProtectedOperation`, `viewUriForHtml`, `OperationConfigurationError`, the request-budget seam (`createServerBudgets`, `RequestLifetime`, `LifetimeCause`, `StageFailure`) and the declaration types | MCP server and MCP Apps server helpers, Zod; no renderer, no view code |
| `@saga-a2ui/mcp/view` | `connectToolResultView` (bridge lifetime: listeners installed before connect, delivery once, teardown, disposal) | types only; no server module, no Node built-in, no renderer |
| `@saga-a2ui/mcp/policy` | `ViewCsp`, `CLOSED_VIEW_CSP`, `DEFAULT_OPERATION_MS`, `DEFAULT_REQUEST_MS`, `startBoundedTimer` | nothing |

`packages/mcp/src/exports.test.ts` imports each subpath by name and bundles its module graph (dependencies included) to show a server consumer pulls in no renderer and a view consumer pulls in no server module; `e2e/view-bundle.spec.ts` repeats the check on the built views.

**What the application keeps.** The listener (`mcp/listener.ts`: hosting, Host-header protection, body bounds), authentication (`mcp/request-auth.ts`), request classification (`mcp/protected-request.ts`), domain authorization (which subscriptions belong to the verified account), backend calls and the renderer. The connector never reads a credential: for a protected operation the application supplies `identity(authInfo)`, which turns the transport's per-request verified context into its own immutable value.

**What the connector does** for each declared operation, in this order:

1. *Registers* the tool and its `ui://` view resource on the application's `McpServer`. Protected registration without an identity resolver, sign-in failure text, projection, view or output contract throws `OperationConfigurationError` naming the missing requirement, before anything is served. A non-finite bound is refused the same way.
2. *Validates input* with the declared Zod contract before the handler runs. Undeclared fields (for example an `accountId`) are dropped; the handler never sees them and a protected operation takes its identity only from the verified context.
3. *Resolves identity* (protected only). No acceptable identity gives the declared sign-in text and the handler does not run. A public operation resolves nothing and hands its handler no identity.
4. *Waits for the handler and its projection* as one bounded `handler` operation of the request's lifetime (see "Bounded requests and playback (STATE2)"): the operation limit (`boundMs`, else the route's or SDK instance's limit, else 3 s), what the request has left, and the caller's cancellation signal. A result that loses that race is ignored; a handler that throws or rejects gives the declared `unavailable` text with no message. A call whose request already ended, or that was cancelled before it began, never starts the handler.
5. *Projects explicitly*: `project(record)` builds the model-facing text and the structured data field by field; the connector validates the data against the strict output contract before serialization. A violation gives the declared `invalidOutput` text, not the validator's message.

6. *Links the result to its view.* Every result the operation returns, success or fixed-text failure (absent, refused, unavailable, invalid output, sign-in required), carries `_meta.ui.resourceUri` set to the declared `view.uri`, so a host can mount the view from the result alone and not only from tool discovery. The value comes from the trusted declaration after the result is built; a tool argument, the handler's record or the projection cannot select another resource, and `content`, `structuredContent`, the resource's MIME type and its CSP are unchanged. A request the server rejects before the operation runs (for example an input that fails its contract) is answered by the MCP server itself, not by the operation, and is not stamped.

The handler returns `record`, `absent` (declared text) or `refused` (a fixed safe text for well-formed but unaccepted business input). Projections are the model-visible `content` text and the validated `structuredContent`. **No recipient mapping is adopted**: that depends on the Captain's MAP1 measurement in ChatGPT web and Claude web, so Play's app-only visibility and `_meta` payload stay in `playback/` until CORE2.

### Bounded requests and playback (STATE2)

Implements the server-budget amendment of [Request and view lifetimes](blueprints/features/request_view_lifetimes.blueprint.md) (contract revision `c674060`). Reference-application limits and wording below are implementation choices within that contract.

**Configuration.** Two independent limits: an **operation limit** (3,000 ms, `DEFAULT_OPERATION_MS`) and a **request limit** (10,000 ms, `DEFAULT_REQUEST_MS`). Each field resolves as per-operation or per-route override, then SDK-instance setting, then the default, and an omitted field never changes the other. `createServerBudgets({ operationMs, requestMs })` is an SDK instance; `forRoute(...)` layers a route's overrides; the listener takes `budgets` (instance) and a `budgets` on each endpoint (route). `boundMs` on an operation declaration (and the listener's `readBoundMs` and `answerBoundMs`) is the per-operation override of the operation limit, not a second timer. Every supplied value must be a finite positive number; zero, negative, `NaN`, infinite and non-number values, including values a more specific setting would shadow, are refused when the SDK instance, route, listener or operation is configured, before a callback or port is opened. Settings are copied when created; instances share no timer or mutable default.

**One request lifetime** (`packages/mcp/src/server/lifetime.ts`, portable, no HTTP types). The Node listener starts it when it admits the request, before the first credential, header or body wait. The request deadline is monotonic and absolute. Authentication, body ingestion, the complete handler with its projection, an authorization lookup, a storage read and a media acquisition are each a bounded stage whose wait is the least of its own limit, every enclosing operation's remainder and the request's remainder. Progress, retries, callbacks and revisited stages never renew a deadline. A timer is not the only witness of a deadline: a result is checked against the absolute deadlines when work returns and when it settles, so work that blocked the thread past its limit is refused even though its continuation ran before the timer (JavaScript is not preempted; the result is dropped and nothing later starts). Every wait uses `startBoundedTimer`, which segments delays so an accepted finite limit above the platform timer maximum (2^31-1 ms) is honored instead of expiring at once. A handler's nested work goes through `request.within(stage, work)`, which shares the handler's aggregate budget and hands the work a signal. Racing is the guarantee and the signal asks for cooperation: an uncooperative verifier, lookup or storage read cannot hold the request open, its late result is dropped, and the gate is checked before later stages (no server is built, no authorization snapshot taken, no capability issued, no storage read started and no grant deleted after it closes). Untrusted input cannot choose these settings: the route is chosen from the path.

| Before the response is committed | Answer |
| --- | --- |
| Verifier or admission wait expires | `500 server_error`, never `401` for a wait that merely expired. A late valid identity is dropped |
| Body never completes | `408 request_timeout`, then the incomplete request is closed |
| Tool handler, authorization or storage | the tool's fixed unavailable `isError` result |
| Media lookup or storage | `503 unavailable` with the existing safe headers |
| Caller disconnects | nothing is written |

Real credential refusals keep their `401`/`403` and challenge. An expired request may attempt one immediate safe answer and gets no extra delivery time; a committed response is never given a replacement status. Causes are typed and inspectable (`operation-timeout`, `request-timeout`, `cancelled`, `disconnected`, `auth-refused`, `dependency-failure`, each with a stage and whether an effect is possible); they may hold the original error, so the listener hands them only to the application's `observe` callback and never to a caller. A timeout proves no rollback: a possibly completed write stays unknown and is never offered a retry.

**Finite delivery.** JSON and media responses are bounded through the transport's `finish`, not through the result being ready. A reader that stops reading is closed at the original request deadline; bytes already buffered are not recalled. Destroying a response can itself emit `finish` (with `writableFinished` and `destroyed` both true) before `close`, so only a `finish` on a response nobody destroyed counts as delivery; the listener's `observe` reports `finished: false` for a response the deadline closed. Finish, deadline and disconnect settle once. Media grants keep their own expiry, a spent proof stays spent, an acquisition is a new request with a new deadline, and a denial that arrives after the request ended does not delete the grant (the next acquisition asks the lookup again).

**Streaming.** The request deadline bounds setup up to the established `text/event-stream` response. An established stream may live as long as the transport keeps accepting its bytes: `answer.streaming.idleMs` (default `DEFAULT_STREAM_IDLE_MS`, 30,000 ms, validated before streaming is enabled) closes a stream that goes idle or backs up. Only bytes the transport actually accepts reset it; progress the application reported but never delivered does not. Each later finite operation keeps its operation limit.

**Playback controller.** Play is one server action built with `Action.server('play', transport)` and bound directly to the rendered control (mapping A, CORE2): one work interval spans every pending stage. The synchronous prefix (`input`, `atActivation`) selects the item, takes a lease from the application's player owner and unlocks audio inside the click. Two prerequisites run in order before the handler, the host-capability check and recipient-key creation, so a failure of either is `unsupported` and a stall in either is plain `unavailable`, with the protected request never sent. The handler makes the host call, validates the grant, signs the proof, acquires the body, decodes and starts the player, and on a confirmed start transfers the lease to the owner with nothing awaited between. The shared runtime's work deadline (30,000 ms by default; override through the action host's `limits`) therefore bounds key creation through the start of audio. Progress never extends it, a successful start ends it without stopping the audio, and a continuation delivered after it passed but before its timer is dropped. The success hook that presents `playing` is under the hook budget (5,000 ms). `App.callServerTool` gets the invocation's signal, a timeout no wider than what remains or the 60,000 ms transport safeguard, `resetTimeoutOnProgress: false`, and the recipient public key as request `_meta` through `call(name, args, { meta })`, never in the arguments. A rejected, timed-out or aborted host call is `unavailable` with `requestOutcome: 'unknown'` (never "sign in" or "denied"): a capability may have been issued, so no retry is invited and the status asks the user to open the episode again, with focus moved to the status. A host call that resolves is classified before anything decides expiry or recovery: only the server's two fixed early refusals (denied, unsupported, both made before a capability exists) and a valid grant for the selected episode and pinned sign-in establish a known result. Any other answer is unknown, with the same unconfirmed presentation: a generic `isError` result (the server issues the capability before it labels and validates the response, so an error can follow issuance) and a success with missing, malformed or mismatched private grant metadata. This does not depend on the error's wording or the host, and it holds when the answer arrives after the deadline but before its timer. A valid grant under another sign-in label still ends the view for good. An expiry before anything was sent, or a proof, media, decode or start failure or expiry after a valid matching grant, is plain `unavailable` or the matching state with its permitted manual recovery. No attempt retries itself. Pause and Resume are local actions that call the player inside the click and present what it reports for the lease it still holds. Pending is presented by the invocation's own prefix and replaced by exactly one of its outcome hooks, so it is shown while the Play binding runs and the binding is idle again once audio plays; Play being unavailable while audio plays is application state, not binding busy state. A changed selection is a changed subject (the binding cancels an undecided Play at its next checkpoint), and every opener, valid or not, replaces the subject's identity, so a malformed opener that keeps the selected item still retires an undecided Play and its late grant fetches nothing, while the unchanged selection keeps its manual Play. The protected media request is preceded by the invocation's own `current()` checkpoint (which reads the work deadline's clock), so an overdue proof or a retired Play dispatches nothing. A Play whose control was retired or replaced while it was pending is not left pending: the view shows `ready` when nothing was sent, plain `unavailable` after a known grant, and `unavailable` with `requestOutcome: 'unknown'` once the request was sent (no blind retry is invited; a replacement control's deliberate press starts a new Play). A lost label, a host teardown and a disposal dispose the bindings and stop the audio through the owner. Late cleanup is scoped to its own lease: an old acquisition's release or start cannot stop a newer player. The former controller-local attempt timer, generation counter and abort controller are gone, and `attemptLimitMs`, `PLAYBACK_ATTEMPT_LIMIT_MS` and `PlaybackConfigurationError` no longer exist.

#### Content identity for a served view (`viewUriForHtml`)

A host or proxy that caches `ui://` resources by URI cannot see that an application's HTML changed if the URI stays the same. `viewUriForHtml(html)` from `@saga-a2ui/mcp/server` derives the URI from the SHA-256 of the exact document, `ui://sha256/<64 lowercase hex digits>.html`, and the application uses it as `OperationView.uri`:

    const html = fs.readFileSync('dist/answer/index.html', 'utf8');   // the final, built document
    registerPublicOperation(server, { ...declaration, view: { uri: viewUriForHtml(html), title: 'Answer', html, csp: CLOSED_VIEW_CSP } });

- Apply it to the **final** HTML, after every build, inlining and stamping step. The same bytes always give the same URI; a change to any byte, in the application or in an SDK bundle inlined into it, gives a new one.
- It accepts a string (hashed as its UTF-8 encoding, which is what the connector serves) or a `Uint8Array`. A string with an unpaired surrogate has no exact UTF-8 bytes, so it throws `RangeError` rather than being hashed with a substituted character.
- It is a pure function: no registry, global state or cache, and no action API. It identifies bytes only; it does not authenticate the document or its builder and does not cover the CSP declared beside it. A host that already holds the URI keeps what it cached under it, so the identity helps only once the application serves the new URI.
- The synthetic `examples/answer-consumer` shows both pieces from the installed packages alone (`server/answer-server.ts`). It serves `mcp.html`, a small embedded entry (`src/mcp-main.ts`) that connects with `connectToolResultView` from `@saga-a2ui/mcp/view` and shows each delivered result in the same FaithfulCard and A2UI surface as the standalone `index.html` (`src/answer-surface.ts`), with no form and no answer function of its own. `scripts/answer-consumer.test.ts` builds that page, serves it through the packed `@saga-a2ui/mcp`, and checks over JSON and server-sent events that results, tool discovery and the resource read agree, that hostile question text does not change the link, and that a changed page gets a different URI. `apps/lit-host/e2e/answer-consumer-mcp.spec.ts` then mounts the page the consumer's own server actually serves in the sandboxed host fixture and delivers real tool results over the bridge: initialization, the first result, replacement, failure and recovery, host teardown with a late delivery, remount, and a link that leaves only as a request to the host. #### Public answer operation

`POST /answer/mcp` (`startEpisodeListener({ answer })`, off unless configured) is a synthetic, explicitly public question-and-answer tool, `answer_question`, with its own built view (`dist/answer-view/answer.html`). No credential is read, none is fabricated, and a presented `Authorization` header is not treated as an identity. `responseMode` is `json` (one body when the answer is ready) or `event-stream` (progress notifications, then the answer, as server-sent events).

- *Binding.* The result repeats the question exactly as asked (`{ question, answer }`, strict, bounded to 500 and 2000 characters). The view shows that pair. If the host also announced the question (`toolinput`), a result is shown only when its question is identical (no trimming or case folding); a result for another question, such as a late copy of an earlier answer, is ignored and the view keeps waiting.
- *Early, repeated, late.* A result before any input is shown with its own question; an input for the question already answered keeps the answer; the same answer again is not shown again; a different answer to the same question replaces it. After host teardown or dispose nothing is delivered. An error, a malformed or undeclared-field result, or an unreadable input clears the answer and shows a problem; only the server's three known safe texts are shown verbatim.
- *One handler call, progress, delay.* The handler runs once per call. `request.reportProgress` sends `notifications/progress` only to a caller that supplied a progress token and only while the operation is live; it is a quiet no-op after the operation finished, was cancelled or timed out. In `json` mode progress is not delivered but the delayed answer completes the one request.
- *Bounds and cancellation.* The wait is one operation of the request (`answerBoundMs` overrides the operation limit for this answer; the default is 3 s) and a dropped HTTP request aborts the handler's signal; a late answer has nowhere to go. STATE2 adds the whole-request deadline and finite-delivery bound above; CORE3 records the full matrix (see "The server request contract and its failure paths (CORE3)" below). The application cleans up work it cannot interrupt.
- *No logging of questions.* Neither the connector nor the listener logs the question or answer.

### The server request contract and its failure paths (CORE3)

CORE3 qualifies the request pipeline that CORE1 extracted and STATE2 bounded, through the installed server export, the real listener and the built answer view, and records what an application can rely on. It is a private, unreleased slice; nothing is published. The connector owns server request execution and the callbacks below. It does not own authentication, hosting, domain authorization or the client-side action runtime: an action's `before`, hooks and busy policy are not a request deadline, and a client prerequisite never authorizes a protected handler.

**Callback contract** (`@saga-a2ui/mcp/server`). An operation's `handle(input[, identity], request)` receives an `OperationRequest`: `signal` (aborts on caller disconnection, a cancellation that reaches the request, the handler's budget, the request deadline, or once the operation has finished), `within(stage, work, { limitMs })` for nested work inside the same aggregate budget (rejects with `StageFailure` carrying the typed cause), and `reportProgress(update)`, a quiet no-op after the operation ended. `handle` returns `record`, `absent` or `refused` (with a non-empty text); anything else it returns, including an unknown kind or a refusal without text, is answered with the declared `invalidOutput` text before the projection runs, and anything else it does is a failure. `project(record[, identity])` synchronously returns `{ text, data }`; a returned promise is refused with the declared `invalidOutput` text without being awaited because projection is a synchronous callback contract (any supported awaited work would still spend the same enclosing budget) and its rejection is consumed so it cannot surface unhandled. The connector runs the complete handler and projection as one `handler` operation of the request's lifetime, so identity, authorization, handler and projection spend one budget; progress and a delayed JSON or SSE completion do not renew it. Decisions recorded here rather than invented defaults: the declared Zod input and output contracts own every size, item and string bound (the connector adds none and never truncates), `Projection.text` is checked for being a string and nothing else (bound it in `project`), and the identity resolver is synchronous: a promise, or a result whose `then` cannot be inspected without throwing, is answered with the declared unavailable text and kept as the typed `authentication` cause.

**Failure map.** Each observation is separate: the HTTP status and challenge, the JSON-RPC error, and the tool result's `isError`.

| Trigger | HTTP | JSON-RPC | `isError` | Internal cause (for `observe`, never sent) |
| --- | --- | --- | --- | --- |
| No, malformed, unknown or expired credential | 401 + `WWW-Authenticate` | none | n/a | `auth-refused` 401 |
| Service-only credential or missing scope | 403 `insufficient_scope` + challenge | none | n/a | `auth-refused` 403 |
| Verifier throws, or its wait expires | 500 `server_error`, no challenge | none | n/a | `dependency-failure` / `operation-timeout`, stage `authentication` |
| Body over the limit, never completes, wrong `Accept` | 413, 408 (then closed), 406 | none | n/a | `request-timeout` for the 408 |
| Body is not JSON | 400 | `-32700`, id `null` | n/a | none |
| Malformed MCP call | 400 | `-32600` | n/a | none |
| Unknown tool | 200 | `-32602` | n/a | none |
| Business input refused, record absent | 200 | none | `true`, declared text | none |
| Handler throws, rejects, stalls or is cancelled; projection throws; identity resolver throws or returns a promise | 200 | none | `true`, declared `unavailable` text | `dependency-failure`, `operation-timeout`, `request-timeout` or `cancelled` with the stage |
| Projection is not `{ text: string, data }`, `data` breaks the output contract, or is oversized | 200 | none | `true`, declared `invalidOutput` text, no `structuredContent` | none |
| Backend answers 401, 429 or 503 | 200 | none | `true`, declared `unavailable` text; no backend status, `Retry-After` or challenge | `dependency-failure` with the original error |
| Request deadline passes before anything is committed | the owned stage's answer above, once | | | `request-timeout` |
| Caller disconnects or cancels | nothing is written | | | `disconnected` or `cancelled` |

A cause says whether an effect is possible: a stage that never started (a request already cancelled when its callback was reached) is `effect: 'none'`; anything that began is `'unknown'`. Success output schemas stay strict and a failure never weakens them.

**Cancellation, disconnection and resume are different facts.**

- *The same request's disconnection* aborts the handler's `signal` and drops everything after it; the transport receives no write. Verified by observing every `write`, `end` and `writeHead` made on a response that was already destroyed or ended, in both response modes and after deadline expiry; the transport's own idempotent bare `end()` on a closed response carries nothing and is not counted.
- *A `notifications/cancelled` in the POST that carried the call* is processed before the SDK reaches the tool callback, and **the pinned SDK (server 2.3.1) then invokes the callback with an already-aborted signal**. The connector does not start the handler (or resolve an identity) and no JSON-RPC response is sent for the cancelled call, as the protocol prescribes; the exchange then ends at the request deadline (JSON) or the stream idle policy (SSE). This settles the lifetime Blueprint's candidate gap 3: the older `withinBound` created the handler's promise before reading `signal.aborted` (by source reading of `6c268cc`, not re-run); since the STATE2 lifetime, `execute` runs the handler only inside `lifetime.run`, which refuses an already-aborted signal first, so entry is prevented rather than only its result discarded.
- *A separately posted `notifications/cancelled`* names no running request on a stateless endpoint (each POST has its own server and transport, and the connector keeps no process-wide request or action registry): it is acknowledged `202` and the running handler's signal stays unaborted. Cancellation in this design therefore reaches a handler only by closing its own HTTP request.
- *Resume and replay.* Endpoints are stateless: `GET` (with `Last-Event-ID`) and `DELETE` are refused `405`, the abandoned handler is not run again, and a client's retry is a new request with its own handler run and budget.
- *Assistant-host forwarding is not established here.* Whether a host forwards cancellation, closes the connection, or keeps waiting is a per-host observation (the CORE2 and STATE2 receipts saw a host cancellation notification that did not abort the entitlement signal). Local abort proves no remote rollback.

**Cleanup responsibilities.** The connector stops waiting, ends the signal, drops late results and progress and refuses to start later stages. The application stops work it can on `request.signal` and `within`'s signal, owns idempotency and compensation for work it cannot interrupt (a timed-out write may have completed; nothing is retried or rolled back for it), keeps per-request state in the request, and, as the listener, starts a lifetime per request, reports disconnects and `finish` to it, and closes the transport and server when the response closes.

**Evidence and its limits.** Hosted by Node 26 `http` with the MCP SDK's Streamable HTTP server transport and client, in JSON and server-sent events, against exact tarballs of the workspace package. Not shown: an actual ChatGPT or Claude host (their forwarding, buffering and reload behavior), a reverse proxy or slow-reader network, remote effect rollback, or an install from a registry (the packages are unversioned; the packed test proves contents and declared dependencies). The installed-export test hosts the packed server export on the test host; the application listener (`apps/lit-host`) is exercised from the workspace, and the packed Lit consumer build and provenance harness belongs to #131. The local `AppBridge` fixture is not an actual host.

Tests: `packages/mcp/src/server/request-lifecycle.test.ts` (cancellation before start, same-request versus separate cancellation, every callback that stalls, throws or misreports, writes after closure, over a real transport and client in both modes), `apps/lit-host/src/mcp/request-pipeline.test.ts` (real listener: which layer reports each failure including backend 401/429/503 and verifier faults, canary disclosure across results, discovery, resources, errors, headers, logs and diagnostics, disconnect/resume/deadline, concurrent principals and progress isolation, claims that authorize nothing), `scripts/request-consumer.test.ts` (the same contract from the packed `@saga-a2ui/mcp`) and `apps/lit-host/e2e/request-pipeline-view.spec.ts` (stalled, oversized and failing answers reach the built view only as the declared safe text, and a late answer changes nothing).

### Core and Lit packages (VIEW1)

`packages/core` (`@saga-a2ui/core`) and `packages/lit` (`@saga-a2ui/lit`) take renderer-independent A2UI processing and Lit binding out of the application. Both are **private, unreleased workspace packages** with no version, like `@saga-a2ui/mcp`; nothing is published and the version policy has nothing to enroll. This is a preparation slice: the interfaces may change until the combined CORE3/VIEW2 qualification, and owned callers migrate together. The application keeps its catalogs, components, content policy and its existing Play operation.

| Export | Holds | Imports |
| --- | --- | --- |
| `@saga-a2ui/core/protocols/a2ui/v0_9` | `a2uiV0_9Decoder` (the `MessageDecoder` strategy), validated message cases with `A2uiMessageVisitor`, `createMessageSession` and the ingest result types | upstream `@a2ui/web_core` and Zod 3; no DOM, MCP or renderer (its `tsconfig` loads neither the DOM nor Node typings) |
| `@saga-a2ui/core/protocols/a2ui/zod3` | `z`, the Zod 3 copy upstream A2UI builds on, for authoring catalog component schemas | `zod3` |
| `@saga-a2ui/lit` | `createA2uiAppElement` (mounts one surface from a session and owns its lifecycle) and `defineElements` (explicit custom-element setup) | `lit`, upstream `@a2ui/lit`, the core types; no MCP, no Markdown parser, no optional components |
| `@saga-a2ui/core/actions`, `@saga-a2ui/lit/actions` | Added by ACT1: see "Direct action attachment (ACT1)" | as listed there |

**What the application keeps.** Its catalog (`saga-panel/` and `lit/integration.ts` for browse, descriptions and Play; `answer-card/` and `lit/answer-card.ts` for answers), the component implementations, the trusted content policy, host links, the Play operation, and the composition roots (`main.ts`, `view-main.ts`, `answer-main.ts`) that choose the decoder and session explicitly. Raw wire parsing exists only in core: renderer code receives validated messages.

**Rejection.** `ingest(input)` never throws for bad input. When the current input is rejected (unsupported version, malformed envelope, or an upstream refusal of a component or update), the element clears the surface and shows a safe fallback (`role="alert"`, inert text). Messages of a rejected batch that were applied before the refusal stay applied in the session: there is no atomic rollback. The next input the session accepts removes the fallback and shows the surface again. An application that wants a fresh surface sends `deleteSurface` and creates it again, as the episode view does.

**Registration.** `defineElements` defines tags that are free, leaves a tag bound to the very same constructor alone (so repeating setup, or two catalogs sharing a component, is harmless), and fails with `ElementConflictError` for a different constructor on an existing tag. The first definition is kept, and a failing call defines nothing. Nothing registers at import time.

**Lifecycle.** Connecting creates a session, subscribes to the surface and applies the initial input. Disconnecting unsubscribes and disposes the session; a late `ingest` on a retired element is refused, and a reconnected element starts fresh.

**Answer view.** `answer-main.ts` now renders the public answer through these packages with its own `AnswerCard` catalog: the view still decides which question and answer to show (`mcp/answer-view.ts`, unchanged), and each state is delivered as one `updateDataModel` that replaces the whole card, so a previous question, answer or problem cannot remain beside a new state. The answer view bundle contains neither the panel catalog nor the Markdown policy.

Tests: `packages/core/src/protocols/a2ui/v0_9/protocol.test.ts` (decoding, message cases, field preservation, partial updates, rejections, session lifetime, no DOM), `packages/core/src/exports.test.ts` (supported names; the bundled graph holds no renderer, MCP or DOM runtime), `packages/lit/src/element-registration.test.ts` (the tag rule), `e2e/fixture.spec.ts` and `e2e/lifecycle.spec.ts` (rendering, rejection clears and recovers, partial application, mount and unmount), `e2e/catalog-isolation.spec.ts` (the panel and answer catalogs in one page and one registry: independent data, rejections and disposal; conflicting tag fails and keeps the first), `e2e/answer-view.spec.ts` (early, repeated and late delivery, binding, markup, teardown through the built view), `e2e/own-catalog-consumer/packed-consumer.test.ts` (an application with its own catalog built from the packed core and Lit tarballs, without optional components, FaithfulCard, a Markdown parser or server code), and `e2e/view-bundle.spec.ts` (built artifacts).

Limits worth knowing. The packages are unversioned, which `npm pack` refuses, so the packed-consumer test packs a copy that carries a throwaway version; it proves the package contents and declared dependencies, not a registry install. Exact public source and npm installation, the combined protected/lifetime qualification (CORE3, VIEW2), STATE1/STATE2 and actual-host runs remain separate gates. Play still runs through the application's own operation; the reusable action contract (CORE2) is not used, and at this slice nothing from the proposed designs #69 or #73 was implemented or claimed (ACT1 later added a subset of #73; see "Direct action attachment (ACT1)"). The early Lynx Web investigation that gates freezing the renderer-neutral interfaces has not been performed here, so these interfaces remain candidates. *Current reading (ACT7): CORE2 has since moved Play onto the reusable action contract, ACT3 ran a Lynx Web qualification fixture, and a default Lynx Web worker investigation has recorded a concrete failure; the Lynx delivery chain is retired, so none of this is a Lynx recipe. See "The action contract across the current codebase (ACT7)".*

### The passive FaithfulCard and an installed second consumer (CARD-PREP)

`@saga-a2ui/components` is a private, unreleased and unversioned workspace package like the other SDK packages. It holds one optional export, `@saga-a2ui/components/faithful-card`, and the Lit element that shows it is the optional `@saga-a2ui/lit/faithful-card` export. This is the **passive preparation slice** of CARD1 ([#19](https://github.com/MachineWisdomAI/saga-a2ui/issues/19), delivered under [#99](https://github.com/MachineWisdomAI/saga-a2ui/issues/99)): it extracts the proven description behavior (POL1, POL2) so a second application can install and reuse it. It does not complete CARD1, CARD2, VIEW2 or the protected Play workflow, and it adds no action attachment.

| Export | Holds | Imports |
| --- | --- | --- |
| `@saga-a2ui/components/faithful-card` | The versioned content contract and its reader (`createFaithfulCardReader`, `describeContentFailure`), the host link contract (`HostLinks`, `LinkOpenOutcome`, `NO_HOST_LINKS`, `describeLinkOutcome`), Markdown interpretation into restricted nodes, the trusted content policy (`createContentPolicy`, `establishImageEnforcement`), image consent scopes (`createImageConsentScope`) and the A2UI catalog contract (`FaithfulCardApi`) | `markdown-it`, `zod`, upstream `@a2ui/web_core` and `@saga-a2ui/core` for the catalog schema; no MCP, no renderer, no DOM or server API (checked on the bundled graph) |
| `@saga-a2ui/lit/faithful-card` | `FaithfulCardContentElement` (`<saga-faithful-card-content>`), the catalog entry `faithfulCardEntry` (`<saga-faithful-card>`), `registerFaithfulCard`, and the view seam (`ContentView`, `provideContentView`, `documentContentSecurityPolicies`; `HostLinks`, `LinkOpenOutcome` and `NO_HOST_LINKS` are in the components export, shared with the React card) | `lit`, upstream `@a2ui/lit`, `@saga-a2ui/components` (an **optional peer**: an application that never imports this export does not install it) |

**Use.** An application builds its trusted settings once and answers the cards inside an element with them:

    const reader = createFaithfulCardReader({ dialect: 'commonmark-tables-strikethrough', maxLength: 50_000 });
    const policy = createContentPolicy({ level: 'standard', imageHosts: ['images.example.com'] });
    const view: ContentView = { reader: reader.reader, policy: policy.policy, hostLinks, imageEnforcement, consent: createImageConsentScope() };
    provideContentView(app, view);        // the cards inside `app` receive this view when they connect
    registerFaithfulCard();               // explicit; importing the package registers nothing

and lists `faithfulCardEntry` in its own catalog. The card's two A2UI properties are `contractVersion` and `markdown`; both are bindable, and the schema is strict, so a layout cannot supply an action, a handler name, a dialect or a bound. `examples/answer-consumer` is a complete application built this way.

**Content contract.** Content is untrusted: `{ contractVersion: 1, markdown: string }`. The reader refuses anything else with an explicit failure kind and never repeats the content: `invalid` (not that shape, or an unknown field), `unsupported-version`, `too-long` and `too-nested`. The element then shows an alert and none of the earlier content, and the next valid value recovers. A card with no enclosing view shows nothing of its content.

**Trusted settings, never content.** The reader is created from `{ dialect, maxLength }`, validated on its own (an unknown dialect, or a missing, fractional, non-positive, infinite or non-numeric bound, fails with `invalid-dialect`, `invalid-limit` or `invalid-config`) and with no defaults. `maxLength` counts UTF-16 code units, is the application's finite bound, and is independent of every other consumer's: the episode view keeps its 2,000-unit CommonMark settings (`EPISODE_CARD_SETTINGS` in `apps/lit-host/src/lit/content-view.ts`), and the answer example accepts 50,000 without changing that. The nesting safeguard (`MAX_NESTING_LEVEL`, 20) applies to both.

**Dialects.** `commonmark` is markdown-it's preset with linkify, typographer, tables and strikethrough off; pipe tables and `~~tildes~~` stay readable text. `commonmark-tables-strikethrough` enables the parser's own maintained `table` and `strikethrough` rules and nothing else. Both go through the one implementation. The parser's table rule drops body cells beyond the header's column count, so the reader splits each body row's source line the way the rule does and keeps the dropped cells after the parsed ones; nothing written is lost. Raw HTML, footnote syntax, task-list markers and the like stay as the characters written. A link reference definition is CommonMark syntax that the parser consumes to resolve the links that use it, so a definition nothing uses is not shown. The card never rewrites, translates, summarises, moves attribution, numbers headings or truncates: numbered headings, attribution-like lines and a footer appear as supplied and in place.

**Presentation.** The element renders into the light DOM with fixed templates and text bindings, and reads `--saga-card-font-family`, `--saga-card-line-height`, `--saga-card-text-color`, `--saga-card-accent-color`, `--saga-card-muted-color`, `--saga-card-border-color` and `--saga-card-code-background` (each with a neutral fallback). Block elements use `dir="auto"` so Arabic text reads right to left where the text does, headings start at `h3` (the surrounding page owns the levels above), and a table scrolls inside its own keyboard-focusable region so a narrow screen does not scroll the page sideways. The application owns the question, the status text, branding, fonts and any footer or attribution semantics.

**Policy and consent are unchanged in behavior.** Standard and Strict, exact-host images, the enforcement gate, Show/Hide images and revocation work as described in POL1 and POL2; the code moved and its owners did not. Policy and consent live in the components package without any transport; the host callback and every DOM interaction live in the Lit element, and each card gets them through its own view, so two cards on one page keep separate policy, callbacks and consent. Consent is revoked by new content, by the view's `revokeAll` and `retire`, by Hide images, and by disconnecting the card, and a control kept from earlier content or from before a disconnect does nothing. A reconnected card starts fresh. No invisible account change is detected, because the view receives no such signal.

**Installed, not aliased.** `scripts/build-answer-consumer.ts` packs the core, Lit, components and mcp packages (the browser page uses the first three; the mcp package serves it, see "Content identity for a served view"), unpacks them as installed dependencies of a clean directory outside the repository, links only the third-party packages their manifests declare, and builds `examples/answer-consumer` against those copies: the standalone page, the `mcp.html` page an MCP host mounts, and the consumer's MCP server (`apps/lit-host/dist/answer-consumer-server/server.mjs`, which the browser test connects to). It records the source commit, runtime, tarball digests and each built artifact's digest in `apps/lit-host/dist/answer-consumer/identity.json` (ignored). Reproduce it from a clean checkout:

    nvm use && npm ci
    npx playwright install chromium
    npm run build                                     # includes npm run build:answer-consumer
    npx vitest run --config vitest.config.ts scripts/answer-consumer.test.ts apps/lit-host/e2e/own-catalog-consumer
    npm run test:browser -w @saga-a2ui/lit-host-app -- e2e/answer-consumer.spec.ts e2e/answer-consumer-mcp.spec.ts e2e/faithful-card.spec.ts

An application with its own catalog installs only core and Lit; `e2e/own-catalog-consumer/packed-consumer.test.ts` shows its build holds no components package, `markdown-it`, FaithfulCard element or delivery code, and that the Lit manifest names the components package only as an optional peer. Building the consumer in a browser found that decorator syntax in `@saga-a2ui/lit` sources is not transformed under a consumer's own toolchain, so `createA2uiAppElement` and the card now declare reactive state with `static properties` and `declare`.

Tests: `packages/components/src/faithful-card/reader.test.ts` (settings validation, bound at and over the limit, versions, shapes, no content leakage), `dialects.test.ts` (tables, alignment, dropped cells, strikethrough, CommonMark's readable source, order, numbered headings, attribution, Arabic, long content), `markdown.test.ts`, `policy*.test.ts` and `image-consent.test.ts` (moved with the code; they characterise the extraction), `packages/components/src/exports.test.ts` (supported names and a bundled graph with no renderer, MCP or DOM), `scripts/answer-consumer.test.ts` (the installed consumer's imports, tarballs, manifests and graph), `e2e/faithful-card.spec.ts` (catalog setup, repeated and conflicting registration, dialects, failure and recovery, Standard and Strict effects at the network and callback boundary, two cards interleaved with replacement and disposal, retirement signals, reconnection, keyboard, status and a 320-pixel layout), `e2e/answer-consumer.spec.ts` (the built external page) and the existing `e2e/description*.spec.ts` (the migrated episode consumer).

Limits worth knowing. The integration CARD1 still needed after this slice (the installed set and an authored protected control beside the card) is recorded in "The FaithfulCard beside an authored control (CARD1)" below. The packages are unversioned, so the packed test uses a throwaway version and proves contents and declared dependencies, not a registry install. The external consumer's link callback cannot learn whether the browser opened a window, so it reports only that the request was made. Image loading is observed in Chromium only. No actual host (ChatGPT web, Claude web) was run, and nothing here is a package release.

### The FaithfulCard beside an authored control (CARD1)

This partial fixture slice qualified composition that CARD-PREP left open; the real protected-player integration is recorded in the next section. It adds no component code, no export and no dependency: the card, its policy and consent, `ActionButton`, `createLitActions` and `Action.server` are used as delivered. What it adds is evidence that they compose, and that the card pages are part of the installed-package qualification (VIEW2).

**The composition.** `apps/lit-host/e2e/card-workflow/` is a test-only page, not an application: one A2UI surface whose list rows each render a title, a `FaithfulCard` for the row's `description` and an `ActionButton`. The catalog lists upstream `Text`, `Column` and `List` with `faithfulCardEntry` and `actionButtonEntry`. The application, not the card, binds the Archive server action of the Blueprint to the control with `watchById('row-archive', ActionButton, …)` and `subject: () => handle.read('id')`; the note identifier comes from the row's data scope. Two rows repeat the same component ids. The page's single view gives the cards a Strict policy with one image host and a consent scope.

**What the specs show** (`e2e/card-workflow.spec.ts`, real clicks, the real data model, Chromium):

- Each row's card shows its own description and each control archives its own row's note, one protected request per press, with the prerequisites counted apart from the request. The control is a direct attachment: the surface dispatches no protocol action.
- Supplied Markdown is only text. Text that looks like a control, an action name, a handler choice, a grant or an `onclick` is shown as blocked markup, an inert link or the characters written; clicking it sends no request and runs no prerequisite, opens no link and dispatches no action. The only buttons are the two authored controls, and the real control still sends the note its own row shows, not the one the Markdown names. A layout that gives `ActionButton` or `FaithfulCard` an `action`, or the card a `dialect`, is rejected whole.
- Image consent and the control have separate lifetimes. Replacing a description revokes only that card's consent and does not touch the same row's pending archive; a row that leaves the list retires its card and aborts its pending request, and the application's cancellation hook then says only that the status is unknown; disconnecting the application ends both, and a reconnected presentation runs `attach` again and starts without consent.
- A refusing session prerequisite is shown by the application and does not change the card: the view receives no account signal, so the reader's consent stays until the application, which observed the sign-in change, calls `view.consent.revokeAll()`. Nothing here claims the card detected an account change.
- An unsupported `contractVersion` shows an alert and none of the private text, leaves the other card and the row's control working, and the next valid value recovers.

**Installed set.** `vite.faithful-card.config.ts` and `vite.card-workflow.config.ts` are now in the pages `npm run build:installed-lit-host` builds from the packed `core`, `lit`, `components` and `mcp` tarballs, and `e2e/faithful-card.spec.ts` and `e2e/card-workflow.spec.ts` are in `npm run test:browser:installed`. `scripts/installed-lit-host.test.ts` checks that both pages load the components package, the card element, `ActionButton` and the server action from installed copies and that no module came from a workspace.

Run it:

    npm ci && npx playwright install chromium
    npm run build
    npm run test:browser -w @saga-a2ui/lit-host-app -- e2e/card-workflow.spec.ts e2e/faithful-card.spec.ts
    npx vitest run --config vitest.config.ts scripts/installed-lit-host.test.ts

**Limits, kept explicit.** The transport, session, confirmation and audit are the page's test doubles (the Archive fixture of ACT6); the real Play control keeps its own view and has no card in this slice, so this is not the Play or subscriptions workflow (the card in the protected player is the next section). No actual host (ChatGPT web, Claude web) was run, so how a host forwards an abort or presents the card is unobserved. The specs were written after the behavior existed and passed on their first complete run; they characterize the join and are not test-first history. Mutations of the source that the new spec catches (each reverted): dropping the card's consent revocation on new content (the replacement case fails), and loosening the card's strict catalog schema so a layout may add properties (the rejected-layout case fails). The packages stay private, unversioned and unreleased, so there is nothing to enroll in the version policy and `THIRD_PARTY_NOTICES.md` is unchanged (`markdown-it` was already covered). ### The description card in the protected player (CARD1)

This completes the application composition PR143 left open: the optional Lit FaithfulCard now sits beside the authored, directly bound Play control in the real protected player (`playback.html` / `playback-main.ts`), not in a test-only page. It adds no component, export, dependency or action runtime; the card, `contentViewFromDocument`, `createAppHostLinks`, the image consent scope, `connectPlaybackView` and the CORE2 Play action are used as delivered.

**The composition.** The player's opener result (`get_playable_episode`) already carried the episode's public `description` and the sign-in label. The page now shows that description with `<saga-faithful-card-content>` (public `@saga-a2ui/lit/faithful-card`, contract `FAITHFUL_CARD_CONTRACT_VERSION` from `@saga-a2ui/components/faithful-card`) between the title and Play. No subscriber field was invented and no card is required of other views: the subscriptions list stays a separate view, and the selection here is the opener result. The page builds one `ContentView` from its own document (`contentViewFromDocument`) and answers the card with `provideContentView`; the description supplies no policy, handler, subject or permission.

- **Authored control, trusted inputs.** Play is unchanged: bound to its own rendered instance, with the subject and `episodeId` taken from the selected opener, never from the Markdown. Text that names an episode, imitates a button, carries `javascript:` or a raw `onclick` is only text; pressing it sends no request.
- **Consent has one owner and its own lifetime.** `PlaybackViewDependencies.contentConsent` (optional; a standalone player passes none) is the page's `view.consent` scope. The controller revokes it before every opener is presented (an unchanged description is still a new selection), and retires it for good on label loss, host teardown and disposal. A press, a Play in flight and its outcome never touch consent, and consent ending never touches a Play. The card element removes the private text when a state has no episode (label loss, no selection), so nothing is shown beside a retired control.
- **Terminal retirement ends the card, not only its consent.** The same one-time retirement call also removes the card from the page (`playback-main.ts` wraps the scope's `retire`; no second consent owner and no new controller state). A card left mounted would keep its revision current, so a safe link kept from before teardown would still ask the host to open it and a host answer still pending would still be shown. The removed element invalidates its link results and consent itself, and the page mounts no card again once the view is over. Image Hide, a content-only change and an unrelated live Play stay as they were.
- **Policy.** The player resource is served verbatim and may connect only to the media origin. An embedded content policy carries `connect-src 'none'`, which would block the media fetch, so the deployed player embeds none: the card runs the default Standard policy with an empty image allowlist. It loads no image, and a link opens only through the host's `ui/open-link`. The page still honours an embedded policy, which is how the specs exercise Strict Show/Hide images, replacement, teardown and label loss; whether Play can work under such a resource is not claimed.
- **What stays outside.** The card's contract version is a page constant, so a server cannot induce an unsupported contract here; version failure, recovery and no partial display are the accepted `faithful-card.spec.ts` and `card-workflow.spec.ts` cases and are not repeated. The Archive page of PR143 is untouched.

**Tests.** `src/playback/playback-view.test.ts` (consent revoked before each opener and the unreadable one, untouched by play/pause/resume and a pending Play, retired on label loss, teardown and disposal, once); `e2e/playback-view.spec.ts` against the built page (order and inertness, hostile Markdown cannot play or change the episode, no image request and host-only links, replacement with a late grant for the old selection, label loss, teardown with a retained link click and a host link answer pending across it, and the Strict consent boundary). `scripts/installed-lit-host.test.ts` now expects the player page to load the installed card, components and `markdown-it`; `e2e/view-bundle.spec.ts` checks the player's markup and element construction instead of every character of its script.

**Limits, kept explicit.** The player resource grew from about 305 kB to 818 kB (84 kB to 236 kB gzipped): the card's single export also loads the catalog entry and so the upstream A2UI Lit renderer, whose unused media templates are why the bundle check changed. A catalog-free content-element export (or a side-effect-free manifest) would shrink it; that belongs to the package owner and is not done here. Image consent is exercised only with an embedded Strict policy; the deployed player has no image host. The specs written for the page's behavior were red before `playback.html` carried the card (the browser specs failed on the missing description element, the controller tests on the missing consent hook) and green after; the Strict specs passed on first run and were checked by mutation (removing the consent wiring fails two; not clearing the card on label loss fails two). Those worker checks establish source, installed and browser evidence. The subsequent [bounded ChatGPT/Claude receipt](https://github.com/MachineWisdomAI/saga-a2ui/issues/146#issuecomment-6278612238) verifies the composed description and protected dispatch, observed retirement/remount and fresh recovery at the reviewed installed resource. [The lifecycle record](blueprints/features/reusable_lit_adapter.blueprint.md#status) maps actual merge `11ce39d6d413a3a9a051b4cd8d2303f00883763e`, independent repaired-head validation and host limits. This completes the scoped CARD1 composition, not audio playback, a public release or production deployment.

### Reading the FaithfulCard accessibly in the Lit flow (CARD2)

This qualifies the optional Lit FaithfulCard for long, multilingual and hostile descriptions in the subscriber flow ([#20](https://github.com/MachineWisdomAI/saga-a2ui/issues/20)). It adds no export, dependency, action runtime or card property, and does not repeat the extraction, policy, consent or protected-player work above; it reuses them and adds the cases they did not cover. The React card is a separate owner (#117, #119, #118, #120) and is untouched.

**Shared, renderer-neutral fixtures.** `packages/components/src/faithful-card/description-fixtures.test-support.ts` is plain data with no imports and no DOM: four valid descriptions (long mixed-script notes, a table with code and strikethrough, a hostile description of refused links, images and markup, and long unbroken tokens) and six refused results (a later version, a version given as text, a non-string, a missing value, one unit over the bound, nested too deeply). Each valid fixture states the top-level block kinds the reader finds and pieces of text that must appear in order, not how any renderer draws them. The package manifest leaves it out of the published files and the type-checked source. `description-fixtures.test.ts` reads every fixture through the production reader and policy (and checks the file imports nothing), so a fixture cannot describe something the component does not do. Another renderer can import it the same way; nothing here claims identical pixels.

**Two defects the fixtures found, fixed in the Lit element** (`packages/lit/src/faithful-card/`):

### Direct action attachment (ACT1)

ACT1 is the first slice of the [action binding](blueprints/modules/action_binding.blueprint.md) design (design revision `c6506adccdeb71ac65fb10c793208d127eea7914`, approved 2026-10-17). It builds a synchronous local action fluently and attaches it directly to the exact rendered Lit control that fires it. It is **provisional**: ACT2 (React) and ACT3 (Lynx) challenge its shared seam before ACT4 builds on it, and it establishes neither full portability nor migration readiness. Both packages stay private, unreleased and unversioned.

| Export | Holds | Imports |
| --- | --- | --- |
| `@saga-a2ui/core/actions` | `Action.local(label)`, `componentKind`, `createInstanceHost` and their types | nothing outside core: no Lit, no DOM, no MCP, no third-party module |
| `@saga-a2ui/core/actions/action-button-schema` | `ActionButtonApi`, the renderer-neutral contract of the opt-in control (moved here by ACT2 so the Lit and React controls share it) | upstream `@a2ui/web_core` and core's Zod 3 export; no renderer |
| `@saga-a2ui/lit/actions` | `ActionButton` (the kind token for setup code), `actionButtonEntry` and `ActionButtonElement` (the opt-in control), `createLitActions` | `lit`, upstream `@a2ui/lit`, core; imported by nothing in the main `@saga-a2ui/lit` entry |

Application code follows three steps; the rest is the SDK's:

```ts
// 1. Layout names the control by ID and type. It carries no action and no handler name.
{ id: 'save', component: 'ActionButton', child: 'save-label' }

// 2. Build the action once. Immutable; one definition serves any number of controls.
const save = Action.local<ActionButtonActivation>('save')
  .input((event) => ({ noteId: String(event.read('id')) })) // optional; copies what the handler needs
  .run(({ params }) => saveNote(params.noteId))             // synchronous
  .build();

// 3. Opt in once: list the entry in the catalog, define the element, and give the app element its setup.
createA2uiAppElement({
  /* createSession, initialInput, surfaceId */
  actions: createLitActions({
    attach: (view) => view.watchById('save', ActionButton, (handle) => handle.bindAction('activate', save)),
    onSetupError: reportSetupProblem,
  }),
});
```

- **Discovery and routing.** IDs select handles during setup only: `getById` for exactly one instance (it throws for none or several, naming the ID) and `watchById` for every present and later instance, such as each row of a template. An activation never looks anything up: the control's own click calls the callable installed in that instance's own slot. A slot belongs to one instance and is keyed by the event names its kind declares; there is no registry, no handler-name table and no action bus.
- **Binding rules.** One instance and event admit one live binding, so a second `bindAction` throws. `dispose()` is idempotent and detaches only its own installation; the same live handle can then bind again. Binding an event the instance does not offer, or through a handle whose instance was retired or whose setup ended, throws. A recreated component is a new instance that starts unbound and idle; handles for the old one are stale.
- **Execution.** A press runs `input` then the handler once, in the click's own call stack. Binding state passes `running` and `settling` and is `idle` again before the click handler returns, with a listener call for each change. A press that arrives while the same binding is still running (the handler caused it) is dropped, the default `ignore` policy. A handler or `input` that throws, or returns a promise the types did not show, ends the invocation, returns the binding to `idle`, and then rethrows to the event caller: this slice has no failure hook, and a failure must not disappear. `event.read(path)` reads the pressing instance's own data scope and answers only during delivery.
- **Ownership (Lit).** `createLitActions` makes the app element give each presented surface its own host. It starts before the surface first renders, so every `watchById` is registered before any control opens an instance, and it ends, disposing every binding and discovery subscription, when the surface is deleted or replaced, when setup fails, and when the element disconnects (before the session is disposed). A reconnected element presents a new surface and so gets a new host and a fresh `attach`. Unsubscribing a `watchById` stops later handles only; it disposes no binding. A setup that throws leaves nothing bound and the element shows its safe fallback; a discovery callback that throws loses only the bindings it made and reports to `onSetupError`.
- **Which mount owns a control.** `ActionButtonElement` finds its host from its place in the DOM, not from the surface object: the walk crosses shadow roots outward and accepts only an app element whose own `<a2ui-surface>` is the nearest surface above the control. A second `<a2ui-surface>` for the same model, outside any app element or inside an app element's own shadow tree, leaves its controls unbound. A control in light DOM or slotted content outside the app element's shadow tree finds no host and is unsupported.
- **Strict opt-in control.** `ActionButton` has a strict schema with `child` and optional `checks` and no `action`, so a layout that adds an upstream action, a `functionCall` or a handler name is rejected when it is ingested, before any property is resolved or any function runs. The element is the only click site (do not add a click listener to a rendered button as a shortcut). A control with no attached action does nothing, and a failing `checks` rule disables it as it does the upstream Button. Upstream `Button`s and their `event`/`functionCall` actions are untouched and deliver exactly once.
- **Lit seam.** The element uses upstream's overridable `createController()` and `isConnected`, the model registry and the data path, never `element.node`, which stays unset on the default `a2ui-surface` path. The existing rejection/recovery (`ingest` clears the surface and shows a fallback; the next accepted input recovers it, without atomic rollback) and `ElementConflictError` behavior are unchanged; a control that returns after a recovery is bound again by the same host without running `attach` a second time.
- **Own-catalog consumers.** The main `@saga-a2ui/lit` entry defines only the `A2uiActions` seam type and imports nothing from the action module, so an application that does not opt in bundles none of it. `packed-consumer.test.ts` builds both kinds of consumer from the packed tarballs.

Implemented in ACT1: immutable `Action.local(...).input(...).run(...).build()` with synchronous input and handler, binding state and subscription, direct attachment through `bindAction(event, definition)`, `getById`/`watchById`, ownership of setup, and the Lit control. **Not implemented**, and deliberately not declared (no placeholder methods, no ignored options): `atActivation`, `before`/prerequisites, `limits`, the four hooks, `whenBusy('replace')`, `observe`, the `subject` option, asynchronous handlers, the invocation scope with resource ownership and transfer, `Action.server`, the React and Lynx adapters, and migration of Play or any controller. They belong to ACT2 (React qualification), ACT3 (Lynx qualification), ACT4 (asynchronous local actions), ACT5 (resource scopes) and ACT6 (server actions and the joined contract); CORE2, CORE3 and VIEW2 are separate. Controller safeguards in the Play and subscriptions views are untouched. The ACT3 repair added two members to the adapter-facing `OpenInstance` (`attached(event)` and `subscribe(listener)`), so an adapter can capture the attached binding by reference and learn when it changes; see the ACT3 section.

Tests: `packages/core/src/actions/actions.test.ts` (through the public interface with a renderer-free fake adapter, plus the type-level cases checked by `npm run typecheck`), `packages/core/src/exports.test.ts` (supported names; the bundled graph has no renderer, MCP or DOM runtime and no dependency at all), `apps/lit-host/e2e/action-binding.spec.ts` against the built consumer `dist/action-consumer` (a catalog of upstream Column, Row, List, Text and Button plus `ActionButton`, two app elements, repeated IDs and data paths, later rows, replacement, stale events, two mounts, a second surface mount, setup failure, surface deletion, disconnect and reconnect, rejection and recovery), and `packed-consumer.test.ts` (both consumers from the packed packages). The browser run is local Chromium through Playwright; it is not evidence for any actual host, React or Lynx.

### Qualifying the shared action seam in React (ACT2)

ACT2 gives ACT1's shared runtime a second, real renderer before ACT4 builds on it. `packages/react` (`@saga-a2ui/react`, private, unreleased and unversioned like the other SDK packages) has one export, `@saga-a2ui/react/actions`, and it is **not React parity**: it is the smallest React A2UI consumer of the common seam, with its fixtures kept for REACT1/REACT2 to adopt. Full workflow, optional FaithfulCard, a packed or public package and any named host remain with E15 and are not claimed here.

| Export | Holds | Imports |
| --- | --- | --- |
| `@saga-a2ui/react/actions` | `ActionButton` (kind token), `ActionButtonEntry` (the opt-in catalog entry), `InstanceHostProvider`, `useActionSetup` and the activation types | React, upstream `@a2ui/react` 0.13.0 and `@a2ui/web_core`, `@saga-a2ui/core` (actions and the shared control contract); no Lit, no MCP |

The application writes the same three steps as for Lit; only the third differs:

```tsx
// 3. List ActionButtonEntry in the catalog, mount one provider per rendered surface, and run setup under it.
function SaveActions() {
  useActionSetup(setup); // `setup` has a stable identity, e.g. a module constant or useCallback
  return null;
}
const setup = (view: InstanceView) =>
  view.watchById('save', ActionButton, (handle) => handle.bindAction('activate', save));

<InstanceHostProvider onSetupError={reportSetupProblem}>
  <SaveActions />
  <A2uiSurface surface={surface} />
</InstanceHostProvider>
```

- **What an instance is.** The component function is not the instance: React may re-run it, discard a render before it commits, or mount a second copy. The instance is the span of one layout effect for one committed `(host, node)` pair of the control's boundary (a wrapper around the entry's generated `view`). A render React never commits publishes nothing. The press handler reads the committed instance at press time and calls its installed callable directly: no handler name, registry or lookup, and nothing from Lit.
- **Retirement.** An instance retires through the layout effect's cleanup (host or node change, unmount), through `node.addCleanup` (the upstream resolver disposes a node synchronously, before React has updated the screen) and through the host's `close()`. Each path is idempotent and disposes the instance's bindings, so a retired handle cannot bind and an old cleanup cannot detach a newer installation. The adapter's liveness pull is `!node.disposed`; retirement is the commit-time signal, which is why a separate "committed entry" check in the proposal's sketch was dropped (no test could tell it apart, because retirement already covers it).
- **Provider and setup.** `InstanceHostProvider` creates its host in an effect and closes it in the cleanup, so Strict Mode's simulated unmount closes the first host and the second effect makes another; children render only once a host exists (one extra render). Closing is terminal: a reference kept to a closed host can neither register a setup nor open an instance. `useActionSetup` registers `setup` per `(host, setup)` pair and ends the registration in its cleanup, disposing the bindings made through it, so changing the definition disposes the old binding before the new one binds. A setup that throws reports to `onSetupError` and then propagates to the nearest error boundary (the React counterpart of Lit's safe fallback), leaving nothing bound. A discovery callback that throws loses only its own bindings and reports to `onSetupError` alone.
- **Discovery timing in the published runtime.** `A2uiSurface` 0.13.0 renders its loading placeholder in the first commit and creates its resolver only when the store subscribes, so no instance exists while the first setup effect runs. `getById` at that moment finds none; use `watchById`, which delivers present and later instances (and call `getById` later, from a retained view, for a unique ID). A new `surface` prop passes through the placeholder again, so the root boundary remounts rather than receiving a new `node` prop; the effect still depends on `node`, which no test can reach in this version.
- **Data scopes.** Repeated IDs give separate instances with separate `dataPath`s. The event's `read(path)` answers only during delivery and `handle.read(path)` is the live reader (`undefined` once retired). Replacing the item at a position keeps the instance and its binding, and the next press and the reader see the new item.
- **Upstream Button.** `@a2ui/react` 0.13.0 ships no basic catalog. The test catalog builds Column, Row, List, Text and Button the way an application does, from `createComponentImplementation` over the upstream `@a2ui/web_core` component contracts; its Button calls the resolved `action`, which dispatches on the surface exactly as an upstream renderer's Button does. An `ActionButton` press dispatches nothing upstream, and an upstream Button press runs no attached definition.

**Exact identities the fixtures ran on** (asserted by `runtime-identity.test.ts`, not just printed): `@a2ui/react` 0.13.0 (the published package, not the 0.14.0 commit `45633b9` that the proposal inspected), one shared `@a2ui/web_core` 0.13.0 copy for the renderer, core and this package, React and React DOM 19.3.1, `@types/react` and `@types/react-dom` 19.3.0, jsdom 28.1.0 for the DOM, and Vitest 5.0.4, run on the repository's pinned Node 22.12.0 with npm 10.9.0 (the lockfile is written by npm 12.0.2 and installs cleanly with `npm ci` on 22.12.0). jsdom 28.1.0 is the newest release whose `engines` accept Node 22.12.0: 29.0.0 needs `^22.13.0` and 30.1.3 needs `^22.22.2`, and 30.1.3's `undici` 8 fails to load on 22.12.0 (`createZstdDecompress` is absent), which is how the first revision of this slice failed in CI before any test started. jsdom is a root `devDependency` as well as this package's, so the single root Vitest resolves the same copy. Resolved tarball integrity is in `package-lock.json`. Installing `@a2ui/react` pulled `@a2ui/markdown-it` 0.2.2 at its newest allowed range, whose peer `@a2ui/web_core ^0.14.0` installed a second, hoisted `web_core` 0.14.0 above every package's pinned 0.13.0. Tests: `packages/react/src/actions/actions.test.ts` runs a real React 19 root in jsdom with Strict Mode on by default, a real `A2uiSurface` and real message sessions from core, and presses real DOM controls. It covers two instances each running only their own definition once, an unbound control and an upstream Button, a failing `checks` rule, Strict Mode, a transition that is held and then discarded, keyed-child replacement, surface swap, synchronous resolver disposal before React updates the screen, a host that changes under a node that stays, unmount and provider closing, repeated IDs, later and removed rows, same-position data replacement, the delivery-only event reader, setup and discovery failure, duplicate attachment, dispose and rebind, and a changed definition. `runtime-identity.test.ts` pins the versions above. `packages/core/src/exports.test.ts` also checks the shared contract's export.

### Rendering the FaithfulCard in React (REACT3-TEXT)

[#117](https://github.com/MachineWisdomAI/saga-a2ui/issues/117) gives React consumers the passive FaithfulCard text and safe links through a second optional export of `@saga-a2ui/react` (still private, unreleased and unversioned). It is the text and lifecycle slice of REACT3, bounded by the [approved design](blueprints/features/content_safety_levels.blueprint.md); it is not React parity or the complete REACT3. Image loading and consent are the next slice, described in the section after this one.

| Export | Holds | Imports |
| --- | --- | --- |
| `@saga-a2ui/react/faithful-card` | `FaithfulCard`, `faithfulCardEntry` (the catalog entry) and `FaithfulCardProvider` with its `FaithfulCardView` | React, upstream `@a2ui/react` 0.13.0, `@saga-a2ui/components` (an **optional peer**) |
| `@saga-a2ui/react/faithful-card.css` | The scoped presentation, imported explicitly | nothing |

An application with its own catalog that lists none of this carries none of it: the `@saga-a2ui/react/actions` graph holds no card, no components package and no Markdown parser (`exports.test.ts` bundles it to show so). The card is used the way the Lit card is, with the trusted settings supplied once and the content supplied by A2UI binding:

    const reader = createFaithfulCardReader({ dialect: 'commonmark-tables-strikethrough', maxLength: 50_000 });
    const policy = createContentPolicy({ level: 'standard' });
    const view: FaithfulCardView = { reader: reader.reader, policy: policy.policy, hostLinks, imageEnforcement, consent };
    <FaithfulCardProvider view={view}><A2uiSurface surface={surface} /></FaithfulCardProvider>   // catalog lists faithfulCardEntry

- **One interpretation.** The card renders the typed nodes the components package already produces: the shared reader, the one maintained parser and the unchanged `{ contractVersion: 1, markdown }` wire contract. Every node case is a fixed element with text children (React escapes the strings; no raw-HTML escape hatch exists), and both `switch` statements over the node types end in an exhaustiveness check, so a new case does not compile until it is rendered. Order, Unicode and right-to-left text (`dir="auto"`), tables (a keyboard-focusable scrolling region) and the content bound's failures (`too-long`, `too-nested`, `unsupported-version`, `invalid`) behave as in Lit, and the failure sentences now have one owner, `describeContentFailure` in the components package. Without a provider the card shows an explicit, inert alert (`data-reason="no-view"`) and interprets, shows and requests nothing. The catalog schema stays strict, so a layout cannot supply a dialect, bound, action or handler.
- **Links.** `HostLinks` and `LinkOpenOutcome` moved to `@saga-a2ui/components/faithful-card`, together with `NO_HOST_LINKS` and the reader-facing outcome text (`describeLinkOutcome`); the Lit element, the Lit application, the MCP link adapter, the example consumer and the tests were migrated in the same change and the Lit export no longer carries them (no alias). Under Standard a validated HTTPS link is a button whose accessible name includes the parsed hostname, pressing it makes one request through `HostLinks.open`, and a denied, unavailable or failed answer leaves readable inert text with the destination and no navigation fallback (there is no `href`). Strict keeps every link inert behind a placeholder; Reveal source shows it as text and changes visibility only.
- **Images.** This slice fetched none. The image-consent slice below extends the provider's view with enforcement and a consent scope.
- **Lifecycle.** The card's state belongs to a content revision and starts over when the content, or the application's trusted view, changes: source visibility, link outcomes and every control from before. Rendering derives values only (state reset follows React's render-phase derivation rule) and runs no effect; the host is asked only from a press. A control applies to the revision it was rendered for, a late host answer for replaced content is not shown, an answer after unmount is dropped without a React warning, and a card asks its A2UI node whether it still stands before it asks the host for anything, so a node that A2UI disposed but React has not yet unmounted is already inert. Writing the Strict Mode tests found one real defect before the first green run: the per-render link and table counters lived outside the component that used them, so Strict Mode's second render of the same props continued numbering where the first stopped; they now belong to the one render, and the table-numbering test failed first.
- **Styles.** Templates (`nodes.tsx`), lifecycle (`lifecycle.ts`) and the stylesheet are separate. Every rule is scoped under `.saga-card`. The seven existing tokens keep their names and fallbacks (`--saga-card-font-family`, `-line-height`, `-text-color`, `-accent-color`, `-muted-color`, `-border-color`, `-code-background`), and `--saga-card-font-size` and `--saga-card-reading-width` (default `70ch`, following the card's own font) are new. The semantic classes (`.saga-card`, `-content`, `-failure`, `-controls`, `-link`, `-link-host`, `-link-status`, `-link-inert`, `-link-destination`, `-blocked`, `-source`, `-placeholder`, `-table-scroll`) are documented in the stylesheet's header, and `styles.test.ts` fails if the card renders one that is not documented. The Lit card's own inline styles are unchanged.

### Image consent in React (REACT3-IMAGES)

[#118](https://github.com/MachineWisdomAI/saga-a2ui/issues/118) lets the React card show the images its content policy permits, and lets a reader Show and Hide them under Strict, without stale consent, effects across views or any way around the policy. It consumes the existing shared policy (`decideImage`, `offerImages`, `establishImageEnforcement`) and the application-owned `ImageConsentScope`; it adds no policy rule, no action runtime and no server call, and it does not touch the resource-policy derivation of [#119](https://github.com/MachineWisdomAI/saga-a2ui/issues/119).

`FaithfulCardView` gains two members, both supplied by the application and trusted like the rest: `imageEnforcement` (`establishImageEnforcement(policy, <the Content-Security-Policy values the document carries>)`; anything else keeps every image inert) and `consent`, this view's own scope. The scope is the **sole owner of view-wide revocation**: the application calls `consent.revokeAll()` when its selection changes or it observes another retirement signal, and `consent.retire()` when the view ends. A card asks the scope for grants and gives back only its own; it never calls `revokeAll` or `retire`.

- **What shows.** Standard shows an image from an exactly listed HTTPS origin (same scheme, host and port) with no consent. Strict shows it only while this card holds a live grant, made by pressing Show images. Everything else (an unlisted host or port, `http:`, credentials, a relative address, a `data:` or `blob:` Markdown reference, and every image when enforcement is not established) stays text in its original position with a `data-reason` (`host-not-allowed`, `not-https`, `credentials`, `malformed`, `enforcement-unestablished`, `consent-required`), and Strict can reveal it as source. Show images is offered only when at least one image would load once consent is given, and says why when it is not. An image the browser fails to load becomes the same text with `data-reason="load-failed"`. The document's derived `img-src` now carries the embedded baseline for the application's own trusted artwork (`data:`, and `blob:` in Standard); that does not reach Markdown, because the content decision refuses a `data:` or `blob:` reference before an element exists, and the browser spec checks it against the built policy.
- **Committed requests only.** React creates and fills in the elements of a render before it knows the render will be kept, and a browser requests an image as soon as an element has an address. The image element therefore receives its address in a layout effect (`image.tsx`), after the commit, so a render that is discarded or whose consent ended cannot start a request. Strict Mode's replay finds the address already set and sends nothing more. Consent can also end between render and that effect: the application owns the scope and may revoke or retire it from an earlier effect of the same commit, which React answers with a later render that is too late to take back a request. So the effect asks the shared policy again, through the card's lifecycle, with the render's owner and grant as they are at that moment (`imageStillPermitted`), and gives no address if it no longer agrees. The scope stays the only owner of consent; the element holds none.
- **Grants and subscriptions stay out of render.** A grant is made only by the reader's press. The card learns of `revokeAll` and `retire` through `useSyncExternalStore`, which subscribes after commit, removes the subscription on unmount and re-reads the state once subscribed, so a revocation between render and commit is not missed. The cleanup of a committed revision revokes the grants that card made and nothing else: during Strict Mode's replay of a mount it finds no grant and the scope stays live, and unmounting one card leaves a sibling's images showing.
- **What ends consent.** Hide images; new content or a replaced trusted view (a new revision); the component being replaced or the surface unmounted (a card's disposal); `revokeAll` and `retire` from the application. The control of a revision that has ended, or of a node A2UI has disposed but React has not yet unmounted, does nothing, and a load or error event for an image that is gone cannot restore consent, because only a press makes a grant and only a live grant shows images. A new press is a new grant.
- **Raw source.** Reveal source changes visibility only: it makes no grant, loads no image and asks the host for nothing.

**Findings, by claim.** Each is a browser spec under `apps/lynx-fixture/e2e` unless it says otherwise.

- *Direct attachment* (`attachment.spec.ts`). One catalog component type serves every instance; setup discovers instances by the layout's own ID with `watchById` and binds a definition to the exact handle. Two definitions on one control kind each run once per tap in the background thread, `input` before the handler. An unbound control and a control whose setup bound and then threw (ACT1 disposes what that callback bound and reports it) refuse every tap. A second bind throws; dispose then rebind runs the new definition on the same mounted instance with no remount. A handler failure reaches the adapter, returns the binding to `idle`, and does not reach the renderer. A protocol `action` on the bound control is rejected whole by the admission store before the processor sees it, so a `functionCall` in it never runs; the same call on an upstream `Button`'s `action` runs during prop resolution, before any tap (the hazard the guard is for), and unrelated function calls and the upstream `onAction` path are untouched. The guard narrows one property of one control kind and does not make catalog expressions pure.
- **Seam repair: a queued tap is bound to the binding its render showed.** The first revision of this slice found that a tap closure queued before a dispose, after a second binding was attached on the same handle, ran the replacement definition, because ACT1's `OpenInstance` never exposed the attached binding. The approved tap-admission contract requires the opposite. The repair is in the shared owner, `@saga-a2ui/core/actions`, and adds no registry and no second runtime: `OpenInstance.attached(event)` returns the binding now attached to an event of that instance by reference (`undefined` while none is, never a disposed binding), and `OpenInstance.subscribe(listener)` calls back synchronously after an attach, a detach and once at retirement, with the change already visible through `attached`. The adapter publishes the attached binding in the snapshot a render reads, so each render's tap token carries it, and `activate` checks in order: installation live and the token's, the observed-key epoch, a binding attached (`unbound` otherwise), the token's binding being the attached one by reference (`stale` otherwise), and the live key. A closure queued before a dispose is `unbound` while nothing is attached and `stale` after the replacement, which is not started; a render after the rebind carries the replacement and its tap delivers. Lit and React keep their calls to `activate` unchanged. Browser specs: `an old queued tap is unbound after dispose and stale after rebind...` and `a closure captured while a binding was attached stays stale across two rebinds...`; core tests under *the binding an instance exposes to its adapter*. Recorded red before the repair, on the real Lynx Web target: the old adapter returned `delivered` for the stale closure (both specs failed at that assertion). The repair was written after the fixture, so this is a repair-time red, not test-first history.
- *Checks and `isValid`* (`checks.spec.ts`). The control calls GenUI's exported `useChecks`, the hook the published `Button` uses, and binds `bindtap` only when `isValid` is not `false` and every check passes; the first failure's message is shown. No expression interpreter is added. **The hook is given the component's stored rules** (`surface.components`, with the component's resource as the update notification), not the props GenUI has already resolved. Resolved props turn a `{ path }` condition into its current value, which `useChecks` does not recognise and counts as passing; the repair in this revision found that on the first revision (a tap on a control with `condition: { path: '/approved' }` and `approved: false` ran its definition once, expected zero). Covered on the real renderer, each as a failing-then-passing sequence on one binding: a false model-bound condition (message shown, a tap runs nothing), then the same model value changed to true (message gone, exactly one invocation), to false again (message back, no further invocation) and true again, with one `opened` probe record and no rebind, on the `ordersLayout` surface; a relative `{ path: 'approved' }` condition in a template row, each row reading its own value; a replaced condition path re-evaluated against the new value; an `equals` function-call condition (the A2UI basic functions are registered by the fixture root, through GenUI's own `registerBasicFunctions`) following the model; plus the earlier cases: a failing literal check, a passing check, the first of several failures, `isValid: false` with passing checks, a replaced literal rule list followed in both directions on one instance. Recorded red before the repair, on the real Lynx Web target: four of these specs failed against the previous control (the model-bound, relative, changed-source and published-Button-comparison ones), and passed after; the function-call spec passed both before and after, because a boolean result survives GenUI's early resolution, so it is not evidence for the change. **Upstream limit, pinned as evidence only:** the published `Button` at GenUI 0.7.0 hands `useChecks` the resolved props, so it does not enforce a model-bound condition; the first spec asserts that next to the control's enforcement. This adapter does not copy that behavior. Not covered: a stored rule whose message is itself a data binding (the message is shown only when it is a string), and `isValid` bound to the data model, which still arrives resolved. Checks gate the interface and authorize nothing. `useChecks` needs `<A2UI>`'s context, so the empty first screen, which `<A2UI>` draws outside it, renders a separate `firstScreenProbe` that shares the slot machinery with the control but not the checks gate.
- *Freshness* (`freshness.spec.ts`). Rows of a template share the layout ID, have distinct expanded IDs (`row-archive:0`), and read their own relative `noteId`; the adapter's `sagaSourceId` annotation survives GenUI's clone and reaches the control. A same-position replacement and a reorder keep each instance (no open or close) and move what it shows; the live reader agrees with GenUI's resolved prop for a literal, an absolute path and a relative path, and returns `undefined` without executing a function-call binding. **Observed notification order on the Web runtime** for `updateDataModel`: the signal callback runs synchronously inside the processor's batched update, first, only for the key that changed; the Resource callbacks of every template row follow; the render comes last. For `updateComponents` replacing `{ path: '/old' }` with `{ path: '/new' }`, the Resource callback moves the watch to the new signal and the new signal's first value is compared with the last seen; a change at the retired path is ignored and the same key at another path does not count. *Checkpoint freshness versus the observed A–B–A count:* the live key comparison at the tap refuses a closure whose key no longer matches, with no notification involved; an observed A, B, A makes the key equal again and only the count of observed changes then refuses the old closure. **Limit:** B set and reverted inside one signal batch is never observed, and the old closure is admitted, as designed; two update messages are two batches and both count.
- *Partition and locality* (`partition.spec.ts`). The template has one background chunk and one main-thread chunk. A `'background only'` function body (the setup) is absent from the main-thread chunk; ordinary module code, including the shared runtime, the adapter and the definitions, is in **both**. What matters is what ran: the main thread rendered the application root and an inert first-screen probe (the control's slot machinery without its checks gate, see above) once for `<A2UI>`'s empty first screen (a slot constructed, no token captured, nothing opened or closed) and then rendered nothing further, because `<A2UI>` builds surfaces from messages in a background effect. Effects, setup, `bindtap`, `input` and the handler all ran in the background Web Worker (`document` undefined, `WorkerGlobalScope`). No binding or function reference was transferred; the evidence is that nothing binding-related existed on the main thread, not a proof about every build. The built template is read when a test runs, not while Playwright discovers tests, so `npx playwright test --list` works on a fresh checkout before `npm run build`.
- *Cancellation primitive.* `AbortController` exists in the background worker and delivers abort once; separately, `fetch` there honors the signal and the server saw its connection dropped. These are Web Worker facts only; the native JS engine is not covered. **Event-turn environment tagging is unresolved and unchecked**: a built definition is a frozen `{ label, plan }` and carries no record of where its callbacks were written, so `bindAction` could not reject a mismatch; no mechanism has been selected.
- *Lifecycle* (`lifecycle.spec.ts`). A keyed session reset (new `key`, new admitting store, new host) closes every instance, disposes every binding, refuses an old closure and starts the new mount unbound until its own setup runs; clearing the store without changing the key is not a reset. Replacing a control with another component type, or deleting the surface, retires its instances; an ID merely omitted from a later update does not. Scrolling the Web `x-list` neither opens nor closes an instance and a row tapped afterwards keeps its item. **The Web list keeps every row's element, so no native node was recycled or reused: recycled-node identity is not exercised, and native `<list>` recycling remains unqualified.** Native removal versus cleanup, three samples: cleanup was recorded 2 to 5 ms *before* the page observed the element's removal. That is one runtime's measurement; it sizes nothing for native and does not close the window. The retirement-tolerant contract holds: presentation is written to state keyed by the business item, `current()` is not used as proof of native presence (ACT4 owns it), and no immediate native retirement is promised.

**Not proven.** The six guard mutations in `src/adapter` from the first revision were each removed once and the named spec failed for five of them (epoch check, live key comparison, retirement at cleanup, admission, watch following a replaced binding); the installation-identity check at tap is defensive and no spec reaches it, since a slot is opened once here. The binding-identity check and the snapshot subscription were added in the repair and are covered by the two attachment specs above, not by a separate mutation run. Spec development was not strictly test-first: the fixture was built first and the specs written against the real runtime, so the mutation run and the recorded repair-time reds, not red-then-green history, are the evidence that they bite. Event-turn environment tagging, native `<list>` recycling, native removal timing and every native or host target remain unqualified.

### Asynchronous local actions (ACT4)

ACT4 extends the one shared action runtime in `@saga-a2ui/core/actions` (no second runtime, no registry, no alternative combinator model) so a directly bound local action can wait for reusable prerequisites, do asynchronous local work and reach the correct outcome without leaving its control busy forever. The fluent interface is the approved one:

```ts
const requireSession = prerequisite('session', async ({ signal }) => (await currentSession(signal)) ? proceed({ user }) : refuse('sign-in-required'));

const save = Action.local<ActionButtonActivation>('save-draft')
  .input((event) => ({ text: String(event.read('/draft')) }))
  .before(requireSession)                      // in the order written; each adds provided values
  .run(({ params, provided, signal }) => saveLocally(provided.user, params.text, signal))
  .limits({ deadlineMs: 10_000 })              // optional: overrides the work deadline for this action only
  .onSuccess(({ result, current }) => { if (current()) showSavedAt(result.savedAt); })
  .onFailure((context) => { /* context.stage and context.failure say what is known */ })
  .whenBusy('ignore')
  .build();

handle.bindAction('activate', save, { subject: () => handle.read('id') });
```

- **Prerequisites** are application work before the handler, not authorization and not pending UI. They run strictly in order, may answer synchronously or with a promise, and see `provided`, `params`, `signal` and their own `current()`. `refuse(reason)` ends the invocation as `failed` in the `prerequisites` stage and the handler never runs; a throw is `prerequisite-error`; a key two prerequisites both provide, or an answer that is neither `proceed` nor `refuse`, is `prerequisite-error` too. An action built only from synchronous pieces still reaches `idle` before the event handler returns, and a local action makes no MCP request.
- **Bounds.** `deadlineMs` covers the prerequisites and the handler together; `hookMs` is a separate budget for each of `onSuccess`, the outcome hook, each resource release and `onFinally`. Neither needs to be declared: each resolves on its own from the action's `limits` override, then the owning SDK instance's configuration, then the default of 30,000 ms and 5,000 ms (see [Configurable action defaults](#configurable-action-defaults-and-error-categories)). There is no whole-invocation timer. A timer is armed only when a step returns a promise. `onSuccess` is awaited before success is decided: its exception or overrun is `failed` (`success-hook-error` or `success-hook-timeout`) in the `running` stage and carries the handler's result. A hook that outlasts its budget is no longer waited for, is recorded as a `budget-exceeded` diagnostic reaching `onFinally`, and cannot keep the binding in `settling`.
- **Eligibility.** Every prerequisite, the handler and every hook gets its own `current()`. It ends for good when the callback finishes, when its promise settles, when its budget or the work deadline expires, or when cancellation or obsolescence makes the runtime stop waiting; it also needs the binding live and undisposed, the invocation not replaced, the adapter's `isLive()` and an equal subject. A late settlement is dropped (the observer sees `late-settlement` and no value), and a late callback cannot start `onSuccess`, change a decided outcome or write over a newer invocation, provided it asks `current()` first. Arbitrary effects a callback already started are not recalled.
- **Outcomes are decided once.** An obsolete failure stays `failed`, does not run `onCanceled`, does not start `onFailure` (or aborts it if running) and still finalizes; an absent `onFinally` does not skip finalization; an older invocation settling beside a newer one (`whenBusy('replace')`) cannot return the newer one to `idle`, and nothing undoes disposal. The runtime never continues an invocation inside one of its own callbacks' call stacks: cancellation from inside a handler (for example `dispose()`) defers the invocation's next step until that callback returns.
- **Busy policy and revalidation.** An activation that arrives while the binding is `running` or `settling` first rechecks the active invocation (so a press on item B ends item A's stale invocation), and only then meets the policy: `ignore` (default) drops it and tells the observer which invocation was busy, `replace` cancels a running invocation with cause `replaced` or, for one already settling, keeps its outcome and makes its presentation obsolete.
- **`subject` and wake-ups.** `bindAction(event, definition, { subject })` takes an optional reader of the item the instance shows; component or model identity alone cannot tell two items at one position apart. The runtime captures it when the invocation starts and compares a fresh `Object.is` read at its checkpoints (before each prerequisite, when the handler's answer is observed, before a presentation hook starts, at the busy decision and on every `current()`). A reader that throws at activation ends the invocation as `invalid-input`; one that throws later counts as a change. Adapters may supply `watchScope(revalidate)` in `OpenInfo`: the runtime subscribes only while an invocation is unsettled and unsubscribes when it settles, is replaced or is disposed, and a call requests the same recheck any checkpoint does. Lit and React wire it to `DataModel.subscribe` through a microtask; the Lynx fixture wires it to its own item watch, which also keeps its separate tap-admission epoch while idle. An unobserved A, B, A cannot be detected (put a revision into the subject if a row can be deleted and recreated under one key), and once an observed B has canceled an invocation a return to A does not revive it. An instance that is no longer live at a checkpoint disposes the binding.
- **Telemetry.** `observe(observer)` receives phases with the label, opaque binding and invocation ids, elapsed time, status, failure kind and the failed cleanup step's name, and nothing else: no parameters, provided values, results or error objects. A throwing or rejecting observer or listener changes nothing and leaves no unhandled rejection.
- **Synchronous failures.** A failure decided in the event's own call stack for a definition with no `onFailure` is still rethrown to the event caller after the binding returned to `idle` (ACT1 behavior; the Lynx fixture reports it), but only for failures that carry an error (`invalid-input`, `prerequisite-error`, `handler-error`, `success-hook-error`). A refusal is not an error and is not thrown. With an `onFailure` hook the hook receives every failure and nothing is thrown, and an asynchronous failure has no caller to return to.

**Not implemented in ACT4, and not declared** (no placeholder methods): `atActivation` and the activation scope, the invocation `scope`, `acquire`/`own`/`transfer` and resource release (these arrived in ACT5, next section), `Action.server` and `call` (ACT6), `eventTurn`, and a `stale-installation` observer event (the adapters refuse a stale tap before the shared runtime sees it). Existing application and controller bounds are untouched.

### Resource ownership in the invocation scope (ACT5)

ACT5 extends the same `@saga-a2ui/core/actions` runtime (no second runtime, no registry, no alternative cleanup protocol) so a local action can acquire an application-owned resource, release it when the invocation ends, or hand it synchronously to an owner that keeps it. The runtime owns invocation-scope cleanup; the application's resource owner stays responsible for what a token means. This slice proves the generic ownership mechanics with an observable fixture owner. It does not decide the current player's lease feasibility or playback's unresolved stage mapping.

```ts
const play = Action.local<ActionButtonActivation>('play')
  .atActivation(({ scope }) => scope.own(owner.begin(), (lease) => owner.end(lease)))   // the event's own call stack
  .run(async ({ activation }) => {
    const started = await owner.start(activation.token);
    if (started === 'blocked') return { state: 'gesture-needed' } as const;               // the scope still owns the lease
    return activation.transfer((lease) => owner.keep(lease))                              // synchronous adoption, no await between
      ? ({ state: 'playing', lease: activation.token } as const)
      : ({ state: 'gesture-needed' } as const);
  })
  .onSuccess(({ result }) => (result.state === 'playing' ? showPlaying() : showGestureNeeded()))
  .onCanceled(({ activation }) => owner.end(activation.token))                            // every stage carries the token
  .build();
```

- **Three ways in.** `atActivation(({ event, scope }) => value)` runs synchronously after `input`, in the call stack and environment of the adapter's event delivery (the Lit adapter's click handler here), and what it returns reaches the handler and every hook as `activation`. Its scope offers `own(token, release)` and has no `acquire`. `scope.own` on the handler's or a prerequisite's scope takes a token the caller already holds. `scope.acquire(acquire, release)` awaits an acquisition after the event turn and owns the token from its arrival. `Held<Token>` carries the `token` and `transfer`.
- **Release at the end.** Every token the invocation still holds is released newest first, after the outcome hook (`onSuccess` having already decided success, or `onFailure`/`onCanceled`) and before `onFinally`. Each release is its own step with its own `AbortSignal` and its own `hookMs` budget; a release that never settles has its signal aborted and is not waited for, and `settling` is bounded by `hookMs` times the tokens held plus the outcome and final hooks. A release that throws or overruns is a `release` cleanup diagnostic (`threw` or `budget-exceeded`) delivered to `onFinally` in `cleanupErrors` and to the observer by step name; it never changes the decided outcome and never stops the releases after it. Releases run for an obsolete invocation too: nothing in them presents.
- **After retirement.** `own` after the outcome was decided releases the token at once (own budget and signal; a failure reaches the observer only) and throws `InvocationEndedError`. `acquire` on an ended invocation does not start the acquisition and rejects with the same error; a token that arrives after the invocation ended is released at once and the acquisition rejects. `scope.active` is true until the outcome is decided; it is work activity, not freshness (that stays `current()`).
- **Transfer.** `held.transfer(adopt)` calls `adopt(token)` synchronously while the invocation is active and returns true only if `adopt` returned a non-thenable value and the invocation was still active when it returned; the scope then no longer releases the token. It adopts nothing and returns false once the outcome is decided (even before the release step has run) or when the scope no longer holds the token (already transferred). If `adopt` itself ended the invocation (for example by disposing the binding) and returned, the transfer is not reported as completed: it returns false and the scope releases the token in its ordinary place, after the outcome hook for a handler still running, or at once when the release sweep has already passed. A throw from `adopt`, or from inspecting what it returned (a `then` accessor that throws), propagates and ownership stays with the scope. A thenable the types could not see makes `transfer` throw a `TypeError`, keeps ownership with the scope and attaches a rejection handler; a later rejection reaches the observer as a `cleanup-error` with step `adopt`. Work the callback already started is not recalled, which is why an owner's `end(token)` must be idempotent. Whatever way adoption fails or is refused after the invocation ended, the scope releases the token itself rather than leak it. Compile-time: `Synchronous<Returned>` rejects an `async` adoption callback, `Promise<T> | undefined` and an `async` `atActivation`; a promise hidden behind `unknown` is caught at run time.
- **Failures of the event-turn callback.** A throw, or a promise the types could not see, ends the invocation as `failed` in stage `input` with kind `activation-error`; the handler never runs, tokens the callback already took into the scope are released after the failure hook, and the error reaches the event caller after release when no `onFailure` receives it. A failure of `input` or of the subject reader prevents `atActivation` from running at all. The runtime does not continue the invocation inside the callback: a disposal from inside it is noted, the scope stops being active at once, and the cancellation is decided when the callback returns, so a callback that returned still gets its canceled hook with `activation`. If the callback disposes the binding and then throws, no activation value exists: the throw is the outcome (`failed`, stage `input`, `activation-error`, a stage whose hooks carry no `activation`), the invocation is already obsolete so the failure hook does not present, and the scope releases what it owned. That cancellation only leaves the invocation obsolete: it neither aborts nor abandons the cleanup the failure started, so the release sweep (one step per token, each with its own signal and `hookMs` budget) and `onFinally` still run to completion, whether a release settles at once, later or never. A canceled hook typed as carrying `activation` therefore never runs without one.
- **What the application's owner provides.** `release(token)` and any token-scoped `end(token)` affect only that acquisition and are idempotent, a no-op for a token the owner has superseded; acquiring a new token from a single-resource owner supersedes the previous one. Stopping everything the owner holds is the owner's own teardown and is not a nameable operation for an invocation; SAGA never calls it on binding disposal, subject change or session reset. A deliberately retained resource therefore outlives a successful invocation, and outlives `failed(success-hook-error)` or `failed(success-hook-timeout)` when the failure hook keeps it under the selected policy. Later disposal of the binding changes neither.
- **Narrowing before presenting.** `activation` is typed in the handler and every hook that can follow the prefix (not in a failure of the prefix itself, which has none), and `failure.result` is the handler's own result type. The Play action above returns a discriminated result, so a started-and-transferred result (`playing`) is different from a blocked start (`gesture-needed`) before `onSuccess` presents or `onFailure` recovers; the failure hook keeps the lease only for `playing`, and ends exactly `context.activation.token` otherwise, which cannot reach a newer owner's lease.

A scope can own a token without any declared limit: each release gets the resolved `hookMs`, whatever the action overrode. `eventTurn` is not declared: the definition records no environment for its callbacks, so event-turn environment tagging stays unresolved and unchecked, and nothing here promises cross-thread execution. The Lynx fixture's background-thread findings and the recorded environment decision belong to ACT2/ACT3 and are not extended. Activation work stays in the event stack and environment the adapter delivers the event in.

### Server actions and the joined contract (ACT6)

ACT6 adds server-call capability to the same `@saga-a2ui/core/actions` runtime (no second runtime, no registry, no handler-name table, no retry layer) and then qualifies the cumulative contract of ACT1 to ACT5 together. Core stays free of MCP: the action takes a `ServerTransport` the application supplies, declared in core by the shape of what it sends and receives. In the example application that transport is the MCP Apps `App` itself. The transport, the server's own handler and every authorization decision stay in the application and in `@saga-a2ui/mcp`.

```ts
export function archiveNoteWith<Event>(noteIdOf: (event: Event) => string, environment: ArchiveEnvironment) {
  return Action.server<Event, CallToolResult>('archive-note', environment.transport)   // `app` is the transport
    .input((event) => ({ noteId: noteIdOf(event) }))
    .before(requireSession(environment))     // the same reusable prerequisites a local action takes
    .before(confirmArchive(environment))
    .before(auditIntent(environment))
    .run(async ({ params, call }) => {
      const reply = await call('archive_note', { noteId: params.noteId });
      if (reply.isError === true) throw new ArchiveRejected('The server declined to archive the note');
      return parseArchived(reply);
    })
    .onSuccess(...).onFailure(...).onCanceled(...)                                      // as for any action; no limits needed
    .build();
}
```

The complete example is `apps/lit-host/e2e/archive-fixture/archive.ts` (test-only application code, one definition for every renderer; only `noteIdOf` depends on the renderer's event).

- **Declaration.** `Action.server<Event, Reply = ServerReply>(label, transport)` starts the same chain as `Action.local` with one difference: the handler context also has `call(name, args, options?)`, where `options` is `{ timeoutMs?, meta? }`. Its work deadline resolves like a local action's, so a server action builds without `limits`. A local handler context has no `call`, by type and at run time. The exported types are `ServerTransport`, `ServerRequest`, `ServerRequestOptions`, `ServerReply`, `ServerCalls` and `ServerCallOptions`; there was no new runtime export.
- **What `call` sends.** The runtime builds the request options. `signal` is the invocation's own signal; `timeout` is the time left on the resolved work deadline, counted from the start of the prerequisites, so time spent in prerequisites is already gone. The handler's third argument can only narrow: `timeoutMs` (finite, positive) is clamped to the time left, and any other field a caller smuggles through a cast (`signal`, `timeout`) is not forwarded. `meta` (a plain object, copied and frozen when the call is made, otherwise a `TypeError` before anything is sent) becomes the request's `_meta` beside, never inside, the arguments; it is per call and shared with no other. `call` returns the transport's reply unchanged: a returned tool-level failure (`isError: true`) is a result, and the runtime does not reinterpret it, so the handler decides what it means. A transport that rejects (a timeout, a lost connection, a host refusal, an abort) rejects `call`, and that reaches the runtime as `handler-error`, or as the deadline's or cancellation's own outcome when that decided first. `call` is invoked as a method of the transport, so an `App` keeps its state, and `Reply` lets a transport keep its own reply type (`CallToolResult` here).
- **When nothing is sent.** A `call` made after the runtime stopped waiting for the handler, after the invocation was canceled, after the work deadline, or after a checkpoint found the subject changed or the instance gone, rejects without calling the transport. The handler never runs while a prerequisite refuses, throws, times out or is canceled, so a protected request is never sent from those stages. The prerequisites' own requests (a session check, a consent prompt, an audit write) are counted apart from the protected request in every test.
- **What an outcome says about the effect.** The runtime reports only how far the handler got, as in the Blueprint's table. A prerequisite-stage or input-stage failure or cancellation: no protected request was sent. A returned tool-level failure that the handler throws on: whatever that tool's own contract says (here "changed nothing"). `handler-error` from a rejected transport, `timeout` in the running stage and `canceled` in the running stage: unknown, with no retry and no invitation to retry. `success-hook-error`, `success-hook-timeout` and `canceled` in the completing stage: the reply was returned, the result is kept on the outcome, and only the client's required work failed or was abandoned. An abort ends the client's wait. It does not show that the host forwarded it, that the server stopped, or that anything rolled back; the integration test below has a stalled host that does not honor the abort and archives the note afterwards while the view correctly reports an unknown status.
- **Prerequisites are not authorization.** A prerequisite that passes locally never stands in for the server's check: in the integration test the server refuses `n-locked` after the session, confirmation and audit prerequisites all passed, and the application reports `declined`.

**The cumulative contract.** The shared runtime keeps the behavior recorded for ACT1 to ACT5, and the server action takes it unchanged: synchronous and asynchronous local work, ordered reusable prerequisites, both busy policies, per-callback `current()`, immutable outcomes, bounded hooks and finalization, retirement by disposal, replacement, subject change and instance loss, and the ACT5 lease acquisition, release and transfer. `server-actions.test.ts` checks the join for a server action (a lease taken in the event turn and transferred or released across success, a timeout and a cancellation; every hook, the release and `onFinally` bounded by `hookMs`). `authoring-qualification.test.ts` runs the Blueprint's positive and negative authoring cases that the earlier slices did not yet check (P1 to P8, L1, N4, N9 to N11, N17, N18, N23 to N25) against the package's real exports and its own tsconfig rather than the evidence companion's stand-in declarations, and names the suites that check the others (N1 to N3, N5 to N8, N12 to N16, N19 to N22). ### Configurable action defaults and error categories

This amendment ([action binding Blueprint](blueprints/modules/action_binding.blueprint.md#bounds-the-work-deadline-and-the-hook-budget), design revision `564bcb2a13dd162515a80e7f491d2870990958ab`) replaces the mandatory explicit limits of ACT4 to ACT6. It changes the one shared module in `@saga-a2ui/core/actions`; there is no registry, mutable global, second API or retry layer. A local or server action, with hooks and owned resources, now builds and runs without declaring any limit.

```ts
const host = createInstanceHost({ onSetupError, limits: { deadlineMs: 45_000 } });   // this SDK instance's defaults

Action.server<Press>('archive', transport)
  .run(({ call }) => call('archive_note', {}))
  .limits({ hookMs: 2_000 })        // this action's override of one setting
  .onSuccess(recordArchived)
  .build();                          // work deadline 45,000 ms (instance), each hook or release step 2,000 ms (action)
```

- **Resolution.** Each setting resolves on its own, in this order: the action's `limits` override, the configuration of the SDK instance that owns the binding, then the default (`deadlineMs` 30,000 ms, `hookMs` 5,000 ms). Omitting a setting (or passing `undefined`) inherits it; it never disables a bound. The definition holds only its own override, so one definition bound under two instances uses each instance's values. An instance is the `InstanceHost`: pass `limits` to `createInstanceHost`, to `createLitActions({ attach, onSetupError, limits })` (each presentation's host gets the same values) or to the React `InstanceHostProvider` (fixed for the provider's lifetime, checked when it first renders). The Lynx fixture sets none and runs on the defaults.
- **Validation and snapshots.** A supplied value must be a finite number greater than zero. Zero, negatives, `NaN`, infinities and non-numbers throw a `TypeError` where they are supplied (`limits(...)`, `createInstanceHost`, `createLitActions`, the provider, or `snapshotLimits`), before any binding, activation or effect, even when another layer would have overridden the value. Every supplied object is copied: changing it afterwards, even during an invocation, changes nothing. An invocation's limits are resolved once when its binding is made, from immutable inputs.
- **Bounds.** `deadlineMs` starts when the synchronous activation prefix ends and is shared by the prerequisites and the handler; progress never extends it, and a late result cannot revive the invocation. `hookMs` is separate for `onSuccess`, the outcome hook, each resource release (including a late acquisition's) and `onFinally`. The default profile therefore makes no 35-second claim: an invocation whose failure hook, release and `onFinally` all stall settles 45 seconds after it started. Timers cannot interrupt blocked JavaScript, a synchronous action still completes synchronously with no timer, a limit longer than one platform timer can span (about 24.8 days) is waited out in consecutive timers, never shortened, and a handler cannot widen `call`'s request below the time left or a narrower transport limit.
- **Error categories.** Every `failure` now also carries `category`, beside its `kind`, the `stage` and any kept `result`. Known names are `timeout`, `canceled`, `authentication-required`, `permission-denied`, `unavailable`, `validation`, `application` and `unknown`; the type is open, so handle a name you do not know. A category comes from evidence only: the runtime's own decisions (a deadline or hook overrun is `timeout`, a refusal is `application`, unreadable input is `validation`), the platform's own `DOMException` of name `TimeoutError` or `AbortError` (what `AbortSignal.timeout` and an aborted `fetch` reject with; an ordinary `Error` that merely carries that name is not one), or an `ActionError(category, message, { cause })` that an application throws when it knows (a 401, a typed server error). Anything else is `unknown`; an unfamiliar error, its message or a `status` field is never read as authentication. The original thrown value stays on `failure.error` (an `ActionError` keeps what it wrapped as `cause`). The SDK shows none of it: choosing a safe message is the application's, and `ObservedEvent` is unchanged.
- **What an outcome says about the effect.** Unchanged and now tested together with the categories: a failure before the handler started sent no handler request; a `handler-error`, a work `timeout` or a cancellation while running leaves the effect unknown (no rollback is implied, no retry is offered or attempted); `success-hook-error` and `success-hook-timeout` keep the handler's result, so a known write followed by a client-step failure is reported as such and is never replayed.

**Migration.** `ServerLimits` is removed (`Limits` has two optional members), a hook, a held resource and a server action no longer need `limits`, and `scope.own` no longer throws without them. The archive example, the Lit and React consumers and the Lynx fixture declare no limits except where a test needs a value.

**Evidence** (Node 26.7.0, npm 12.0.2, Chromium 156.0.8078.4 through Playwright 1.64.0): `packages/core/src/actions/action-limits.test.ts` covers the amendment table through the public builder, instance host and binding with a controlled clock (defaults for a local and a server action, the seven precedence cases, isolation and snapshots, every invalid value at every layer including shadowed ones, the 45-second separate-cleanup timeline, a work deadline that progress cannot extend, a longer override meeting a shorter transport limit, the categories, known success after a hook failure, unknown effects) and its type cases; `packages/lit/src/actions/lit-actions.test.ts` and `packages/react/src/actions/instance-host-limits.test.ts` cover the adapter seams; the earlier suites were migrated to the new contract, and the built Lit, React and Lynx Web browser suites pass unchanged in behavior. The red-green order was followed for the core and adapter tests: they failed first because the API did not exist. Hand mutations of the runtime that the suites catch (each reverted): the instance configuration beating the action's override (3 failures), the timer delay capped at one platform span instead of chained (3), `null` read as an omitted setting (7), an ordinary error carrying a platform error's name accepted (1), a `status: 401` read as authentication (1), the late-release path ignoring the resolved `hookMs` (1), hooks timed by the work deadline (21), and the work deadline restarted at the first wait instead of the end of the prefix (1). The last three of those survived the first mutation run, and the tests that catch them were added after it.

It says nothing about an actual host, a server stopping, rollback or an HTTP status mapping (STATE2 [#13](https://github.com/MachineWisdomAI/saga-a2ui/issues/13) keeps those decisions), and the numbers are product defaults, not measured latency guarantees. **What each entry point may load** (`scripts/pack1.test.ts`, built from the installed copies; "runs" means the bundle was executed):

- *Server imports without renderer code:* `@saga-a2ui/mcp/server`, `/policy` and `@saga-a2ui/core/actions` bundle for Node with no Lit, upstream renderer, React, components or Markdown parser, and run with no `document`, `window` or `HTMLElement`.

**The browser flow** (`apps/lit-host/e2e/pack1-consumers.spec.ts`, once for each consumer, Chromium through Playwright). The page under test is the one that consumer's own server serves over a real Streamable HTTP MCP connection, mounted by the local host fixture in its sandboxed iframe (`sandbox="allow-scripts"`, opaque origin) under the CSP the server declared (a closed view). Its `tools/call` requests go through the fixture's real `AppBridge` to the same server.

- *Resource and policy.* The tool result links the SHA-256 URI of the built bytes; `resources/read` returns those bytes; the two view-only tools are `visibility: ['app']`. Allowed: results arrive and the view calls the server over the bridge. Denied: from inside the frame a `fetch` to another origin, an image from another origin and `new Function` are each blocked and each reports a `securitypolicyviolation` for `connect-src`, `img-src` and `script-src`. The body of a note, which carries a tracking image and a link, fetches nothing in either consumer; in `card` the link leaves only as the host's `ui/open-link` request, in `own` it is text.
- *Authorization and disclosure.* Private backend fields (a canary) reach neither the wire nor the DOM; another account's note is never shown; an unauthenticated call gets the sign-in sentence and no data. The server decides every `archive_note` itself: after the session check passed, withdrawing the account's permission still gets a refusal; an absent note and another account's note get one identical sentence, so nothing tells them apart; an account named in the arguments is rejected.
- *One definition, two rendered instances.* `archiveNote` is built once and bound with `watchById`/`bindAction` to each row's own `ActionButton` instance; the layout names no action. Both rows pending at once make two session requests and two protected requests, count apart, and each row's result, status and hold arrive on its own row whichever answers first. A press while a row is pending sends nothing. A local action (`mark-read`) on the same rows sends no request.
- *Prerequisite, item change, disposal.* An asynchronous session prerequisite that refuses leaves the protected request count at zero. When the list is replaced so a row shows another note, the in-flight archive is canceled, the server still applies it (so it is reported to nobody on that row) and the row shows nothing; the row then archives its new note. Tearing the view down while a request is pending removes the notes element, gives the hold back, and a late reply presents nowhere.
- *Application-owned resource.* The archive takes a hold (`row-holds.ts`) in `atActivation` with `scope.own`; the scope gives it back on every non-success end, and `onSuccess` hands it to the application's owner with `transfer`. The page shows both lists.

Mutations of the source that the checks catch (each reverted): a `file:` range for a SAGA dependency in the Lit manifest fails the leak check, and binding the archive without its `subject` lets the late result present on the new item and fails the item-change case for both consumers. Removing the success hook's own `current()` check changes nothing, because the runtime does not call `onSuccess` for an invocation it already canceled; the check is a second guard and not what the case depends on.

The bounded candidate-preparation scope is accepted at [PR #158](https://github.com/MachineWisdomAI/saga-a2ui/pull/158), actual merge `06aa486e6b8f4d99990d235a0c6177e5c8f14a32`. The maintainer guide is [docs/candidate-update-and-rollback.md](docs/candidate-update-and-rollback.md); this section records what the change did and found.

What changed in the code:

- `scripts/packed-consumer.ts` is now the one place packages are packed. `installPackedSdk` no longer stamps a throwaway `0.0.0-packed-test`; every consumer of this repository (the answer, PACK1, React card and installed Lit application builds, and the tests that install packages) installs the same candidate tarball: version `0.0.0-candidate.g<12 hex of the commit>` (`.dirty` when tracked files differ), every SDK dependency and peer pinned to exactly that version, `LICENSE` in every tarball and `THIRD_PARTY_NOTICES.md` in `components`, which brings `markdown-it` into a consumer's view. The repository manifests are untouched, so no owned version is introduced and no enrollment applies.
- `scripts/release-candidate.ts` (`npm run candidate:pack -- --out DIR`, run by CI after `npm run verify` and uploaded as a workflow artifact) packs the five packages into `DIR/packages`, requires every consumer identity under `apps/lit-host/dist*` to name exactly those tarball digests and this revision, installs the tarballs with the real package manager into a clean directory, runs `npm ls --all`, tries a set that mixes two builds, and writes `candidate.json`, `CANDIDATE.md` and the consumer lockfile. `npm run candidate:verify -- --candidate FILE --modules DIR --combination own|card [--page FILE]` resolves the named combination and reports, with the tarball to reinstall, each package of the installed set that is not the candidate, a package of that combination that is not installed (the optional `components` is required for `card` only), a `--modules` location with no `@saga-a2ui` package, a sibling at the wrong version or missing, a built view that is not the recorded resource, and any carried check the record predates (exit 1; a missing or unknown combination is exit 2). `npm run candidate:rehearse -- --candidate FILE` (`scripts/candidate-rehearsal.ts`, run by CI after `candidate:pack`) rehearses an install of candidate A, an update to B and a rollback to A as built applications, below.
- `examples/pack1-consumer/src/notes-view.ts` (an application-owned starter file): a successful result that fails the view's contract now shows `MISMATCH_TEXT` and renders none of it, where before it showed the generic problem sentence.
- `apps/lit-host/e2e/pack1-consumers.spec.ts` gains two cases for both consumers, below. CI uploads the artifact; `.gitignore` ignores `candidate-out/`.

Findings that shaped the candidate:

- **A fresh `npm install` of the packages needs an override.** `@a2ui/markdown-it` 0.2.2 (what npm resolves) peers `@a2ui/web_core ^0.14.0`, which conflicts with the pinned 0.13.0, and npm stops with ERESOLVE. The workspace root carries `overrides: { "@a2ui/markdown-it": "0.2.1" }`; npm honors overrides of the root project only, so an application must carry it. The earlier PACK1 harness linked dependencies by hand and could not see this. The candidate install check uses the root's overrides and records them. Declaring the dependency in the packages instead would change their manifests and is left to the owner.
- **`private` does not stop `npm publish`.** npm 12.0.2 accepted the private candidate manifest in `npm publish --dry-run`, for a directory and for a tarball. Candidate manifests therefore also name `https://candidate-artifact.invalid/` in `publishConfig.registry` (a host that cannot resolve, RFC 6761), which npm honored in the same dry run ("Publishing to https://candidate-artifact.invalid/"). Neither field is the safeguard on its own: no CI job holds a publish credential and the release recipe in the guide builds from a reviewed release change.
- **The tarballs carried no license.** Apache-2.0 requires it to travel with the code; the staged copy now adds it.
- **A mixed set is refused at install.** npm answers `E404` for the sibling at the exact version that is not among the tarballs named beside it; the check is recorded as `versionMismatch.installProbe` in `candidate.json`.

**First version, no predecessor.** No SAGA package has ever been published, so there is no earlier release and no upgrade from one was tested. The update and rollback sequence is rehearsed between two candidate builds only (`scripts/release-candidate.test.ts`): it packs two builds, installs one, updates to the other (a half-updated set is reported per package with the tarball to reinstall), and restores the first, whose package manifests return byte for byte. `scripts/candidate-rehearsal.ts` (`npm run candidate:rehearse`) then does it as applications: for `own` and for `card` it installs candidate A, updates to B and restores A, each time installing the consumer from that stage's tarballs alone, checking the installed set against the combination, rebuilding the page and the server, connecting a real MCP client to the rebuilt server to confirm it serves the rebuilt page, and running the ten `pack1-consumers.spec.ts` cases (disclosure, per-request authorization, known versus unknown effect, one definition on two rendered rows, prerequisite, subject freshness, disposal, page teardown, no handler-name routing, view/server mismatch) in a real browser against that stage's rebuilt files (`SAGA_PACK1_DIR` points the spec at them). It fails unless each case ran once per consumer and passed, and unless the rollback restored the first install's view digest and (with the scratch directory name in its region comments normalized) its server bundle. A and B are one revision with different version strings, so the rebuilt views are identical and nothing observable changes in the update: this shows the procedure and the per-stage behavior, not an upgrade between two versions of the code. `rehearsal.json` and a `CANDIDATE.md` section record the artifact digests and the cases that ran.

**Carried through every claimed combination.** The combinations are `notes-own`, `notes-card` and the browse and Play application (each lists its packages, its `ui://sha256/…` resources, its server bundle digest and its catalog entries in `candidate.json`). `CARRIED_CASES` in `scripts/release-candidate.ts` names the 15 checks each claim rests on, by file and exact title: disclosure and per-request authorization (including after a withdrawn permission), known versus unknown effect, one definition bound to two rendered instances, prerequisite, subject freshness, disposal and page teardown, the installed listener's authentication, scoping, entitlement and media binding, and two added here: a layout that names an action or handler is refused by the installed catalog and a press sends nothing (so a resource cannot route by handler name), and a result from a server of another build is refused with guidance and renders none of it. ### The Fastify starter (STARTER-FASTIFY)

[#64](https://github.com/MachineWisdomAI/saga-a2ui/issues/64) qualifies the second pair: the `lit-mcp` stack on the `fastify` server target, `templates/lit-fastify`. It adds no package, runtime export or dependency to the SDK and changes no shared harness code: it reuses the STARTER1 export, stamping, snippet and packed-install code (`scripts/starter-template.ts`, `scripts/build-starter.ts`) and the shared qualification (`scripts/qualified-starters.ts`, `scripts/starter-qualification.ts`) as they are; it joins the inventory by adding `lit-fastify` to `QUALIFIED_STARTERS`. The view, the operations, the authentication and the identity and authorization files are the Node starter's own text; only `server/listener.ts`, `package.json`, `template.json` and the README differ.

**Adapter and peers, from the installed packages.** `@modelcontextprotocol/fastify` 2.0.1 (the official adapter; its peers are `fastify ^5.2.0` and `@modelcontextprotocol/server ^2.3.0`), `fastify` 5.12.7 and `@modelcontextprotocol/server` 2.3.1, with the Streamable HTTP transport of `@modelcontextprotocol/node` 2.1.1 that the adapter's own documentation pairs it with (the adapter implements no MCP transport). Node 2.1.1 is not evidence for Fastify, so the pair is qualified on its own. `template.json` keeps the existing schema: the adapter is `@modelcontextprotocol/fastify` 2.0.1 and the other pins are in the template's manifest. **What the Fastify listener does.** `createMcpFastifyApp` creates the app and validates the Host and Origin headers (`ALLOWED_HOSTS` is the application's list of host names; the transport carries no second copy of that check). Authentication is an `onRequest` hook of the protected route only (the `identity-handoff` snippet): it runs before the body is read, hands the frozen per-request `AuthInfo` to the transport as the request's `auth`, and answers a refusal with the challenge and an empty body. Fastify's own body parsers read a body with no deadline, so the listener replaces them with one that passes the unread stream on; `readJsonBody` reads it as the request lifetime's bounded `body` stage, and the route handler hijacks the reply so that the transport and the deadline answer it. The 3 s operation and 10 s request defaults, the per-field overrides, the 408 with a closed connection, the 413 and 400 answers, and the destruction of a response the deadline overtakes are the Node listener's, moved to module level; the lifetime starts in the first application `onRequest` hook, after the adapter's Host and Origin checks.

### Creating a project with `saga init` (CLI1)

[#26](https://github.com/MachineWisdomAI/saga-a2ui/issues/26) adds the command a developer runs to get the starter above as a new project. It is `scripts/saga.ts`, run from a checkout like the other scripts; it is not a package and nothing is published.

```sh
npx tsx scripts/saga.ts init --a2ui-stack lit-mcp --server node ./my-app
npx tsx scripts/saga.ts --help        # usage and the supported pairs
```

**What it does.** `--a2ui-stack <renderer>-mcp` and `--server <target>` name a pair; `init` copies that pair's maintained template (`exportTemplate`, the one implementation the starter, the snippets and the qualification share) into the new directory, with every `@saga-a2ui/*` dependency pinned to the build of the checkout it ran from (`0.0.0-candidate.g<12 hex>`, `.dirty` when tracked files differ; the identity of PACK2, not a release). It then prints the ordinary next commands (`cd`, `npm install`, `npm run build`, `npm start`) and says that the candidate is not published, so the install has to come from that build's tarballs ([candidate guide](docs/candidate-update-and-rollback.md)). Exit status: 0 created, 1 refused or failed, 2 command line not understood, 130 interrupted.

**What it offers.** `SUPPORTED_PAIRS` in `scripts/saga.ts` is a plain list of the pairs CI qualifies: today only `lit-mcp` on `node` (`templates/lit-node`, qualified by `scripts/starter.test.ts` and `apps/lit-host/e2e/starter.spec.ts`). A template directory existing does not add a pair, and a pair whose template stops declaring that stack and server is refused. Any other pair is refused before anything is written, and the refusal lists the supported ones. The owner of each further pair (`express`, `hono`, `fastify`, `hapi`: #62 to #65, or a React recipe) adds one row when its own qualification passes, and removes it while that fails; there is no registry or generator behind the list.

**What it will not do.** It creates one new directory and nothing else. A target that exists (a directory, a file, or a symbolic link, including a dangling one) is refused and left as it was; a missing parent directory is refused rather than created; a parent that is a symbolic link is resolved first, so the copy goes where the path leads. It starts no process: no install, no package manager, no script and no hook, and the starter's manifest declares no lifecycle hook. The directory is created only if it does not exist at that moment, so a competing creation is refused instead of merged into. If a write fails, the directory this run created is removed and nothing beside it is touched. "The directory this run created" is identified by the directory itself (device and inode from the exclusive creation), not by its path: before every file, after the last one and before any removal, the path is checked to still lead to that directory. If another process moved it away and put something else at the path, the command stops writing, removes nothing there, leaves the replacement as it is, and says so. Node has no directory-relative file calls, so a replacement landing between that check and the one call that follows it is not excluded; the check narrows the window to that instant, it does not close it. The copy hands control back to the event loop before each file, so a real SIGINT or SIGTERM is seen before the next write or before success is reported (a synchronous copy would run the signal callback only after it had finished): the directory this run created is removed, the created message is not printed, and the command exits 130. A second signal during that short cleanup is ignored. A process killed outright (SIGKILL, power loss) can leave a partial directory, which the developer deletes and re-creates with the same command.

**Evidence.** `scripts/saga.test.ts` (34 cases, headless) calls the command through its entry (`runCli`) for the created project, the clean output, an unsupported pair, command lines it cannot understand, every refused target and parent, a failing write, an abort during the copy and an output path replaced during the copy (the replacement is kept intact whether a write then fails, the copy carries on, the replacement comes after the last file, or an interrupt arrives), each time comparing the disk before and after; four further cases run `scripts/saga.ts` as a real process with stand-in `npm`, `npx`, `pnpm` and `yarn` on the `PATH` and show none was run, and that a real SIGINT and a real SIGTERM (sent by the process to itself on its fourth write; not SIGKILL) end with exit 130, no output directory and the neighbours untouched. `scripts/starter-template.test.ts` gained the case for a directory that appears between the existence check and its creation, one for an output replaced before a failing write, and one for the interruptible export reacting to a callback that only the event loop can run. Template content, stamping and snippets, and the behavior of the exported starter, keep their STARTER1 qualification and are not repeated. Not claimed: a registry install of the created project, other operating systems, and any pair other than `lit-mcp` on `node`.

### MCP Apps 2 recipe (MCPV2)

The browse and Play paths run on one peer-complete MCP Apps 2 recipe. It replaces the earlier `@modelcontextprotocol/sdk` 1.32.1 / `ext-apps` 1.7.5 / Zod 3 set; nothing of the old set remains installed or imported, and there is no compatibility layer. This is **local qualification** of the candidate that actual-host mapping (MAP1) will measure. It is not host evidence: the local `AppBridge` fixture does not stand in for ChatGPT web or Claude web, and the open recipient-mapping question in the [connector Blueprint](blueprints/features/reusable_mcp_connector.blueprint.md) stays open.

| Package | Exact version | License |
| --- | --- | --- |
| `@modelcontextprotocol/ext-apps` | 2.0.3 | MIT |
| `@modelcontextprotocol/client`, `core`, `server` | 2.3.1 | Apache-2.0 |
| `@modelcontextprotocol/node` | 2.1.1 | Apache-2.0 |
| `zod` (MCP seam, hoisted to the workspace root) | 4.6.7 | MIT |
| `@a2ui/lit`, `@a2ui/web_core` (unchanged) | 0.13.0 | Apache-2.0 |
| `zod` (each A2UI package's own nested copy) | 3.25.76 | MIT |

Install with `npm ci` on Node 22.12.0 or newer (the MCP packages need Node 20+, so the workspace engine is unchanged). `ext-apps` declares `zod ^4.2`, `core`/`client`/`server` as peers and `node` requires `server ^2.3.0`; all are direct dependencies of `apps/lit-host`, so `npm ls --all` reports no missing or invalid peer.

**Two Zod versions, one boundary.** Zod 4 belongs to the MCP seam: tool, projection and request-metadata schemas (`mcp/episode.ts`, `mcp/subscriptions.ts`, `playback/playback.ts`, `mcp/request-auth.ts`) and the FaithfulCard reader and content policy configuration (`packages/components/src/faithful-card/reader.ts`, `policy.ts`) import `zod`; the component's A2UI catalog schema (`catalog.ts`) imports Zod 3 from `@saga-a2ui/core/protocols/a2ui/zod3`. Zod 3 belongs to upstream A2UI, whose `ComponentApi` and message schemas are Zod 3. Anything this application authors *for A2UI* (`saga-panel/contract.ts`, the decoder's types, the protocol test) imports `z` from `protocols/a2ui/zod3.ts`, which re-exports the exact-version `zod3` alias. `zod/v3` inside the Zod 4 package is not a substitute: its declarations differ from upstream's and the compiler's comparison runs out of memory. The root `package.json` declares `zod` 4.6.7 so that npm hoists it where `ext-apps` and the MCP packages share one copy and leaves each A2UI package its own Zod 3. `zod-to-json-schema`, which A2UI uses, is locked under `@a2ui/web_core` for the same reason (hoisted, its peer would resolve to Zod 4); `npm run candidate:identity` and its test fail if that placement drifts. A change to the A2UI pin is a separate decision. No Ansari package or version was touched.

**What moved together** (one change, no old path kept):

- Transport: `NodeStreamableHTTPServerTransport` from `@modelcontextprotocol/node` replaces the monolithic SDK's transport. The listener still owns hosting, the Host-header rebinding check, the body bound and the request-classification gate (`protected-request.ts`) before any server is built.
- Verified request context: the application's `authenticate` is unchanged in behaviour, but its seam is now the server package's `OAuthTokenVerifier`/`OAuthError`, and the frozen snapshot reaches a tool as `ctx.http.authInfo`. The request signal and `_meta` are `ctx.mcpReq.signal` and `ctx.mcpReq._meta`.
- Runtime schemas: input and output are Zod 4 objects passed whole (no raw shapes). `PlayRequestSchema` is a `strictObject` with one fixed sentence for every issue; the recipient key's `d` member stays "absent or rejected" (`z.undefined().optional()`, because Zod 4 no longer treats an `undefined`-typed key as optional).
- Browser integration: views use the `App` and `PostMessageTransport` from `ext-apps` 2, whose runtime is built on `@modelcontextprotocol/client`; the view modules import types from that package. The test host fixture uses the matching `AppBridge`.
- Removed: the `@modelcontextprotocol/sdk` dependency, the raw-shape request exports (`EpisodeRequestShape`, `SubscriptionsRequestShape`) and the hand-written legacy `ui/resourceUri` key on Play (`registerAppTool` now accepts the strict schema and writes it).

Behaviour kept from the merged Play code: freshness and recipient binding, the 60-second capability, revocation on every acquisition, ranges, cache headers, the declared-origin-only `connect-src`, no redirects, and the fixed unsupported-recipient failure with zero entitlement checks and zero media reads. The unchanged specs (`playback.test.ts`, `media.test.ts`, `playback-view.test.ts`, `e2e/playback-view.spec.ts`) pass against the new recipe without edits to their expectations.

**Built views now carry the MCP client library.** `ext-apps` 2 imports `Protocol` from `@modelcontextprotocol/client`, so the single-file views grew and now contain the client's OAuth error classes. The bundle guard (`e2e/view-bundle.spec.ts`) therefore matches the credential header as a quoted name (`"authorization"`) instead of the bare word, and also forbids the HTTP client and server transports by name. The views set no header, use no HTTP client and read no credential. Inlined MIT and Apache-2.0 code keeps its license; carry the upstream notices with any view you distribute outside this private repository (see [public install](docs/public-install.md)).

**Candidate identities for MAP1.** After `npm run build`, `npm run candidate:identity` prints the source commit, the lockfile hash, every recipe package's resolved version and tarball integrity, the three served `ui://` resources with their built file and SHA-256, the Node version and the last verify receipt's per-command results (`--out FILE` writes it instead; keep the file in ignored `.wise-agents/`). The episode view is not served verbatim: the content policy embeds its restrictions in the document, and the URI is the SHA-256 byte identity of that served document (`ui://sha256/<digest>.html`). The report therefore builds that resource through the same `contentResource` the server registers and gives the served URI, byte count and SHA-256, with the raw build identified separately under `rawBuild`. Pass the candidate's configured policy as `--image-host HOST` (repeatable), `--level strict` and `--blocked-presentation placeholder|inert-text`; without them the report describes the default policy, and an invalid value is an error rather than a fallback. `scripts/candidate-identity.test.ts` compares the report with the resource a server returns for the default and for a configured policy. The same lockfile and sources produced identical resource hashes in this tree and in a fresh `npm ci` copy. Quote the output with the PR head in the acceptance record; do not commit a pasted copy, because the commit hash cannot name itself.

**Run it.** `npm ci`, `npx playwright install chromium`, `npm run verify`. The browser specs exercise the real listener and the built views: the public result (`mcp-view.spec.ts`), allowed, denied, changed-sign-in and refused browse (`subscriptions-view.spec.ts`), the app-only Play (declared `visibility: ['app']`, capability only in result `_meta`), and the unsupported-recipient failure for a host that drops request metadata (`playback-view.spec.ts`).
